# Kodo 产品定位、特色与设计收敛

> **已被取代：** 定位以 [最终产品定位与执行方案](kodo-final-positioning-20261103.md) 为准。本文第 3、4 节的偏离与缺口盘点仍可参考。

日期：2026-11-03。状态：定位收敛提案，已被取代。本文统一 [设计方案](design.md) §1（10-19）、[通用任务定位](kodo-general-task-positioning-20261102.md)（11-02）和 [阶段能力设计](kodo-stage-capability-design-20261103.md)（11-03）三版说法，并据现有代码与实验盘点偏离与缺口。本次只新增文档，没有修改代码或既有文档。

## 1. 三版定位与证据

| 版本 | 定位 | 现有证据怎么说 |
|---|---|---|
| 10-19 设计方案 | 以 Agent 为单位共享和运行工作流的轻量 Harness；主 Agent 组织子 Agent 协作 | 自主委派 7 轮实质任务为 0；指定分工能并行，但增加总费用（[协作收益](collaboration-benefit.md)）。“组织协作”没有成为用户可感知的收益 |
| 11-02 通用任务定位 | 处理重复性数字工作的 AI 工作台：把工作做成，把做法留下 | 方向与证据一致，但尚无一次非编码任务实验 |
| 11-03 阶段能力挂载 | 专业能力随阶段加载、卸载 | 通用方法自主加载 0/8（五组复测）；项目专属方法 2/2（[方法发现诊断](experiments/kodo-method-discovery-20261103.md)）。机制只有在方法含模型不知道的信息时才会被用到 |

结论：**11-02 版是正确的产品定位；11-03 版是它的一种实现机制，不是新的定位；10-19 版的“组织协作”应退为内核能力。**

## 2. 统一后的定位

一句话：**Kodo 让 AI 学会你的做事方法——纠正一次，下次照做，改了能验证。**

- 产品类别：面向重复性数字工作的本地 AI 工作台（技术上仍是通用 Agent harness）。
- 首批用户：每周反复整理多源资料、产出固定格式交付物、需要核对口径与来源的个人和小团队。编码用户由 CLI/TUI 继续服务，不作为首批验证对象。
- 品牌释义 Know · Organize · Do 保留，“Organize”从“组织协作”改释为“把做法整理成方法”。

### 2.1 用户可感知的三个特色

| 特色 | 用户看到什么 | 依赖的现有能力 | 与竞品的差别 |
|---|---|---|---|
| **纠正会被记住** | 第一次交付后指出口径错误，系统问“以后同类任务都按这条吗？”，确认后存入方法；第二次换材料，不再犯同样的错 | 方法提炼、能力包、Skill 按需加载、阶段挂载 | 竞品的记忆/规则文件需要用户手写或不分适用范围；Kodo 从实际纠正生成、带适用条件 |
| **方法升级前先验证** | 方法改了之后，用旧材料和新材料各跑一遍，显示“5 份样例中 4 → 5 份合格，可采用”，不合格可回退 | 冻结案例、版本比较、采用/回退 | 竞品没有面向普通用户的“方法版本对比后采用” |
| **交付卡说清楚哪些核过** | 结果旁列出：已核对（总数、来源覆盖、字段完整）/ 未核对 / 用了哪个方法版本 | 完成验收、`quality` 状态、证据记录 | 不把“跑完”说成“做对” |

断点续跑、预算上限、多供应商与备用线路是基础保障，写在说明里，不作为首屏卖点。

### 2.2 设计方案（收敛后）

```text
用户任务
  → 单主循环（一个模型、一个上下文，默认）
      ├─ 方法：项目/团队专属规则包，skill.list 发现、skill.load 内联加载（默认）
      ├─ 工具与连接器：读写业务文件、按需 MCP
      ├─ 项目知识：带来源与新鲜度的跨会话事实
      └─ 子运行（按需）：大量探索、并行独立任务、独立复核；fresh 或 fork 上下文
  → 交付卡（检查结果 + 方法版本 + 未核对项）
  → 用户纠正 → 候选规则（问适用范围）→ 方法候选版本 → 案例比较 → 采用/回退
```

设计原则：

1. **方法装的是模型不知道的东西。** 口径、格式、禁忌、客户约定、检查规则；不装“先理解再实现再验证”这类通用流程。
2. **内联优先，子运行按上下文拆。** 与 Anthropic 2026-10-22 文章一致；多 Agent 是执行选择，不是卖点。
3. **检查跟着方法走。** 每条可机械检查的规则都应能转成案例断言。
4. **阶段、卸载、动态工具是基础设施。** 保持默认关闭，等真实任务出现上下文压力或方法冲突再启用。

## 3. 偏离：投入与定位不一致的地方

| # | 偏离 | 证据 | 影响 |
|---|---|---|---|
| D1 | **对外叙述仍是多 Agent 协作** | [README](../README.md) 第 5 行首先介绍主/子代理执行循环；设计方案 §1 仍写“组织协作” | 新读者得到的定位与 11-02 决定相反 |
| D2 | **验证对象全是编码任务** | `docs/experiments` 共 43 份报告，任务为 statemachine、FastAPI、ky 等；非编码任务 0 份 | 首批用户场景从未被测过 |
| D3 | **实验测的是内核机制，不是产品假设** | 委派、压缩、组装、卸载、工具视图各有多轮矩阵；“第二次使用是否减少人工纠正”0 次 | 花费的 credit 无法回答产品是否成立 |
| D4 | **机制先于采用证据扩张** | 阶段设计修订版要求首轮只做 P1、卸载可用前不扩大目录；实际完成 P1–P4 与会话热插拔，并接入 SDK/CLI/TUI/Web | 维护面扩大，且机制在实验中触发次数为 0 |
| D5 | **实验用通用方法，必然不被采用** | 三张卡为理解/实现/验证；同期诊断已证明专属方法才会被加载 | 两轮共约 220 credit 测到噪声（见 [五组复测](experiments/kodo-statemachine-five-arm-20261103.md)） |
| D6 | **默认入口仍是编码 Agent** | `src/runtime/lean-prompt.ts:13`：“You are Kodo, a coding agent.” | 通用任务进入编码人设 |

## 4. 缺口：核心闭环尚未打通的地方

核心闭环：完成任务 → 纠正 → 保存方法 → 换输入复用 → 验证 → 采用。

| # | 缺口 | 现状依据 | 阻塞哪一步 |
|---|---|---|---|
| G1 | **业务文件读写** | `file.read` 只读 UTF-8 文本；源码中没有 xlsx/docx/pdf 处理 | 完成任务：首批场景的表格和文档无法直接处理 |
| G2 | **纠正 → 带适用范围的规则** | 未见从对话纠正生成候选规则、询问适用范围的实现 | 纠正、保存 |
| G3 | **提炼结果是子 Agent 卡，不是内联方法** | `src/agents/authoring.ts` 生成 name/tools/inputs/steps/checks 与提示词，不带 Skills/MCP，也不声明 inline | 保存、复用 |
| G4 | **业务检查断言** | `src/cases/schema.ts` 只有 file/json/output/command；没有字段完整、汇总一致、来源覆盖 | 验证 |
| G5 | **Web 主流程** | README 第 157 行：案例管理与包导入/验收仍使用 CLI | 非开发者无法完成保存—比较—采用 |
| G6 | **交付卡** | 有 `quality` 状态与证据，但没有按方法规则逐项展示已核/未核 | 让用户信任结果 |
| G7 | **内核两处问题** | 共享执行默认写范围导致同批派发冲突；25 秒内 3 次 502 即判失败（五组复测日志） | 稳定性，非定位问题 |

## 5. 建议的推进顺序

1. **冻结机制实验。** 不再用编码任务跑阶段/卸载/工具视图矩阵；P1–P4 保持默认关闭，不删除。
2. **修 G7。** 改动小，避免后续实验再被干扰。
3. **统一叙述（D1、D6）。** README 首屏与设计方案 §1 按第 2 节重写；通用入口提示词去掉编码人设，编码方法作为可加载方法保留。
4. **打通一个非编码场景（G1、G6）。** 选“周期业务简报”：先支持 CSV 与 xlsx 读取、表格输出，交付卡展示汇总与来源检查。
5. **做核心实验（G2、G3、G4）。** 同一用户、同一方法、4 份不同期材料：第 1 期允许纠正并保存方法，第 2–4 期测人工纠正次数和合格率。这个实验同时检验专属方法能否被自主加载，替代原阶段矩阵。
6. **Web 主流程（G5）。** 第 5 步出现可重复的纠正次数下降后再做。

停止条件：若第 5 步中第 2–4 期纠正次数相对第 1 期没有下降，先改方法提炼与加载，不扩展 Web、社区或更多机制。

## 6. 证据边界

本文的定位与特色是待验证的产品假设。专属方法 2/2 自主加载来自小型合成任务，不代表真实业务任务；竞品比较基于公开资料与既有调研，没有新增对照实验。
