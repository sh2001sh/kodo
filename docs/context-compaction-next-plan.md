## 3. P0：必须先完成的确定性修正

### P0.1 统一预算契约，不再增加独立阈值

涉及：`src/runtime/summary-projection.ts`、`compaction.ts`、`summary-schema.ts`、`summary-install.ts`。

保留四个不同含义：

| 名称 | 含义 | 是否决定拒绝 |
| --- | --- | --- |
| 生成偏好目标 | 希望正文达到的简洁程度，当前约 8% H，再乘生成裕量 | 否 |
| 正文硬上限 | 从有界展示预算扣除包装、目录和安全量后得到 | 是，但要明确计量对象 |
| 最终展示上限 | 最终 marker 的允许长度 | 是 |
| provider 输出上限 | 一次请求允许的总输出，可能含推理 | 是，由 provider 契约决定 |

v2.1 已修正“偏好目标当硬上限”的主故障。后续工作是补齐单一契约及边界，不再将 8% 作为安装门槛：

1. 生成提示、解析器、事件、envelope 和检查界面来自同一预算计划，名称和单位一致；禁止将旧 `bodyTokens` 在不同报告里同时解释为偏好和硬上限。
2. `plannedMarkerTokens` 明确表示**按偏好正文计算的计划量**，并非所有合法响应的最大 marker；检查界面不得把实际值高于它判失败。
3. 生成时保留安全余量，最终仍按实际序列化 marker 验证，不取消 `no-gain`、权限或版本守卫。
4. 计量空白等非语义格式：当前 `validSummaryResponse` 对提取后的原始 JSON 估算。离线增加“相同内容不同缩进”的反证；若仅因空白造成可安装内容被拒绝，改用与投影一致的规范化短引用正文计量。原始输出照常保存，不能对展开完整来源后的正文计量。
5. 解析前仍保留防止异常响应耗尽资源的大小上限；它与语义预算区分。预算附近的响应不可因为 `maxChars` 先拒绝而绕过应有的有界缩写路径。用用例判断是否存在，存在才修。
6. 结构限制也区分软硬目标：当前提示 20 项/4 个引用、解析器容许 64 项/8 个引用，可以作为容错设计；必须明示且使用共享常量。未知来源、字段类型错和权限不成立仍不能“容错接受”。

还需更正文档中的数字解释：旧四次尝试按 v2.1 公式回算的硬上限依次是 **1,820 / 2,720 / 2,473 / 2,617**；失败的三次分别对应后三个值，不是三次都只能容纳 1,820。说明这是事后公式重算，不是旧事件已记录字段。

验收：相同语义响应不因格式空白被迫付费重写；正文位于偏好与硬上限之间直接接受；超过硬上限最多一次语义修正；最终 marker 超额明确拒绝。未知引用不能因简化计量进入安装。

### P0.2 将“运行状态、任务质量、处理覆盖、协议结果”分开

涉及：`scripts/comparison/compaction-continuation.mjs`、`continuation-audit.mjs` 及评测回归。

新注册使用现有报告加少量独立字段，不引入通用评测框架：

```text
runStatus: completed / failed / interrupted / not_run
qualityStatus: pass / fail / not_observed
mechanismStatus: pass / fail / not_observed
exposureStatus: sufficient / insufficient / not_observed
protocolStatus: pass / fail / incomplete / stopped
```

语义规定：

- A 交付通过但确定性摘要失败：`quality=pass`、`mechanism=fail`、`protocol=stopped`。
- B 因 A 停止未运行：三个观测维度均 `not_observed`，不进入已观测任务质量分母。
- B 正确交付且仅压缩一次：`quality=pass`；若无机制错误则 `mechanism=pass`；但多次续做覆盖 `insufficient`，注册目标未完成，不能晋级。
- 已运行但缺少必要证据：不能记为 `pass`，也不能假装为一个明确的任务行为失败；登记证据缺失。
- 批次达到预算上限或触发停止：保留 `stopped`，不能因已完成子集全通过就报告批次成功。

新注册明确 A 至少 1 次、B 至少 2 次成功安装才覆盖各自筛查目标；runner 与独立审计读取同一冻结注册值。审计仍从原始事件、响应和产物重新计算，不直接相信 runner 的判定。

保留旧协议与旧审计输出。新审计如果重新解释旧数据，应使用新输出目录，并标注“旧证据的新展示口径”，不覆盖历史。

验收至少覆盖：A 质量过/机制败、B 未运行、B 一次安装、B 两次安装、保护文件被改、没有最终交付、证据缺失，以及旧结果导入时 unknown/未观测不被转换为通过。

### P0.3 准确标识实验运行的代码和构建产物

本仓库工作树变更较多，`git HEAD` 不能单独确定实验版本。新实验生成一个运行清单，包含：

- Git commit 和 dirty 状态；参与运行的源码、`dist`、runner、审计脚本、fixture、协议和 lockfile 的内容摘要。
- 非敏感模型绑定：协议、模型名、声明上下文/输出能力；连接信息只保存非敏感标识或摘要，不保存认证信息。
- 所有运行限额、压缩策略、H、工具集合、环境版本和启动命令。
- 构建命令、构建结果及冻结时间；注册摘要先于首次模型调用。

直接复用现有 report/manifest，禁止新建一套检查点系统。若旧运行没有完整构建快照，明示无法完全重建其二进制；不能用当前 dist 代称旧 dist。

验收：运行前只读 dry-run 确认源码/构建/fixture 一致；启动时不一致即拒绝联网。退出后再次计算 fixture 与构建摘要，检查运行期间是否变化。

3. **固定后续观察模拟**：假定继续输入旧运行后续工具结果，分析预算/触发变化。清楚标注这些后续动作是固定重放，不代表修复后模型真的会如此执行。

## 5. P1：只有 E0 给出证据才修改触发策略

不要在一次修改中同时更换模型、调高 H、调输出限额、缩减工具正文、修改提示和触发算法。每个策略修改都要对应一条可复现轨迹，并保留未改策略的 v2.1 作为比较基线。

### P1.1 已经低于工作预算，仅因隐藏量触发

当前 `foldWorthwhile` 包含：

```text
mask 后输入 > H
或 hybrid 隐藏原文量 >= 25% H
```

如果 E0 证实第二项造成无当前压力的付费摘要，最小候选是：**普通在线自动摘要仅由活动窗口压力触发**。旧证据仍保留导航与读回，知识沉淀不能借此变成强制付费维护。

先做该条件的单因素离线对照。仅改变触发条件，不同时改变窗口、模型或摘要提示。检索是否因此增加，留到真实任务对照计量；不能仅凭少调用摘要就宣称更优。

若未发现此路径贡献开销，本轮不改它。

### P1.2 失败后在几乎相同证据上反复重试

现有 `attemptKey` 能避免完全相同输入重复尝试，先测它是否已经足够。只有证实归档包装变化等因素造成相同源证据不断绕过抑制，才调整身份依据。

最小规则：同一已解析原始证据集合、任务/权限版本、模型绑定和预算计划，不能在确定性失败后无变化再次付费；真正新增证据或相关计划变化才有新尝试依据。传输恢复继续使用现有有限重试，不额外叠加实验 runner 自动重跑。

遇硬上下文上限，不能靠冷却计数强行发送超窗请求。必须使用合法的确定性缩减或明确返回受阻。不得静默丢用户约束或未完成工具结果。

### P1.3 安装后余量小，随后再次触发

本批只剩 1,409 token 是诊断线索，不足以立刻把 70% H 改为硬安装门槛。先区分：

- 下一步确实引入大而必要的观察：再次维护可能合理。
- 没有显著新增观察却再次摘要：检查触发原因与重复处理。
- 当前受保护/近期内容本身占满：缩短摘要也解决不了，检查折叠资格与近期保护原因。
- 常见工具返回远大于本轮工作空间：评估该工具的有界展示与原文读取，保持产物完整存储；不全局粗暴截断所有工具输出。

如果需要选择更多可折叠旧交互，按现有完整工具组与权限边界逐步扩大，记录期望释放量；不得靠过早丢掉当前任务证据达到目标。

70% H 继续作为偏好目标；未达到不自动判失败。验收看实际工作间隔、重复工作、恢复次数和最终任务质量。先不增加“最低步数”“冷却时间”等用户配置。

### P1.4 多块和高输出成本

先统计各维护请求的输入组成与 provider 已提供的推理 token 字段。没有细分就记 unknown，不将 39,818 输出全部解释成摘要正文或推理。

如果普通在线任务多次恢复同一批旧原文，修为“旧交接 + 新增可折叠交互”；若是一次超大工具结果或冷归档导入，单独标识，不能一律禁止分块而丢信息。

更换便宜模型、关闭推理或大幅减小输出预算均暂不纳入核心修正。之后若维护仍主导成本，只选其中一个作为独立实验变量，避免回到输出截断问题。

## 7. E1：新版 A/B 最小真实续做检查

### 7.1 注册与版本

旧 A 运行保持负结果，旧 B 保持未观测。新实验使用新的协议编号、输出目录、run ID 和冻结清单。可复用原 fixture 内容与任务目标，方便与旧事实比较，但不合并成同一预注册样本，也不将它作为盲测泛化能力。

先完成 P0/E0；只有必要的 P1 修改进入候选版本。若没有触发策略修改，候选仍称“v2.1 契约修正版”；若改变了触发，另记行为版本，不能仍声称只修预算。

### 7.2 任务、模型与资源

| 项目 | 新注册建议 |
| --- | --- |
| 模型 | 继续使用 `codego1/deepseek-v4.1-flash` 的同一绑定；记录实际声明能力 |
| 顺序 | A 单次，满足进入条件才运行 B 单次 |
| H | 保持 16,384，作为压力筛查，不为了安装数调大/调小 |
| 硬窗口/输出 | 沿用旧 262,144 / 8,192，前提是模型绑定实际支持；不支持则联网前终止注册准备 |
| 每任务最大模型调用 | 64，必须包括所有摘要、修正和重试 |
| 每任务累计 token 预留上限 | 沿用 4,000,000，含全部调用；不作为期望消耗 |
| 每任务工具调用/时长 | 沿用 200 次 / 900 秒，单工具上限 120 秒 |
| fixture | 新鲜工作区；固定文件集合、哈希及验证脚本 |
| 取证能力 | 保留正常文件与历史读取，不为证明摘要记忆而禁用 |

新批次的最大范围是 **2 个任务尝试**，若两者都达到旧上限，最多 128 次模型调用、8,000,000 token 预留、30 分钟任务时间；这只是安全上界，含失败请求未知用量时按保守预留处理。实际预计费用不能从旧 token 总数直接换算；没有定价时不报货币数字。

这是一份计划，不是本轮付费调用授权。实际执行应在实现与离线证据完成后，呈现冻结的新注册与总预算，再取得执行许可；不能沿用旧注册的已结束尝试。

### 7.3 四个维度的验收

**机制**：无确定性摘要失败；所有已安装 marker 都满足最终预算、来源授权和版本条件；事件与原始响应可对账。

**处理覆盖**：A 至少一次、B 至少两次成功安装，且安装后还有正常业务行动或最终交付；不是任务已经完成后才压缩。来源读回路径仍可用。

**质量**：独立 `node verify.mjs` 通过，全部受保护文件集合及哈希保持，最终交付完整，冻结约束满足。最终回复说出 37 继续作为观察项，不能当作记忆能力的唯一证据。

**资源**：全部调用计数和用量一致，失败不漏账，预算没有被绕过。记录维护占比，不在这两个小样本里临时设置“必须低于 20%”之类门槛。

如果模型合法地少读文件、较早完成，未达到压缩次数，登记 `exposure=insufficient`，不强迫再读文件或降低 H 获取次数。该实验无法覆盖既定目标，不晋级；后续如需构造新任务必须另行注册。

### 7.4 停止规则

新注册采用明确的**任务边界停止**，与旧运行便于解释：任务执行内部保留现有有界恢复；当前任务终止并记录后，不再启动下一个任务，若存在以下任一项：

1. 确定性摘要错误，含来源错误、正文/展示预算错误、安装冲突未处理和无收益候选。
2. 任务未完成、预算耗尽、保护文件损坏或验收失败。
3. 所需压缩覆盖不足，无法完成本次检查目标。
4. 未恢复的模型/传输错误、用量无法按注册规则界定，或审计证据缺失。
5. 已证实的无进展循环：相同原始证据、计划和权威版本发生第二次重复付费维护，且没有新增业务证据；按实际来源身份判断，不凭安装间隔短就认定循环。

安全/授权问题按产品已有机制立即停止，不等待任务边界。协议终止不允许强行中断一个状态未知的写操作并将其当完成；保留恢复状态。

不加入 runner 自动重跑。已有运行时有限传输重试/一次正文修正属于同一个任务尝试，次数和成本必须全部记录。出现异常并被恢复也要披露；未解决的传输问题使该筛查不能晋级，不能将其直接算为摘要语义失败。

### 7.5 E1 通过后能说什么

可以说：“这个冻结实现通过两项压力续做筛查，值得进入配对实验。”

不能说：“压缩可靠率达到某值”“长期语义无损”“已经降本”“可以默认开启”。若 A 失败，B 继续为未观测；若 B 失败，A 的成功事实保留，不能重跑 B 挑结果。

## 8. E2：六次真实任务配对，首次检验产品收益

E1 通过后才准备这一阶段的新注册。先只比较两个策略，防止同时引入四组或多个模型：

- **基线 B0**：现有产品未启用实验压缩/assembly 的行为；保留它原本的硬容量保护。
- **候选 B1**：E1 通过的确定实现，启用选定的单一策略；assembly 关闭。

这比较的是**完整策略效果**，包括候选的工作预算和压缩触发，不是同等长度下摘要算法的纯效果。两组 provider 硬窗口、输出、任务总调用/token/时长上限、工具权限完全相同；基线不额外施加一个伪造的 H 截断器。

### 8.1 任务矩阵

| 独立任务 | 工作负载与观测 | 必须验收 |
| --- | --- | --- |
| T1 短修复 | 少量文件、局部缺陷，不应产生压缩维护 | 测试与交付正确；候选无额外摘要模型调用 |
| T2 长编码续做 | 真实仓库的多个相关实现/测试步骤，实际产生窗口压力 | 可编译、目标测试、硬约束、最终变更与解释一致 |
| T3 多来源交付与目标变化 | 需要综合多个来源，中途收到固定的需求修订，随后完成报告或代码交付 | 多主题事实、负约束、来源支持和最终文件落盘 |

T1/T2/T3 不复用 A/B 的分页问题作为全部任务；A/B 是开发与筛查集，新的任务应包含此前未用于调策略的实现与证据。不能先跑候选，再选择对它有利的任务或问题。

目标变化按预定义业务里程碑注入，例如第一次完成指定探索结果后；不按“候选发生压缩”触发，避免两组收到不同流程。模型未到达里程碑则保留该事实，不人为补齐。

候选默认先采用拟发布的工作预算（当前默认配置路径为 65,536，注册时再次核对），而非继续用 16k 制造频繁压缩。先用公开任务大小和离线基线轨迹确认 T2/T3 有机会触发；真实运行没有触发则报告处理暴露不足，不能声称检验了压缩后的质量。

### 8.2 配对控制

- 每任务两个全新隔离工作区，相同初始 commit/文件哈希、目标、工具集合与 provider 绑定；不得共享可写知识库或任务记忆。
- 两组使用相同的用户/代理提示，除策略必需的能力提示外不添加额外“更认真收尾”等指导。
- 运行顺序预先随机并保存；小批可交替顺序，保持串行以减少共享通道拥塞。记录缓存条件，无法保证冷/热缓存一致就披露，不能以缓存率相近代替控制。
- 有 seed 参数则记录并配对，但不要假定 provider seed 保证确定轨迹；无 seed 明确说明。
- 评分按产物和原始证据，能隐藏策略标签就盲评；不能由候选 agent 自己声称通过。

### 8.3 指标及筛查判定

主要指标：完整交付、硬约束违背、事实准确与来源支持。其次是端到端时间、全部模型调用、分类 token、可用时的货币费用、峰值活动上下文、重复工作和来源恢复。

统一计量口径：

- 每个模型请求按唯一 call ID 计一次，不能将 `summary.failed` 和 `repair.failed` 两条事件当两次请求；分类为正常业务、摘要生成、正文修正、传输重试。
- 输入总量包含 provider 已计入的缓存输入，不能再把 `cacheRead` 加一遍；输出与可用的推理明细分别报告，缺失明细记 unknown。
- 费用由实际绑定的输入/缓存/输出价格计算，标明币种与时间；未知请求费用不填零。全请求清单是总账，不能只加已安装 envelope 的 usage。
- 同时报告正常业务请求峰值和包含摘要调用的全部请求峰值；仅前者下降，不能声称整个运行的最大上下文需求下降。
- 端到端时间从任务提交至交付/停止，包括摘要、等待、重试、工具和检索；另列离线独立审计时间，不混入 agent 执行时延。
- “安装间隔”按两次成功安装之间的正常业务模型请求数计算；同时报告两次付费摘要尝试间隔，失败不能从维护频率里消失。

报表同时给出所有分配任务、已启动任务和完成任务数量。停止后未运行的配对部分明确缺失；不拿剩余成功任务算一个“平均提升”。

六次筛查的晋级规则：

1. 不出现确定性安装错误、越权或保护文件破坏；出现即停止后续付费任务。
2. 候选三项任务完整交付且硬约束通过；任何候选交付失败进入诊断，不继续扩样。
3. T1 不额外调用摘要模型；费用/时延报告原数，小样本不以波动数个百分点断言退化。
4. T2/T3 至少有可确认的实际处理暴露；只发生短任务不触发不能验证长任务方案。
5. 对已触发的长任务，在质量合格基础上检查容量或效率价值。建议将峰值输入减少 ≥20% 作为容量收益的**探索性信号**，或完整任务费用/时延减少 ≥10% 作为效率信号；这些不是统计结论，也不允许临时换指标挑胜。
6. 候选在任一长任务中，已知可比费用或时间增加超过 50% 且没有缓解基线实际容量失败，应先停止效率扩样并做开销诊断。将其登记为资源筛查阈值，不回写旧实验。

没有定价时货币指标为 unavailable，不能用输入+输出相加声称省钱；可比较时间、调用数、分类 token 和峰值窗口。若有容量收益但没有效率收益，产品只能定位为“减少容量压力”，不能宣称降本提速。

### 8.4 本阶段资源上界

准备注册时先按每个任务尝试 64 次全口径模型调用、4,000,000 token 预留、900 秒、8,192 输出上限估算可行性；两组严格相同，不因候选更容易耗尽而单独加预算。离线检查认为长任务不适配时，首次联网前重新选择任务或调整**两组一致**的上限，并冻结；运行后不能加码。

沿用上述数值时，六次尝试的批次上界为 **384 次模型请求、24,000,000 token 预留、90 分钟任务时间**。这不是预计消耗或费用承诺；三个上限谁先到谁生效，停止规则通常更早生效。E1 与 E2 分阶段批准和执行，不能把本方案视为自动消费两阶段合计额度的指令。

## 9. E3：按失败类型做单因素诊断，不无条件开启

### 9.1 信息损失的反证

只针对“基线完成、候选未完成”的具体任务，定位压缩后的第一个有意义分歧。从同一个任务快照分别执行：

- 候选原投影；
- 候选投影 + 一条疑似缺失原始证据。

工具权限、后续目标、仓库状态和资源一致。若相应错误恢复，支持该信息缺失参与因果链；仍要考虑模型随机性，不能一次成功就定论。若两者都失败，继续检查工具、执行和收尾，不为了符合预期继续增加摘要内容。

这是调试样本，不进入原 E2 的胜率或费用统计。必要时加一个不相关但长度相近的证据控制，区分内容作用与纯粹额外提示作用。

每次诊断先冻结两个分支；确需长度控制时最多三个分支。单分支继承分叉点剩余的原任务资源预算，不重新获得完整预算；绝对上限不超过 64 次模型调用、4,000,000 token、900 秒。因此一次三分支诊断最多 192 次请求、12,000,000 token 预留、45 分钟，实际以剩余额度为准。它需要独立执行许可，不能在 E2 失败后自动开展。

### 9.2 来源恢复的贡献

若产品主张是按需读回，记录每个关键约束在决策前可能出现的通道：用户原文、近期工具、摘要正文、历史读回、重新读文件。来源可获得不等于模型实际使用，不能仅按字符串出现在上下文就宣称因果。

想隔离摘要保留能力时，可做禁用读回的诊断分支；但这与实际产品不同，不能替代开放工具下的质量验收。

### 9.3 与简单策略比较

只有准备声称“摘要比简单隐藏更值得”时，增加 **mask-only vs 候选** 的同 H 对照；同模型、同 provider 硬窗口、同证据访问权限。先在一个明确触发的长任务上做配对诊断，再决定是否扩展。基线与候选均可读取原文，不能制造一个无证据基线。

不要同时改变摘要模型或推理参数。针对高维护成本的参数实验也一次只改一个因素，并单独注册，不合并进核心方案收益。

## 10. 后续正式验收与停止研发条件

E2/E3 只用于选择是否继续投入。正式发布前，冻结算法，使用独立任务集并按任务配对；同一任务多随机重复按任务聚类，不把每道题或每次工具调用当独立样本。

建议保留原发布目标：完整交付率差值的 95% 区间下界不低于 -5 个百分点，硬约束严重违背单独否决；通过质量门槛后才判断费用/时间收益。具体样本量由先导任务的基线成功率、配对不一致率、预设功效决定，20 个任务不自动足够。不能在看到结果后修改非劣效界。

以下情况不继续堆功能：

- 修正契约后仍反复遇到相同确定性拒绝：回到单一预算/投影函数验证，不继续付费。
- 真实任务中摘要维护与恢复长期抵消节省、也没有容量价值：保留为可选功能，不作为默认卖点。
- 简单隐藏和读回已满足任务，摘要无稳定增益：采用简单路径；不为维护既有复杂实现而寻找指标。
- 只有压低 H 才能测出收益，正常预算下无价值：明确适用范围，避免全局默认。
- 只有固定 A/B 可通过、新任务无法维持：按过拟合处理，停止以该夹具作为产品证据。

## 11. 工程任务清单与完成定义

| 顺序 | 范围 | 完成定义 | 是否需要模型费用 |
| --- | --- | --- | --- |
| 1 | 契约与计量收口 | 偏好/硬上限/最终投影一致；真实响应和边界通过 | 否 |
| 2 | runner/审计口径 | 未观测不算失败；B 的覆盖目标一致；旧数据解释不被改写 | 否 |
| 3 | 清单与构建识别 | 源码/dist/fixture/注册可定位；联网前不一致就停止 | 否 |
| 4 | 触发与开销复核 | 四次旧尝试逐项归因，区分事实/反事实/固定轨迹模拟 | 否 |
| 5 | 条件性 P1 | 每项策略修改均有复现；无证据的分支不实现 | 否 |
| 6 | 新 A/B 注册和 dry-run | 冻结协议、预算、来源和停止条件；独立核对 | 否 |
| 7 | E1 | A/B 覆盖、机制、质量、资源全通过，或按规则保存停止 | 是，最多两任务尝试 |
| 8 | E2 | 六次配对或提前停止；原始结果与解释一致 | 是，另行冻结预算 |
| 9 | E3/正式验收 | 只有上一阶段有信息增益时进入 | 条件性，单独注册 |

本方案阶段性完成的标志不是测试总数增加，也不是安装次数变多，而是：**同一契约不再误拒绝可用摘要、每次维护有可解释的必要性、真实任务能完成，且全部开销可追踪。**
