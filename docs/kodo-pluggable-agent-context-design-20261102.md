# 可插拔 Agent 与动态上下文组装

> 2026-11-03 评审更新：本文仅为历史背景，不是当前实施依据。以 [阶段驱动的能力挂载设计](kodo-stage-capability-design-20261103.md) 为准：先用 skill.load 隐式加载方法、切换时追加失效说明，保留执行过程；方法物理卸载等到压缩检查点，显式阶段协议与更多能力依据对照实验决定。以下以独立专家派发为主的实施顺序已被替代。

日期：2026-11-02。方向依据：用户要求保留 Agent 热插拔设计，在独立 Agent 的方法、能力和领域知识之外，按需继承主 Agent 已探索的项目知识，减少重复探索。本文细化设计与实施顺序，未实现运行时代码。

## 1. 设计结论

保留 Agent 作为可安装、可选择、可版本化的独立能力单元。主 Agent 负责用户目标、有效约束与交付；独立 Agent 保留自己的方法、工具、Skills、领域参考资料和工作上下文。

动态组装发生在任务派发、知识更新和必要的压缩检查点。主 Agent 与独立 Agent 共用可追溯的项目事实，不复制全部主对话，也不在每轮重新排序或替换历史。

这里的“项目”是一次持续工作的资料与资源范围，可以是代码仓库、业务材料目录或用户授权的工作空间，不要求 Git。

一个独立 Agent 的有效输入由以下部分组成：

```text
宿主执行规则与当前授权
  + Agent 固定版本的方法、能力目录
  + 当前目标、约束、必要输入、完成标准
  + 与本任务相关且仍适用的项目事实和来源片段
  + 按需加载的 Agent 领域资料
  + 本 Agent 后续追加的工作历史
  + 请求末尾的当前状态
```

领域资料决定“怎么判断、怎么做”，项目事实说明“这次具体是什么情况”。两者分别维护，不把一次任务的客户数据写进可分发的领域方法。

## 2. 四种信息的归属

| 信息 | 来源与归属 | 使用方式 |
|---|---|---|
| 用户目标与决定 | 主会话，沿用 decisionVersion | 传递相关的当前有效约束；决定变化时通知受影响任务 |
| 项目事实与观察 | 主 Agent、独立 Agent 的真实工具结果 | 带来源、版本、适用范围；按任务检索与引用 |
| Agent 方法与领域知识 | 固定版本的卡片、Skills、参考资源及已绑定服务 | 方法简介先可见，正文和参考资料按需读取 |
| 私有工作过程 | 各运行自己的消息与工具历史 | 独立保留；回传结果和必要证据，不广播全部探索过程 |

原始材料被读取不等于结论正确。区分观察、推断、未决问题与用户决定；来源仍未改变，只证明观察仍适用，不证明推断已经成立。

Agent 之间出现分歧时，保留不同结论及各自依据，定位到具体矛盾后核查。不能因为结论来自主 Agent 或某个专家，就自动覆盖另一方。

## 3. 一次派发的实际流程

1. 主 Agent 确定具体目标与独立 Agent，提交已经确认的事实引用、资料入口和未知问题。
2. 宿主解析卡片固定版本、实际工具绑定、读取范围和预算，检索相关的已有项目知识。
3. 按读取资格、来源可用性、版本和任务约束检查候选知识。无权读取的内容不通过摘要间接传递。
4. 把明确引用的必要事实与关键来源片段直接放入任务输入；其他候选只提供简短目录和读取引用。必需输入不足时明确暴露缺口，不能悄悄截断后声称上下文完整。
5. 独立 Agent 从已给出的事实和入口开始，按需加载自己的领域资料，只调查缺口、矛盾或已变化的来源。
6. 完成后回传交付物、结论、实际证据与未决问题。可复用的项目观察进入同一知识体系，主 Agent 按需采用。

起步不增加专门的“上下文选择 Agent”。先复用显式引用、任务输入、已有关键词和路径检索，以及来源检查。检索不足时允许模型补充查询，不先引入向量数据库或全仓预扫描。

只给证据指针仍可能让新 Agent 重复定位；全部塞入正文又会造成膨胀。因此必须传入足够启动工作的关键事实和少量必要原文，并使完整证据可按引用展开。

## 4. 主 Agent 的探索如何留下来

当前 `ProjectKnowledge.prepare()` 只接受宿主分配的结构化 exploration 运行，证据来自该运行成功的 `file.read`。主 Agent 普通读文件、分析材料得到的知识尚不能直接复用这条入口。

最小调整：把“校验来源并形成候选知识”的逻辑从探索结束流程中抽出复用，允许主 Agent 和普通独立 Agent 提交自己的观察及真实调用引用。沿用现有知识版本、工件与事件，不建立另一套 memory 数据库。

在派发前确有可复用发现、产生新的重要事实、任务交付等必要时机提交。不要每次读文件后都额外调用模型生成摘要，也不要把所有工具输出自动提升为事实。

第一步继续支持已有文件证据，优先证明主 Agent 的观察能被独立 Agent 复用。以后为真实使用到的网页、表格或应用记录增加来源适配：保存资源身份、可获得的版本或查询条件、时间和原始结果引用；无法检查新鲜度时标记未知，不套用文件 SHA-256 的结论。

当前知识条目保存的是候选观察，应继续保留这个语义。项目知识不会随能力包默认导出。

## 5. 怎样减少重复探索而不阻止必要复核

派发输入要让接收者知道：已知道什么、依据在哪里、依据何时或针对哪个版本成立、还缺什么。无须重新书写一份完整项目介绍。

| 状态 | 处理 |
|---|---|
| 来源未变，知识覆盖当前问题 | 使用结论与证据，直接继续任务 |
| 只有部分来源变化 | 复查受影响部分，保留其他仍适用的观察 |
| 结论与新证据矛盾 | 记录冲突并定向核查 |
| 任务需要新的细节或修改当前对象 | 读取必要原文或当前版本；这属于正常工作 |
| 已有 Agent 正在调查同一问题 | 复用已有任务、补充信息或等待，避免重复派发 |
| 无匹配知识 | 正常探索，不因知识库存在就限制新调查 |

对运行中的任务发送相关的知识增量，附事实版本及替代关系。不要每次新发现都广播所有 Agent；不受影响的工作继续推进。

是否“相同问题”优先依据显式任务标识、声明的输入与消费者判断。语义相近只能作为提醒，不能直接合并可能不同的任务。

优化目标是减少没有新增信息的重复定位和重复阅读，不是把读取次数降为零。来源核查、独立审查和变更后验证必须单列，不能记成无效探索。

## 6. 热插拔的准确语义

热插拔分为安装资源、使当前会话可发现、创建具体运行三个步骤；安装不等于启用，启用不改写正在执行的运行合同。

当前会话名册是冻结快照，`resolveAgentReference()` 会拒绝不属于该快照的卡片。因此要支持同一主会话中新加入 Agent，需要对现有名册快照增加显式修订，并记录此次变更；仅调用 `registerCard()` 不够。

建议规则：

- 已经安装并可用的 Agent 按需派发，不要求用户重开主会话。
- 新资源在当前会话的工具调用边界完成校验与绑定后，成为后续派发的候选；不能替换正在运行的工具回调或凭据绑定。
- 每个新运行固定卡片、资源和绑定版本。升级只影响后续派发，旧运行继续使用原版本。
- 停用阻止后续派发；正在执行的运行需明确完成或取消，再释放连接与资源，不能直接让它失去工具。
- 授权仍由宿主和用户约束决定。能力包自带的声明不能增加执行权限，也不能令 Agent 自动看到全部项目知识。

这需要对现有冻结语义做明确扩展。本提案不把“配置可导入”描述成“当前已支持任意运行中热插拔”。

## 7. 动态组装与缓存的边界

主干保留原始记录。任务相关知识在派发时组装，执行中通过追加增量补充；只有达到容量压力或明确的上下文重建检查点时才替换投影，并保留旧原文引用。

独立 Agent 具有不同方法和工具，其初始请求通常与主 Agent 不完全一致，不能承诺复用父级整个缓存。优先保持每个 Agent 自己的提示、工具顺序和历史稳定；重复使用同一专家时优先沿用仍适用的运行上下文。

不要为了命中缓存把所有专家能力都塞进主 Agent，也不要为了保留专家身份频繁改写主干 system。新增 Skill 正文和知识以追加方式进入历史；工具集合确需改变时，记录能力版本变化并接受实际缓存代价。

fork 不作为本方案前提。只有任务确实依赖大量父级细节、方法与工具条件适合时，才单独评估完整历史继承。默认先证明“共享必要项目事实 + 独立专家方法”的收益。

## 8. 对现有代码的最小实施顺序

| 顺序 | 落点 | 交付结果 |
|---|---|---|
| 1 | `src/knowledge/index.ts` 与现有观察记录入口 | 主 Agent 普通探索可以形成带真实来源的候选项目知识 |
| 2 | `src/messaging/child-config.ts`、`handoff.ts`、`index.ts` | 专家派发携带相关事实版本、关键片段、未知问题，保留原卡片的能力与方法 |
| 3 | `src/runtime/tool-view.ts`、`role-view.ts` | 精简模式可到达已授权的 Skill、知识与扩展能力，不被固定工具映射全部隐藏 |
| 4 | 现有消息、知识版本与任务状态 | 专家回传的相关观察可被主 Agent 及后续任务采用；变化只通知相关任务 |
| 5 | 名册快照、资源注册与绑定恢复 | 当前会话能显式接入新 Agent；旧运行版本不变，重启后可以解释使用过的配置 |

前四步先使用会话已有 Agent，能独立检验减少重复探索的价值。第五步补齐运行中新增能力的语义，避免把热插拔与知识复用绑成一次大重构。

动态组装保留为运行时能力，不要求模型手写长交接文档或每次维护一份上下文清单。用已有请求快照和事件记录采用的知识版本与来源，足以追踪选错或漏选的内容。

## 9. 验证范围与收益判断

对照同一个专家、模型、能力、任务和预算：旧任务包交接与新的项目知识组装。起步不同时更换模型、增加 fork 或修改调度政策。

必须包含以下情形：主 Agent 已有相关发现；专家仍需独有领域知识；知识仅部分过期；主 Agent 结论与实际来源不符；没有可复用知识；资料过大需要回读；专家回传后另一任务使用；新增卡片与在途运行并存。权限与资源版本沿用已有校验，不为试验放宽。

质量以任务实际完成及领域要求为主；过程记录重复定位、同版本材料重复进入模型的数量、首次有效动作前往返、缺口复查、知识采用与来源回读，以及全部运行的费用和耗时。缓存命中只作为解释指标。

至少在资料整理/表格分析与编码两个不同场景验证，防止方案退化为只适用于仓库文件的上下文优化。知识相同但没有减少用户劳动或模型重复工作时，不宣称形成竞争力。

## 10. 产品表达与现状

推荐表述：**按任务接入专业 Agent，让它带着自己的能力，接着已经确认的项目事实工作。**

这一机制支撑通用任务产品及工作方法复用，不代替前述产品定位。对用户展示“沿用了哪些资料和规则、补查了什么、哪些依据已变化”，协作详情按需展开。避免承诺“完全不重复探索”或“所有 Agent 天然共享缓存”。
