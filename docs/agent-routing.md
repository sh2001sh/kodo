# Agent discovery and session routing

`searchCards(store, options)` remains a stateless host metadata API. Queries split on whitespace; every term must match. Terms of at least three Unicode codepoints use SQLite FTS5's trigram tokenizer. One/two-character terms use literal containment, including short Chinese queries such as `库` or `数据`. Input is quoted as literal phrases; SQL and FTS operators are never executed. Exact IDs, exact names and ID prefixes rank before weighted trigram relevance, with stable ID/version tie-breaking. Explicit `tools` and `skills` filters require every listed capability.

The derived FTS index contains ID, name, description, tool names and skill IDs. Private prompts are excluded. Initial construction indexes existing cards, and SQL triggers keep later insertions, updates and deletions consistent. Card references always retain immutable `id`, `version` and `digest`. The index requires the bundled SQLite FTS5 trigram extension; an unavailable extension produces a visible SQLite error instead of silently changing retrieval semantics.

`directoryCards(store, { namespace?, tools?, skills?, offset?, limit? })` provides vocabulary-independent browsing. Omit `namespace` to page publisher names and their agent/version counts. Supply an exact namespace to page its installed immutable card versions. Both directory levels are bounded, and the same exact capability filters apply.

`routeCards(store, { query, tools?, skills?, limit? }, policy?)` first retrieves complete term/capability matches. If none exists, it performs at most eight partial-term searches, each limited to 40 versions. These near matches explicitly report `missingTools`, `missingSkills`, and unresolved task fit. The result contains up to 20 distinct agents; one version represents each agent. An immutable `policy.preferredVersions` entry can identify a trusted host preference; otherwise routing selects the numerically newest matching installed version and explicitly does not claim that it was adopted. A supplied digest must match. Routing never creates agents or grants permissions.

New sessions freeze a full member roster in SQLite. Sources resolve by ID with project cards ahead of user cards, then builtins. A main card's explicit `id/version/digest` reference pins its version within the same source; a higher source may override it. Each snapshot includes the selected full card, availability reasons, resolved file scope, catalog descriptions and a deterministic digest. Later registrations affect future sessions only. Model `agent.search`, `agent.directory` and `agent.route` query snapshot members through SQL; the host APIs above keep their global installed-registry semantics. Sessions restored without a snapshot retain the old global discovery behavior.

`agent.search { query?, path?, mode?, tools?, skills?, mcp?, cursor?, limit? }` applies all structural filters to the same available member before ranking its metadata. Routing also indexes `use_when`, `not_for` and catalog aliases. `agent.directory { path?, cursor?, limit? }` returns direct child catalog nodes and leaves, including unavailable members and their reasons; branch capability unions are navigation hints only. Member summaries expose public `inputs`, `report` and `resolvedScope`, so a member omitted from the initial context can still be delegated after discovery. Prompts and private rule bodies are excluded.

Follow `next.cursor` with unchanged filters. The cursor binds the snapshot digest, operation, query and offset; stale or mismatched cursors fail. In the modern catalog schema, `namespace` remains an alias for `path`. When both A and C are disabled, or restored sessions have no factor flags, model tools use the old result projection: metadata-only summaries, publisher namespaces, `next.offset`, and the old routing reasons/version-selection labels. These queries still select only frozen rows, and routing aliases/private fields do not enter baseline metadata matching. The old version-selection labels describe the compatibility projection; they do not switch lookup back to the live registry. Legacy sessions without a snapshot retain the original global semantics.

The three model tools share a durable session exploration allowance, including child runs and process restarts. Defaults are 12 successful calls and 100 distinct returned `id@version` leaves. Internal catalog nodes consume calls but no member allowance; repeated leaves are counted once. This accounting also applies to frozen sessions using the old projection: publisher namespaces are not leaves. Empty searches consume calls. Every successful exploration persists `agent.discovery.explored` atomically with newly seen members and the budget check. Once established, limits can only narrow. Invalid arguments do not consume the allowance, and host API calls are unmetered. Legacy sessions without snapshots retain their previous candidate/directory-entry counting. Baseline response comparisons therefore cover ordinary discovery over identical frozen contents; budget equality requires a sequence without repeated leaves or namespace-only pages, and compatibility does not extend to later live-registry changes.

Model results distinguish `matched`, `no_match`, `missing_capabilities` and `budget_exhausted`. Snapshot routing returns `missing_capabilities` when every returned partial candidate lacks requested tools, skills or MCP servers, with each candidate's specific gaps; global routing retains its old response shape. Exhaustion includes explored paths and remaining unexplored branch count. If a page exceeds the remaining leaf allowance, it retains already known and affordable members, removes excess members and clears continuation. Internal nodes and known leaves can still be read after the leaf allowance reaches zero while calls remain. A final allowed page does not promise another call. Exhaustion means incomplete exploration, not evidence that no suitable member exists.

The general card directs the main agent to find independent bounded work, use routing when specialist discovery helps, and call `spawn_agent` when the benefit exceeds coordination cost. Children receive explicit inputs, acceptance evidence and disjoint write scopes. No fixed child count is imposed. If no specialist fits, omitting both card reference fields can inherit the current card for suitable independent work. Runtime permissions, scope, maximum-agent budget and main-agent-only spawning still apply.

`spawn_agent` accepts an exact member reference through `agent`, named `slots` matching that card's input contract, and optional `inputs: string[]` and `acceptance: string[]` alongside `objective` and `context`. The two lists permit at most 16 nonempty strings of at most 2000 characters. The child receives them as task data and requested evidence; it gets no implicit copy of its parent's conversation. Legacy cards without required input slots retain objective/context-only calls. V2 cards validate their required slots before creating a child. See [the card design](agent-card-design.md) for input kinds and report contracts.

The spawn tool description reports the configured session child-creation maximum and the routing tools approved by the selected card under the current read grant. Volatile balances stay in tool results so child creation and spending do not change tool schema identity or invalidate measured-input token calibration. `list_agents` and successful spawns return a live `delegation` snapshot: created/remaining/active children, main-run creation availability, approved routing tool names and remaining shared model, tool and token allowances. A remaining allowance of `null` means no configured limit. The child-creation maximum counts all children in the session, including completed, cancelled and failed children; it is distinct from `maxConcurrentModels`. Every child spends from the same session counters. Snapshot values can change after another run acts and never promise runtime admission or extra permissions.

The intended tool sequence is a model decision: route a concrete independent task, spawn the selected exact card version with inputs and requested evidence, continue useful nonconflicting work, wait when blocked, inspect the terminated child's result and original tool evidence, and integrate the finding. An unavailable version or denied permission produces a reviewable tool failure without creating a child. A failed child wakes its parent with failure evidence; it is not converted into successful acceptance. Small tasks can finish directly without routing or child creation. The runtime does not infer arbitrary task splits or create agents automatically.

Coverage includes frozen source/version selection, public delegation contracts, short aliases, same-member filters, cursor binding, late-registration isolation, distinct-leaf accounting, restart persistence, transaction rollback recovery, capability-gap status, and legacy installed-registry behavior. The separate `autonomous-delegation.test.ts` and `collaboration.test.ts` suites cover coordinator execution.

The autonomous-delegation regression drives the real coordinator using a deterministic scripted provider. It covers the actual `agent.route → spawn_agent → child file.read → wait_for_events → inspect_run → parent final` tool loop, immutable card selection, independent contexts, narrowed permissions/scopes, shared session accounting, explicit failed-child handling, task-packet bounds and creation-capacity exhaustion. This establishes execution and enforcement behavior; it does not measure how frequently a live model chooses a useful decomposition or whether delegation improves cost or task quality.
