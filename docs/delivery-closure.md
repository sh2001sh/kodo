# 交付闭环修复与验证

2026-10-21。本轮保留原协作策略，优先修复共同的交付基础设施。空白回复与半成品同时出现不能证明因果关系；这里分别检查答复完整性和公开验收，未以强制创建子代理改变成绩。

## 当前完成条件

- 默认要求非空白最终正文。空白、null 或只存在私有推理均不能完成；复用 completion.checked、completion.correction_requested 和原有两次纠正机会，第三次仍不满足则 DELIVERY_FAILED，产物及调用证据保留。
- 正文检查单独记为 result.delivery；没有公开验收器时 quality 仍为 not_checked。非空不代表需求正确，也不将私有推理补成最终回复。
- 配置 `--verify-command` 或库的 `setCompletionValidator` 后，正文与公开检查必须同时通过。每个候选都重新检查实际交付目录，不缓存前次通过；正文为空也执行公开检查并分别记录 deliveryPassed 与 qualityPassed。公开检查失败时反馈真实错误，耗尽后 QUALITY_FAILED。
- 验收期间的受管写入、未结束写入或提交完成前的新写入使通过结果失效。核对同一工作目录中已登记的工作区写调用，并复用已有 recovery.resolved 判定，避免把已核验恢复但保留原记录的 unknown 调用误判为仍在写入。提交前失效会重验原候选，不额外生成一次答案。
- `CreateRunOptions.finalResponse: 'optional'` 或 CLI `--allow-empty-response` 明确允许静默／仅产物交付。该约定持久化，恢复及后续任务保留；公开验收仍适用。子代理默认仍需文字交付，不因主任务允许静默而自动豁免。

公开检查必须由宿主选择并信任。内核不会猜测任意仓库的验收命令；未配置时不会宣称构建或测试已通过。隐藏评分仍在运行结束后独立执行，不作为纠正反馈。

库调用示意：

```ts
const run = app.createRun({ objective, workspace, binding });
app.setCompletionValidator(run.id, async ({ signal }) => {
  // 在实际交付目录运行公开命令，返回真实退出码／证据及有上限的错误反馈。
  return publicAcceptance(workspace, signal);
});
await app.run(run.id);
```

CLI 的 `--verify-command` 仍使用完整 JSON 参数数组；正文完整性由内核组合，无需命令再次解析模型答复。验证责任写入主／子共同的交付约束：工作者检查各自模块，主代理执行最新状态的集成检查，协调全局命令以避免重复。这是方法指导，不承诺已实测减少重复调用。

## 破坏性验证的副本入口

`scripts/verify-in-copy.mjs` 复制本仓库源码、测试、脚本及构建配置到独立临时目录，命令在那里执行；不复制 `.git`、`.kodo`、环境文件或交付目录外资产，不向原目录恢复／回写。源码符号链接明确拒绝，避免悄悄得到不完整副本。依赖链接指向预装 node_modules，可信命令须保持依赖只读。

```powershell
node 'scripts/verify-in-copy.mjs' -- node 'scripts/my-mutation-check.cjs'
```

命令参数使用副本内相对路径；这是本仓库的验证辅助入口，不是新增沙箱或通用回滚系统。普通结束清理副本；强制杀死可能留下临时目录，但不会依赖 finally 恢复交付源码。最终公开验收仍针对实际交付目录。

受管写入检查不监控其他数据目录、未登记外部进程、后台副作用或任意外部编辑器。高权限进程也可以显式访问原路径或写共享依赖；需要严格隔离时由宿主提供独立工作目录／系统权限。宿主验收命令自身也应避免改变被验收源码。这些边界不能被描述成“任何源码变化都能自动捕获”。
