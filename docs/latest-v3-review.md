# Kodo 最近改动与实验复核：v3 压缩及 explore

日期：2026-10-24。审查对象是当前工作区、v3 T8 原始实验目录及模型调用账本，不是此前 v2.1 的结果。本次只进行只读审计、离线验证并新增本报告，没有修改运行时代码或调用付费模型。

## 1. 判断

v3 的简化已有真实效果：自由文本摘要能安装，能支撑当前分页修复任务续做，工作上下文和总 token 都下降。此前“严格结构与多层预算拒绝让摘要不可用”的主要障碍，在这批任务上已经消失。

但“更省钱、更快、普遍保质”仍不成立。原始账本显示：summary 的未缓存输入和输出都增加，累计运行时间增加约 56%。降低总 token 不能代替费用与时延验收。

explore 接口已可用，运行时提醒确实伴随两次真实委派；其主要问题已从“能否创建”转为“划分是否值得、范围是否合适、查到答案后何时停止”。不应继续以委派次数作为主要优化目标。

## 2. 已核对的改动

- `src/runtime/compaction.ts`：自由文本交接、复用当前消息和工具定义、禁止摘要调用工具；窗口处理和瞬态重试有界；保留共享预算记账。
- `src/runtime/summary-install.ts`：去掉旧正文目标的强制拒绝，保留输入缩减检查、取消/版本检查与原子安装；失败或收益不足时停止本 run 的摘要尝试。
- `src/runtime/context.ts`：固定前缀 F 与剩余空间 W=H−F 分离，尾部、安装目标、防抖阈值分别按剩余空间计算。
- `src/runtime/summary-schema.ts`：新写入自由文本 v2 envelope；归档仍保留原文，旧 v1 可读。新摘要不再提供旧式逐条短来源 ID。
- `src/messaging/explore.ts`：一次调用创建 1–4 个只读子代理并等待，直接返回有界报告，降低手动 spawn/wait/inspect 的操作成本。
- `src/runtime/explore-nudge.ts`：主代理累计成功读取达到阈值后提示一次；默认阈值 8，默认开启，允许显式关闭。子代理及收尾阶段不提示。

这些改动总体符合精简方向。自由文本不等于取消工程约束：协议合法性、共享预算、可恢复原文和原子安装仍然必要。

## 3. 压缩实验：成功是真的，但收益需要重述

证据目录：`.kodo/v3-t8-compaction-paid-h24k/`。

逐个以 SQLite 只读模式读取 calls、events 与结果 blob，重算所有 12 个 trial 的用量；与各自 report.json 全部一致。复制产物到临时目录重新执行 `node verify.mjs`：12/12 均通过 27 项检查。保护文件不仅核对原文件哈希，也与对应夹具比较完整保护文件集合，全部相同；12 份最终答复均非空。

时长按每个 trial 首、末事件时间差相加，是运行期间墙钟时间，不含启动前准备和事后独立验收，不是用户端完整端到端时延。本批 summary 四个配对运行分别都慢于 off；样本仍不足以外推稳定比例。

summary 共安装 12 次，未记录摘要失败；维护 token 161,142，占总量 18.75%。四次 summary 的总 token 分别均低于对应 off，组总量减少 33.28%，主请求输入峰值降低 51.42%。这些是本批可重复核算的正向证据。

但未缓存输入增加 18.67%，输出增至 3.22 倍，运行时间增加 56.01%。本批 cacheWrite 为零；若三种单位价格分别为未缓存输入 p_in、缓存输入 p_cache、输出 p_out，则 summary 相对 off 的费用差为：

```text
Δ费用 = 49,825 × p_in − 509,952 × p_cache + 31,348 × p_out
```

只有代入同一 provider 的真实价格后，才能判断是否省钱；若另有计费种类，还需加入相应项目。

摘要请求本身：输入 129,825，输出 31,317，cacheRead 1,408，缓存读取比例约 1.08%。因此“复用了前缀结构”可以从代码证明，“实际摘要有良好的缓存收益”则被本批数据否定。检查 task-a-summary-1 的两次摘要，工具定义确实与前次主请求相同，前 17 条消息相同；仍不足以推定 provider 的缓存命中。缓存键、tool_choice、上游处理及精确消息序列应进一步分离验证，不能直接认定某一个是根因。

另一个值得离线诊断的信号：该 trial 两次摘要前估算输入为 27,649 / 24,829，实际摘要输入（另含压缩指令）只有 11,589 / 9,367。两次均未丢弃摘要请求轮次。当前估算校准要求历史请求完整消息序列为精确前缀；末尾动态内核状态会破坏这种匹配。可以怀疑估算保守导致过早触发，但需重放每次请求的估算分支后再归因，不能直接用一个比例降低容量安全余量。

证据边界：

- A/B 属于同一个分页微型项目的文档长度变体，不能视为四个独立项目任务。
- 原始 `summary.json` 的维护占比 <15% 门槛失败；`summary-rescored.json` 按用户调整后的“总 token 不高于 off”门槛通过。调整产品指标合理，须称为事后重评分，并以新批次验证。
- 这些夹具的正确约束也可从源码、保护文件和验收脚本再次获得。因此成功证明可续做，不单独证明“摘要记住全部关键事实”或“归档读回是成功原因”。
- 本批 12 次安装的 droppedGroups 均为 0，未覆盖真正挤满窗口后的摘要丢组恢复。

## 4. 委派实验：成本差异已有具体解释

证据目录：`.kodo/v3-t8-delegation-paid/`、`.kodo/v3-t8-delegation-survey-paid/`、`.kodo/v3-t8-delegation-nudge-paid/`。

无提醒的两批实验中，两种模型均未自主委派。八个问题可以通过主代理批量 search/read 完成，不能据此判定不委派就是决策错误，也不能把两组 token 差异归功于协作。

增加提醒后，survey 六次全部触发提醒，每种模型各 1/3 创建子代理，两次均创建四个且完成。说明工具可用，策略可被干预；尚未达到原先 2/3 的观察线。最新提醒批次没有同期 Solo 或无提醒控制，不能据此估计提醒的因果收益。纠正后的答案评分为每模型 24/24，是脚本口径，并非所有陈述均经独立语义审计。

| 实际发生委派的运行 | 主代理调用 | 四个子代理调用 | 合计 token |
| --- | ---: | ---: | ---: |
| Flash survey #2 | 11 | 27+13+13+17=70 | 1,222,023 |
| Pro survey #3 | 8 | 5+10+7+5=27 | 343,324 |

Flash 的四个任务全部设置 `thorough`，scope 未限定 read 根目录。Pro 全部使用 `medium`，分别限制在 runtime、web、packages、sandbox。两者派发的问题组合也不同，不能把差异全归因于模型或单个参数。

Flash 最贵的子任务只为查清报告上限，却单独使用 552,015 token：第 4 步读取 `explore.ts`，第 6 步读取常量使用位置；此后继续查消息投递、存储、UI、截断路径等，到第 26 步才交付。任务提示还要求排查竞争上限，thorough 又要求多处确认，这能解释过度调查的一部分，不能笼统称作无意义循环。

最直接的优化是任务契约：常量查询使用 quick、限定目录、提供已知搜索结果；找到定义和一个实际使用点即返回，只有发现矛盾才扩展。架构调查再使用 medium/thorough。先验证这项小改动，不必新造复杂路由器或增加强制委派。

8 次读取阈值适合当提醒机会，不适合作为收益预测：快速批量查询也可能两轮就达到阈值。提醒目前默认开启，尚无稳定收益证据；建议暂限实验配置，至少对默认用户避免未经验证的高开销行为。

## 5. 需要优先修正的评测缺口

### P1：停止指令没有退出整个付费矩阵

`scripts/comparison/v3-compaction-eval.mjs:144` 的 relay rejection 分支只有 `break`，退出的是最内层 arm 循环；后续 fixture/repeat 仍会执行。因此打印 stopping 并不代表停止全部后续请求。

应使用外层退出或返回，先持久化中间结果，并以模拟 relay 拒绝验证之后不会再启动任何 cell。本批没有 relay 拒绝，未据此判定已有结果失效，但下次付费前应修正。

### P1：通过判定允许“不完整、全部失败、费用未知”的组合

`scripts/comparison/v3-compaction-eval.mjs:108` 的 summarize 只比较相对完成率与累计 token，没有检查注册矩阵完整性、配对数量、绝对交付要求及未知用量。

本次零费用直接调用真实 summarize，反例输出：

```json
{"allFailedAndUsageUnknown":true,"incompleteMatrix":true}
```

第一组是 off 和 summary 均失败、summary 有一次安装且用量未知；第二组只有一对 task-a，而非完整矩阵。两者都被判 passed。

另外 `v3-eval-common.mjs:77` 跳过 failed model call 的 token 累计，缺失 usage 的成功调用也不计入总量。未知用量应显式阻止“费用不劣”的判定，不能算成零。

建议通过条件同时要求：注册矩阵或预声明停止后的判定规则完整；固定质量底线达成；配对有效；费用口径完整；无禁止的错误类别。未知结果标记 inconclusive。本批 12 个 cell 完整、均成功、均有用量，故这些缺口没有推翻本批 token 对账结果。

### P2：交付和冻结检查需要补齐

`completed` 当前只检查 run 状态、verify exit 和原保护文件哈希，不检查最终答复非空，也不检查新增保护文件。正式付费前还应先写入不可变注册与代码/夹具清单，禁止复用已有结果目录；survey 每次从实时 src 复制，需改为整批同一冻结副本。

本次独立审计补做了非空答复和完整保护集合检查，均通过；这不替代 runner 以后自动执行这些检查。

## 6. 可追溯性与文档边界

v3 保留的是“摘要 → 历史消息归档”的可追溯性，不是每条结论到精确证据的映射。`coveredOffsets` 表示从工作上下文折叠掉的消息，不能解读为这些事实已经完整进入摘要。

`fitWindow` 可以移除旧轮次，但当前只记录 droppedGroups 数量；history 之前也可能经过 mask/hard 投影。应区分归档/替换范围、摘要实际看到的来源范围、验证过的事实保留率。若进一步需要精确观测范围，优先记录现有消息来源偏移，不恢复让模型生成巨大来源 JSON 的旧方案。本批不据此判定发生了信息丢失。

`docs/context-compaction.md` 顶部仍写 T8 未运行、0.3H/0.5H/0.7H，以及“mask 后仍超 H 才摘要”。这些与最新状态有差异：

- T8 已运行并事后重评分；
- 实际份额以 W=H−F 计算；
- 正常纯 summary 路径不会先 mask，hybrid/fallback 才会，参见 `context.ts:490`。

本报告保留旧实验原文；后续应统一主设计入口，避免再以旧 v2.1 结论描述当前实现。

## 7. 建议执行顺序

1. 先修评测器停止、完整性、未知费用和冻结检查，补上述反例；这是下次付费的前置条件。
2. 用现有请求离线分析估算偏差、触发次数、摘要输出长度及缓存前缀。先定位为什么提前压缩和缓存未命中，不直接改写摘要架构。
3. 冻结当前 v3 为基线，保持 compaction 默认关闭。先在少量独立任务上比较 off 与 v3；若离线有清晰证据，再增加一个针对性候选，避免同时修改触发、模型、提示和存储结构。
4. 新任务至少覆盖：多文件代码续做、不可从当前源码直接恢复的早期用户约束、多来源长报告、目标切换后按归档找回旧证据。保持工具能力一致，允许开卷，以最终交付正确性为主指标；闭卷只作记忆诊断。
5. 交错/随机运行顺序；记录缓存输入、未缓存输入、输出、摘要/主任务分项、整体时延、恢复调用及重读成本。锁定价格后计算金额；无价格时不宣称省钱。少量探索通过不等于统计验收。
6. 委派实验与压缩实验分开。使用同批、同代码、同预算的无提醒与有提醒组，保留简单批量查找负控制，再加入需要独立深入调查的任务；按交付、费用、时延判断是否值得，不按创建率奖励系统。
7. 对 Flash 的过度探索，先做零费用轨迹审计和任务契约修订；再以匹配任务比较现有契约与 quick/范围/停止条件明确的契约。若需要指定委派正控制，只用于验证执行效率，不混充自主选择成功。

当前不建议恢复严格 JSON 摘要、多层分类、复杂覆盖算法，或为了提高委派率强制拆解所有任务。最新证据支持保留简单内核，并把工作重心移到实际成本、触发准确性和任务结束条件。

## 9. P3 零费用压缩诊断（2026-10-24）

脚本：`scripts/comparison/v3-compaction-diagnosis.mjs`（只读打开 SQLite，blob 从磁盘读取，不写锁）。输入为 `.kodo/v3-t8-compaction-paid-h24k` 的 12 个试次，输出在 `.kodo/v3-compaction-diagnosis-h24k/diagnosis.json`。估算使用当前 dist 估算器逐次重放，每次只看该调用之前已有的调用。付费模型调用：0。

| 观察 | 数值 |
| --- | --- |
| 估算是否复用了实测前缀（calibratedShare） | 12/12 试次均为 0 |
| 工作请求估算 / 实际 input | 1.67–1.78 |
| 首个请求（近似固定前缀 F） | 估算约 10,050，实际约 5,030 |
| 前缀断点 | 主要为 `kernel-state`：上一请求末尾的执行状态消息每步被替换，精确前缀匹配因此全部失败 |
| summary 组实际触发点 | 12 次摘要前一个工作请求实际 input 为 11.9k–15.1k，估算为 21.2k–24.6k，H = 24,576 |
| 摘要安装 | A/B 各两次重复：2、4、2、4 次安装；4 次安装组各有 2 次 geometry 跳过 |
| 摘要请求缓存读 | 0–256 token（约 0.6%–1.5%）；工作请求为 56%–92% |
| 摘要请求与前一请求共同前缀 | 11–21 条消息，只在末尾 kernel-state 处分叉，tools 相同，tool_choice 为 none |

结论：

1. 估算校准在真实轨迹上从未生效，原始估算约高估 1.7 倍。summary 组的压缩实际在约 55%–60% 的 H 处触发，即“过早压缩”的直接原因是估算，而不是几何参数。不应先调整软阈值或防抖。
2. 摘要请求与上一请求的消息前缀基本一致，provider 却几乎不命中缓存。离线数据无法区分是 `tool_choice` 变化、末尾状态消息还是 relay 的缓存策略所致，需要单独的 provider 微实验；修复估算不能推定缓存改善。
3. 摘要请求含更多消息，实测 input 却低于前一个工作请求（例如 11,589 对 13,653），原因未确定，暂不据此下结论。

单点候选（对应 §6.2 第一行，尚未改运行时代码）：前缀匹配时，若历史请求最后一条是 kernel-state，则把它的实测 input 归于去掉该消息后的前缀；当前请求中新增的部分（包括新的 kernel-state）照常估算。被忽略的那条消息已计入实测值，因此只会高估、不会低估。按真实估算器做的反事实重放（`stateTolerantStore`）：

- 校准命中率由 0 变为 1.00（task-b-mask-1 为 0.63，其中有工具结果被 mask 改写）。
- 估算 / 实际由约 1.7 降为 1.16–1.47，最小值 1.03，无一低于 1。
- 超过 H 的工作请求估算数明显减少（例如 task-b-mask-2 由 16 降为 6，实际为 0）。

可证伪假设：采用该候选后，同一任务的 summary 组应推迟触发、减少安装次数，且不出现超出模型硬窗口的请求。需新注册（r2 评测器）后验证，旧批次通过线不改写。

实施状态（批次 5，2026-10-24）：候选已在 `src/runtime/context-tokens.ts` 实施（`calibratedMessages`），只去掉历史请求最后一条 role 为 system 的 kernel-state 消息。反例测试在 `tests/context-hardening.test.ts`：同名前缀的 user 消息不被去掉，位于中间的状态消息仍须精确匹配，新增内容全额估算。用当前 dist 重放同一份证据（`.kodo/v3-compaction-diagnosis-h24k-calibrated`），结果与反事实一致：命中率 1.00（task-b-mask-1 为 0.63），估算/实际 1.16–1.47，最小 1.03。付费验证见 §10，压缩仍默认关闭。

若 p_out = 2·p_in，则只有当缓存单价高于未缓存输入单价的约 14% 时，summary 才省钱；若 p_out = 4·p_in，门槛约为 16%。缓存折扣越深，summary 越可能更贵。锁定该 provider 的真实价格后才能下结论。
