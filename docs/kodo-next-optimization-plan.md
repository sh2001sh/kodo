# Kodo 下一阶段修复与优化整体方案

日期：2026-10-24。状态：待实施方案。本轮交付方案，不代表其中修改已完成，也未启动付费实验。

依据：[v3 最近改动与实验复核](latest-v3-review.md)、当前 `explore` / `spawn_agent` / 卡片与能力绑定实现。此前原始实验及预注册保持不变。本方案作为下一阶段入口，不回写历史验收结果。

任务设计补充：[真实工程任务评测设计](engineering-evaluation-tasks.md)。后续主评测采用冻结工程上的修复和完整功能交付；常量查询及分页微项目只保留作机制回归。任务资产与独立验收尚待制作，不能将规格文档视作任务已可运行。

## 1. 目标与优先级

目标是让 Kodo 以较小的协调和上下文成本完成用户任务，并允许主代理动态创建合适的子代理、复用和导出有效配置。

当前有三项已证实的问题：

1. 评测器可能没有真正停止后续付费单元，且不完整或全部失败的矩阵可能被判通过。
2. v3 压缩在当前任务上确实可用，但总 token 减少伴随未缓存输入、输出及运行时间增加；尚未证明省钱。
3. explore 已可运行，但简单查询被设置为全仓库深入调查，导致部分子代理过度工作。动态任务分配已有，运行时动态能力组合尚未完整打通。

顺序为：**修评测底座 → 收紧子任务契约并诊断压缩开销 → 打通统一创建与临时配置 → 分别验证收益 → 完成卡片复用闭环 → 有证据后调整默认值。**

不以子代理数量、摘要次数、知识条目数量、单纯 token 降幅作为成功指标。主要结果是完整交付、约束遵守、实际费用、用户等待时间；上下文峰值和创建率用于解释结果。

## 2. 目标架构：统一运行机制，配置可组合

```text
用户目标
  └─ 主代理：识别工作、决定直接执行或委派
       ├─ 直接执行：简单任务与集成收尾
       └─ 子任务：目标 + 已知资料 + 范围 + 验收/结束条件
            ├─ 继承当前配置
            ├─ 选择已注册社区/本地卡片
            └─ 临时组合宿主允许的能力
                 ↓
          同一套配置解析、权限校验、预算、创建、通信、恢复
                 ↓
          子代理独立上下文 → 报告及证据引用 → 主代理验收
                 ↓
          值得复用时保存新卡片版本及能力包
```

区分三个概念：

| 概念 | 内容 | 是否必须预定义 |
| --- | --- | --- |
| 任务 | 目标、背景、输入、范围、验收与结束条件 | 否，随需求生成 |
| Agent 配置 | 方法说明、工具、Skill、模型及能力绑定 | 可继承、引用卡片或临时组合 |
| 执行约束与交互方式 | 权限、预算、并发、等待、结果投递 | 内核定义机制，参数受宿主管理 |

不新增 `researcher/coder/reviewer/...` 内核类型枚举。探索、审查、实现可以是卡片或任务角色；新增专业角色不应修改调度器。

`explore` 保留为“批量只读调查 + 等待 + 返回报告”的快捷入口。`spawn_agent` 的通用描述应覆盖有界子任务，不再把它限定为修改代码。两者继续复用现有 prepare/commit 路径；不建立第二套调度器。

统一机制不要求两种入口的产品行为相同：explore 仍不能写文件，spawn 可以异步返回，结果可按入口选择现有报告投递形式。

## 3. 阶段 P0：先修评测器与事实入口

涉及 `scripts/comparison/v3-compaction-eval.mjs`、`v3-delegation-eval.mjs`、`v3-eval-common.mjs` 及相关测试。

### 3.1 矩阵执行与停止

- relay 拒绝、累计预算到顶或预注册的致命条件触发时，停止整个矩阵，不仅退出最内层 arm 循环。
- 每完成一个 cell 就持久化结果；停止时保留原因、已完成、未开始和中断 cell。
- 启动前写入注册快照，包括代码/构建/夹具哈希、模型与限制、策略、价格口径、任务列表、执行顺序、重试与停止规则。
- 输出目录必须为空或新建；恢复只能按同一注册显式执行，不能覆盖或混用原结果。
- survey 整批使用同一份冻结源码；构建产物与源码对应，避免 dist 与 src 不一致。

验收：模拟第一次、居中一次、最后一次调用被拒绝；拒绝之后新 cell 启动数和网络请求数均为零。模拟中途退出，已完成证据仍可读取且不会被覆盖。

### 3.2 通过判定与交付

- 校验注册单元集合、配对键和重复次数；缺单元、重复单元、策略混用均不能判收益通过。
- 质量要求有绝对底线；off 与候选同时失败不能靠相对完成率通过。
- 交付检查包含非空最终答复、要求的文件产物、独立功能验收、完整保护路径集合及哈希。
- failed/unknown usage 不按零费用处理；分开记录已测量、已知零和未知，未知导致费用结论为“不确定”。
- 任务错误、提供方故障、摘要失败后恢复、run 终态分别记录，不能互相覆盖。

验收：把上轮两项反例加入测试，并补“少跑昂贵样本”“失败调用有费用但无 usage”“新增保护文件”“空回复但 run completed”的反例。任何一个都不能产生收益通过。

### 3.3 报告口径

按主任务、摘要、各子代理分别统计：请求数、输入/输出、cacheRead/cacheWrite、未知用量、峰值输入、工具重读、首尾时长。费用按冻结价格计算，区分子代理累计耗时与用户实际等待时间。

公开报告使用 session 调用账本计总开销，不能只加成功安装摘要的 envelope usage。每种 provider 的缓存 token 是否包含在 input 中按适配器语义核对，防止重复计费。

同步 `docs/context-compaction.md` 顶部：T8 已运行、事后重评分、W=H−F 几何、summary 与 hybrid 的触发差异、压缩默认关闭。本轮先落方案，实施时统一入口。

## 4. 阶段 P1：先控制当前子任务的范围和结束条件

这一阶段可在不扩展创建协议的情况下先实施，用来处理已有 55 万 token 常量查询样本。

### 4.1 用现有任务包表达足够的信息

复用 objective/context/inputs/acceptance，不为每一种调查再新增必填字段。主代理派发时应明确：

- 要回答的问题或要交付的产物；
- 已找到的文件、搜索结果或原文引用，以及尚未解决的部分；
- 可读/可写范围和不得改动的内容；
- 何种证据足够结束，何种矛盾才值得扩大调查。

示例：查询报告长度上限，给出 messaging 目录线索，要求返回常量定义和实际截断调用；两处一致即可结束。不要额外要求证明整个仓库不存在其他限制，除非用户的目标确实需要这种保证。

### 4.2 深度与预算

保留现有 quick/medium/thorough，作为调查强度提示，不把它们当 Agent 类型或质量等级。事实查找优先 quick，调用链分析使用 medium，跨模块语义冲突才考虑 thorough。

先通过范围、任务提示和现有共享预算改善；暂不新增多套子代理预算系统。若真实对照仍出现明显超支，再使用现有调度入口增加可执行的子任务开销上限，并保留主代理交付额度。不能只在提示中写预算，却宣称已有硬限制。

子代理应返回已证实结论、关键证据、未解决项；未解决不等于失败，不能为了“完整”无限搜索。主代理验收优先读取必要原始证据，不把所有子轨迹重新注入主上下文。

### 4.3 委派决策与提醒

提示集中表达三项条件：存在值得独立解决的工作、隔离调查上下文或并行确有预期价值、共享预算能覆盖调查与集成。直接批量读取可以解决的几个已知事实，无需委派。

创建率只记录，不作为最低配额。8 次读取阈值只能表示提醒机会；不能解释为工作复杂度。建议将未证明收益的 exploreNudge 改为默认关闭，实验中显式开关；保留 explore 工具本身。

验收：离线 provider 覆盖正常交付、找不到答案、范围不足、取消、部分子任务失败和报告截断；主代理收到明确结果，不重复注入报告，不静默扩大权限。

## 5. 阶段 P2：打通临时 Agent 配置，保持创建内核简单

### 5.1 最小接口增量

保留 spawn_agent 现有字段与卡片选择方式，仅增加一个可选的临时配置覆盖对象。

> 实施状态（2026-10-24，批次 3 第一步）：`configuration {instructions, tools, skills}` 已实现（`src/agents/configuration.ts`、`src/messaging/child-config.ts`，测试 `tests/spawn-configuration.test.ts`）。第一版只允许在基底卡片的子代理视图内收窄 tools/skills，不新增授权；派生卡片不注册，带独立 digest 与 `derivedFrom`。explore 共用同一解析器。批次 4 已接入：explore 每个任务可带 configuration，所选工具按只读子代理权限校验（写入/执行能力在创建前失败，整批不留子代理），必须保留 file.read，显式选择的 Skill 真实生效；不带 configuration 时行为不变。

接口示例：

```json
{
  "objective": "检查分页模块是否遵守已有接口约束",
  "inputs": ["先看 src/pager.mjs 和 docs/api.md"],
  "acceptance": ["列出有证据的问题；没有问题也说明核验范围"],
  "permissions": ["read"],
  "scope": { "read": ["src", "docs"], "write": [] },
  "configuration": {
    "instructions": "检查接口兼容性；核对文档与实现，遇到差异给出来源。",
    "tools": ["file.read", "file.search"],
    "skills": []
  }
}
```

规则：

1. 不指定卡片和 configuration 时完全保持现有继承语义；指定卡片时用不可变 id/version 作为基底。
2. configuration 中未提供的字段继承；tools/skills 明确提供时为替换集合，空数组表示不选用，不能被当作省略。
3. instructions 是任务方法补充，不替换宿主规则；最终上下文明确分隔配置方法、用户任务和不可信来源材料。
4. 派生配置在运行前规范化、验证并生成内容摘要；记录基底和最终快照，不能修改注册卡片，也不能冒用原卡片 digest 表示不同配置。
5. 临时配置不要求模型编造 card_id/version，不自动进入全局社区卡片列表；内部身份由宿主生成。
6. model_binding 沿用已批准的别名机制，不新增任意 endpoint 或凭据字段。

### 5.2 能力与授权

有效能力必须同时满足：宿主已安装/注册、允许该 session 委派使用、符合权限与路径范围、版本绑定可用。

“主代理自身加载了什么工具”与“它可委派哪些专业能力”应区分。主代理不必加载全部 MCP 工具定义，但不能因宿主安装了某工具就自动获得委派授权。优先复用现有卡片可见性、包激活与绑定校验；缺少授权信息时保持现有限制，显式报错。

工具选择以实际展开后的闭包校验：Skill 可能间接提供工具，MCP 的只读声明不等于已经实施只读约束。检查展开后的效果与绑定，不能只检查顶层数组。

MCP 继续通过现有能力包/宿主连接映射到工具引用。第一版不在 spawn 中添加服务器地址、安装命令或原始密钥。需要的能力不存在时返回可理解的缺失项，不静默退回另一套 Agent。

主代理只读取少量相关卡片或能力简介。优先复用 agent.route/search/directory；确有临时配置发现需求且现有接口无法满足时，再增加有界能力描述查询，不把全部工具目录塞进系统提示。

### 5.3 explore 的兼容路线

第一步保留现有文件探索行为，内部使用同一配置解析器，把只读权限、工具子集、深度提示、等待和报告策略转换成统一的创建请求。

第二步才允许 explore 选择可选卡片或相同 configuration，以支持有 Skill、LSP 或宿主已授权只读 MCP 的调查。显式选择后必须校验，不能继续无条件清空 skills 又声称配置已应用。写入或无法约束效果的能力返回错误。

普通 spawn 与 explore 同配置时应在身份快照、工具绑定、模型、预算、取消与恢复上行为一致；快捷入口额外施加的只读约束和等待方式必须可观察。

### 5.4 通信和上下文

复用已有消息、询问、等待及 inspect_run 路径。子代理可以按现有权限向同会话代理询问，主代理处理需要用户决定的问题。结果包含来源和未解决项；避免全员广播完整历史。

继续保留“主代理负责创建子代理”的边界，本轮不扩展递归创建。子代理需要进一步分工时向主代理提出需求，避免同时改变预算树与调度结构。

验收：不注册新卡片也能创建临时审查 Agent；同一基底能派生不同方法/工具而不污染原卡片；越权或缺少能力在创建前失败；批量中任一配置非法不留下半批子代理；重启后有效配置和能力绑定不漂移；旧 spawn/explore 调用仍通过。

## 6. 阶段 P3：压缩先定位真实开销，再做单点改进

冻结当前 v3 为基线，保留自由文本摘要、归档读取与原子安装。compaction 与 assembly 继续默认关闭。

### 6.1 零费用诊断

从已有真实请求及事件重算：

- 每次触发时的估算输入、实际 usage、固定前缀与可变历史、估算校准是否命中。
- 历史请求与当前请求的最长相同消息前缀；工具 schema、动态状态、tool_choice 等变化。
- 摘要输入/输出及缓存分项；摘要时间；安装后多少步再次触发；重复总结和恢复读取占比。
- 请求被 mask、硬裁剪或 fitWindow 丢组后，实际送入摘要的来源范围。

明确区分：token 估算中的前缀校准与 provider 侧缓存是不同机制，一者修好不能推定另一者改善。缓存低命中的 provider 根因不能仅靠离线响应重放确认。

### 6.2 根据证据选择一个候选

| 离线发现 | 最小候选修复 | 需验证的副作用 |
| --- | --- | --- |
| 动态尾部让历史估算校准总失效 | 对可证明相同的部分复用计量，变更部分保守估算 | 不低估新内容或漏计工具/图片 |
| 摘要明显过早或重复发生 | 在估算准确后调整工作软阈值/防抖 | 不触及模型硬容量，不牺牲交付 |
| 摘要输出过长且包含大量重复叙述 | 调整软目标和交接提示 | 不恢复“超偏好目标就拒绝安装”的旧错误 |
| 特定请求差异破坏实际缓存 | 最小化不必要变化，做单独 provider 微实验 | 不删除必要状态，不将不兼容参数强行统一 |

不同时改触发、提示、模型和检索。候选应有可证伪假设；没有明确定位时保持当前实现，先补数据。

### 6.3 可追溯性

保留原文归档与可读指针。coveredOffsets 仅表示折叠范围；droppedGroups 不表示事实丢失率。为调试实际丢组恢复，记录可复用的原始消息偏移及摘要请求来源关系，不要求模型输出逐条来源 JSON。

语义保留率由任务验收或事实标注计算；原文存在、摘要安装、模型看到某消息都不能代替语义保留。不得以压缩事件的覆盖数量宣传事实完整性。

验收：正常压缩、超窗口丢组、空/不完整响应、未知用量、取消、决定版本变化与重启；失败保留可读原文和显式原因；同一材料不进入无限摘要重试。

## 7. 阶段 P4：卡片复用与导出闭环

运行时临时配置通过后，复用现有 authoring 与 package 机制完成：临时配置 → 可编辑草稿 → 本地保存新版本 → 导出 → 新环境导入 → 执行独立用例。

保存方法和依赖，不默认保存整段私人历史。导出包含卡片、允许分发的 Skill 资源及工具/MCP 依赖声明与版本；凭据、绝对工作区路径、运行权限不能随包传播。不能打包的依赖显式标记，不将未连接 MCP 宣称为可用。

为配置记录运行来源和已做过的验证；一次成功只能标作单次证据，不自动认定为普遍优质 Agent。更新生成新版本，保留可回退版本。

首轮用现有 CLI/API/UI 保存和导出，不同时建设社区服务、排行榜和自动进化系统。关键验收是在干净环境可复现能力，且缺少依赖时给出明确诊断。

> 实施状态（2026-10-24，批次 6 第一步）：`kodo agent save-config` / `saveConfigurationDraft`（`src/agents/configuration-save.ts`）把已完成子运行实际使用的临时配置保存为新卡片版本，不调用模型，复用 `writeAgentDraft` 与 `exportPackage`。测试 `tests/configuration-save.test.ts` 覆盖导出→新登记目录导入→干净宿主按相同工具与方法运行、跨会话/未完成/非临时配置拒绝、私有路径与指定私有值拒绝、版本不覆盖、CLI 离线流程。带 Skill 或扩展工具的配置明确拒绝，尚未支持把这类依赖一起打包；Web UI 入口未做。

## 8. 实验安排：分开回答三个问题

所有付费轮次均在 P0 通过后单独冻结注册；本方案本身不启动付费调用。保持相同模型版本、能力、共享预算和任务快照；随机或交错执行策略顺序，记录缓存及时间条件。

### E0：零费用机制与反例检查

覆盖 P0 反例、配置派生/拒绝、通信、取消/重启、压缩边界。使用脚本 provider 和历史响应重放，不推断真实模型质量或费用。完成后先构建并执行现有检查命令。

### E1：委派能否高效执行——正控制

从真实工程任务抽取 3 个固定子交付物，例如版本查询 CLI 合同验证、Web 重连复现分析、取消路径的生命周期核对。两个现有模型，各比较当前契约与范围/结束条件明确的契约，共 12 次子任务运行。明确要求运行子代理，仅用于测接口和执行效率；常量查询不再承担主要工程收益判断。

主指标：问题回答与来源是否正确、交付是否完整；次指标：请求数、价格加权费用、时间、找到充分证据后继续工作的次数。合理的额外核验单独标注，不把所有后续调用判成浪费。

若新契约产生额外事实错误，或仍有明显失控调查，先复查该失败，不将指定委派成功算作自主选择成功。

### E2：自主选择是否值得——同批对照

首轮使用工程任务 E01/E03/E05/E06：分页回归、API/CLI 功能交付、Web 重连和取消收尾；具体公开需求、独立验收及暴露情况见任务设计。它们来自同一工程，按相关任务族分析，不能声称跨仓库泛化。

先在一个固定模型上跑 Solo 与可自主委派但无提醒两组，共 8 次；需要定位提醒作用时，再以新注册的同期三组对照加入提醒。无提醒/有提醒组除提醒外完全一致；Solo 的提示不引用被移除的委派工具，仍可批量调用正常工具。整个 session 的业务能力一致，工具定义大小差异作为实际产品代价记录。

任务未要求创建子代理。评分者按固定验收表评交付，不按是否委派加分。记录创建发生时点、任务重叠、主代理复查开销、实际总费用和时延。简单任务不委派是合理结果；复杂任务不委派仍要看最终代价。

该 8 次是开发筛查，不作为统计发布门槛。发现可解释趋势后，在独立外部工程、第二个模型和新任务上确认，不反复重跑失败样本挑结果。已曝光的分页和版本查询不作未见任务证据。

### E3：压缩是否改善续做——独立任务配对

从任务设计 E04–E08 等已准备好的工程任务中，先选 4 个有自然历史增长的任务，覆盖跨层修复、多来源故障分析、多轮需求变更。选择和预算在开发校准后冻结，不要求全量读文档，也不靠填充资料让摘要触发。

先比较 off 与冻结 v3，共 8 次筛查，固定相同委派策略。若 P3 得到明确候选，再单独注册 v3 与候选的比较；不同时扩展 mask/hybrid/assembly 全矩阵。继承的硬容量保护、工具权限和总体资源限制保持一致；未触发摘要的正常样本保留。常规条件与预先注册的小预算压力条件分开报告。

早期信息保留用例应包含只出现在早期观察中的任务事实，并核对它实际移出了工作上下文；不能把仍在固定用户提示或验收源码中的数值当作摘要记忆证据。用户禁令可另作为约束遵守检查。答案标注和评分脚本不能意外暴露完整预期答案。

所有组允许同等的正常工具和历史读回。主指标为交付质量；恢复成功率、重读成本、错误原因解释机制。若要区分摘要和归档的贡献，另设小型诊断，不混入主要产品排名。

费用按完整 session 计算；未知用量不判省钱。超过硬窗口的 off 仍使用现有保护，报告说明该基线是“关闭软压缩”，不是无限上下文。

### E4：机制整合检查

E1–E3 分别清楚后，选择两个新任务，各跑两组：统一创建 + 压缩关闭，以及相同创建方式 + 候选压缩，共 4 次。

检查主子共享预算、子任务报告进入后触发压缩、归档恢复、取消及最终交付，不将这 4 次当作长期统计验收。至少一个任务使用临时配置，一个使用导入卡片与可用能力依赖。

### 停止、重试与判定

- 先固定每轮模型调用、token、金额（价格可得时）和墙钟上限；预算不得用“最多跑完矩阵”代替。
- 发现停止逻辑失效、越界写入、原文不可恢复、记账无法对账或其他确定性契约错误，立即停止后续付费单元，保存证据并离线复现。
- 提供方连续两次基础设施失败则暂停该批；已发生请求的费用仍记账。注册允许的有限重试保留全部记录，不能只保留成功尝试。
- 普通任务质量失败作为结果保留；按预注册规则决定剩余单元，不现场改题、改阈值或删除失败样本。
- 重复运行按任务聚类统计；同一任务的多道题、多个子代理和多次摘要不当作独立样本。

小矩阵的作用是筛除明显坏策略、估计方差和确定下一轮样本量。正式收益验证使用新任务集，依据探索数据规划样本量与功效；“每组 20 次”本身不保证足够。

## 9. 默认启用与发布门槛

| 功能 | 建议状态 | 改变状态的条件 |
| --- | --- | --- |
| 通用 spawn / explore 快捷入口 | 保留可用 | 旧接口和生命周期回归通过 |
| 临时能力配置 | 先显式启用 | 配置、授权、重启、导出闭环通过 |
| exploreNudge | 建议默认关闭 | 同期对照证明净收益，简单任务无明显退化 |
| v3 compaction | 继续默认关闭 | 独立真实任务质量与费用/时延门槛达成 |
| assembly | 继续默认关闭 | 另行证明相关性选择不伤害交付 |

建议下一轮正式“经济性”验收预先采用：质量非劣效界不超过 5 个百分点，配对费用比的置信区间上界 ≤0.90，时延比上界 ≤1.15；这些是待在运行前锁定的产品门槛，不是本批已达到的结论。关键禁令、破坏性越界及不可恢复证据另设零容忍门槛。样本量必须支持这些判断，不能用几次全通过代替置信区间。

若只能证明上下文峰值下降而费用/时延不达标，可继续提供显式“较小工作上下文”选项，明确其代价；不能事后换指标宣布默认省钱策略成功。

## 10. 实施批次与完成定义

| 批次 | 主要修改位置 | 独立完成定义 |
| --- | --- | --- |
| 1. 评测可靠性 | comparison runners/common/tests、主设计状态 | 致命停止后零新增调用；不完整/未知结果不通过；注册和结果可复算 |
| 2. 子任务契约 | context、child-card、explore、nudge 默认配置 | 小任务契约明确、旧接口兼容、失败/截断/取消可见 |
| 3. 统一临时配置 | spawn-spec、prepareSpawn、card、bindings、scope | 无预注册类型可创建；授权和绑定正确；重启无配置漂移 |
| 4. explore 接入 | explore、统一解析器、报告投递 | 快捷入口共用创建机制；显式 Skill/只读能力真实生效 |
| 5. 压缩单点候选 | context-tokens/context/compaction，按定位选改 | 有具体假设、反例及估算/费用分项；旧原子性不退化 |
| 6. 卡片闭环 | authoring、packages、现有 CLI/API/UI | 新环境导入后能复现；依赖缺失明确；不携带凭据与私有轨迹 |
| 7. 对照与默认值 | 冻结注册、评测报告、配置文档 | 以新证据做决定；不重写旧批次通过线 |

每批只包含服务其验收的最小改动。相关测试通过后运行 `npm run check`；运行时与接口批次执行全量 `npm test -- --maxWorkers 2`、`node --test scripts/comparison/*.test.mjs`，协作/恢复路径改动额外运行现有 kernel/recovery demo。实际命令输出随实施记录，不能把本方案中的完成定义写成已验证结果。

最先动手的是批次 1 与批次 2；压缩离线诊断可同时开展，付费实验必须等待评测底座修复。统一临时配置完成后再验证社区卡片闭环，避免把调度、上下文、生态与网站建设同时混成一轮大改。
