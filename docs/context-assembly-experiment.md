已实现 `ApplicationOptions.assembly` 与 CLI `--assembly deterministic [--assembly-work-tokens N] [--assembly-evidence-tokens N]`。内核从当前目标和最近六条用户输入提取确定性词项，最近输入权重最高；保留最近两个工具轮次及失败／未完成轮次，在证据额度内保留相关旧证据，其余旧工具正文替换为带归档引用和消息偏移的 `history.read` 指针。焦点变化后可在现有授权、文件范围和调用可见性检查下恢复已登记原文。组装不创建辅助模型请求，策略随 CLI 会话持久化；事件、检查视图和会话聚合分别记录 `context.assembled`。

## 1. 决策与待验证假设

推荐方向：**动态组装负责让当前问题得到相关背景，压缩负责控制历史状态与容量；默认不在每次回答前额外调用模型整理。**

二者处理的维度不同。压缩改变内容的表达和长度；组装选择本次要带入的内容。可以没有语义摘要而仍按需选取原文，也可以在已有任务摘要之外动态读取证据。所有路径都必须保留硬容量检查和不可变原始记录。

“先根据需求调整，再回复”在逻辑上成立；在实现上分为两条路径：

- 内核依据有效目标、当前步骤、显式来源和文件元数据做确定性选择，不调用额外模型；信息不足时由主代理正常调用读取工具，再继续回答。
- 增加一次模型请求，读简短目标、状态与候选来源，选择该读哪些内容，再给主代理执行。它可能提高相关性，也增加输入、输出、时延和故障点，应单独设实验组。

核心假设：动态组装在切换任务阶段、旧证据回查和多轮需求变化时可能优于仅按时间裁剪；短任务中额外准备调用可能是纯开销；动态组装结合小型状态摘要可能优于任一单独方式。以上均待真实任务求证，不把推测写成收益。

## 2. 输入空间和额外调用费用分开管理

沿用主设计的安全输入容量 C、工作上限 H、输出预留 R 和误差余量；不更改模型真实窗口。每次实际请求估算包括工具 Schema 和协议开销：

```text
P = 必须保留的宿主规则、有效用户要求、工具及运行状态
S = 当前接手摘要与去重后的工作记录
T = 近期完整交互（协议配对完整，正文有界）
D = 针对当前问题选中的证据

P + S + T + D <= H <= C
```

这是装配约束，不要求把 H 填满。保留既有 P/S/T 上限与优先级；D 初始候选沿用主设计 §7.3 的 `min(8192, floor(H × 0.10))`。在 H=65536 时约为 6.5k token；实际分配还受剩余空间限制，不提前注入等量占位内容。

D 增加时优先移出已失去关联的旧证据和可归档的旧轮次，不裁掉未处理工具结果、有效用户约束和未知副作用。实际返回超过额度就分页。未使用的额度可用于保留有价值的近期内容，但不机械扩大每次提示。

完整性要求导致 P/S/必要近期内容已经超出软 H 时，优先保持执行安全，显式记录软目标未满足；真实硬容量不能突破。算法隔离实验遇此情况要记录为统一预算不适配，不悄悄给某一组更大空间。用户明确要求逐段完整审阅时按任务推进，不能用恢复额度跳过要求。

若额外调用选择模型，其账本为：

```text
总费用 = 选择调用 + 摘要调用 + 主任务调用 + 所有工具结果的后续模型输入
总耗时 = 整条执行链的实际端到端耗时
```

给主请求预留输入空间，不等于选择模型免费。被选证据随后还会被主模型读取；前缀被替换也可能降低缓存命中，所以不能只用主请求缩短比例判断收益。

## 3. 默认路径：轻量组装，缺信息时正常读取

### 3.1 选择依据

优先级：当前步骤明确引用的证据 → 最新相关调用与失败 → 目标中明确出现的路径/符号对应来源 → 已采用且有效的知识条目。模型在正常进度更新中表达所需证据，内核不靠猜测完全理解问题。

没有来源线索时，主代理依然可以先搜索、列目录或读文件；无需为了动态组装再调用一个模型“判断该怎么搜索”。只有存在候选证据才选取，不每次请求都扫描全部项目。普通问答无外部背景需求时直接回答。

### 3.2 装配流程

```text
接收并持久化新输入/工具结果
→ 重建有效目标、授权、当前步骤及未完成状态
→ 判断现有证据是否需要替换
→ 必要时按授权来源元数据筛选候选
→ 去重、校验版本、在 D 内选入片段
→ 保护当前状态，必要时生成有界接手摘要
→ 完整工具协议和容量校验
→ 主模型正常执行或回复
```

现有证据有效且下一步未改变时复用装配结果。明显的更新信号包括用户改变目标/约束、当前步骤完成、出现新失败、子任务结果返回、证据文件变更，以及主代理明确请求另一份来源。输入 token 增加本身不是检索全部历史的理由。

每次模型请求仍做最新状态与容量检查，但全文检索、正文读取和证据替换按事件发生。稳定规则和工具列表保持前缀，动态证据集中在允许替换的区域；相同证据不每轮改写措辞或顺序。

### 3.3 保留原始事件与协议合法性

复用现有 Store、来源索引、history/knowledge/inspect 工具和主循环，不创建新 Agent 或第二套记忆库。所有预读取也经过既有权限、预算和调用记录，不能由组装器绕过工具执行契约直接读取任意 blob。

原始消息、归档、工具调用结果不随候选变化重写。最终模型请求使用请求快照，记录入选来源、范围、版本、估算 token 与选择原因；这些信息可附在现有请求元数据或有变化时的组装事件，不生成每轮全历史副本。

近期未闭合工具协议和供应商签名状态按原契约保留。旧证据可以通过真实读取结果或明确标注的来源资料进入请求，不能伪造“本轮执行过”的工具调用。上下文中未被选中的档案仍可检索，目录匹配失败不表示事实不存在。

### 3.4 恢复循环与降级

复用主设计的累计恢复额度、无进展判断和当前可见范围去重。失效、缺失、未扫描完、权限不足分别反馈。组装失败时保留最近合法投影并走既有容量保护，同时记录原因；不能静默宣称已经读到相关背景。

普通检索不创建子代理。只有问题本身具有可独立调查的范围，才使用已有探索能力；专项建库不成为组装前置步骤。跨任务读取仍按现有历史授权和正式知识发布规则进行。

## 4. 可选路径：模型选择候选证据

先通过内核拿到有限候选，再让模型从短列表中选择。不能把全部历史先交给选择模型，否则只是把长上下文成本搬到另一请求。

选择请求只包含当前问题、有效约束、当前步骤和候选的短 ID/路径/版本/有界预览。初始实验限制为最多 20 个候选、约 8k 输入与 512 输出 token，仍受该模型真实容量及剩余运行预算限制；这些是实验上限，不是每次必须消费的配额。

输出只包含所需来源 ID、读取范围及必要的检索线索。沿用宿主短 ID 映射、来源授权和版本检查；禁止业务工具、写入或创建子代理。选择模型不负责最终回答，也不输出长篇规划。未知 ID 拒绝，失败不反复重试，反馈失败后回到确定性组装或主代理正常检索。

生产候选策略是按需触发：例如任务重点改变、现有证据无法支持下一步，且元数据检索产生了超过 D 能容纳的候选。是否相符仍是启发式，不能只因检测到关键词就启动。不要用选择模型每轮打分所有历史。

实验另设“每次正常模型请求前都调用选择模型”的对照，专门检验用户提出的先整理再回答方案。正常请求包含工具调用决策轮；额外选择与摘要请求不递归触发新的选择请求。这样调用量和代价有明确边界。

## 5. 真实任务实验：两个因素分开测

### 5.1 四个主组与一个准备调用组

所有组使用相同模型/端点、真实窗口、工具权限、初始仓库、工作输入上限、输出预留、缓存配置与最终验收，且均可正常搜索和读取证据。普通任务进度、用户约束保护、来源持久化对所有组相同。

| 组别 | 语义压缩 | 动态证据组装 | 要检验的问题 |
| --- | --- | --- | --- |
| A | 关闭；仅现有确定性硬裁剪 | 关闭；正常工具读取 | 基线 |
| B | 固定使用当前 hybrid 策略 | 关闭 | 现有压缩配置有无收益 |
| C | 不生成模型摘要；容量仍有确定性保护 | 确定性动态组装 | 只增加组装能否改善 |
| D | 与 B 相同 hybrid | 与 C 相同组装 | 两者结合有无额外收益 |
| E | 与 D 相同 | 每次正常请求前增加一次有界模型选择 | “先额外整理再回答”是否值得 |

主比较为 C−A、D−B（组装收益），B−A、D−C（压缩收益），E−D（额外模型选择收益）。本轮不同时引入新的语义状态触发规则；主设计 §8.8 的新触发方式另行比较，避免把摘要触发变化误当组装收益。

hybrid 可能只触发观察隐藏，必须按实际调用记录报告；若没有调用摘要，不能称为验证了语义摘要效果。确需分离该分支时，追加预注册的 summary 策略组，同样从任务起点运行，不只挑成功摘要样本。

算法隔离实验先取 H=65536，A 同样通过请求输入上限约束到 H；这属于受控硬裁剪基线，不冒充当前产品默认配置。之后另报原生默认配置的产品比较。另用 H=32768 做预注册压力组时，所有组同步设置且独立汇总，不只给某一组减小窗口。

### 5.2 首批四类真实工作流

| 工作流 | 起点与产物 | 关键验收 |
| --- | --- | --- |
| 短修复 | 复用 pagination 游标缺陷任务和冻结副本 | 中文/Unicode 分页准确还原，权限检查保留，实际验证及最终答复；测额外准备是否拖慢 |
| 跨模块实现 | 复用 package-versions 的库/API/CLI/文档任务 | 多入口行为一致，版本排序与非法输入通过独立验收，完成最终交付 |
| 项目理解与证据报告 | 复用 onboarding，但冻结当前源码与评分依据 | 结论与源码一致、来源可读，已实现/计划区分正确；测试自然相关性选择 |
| 多轮变化与旧证据复用 | 先完成接口调查，再通过真实用户后续输入提出实现及兼容要求，并在约定阶段改变一个来源文件 | 正确更新计划、发现旧知识失效、找到必要历史，未重复副作用；各阶段验收均计入 |

第四类须新增工作流与独立验收。要求变化按固定语义里程碑派发，例如阶段报告完成后，而非按模型调用数派发；不通过直接改 contextRef/step 绕过真实产品后续输入路径。不得预先给 Agent 看隐藏验收题、答案或测试代码。

这些首先是同一项目中的四类任务，不代表跨项目泛化。正式 C4 再扩到至少 20 个独立任务，覆盖不同模块、需求和项目；仅打乱同一事实集不算新增独立任务。执行中自然产生长历史，不注入 filler。未触发压缩也是合法结果，说明该任务没有测试到压缩分支，不强行凑触发次数。

首次试运行每任务每组两次：四主组共 32 次。E 额外 8 次。默认先验证实现与判题，再串行执行模型实验；不以此次设计文档授权状态推定已经跑过上述实验。

### 5.3 预算、失败与运行顺序

预注册每次运行的模型调用、工具调用、总 token 和时间上限；候选起点为 80 次模型调用、160 次工具调用、200 万累计 token、15 分钟，具体需在无付费 dry-run/现有轨迹检查后统一冻结，不按某组结果临时放宽。选择模型和摘要均占用同一限额；任务确实不适合这些资源时在正式评分前统一修订，并保留版本。

`compaction-real-tasks.mjs` 已支持 `assembly[:work[:evidence]]` 与 `assembly-hybrid[:work[:evidence]]`，并默认给单次运行设置 80 次模型、160 次工具、200 万累计 token 和 32768 输出上限；可由显式参数统一覆盖。`--dry-run` 在读取 provider 配置和凭据之前退出，并打印冻结的任务、组别与预算。已有任务、oracle、隔离副本、计费与日志逻辑继续复用。第四类多轮变化任务和 E 组额外选择模型仍未实现。

运行前用冻结配置做一次短请求、一次代表性长请求及一次工具回合的 provider 健康检查。它们单独计费记录，不计任务准确率。连续基础设施故障时停止整批，保留失败数据，不反复挑能成功的端点/结果拼成对照。

每任务内随机或平衡交错组别顺序，保存种子、模型配置、代码哈希、缓存量和失败阶段。每个 trial 使用独立数据目录；同工作流后续阶段保留本 trial 的合法知识与历史，禁止跨 trial 泄漏。正常失败、安装失败和检索超时保留在端到端统计中；明确的上游不可用单列可用性，并给出包含全部尝试的结果，不能选择性删除。

## 6. 指标、解释和启用条件

首要指标是完整任务交付通过率及重要约束/副作用违规；其次是总费用和端到端耗时。功能代码正确但无最终交付、错误声称已验收或留下不可编译修改，都按原任务验收处理。

记录所有调用成本、输入/输出、缓存读写、首个有用动作耗时、峰值输入、实际摘要次数/覆盖范围、动态入选来源、命中前扫描量、重复读取量、旧证据误用和计划调整是否正确。自动判题失败做盲审，补充复核不覆盖原成绩。

先做少量固定历史分支诊断，确认组装能够读取正确来源、没有丢协议、额度可执行；这不能替代从任务起点运行。正式轨迹允许各组因策略不同产生不同工具调用，因为那正是要测的总体影响。

四任务试运行只作描述性结果；同一任务两次重复不能当作八个独立任务。正式实验按独立任务聚合配对差异，继承主设计 §11.3 的质量非劣效门槛，并报告费用/时延区间。短任务不能因额外准备出现无法接受的开销。若只有 token 减少、完整交付或时延没有改善，不认定默认启用达标。

决策规则：

- C 在质量合格前提下优于 A：动态组装值得作为独立功能，即使暂不启用模型摘要。
- D 优于 B 且优于 C：动态组装与摘要互补，优先组合。
- D 与 C 相近而费用更高：保留语义摘要为条件性能力，不强制使用。
- E 没有弥补其额外调用成本：不采用每次预整理；下一轮只对明确事件触发做小范围消融。
- 质量或来源权限退化：保持实验关闭，按实际丢失环节修复，不能仅靠扩样本掩盖。

### 8.4 评分与归因

保留现有自动 score、automaticPassed 和原始 acceptance。以下是本轮独立审查口径，现有 results.json 尚未自动计算，不能把人工 pending 记成完整通过。

**质量 Q（0–100）**：内核、能力包分发、依赖准备、MCP、操作系统沙箱、写入恢复六主题各 10 分；每主题“当前实际行为”和“默认/授权/失败或边界行为”各 5 分。其余 40 分：至少六个真实引用且三处源码 10 分；引用确实支持结论 10 分；三条有效且去重的运行/验证命令 10 分；三个具体限制 5 分；区分已实现/计划 5 分。缺报告 Q=0，不因没有修改其他文件赠送内容分。

运行前由评测侧冻结各项源码依据和可接受语义，不能只看关键词。答案与事实来源映射放在实验根目录的评测侧，不进入模型工作区。先匿名审查报告和执行证据，隐藏组别、费用、组装次数，仅替换工作区根路径、不改技术内容；再查看策略轨迹分析原因。验证声明必须与实际调用证据匹配。

**完整交付 success** 要求：产物存在、运行 completed、最终答复非空、Q≥80、六主题均有正确核心行为、引用/三条命令达标、无重大错误或虚构验证、无越权/未解决未知写入、修改范围合规。各条件单列。运行失败的部分报告仍评 Q，但 success=false。

**证据路径**：每个必要事实记录“是否获取 → 写作请求是否可见 → 隐藏后是否可合法读取 → 是否实际恢复 → 是否正确采用”，附调用 ID、请求快照和来源区间。不确定记 unknown；不为实验整理全部历史。已获取后丢失、从未获取、可见却写错必须分别统计。

**费用/耗时**：全部尝试的输入/输出/缓存/未知用量、费用区间、首次保存报告时间、总时长、模型/工具区间、失败阶段、重复读取、history.read 与宿主自动恢复次数。累计调用区间不冒充并行关键路径。失败照计成本；仅在两组均完整成功的区组比较等质量费用/耗时，若没有完整配对就不报效率收益。

### 8.6 后续实验由结果触发

**失败定位：同状态报告分支。** 预定决策点为首次写 REPORT.md 的请求之前；从未写报告则取最后一个正常模型请求之前。克隆工作区、Store/授权与来源闭包，不能只复制消息；无未完成外部副作用，重置等额分支预算。同版本 off/assembly 使用相同预算，H/D不变，均允许恢复。最小执行器已实现为 `context-assembly-finalization-branch.mjs`；§8.10 首次真实运行采用更严格的四模型/八工具上限，以直接检验交付预留的四轮假设。

**首批过门槛：扩展现有任务。** pagination、package-versions 各跑 off/assembly 两次，共八次；按任务配对汇总，不将长短任务 token 直接平均。未触发组装的短任务只检验额外开销。

主题覆盖、hybrid、额外选择模型都要独立版本和消融，不在一次失败后叠加全部功能。正式 C4 仍按独立任务与预定统计门槛验收；本轮小样本不改变默认关闭状态。

assembly-1 共 5 次装配、assembly-3 共 4 次装配；两者当前检查视图各隐藏 50 条观察，最后一次分别从 57/55 个候选组中选 4/3 组，使用 6,358/6,345 个证据 token，均没有 `history.read` 或 `history.search`。归档中确有能力包、MCP、恢复、沙箱和 README 等多主题证据被隐藏，但两个运行都没有报告，无法建立“某证据被隐藏 → 某主题写错”的链条。assembly-2 在装配前即失败，也不能用于判断选择器质量。

组级原始统计：off 共 4,741,764 token、137 请求、平均 320.1 秒、估算 ¥1.941；assembly 共 4,582,060 token、159 请求、平均 342.5 秒、估算 ¥0.296。assembly 的累计 input 低 2.8%、平均请求字符低约 15.6%，但请求更多且没有完整交付；费用差主要受缓存计价和执行轨迹影响，不能认定为降本。没有完整成功配对，禁止计算等质量效率收益。

分流结论：修复后 assembly 仍未在 onboarding 完成交付，但当前证据首先指向共同预算收尾和执行路线问题。off-2 证明收尾失败不是 assembly 独有；assembly-2 证明未知写入可在选择器介入前发生。现阶段没有证据支持立即实现跨主题覆盖，也不扩展短修复或多轮任务。优先修复首次阶段性保存、真实模型对 `finalizationRequired` 的响应、长验证与宿主时限协调；默认开关继续关闭。

评测 runner 另发现清理覆盖缺陷：真实 run 已记录 `UNKNOWN_WRITE` 后，`app.shutdown()` 的清理异常会覆盖 outcome 并清空 runId/调用统计。未来 runner 已改为保留已形成的 outcome，清理错误单列为 `cleanupError`；历史 `results.json` 不改写，assembly-2 的归因以 trace 和 SQLite 为准。

### 8.9 可靠交付最小实现与离线同状态分支（2026-10-23）

本轮暂停跨主题覆盖、Herdr 界面和付费扩样，只修复 §8.8 暴露的共同交付链路。

- 主代理正常工作阶段保留最多四次模型请求及其累计输入/输出额度，覆盖“首次保存失败、参数修正、定向确认、最终回复”。输出进入后续请求造成的重复输入按三角增长计入，不再只保留一次最终答复。
- 达到调用或 token 阈值后持久记录 `delivery.finalization_started`。此后隐藏并在执行端拒绝新委派、目录/历史/网络搜索和任意进程执行；仍允许文件/私有产物保存、`process.run`、LSP 诊断、已有子任务等待与 `inspect_run` 等定向核验。收尾阶段不再启动模型摘要。
- 已有成功写入且只剩最后一次模型请求时，内核设置 `toolChoice=none`，确保该请求用于公开回复。预算从一开始就不足以覆盖四轮时进入降级收尾，允许当前请求保存已有产物或明确失败，不伪造验收成功。
- 工作区内绝对路径失败现在返回可直接采用的相对路径，例如 `REPORT.md`。失败写入的副作用状态仍为 `not_started`；下一轮保留原 assistant 工具参数和正文，并追加“只修正被拒参数、不要重新探索”的运行时指导。未知写入仍不自动重放。
- 子代理准入同时保护主代理的调用次数和 token 交付预留；低预算下子代理在模型调用前以 `CHILD_BUDGET` 拒绝，而不是先消耗主代理最后几轮。

离线同状态分支以同一目标、正文、四轮预算和脚本化 provider 分别运行 off 与 assembly。两组均完成：绝对路径保存失败 → 使用同一正文改为 `REPORT.md` → 读取确认 → 无工具最终回复；工具状态均为 `failed, succeeded, succeeded`，且 `delivery.finalization_started` 只记录一次。另一个反证用例确认收尾阶段即使模型请求未公开的 `process.exec`，副作用也不会启动，同时 `inspect_run` 仍可见。

这只证明确定性内核链路，不证明真实模型会同样利用证据，也不是 §8.6 的真实同状态模型分支。未新增付费调用。相关验证为 `tests/context-assembly.test.ts` 37/37、交付/协作相关七文件 144/144、最终全仓 1069 passed/8 skipped、Web 单独复核 20/20、评测脚本 74/74。assembly 默认继续关闭；真实同状态分支应在代码冻结后单独运行并保留失败，不能把本轮脚本结果计为产品质量或成本收益。

### 8.10 真实同状态收尾分支（2026-10-23）

原始证据位于 `.kodo/context-assembly-finalization-branch-20261023/`。执行器从 onboarding off-2 第 50 步请求分支：上一轮 assistant 消息仍含 14,826 字报告正文，随后是绝对路径写入的 `PATH_DENIED` 结果；克隆完整 Store、归档 blob、session 身份和工作区，再重置相同交付预算。off/assembly 各两次，顺序为 O1→A1→A2→O2；每次最多四个模型、八个工具、800,000 token，工具时限 120 秒。四次均为真实 `deepseek-v4.1-flash` 调用，失败不重跑。

| 运行 | 终态 | 报告 | 请求 | 输入 token | 输出 token | 直接失败点 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| off-1 | `MODEL_PROTOCOL` | 有，14,696 字 | 4 | 147,244 | 7,257 | 最后一轮要求无工具，上游仍返回 `shell_exec` |
| assembly-1 | `MODEL_PROTOCOL` | 有，14,484 字 | 4 | 118,635 | 6,655 | 同上；第一轮保存后发生一次装配 |

三份已保存报告的自动分均为 70、覆盖率 0.6。人工按现有十项语义复核：依赖准备和运行中版本不变两项实际已表达，自动正则漏认；Windows 同用户单写沙箱约束确实遗漏。因此三份内容均为 90 分、8/10 条件通过，但都缺正常最终答复，完整交付仍为 0。不能用报告存在替代 completed。

交付约束有两项正面证据。第一，四次均在首轮持久记录 `delivery.finalization_started`，所有 `shell_exec` 请求都在执行前被拒，没有启动广域命令或留下未知写入；报告在三个运行中优先落盘。第二，assembly-1 从 16 个候选组选 2 组，保留含报告正文的近期来源并隐藏 14 条旧观察。其后三次请求上下文合计 290,972 字符，相比 off-1 的 409,251 和 off-2 的 401,307 少 28.9%/27.5%；总输入比两个 off 的均值少 20.2%。报告六主题仍在，当前样本没有“正文被隐藏导致遗漏”的证据。

但可靠交付门槛仍未通过。三个已保存运行的第四次请求均发送 `tool_choice: none` 且没有 tools 字段，上游仍以 HTTP 200 返回工具调用和 `finish_reason=tool_calls`；内核正确拒绝为 `MODEL_PROTOCOL`。保存后仍开放两轮定向工具机会，使模型继续请求已禁用的 wire 名 `shell_exec`，通用 `TOOL_DENIED` 没有促使其立即结束。四轮预留因此只证明容量被保住，不等于真实模型一定按四轮闭环。

assembly-2 不能作为选择器负例：唯一的 `context.assembled` 发生在第四次工具完成之后，后续没有模型请求消费该投影。它的无报告首先是模型反复请求禁用工具和四轮耗尽。组级 assembly 输入少 8.8%、估算费用少、平均更快，但包含一个无报告短轨迹、缓存命中差异且两组完整交付均为零，禁止解释为效率收益。

本分支还有一个方法边界：它导入了旧失败结果和正文，但没有在新 run 内重新执行失败写入，因此没有触发新内核追加的“复用原参数和正文”纠正消息。三份报告均由模型重写，未逐字复用旧正文。该批验证了真实模型下的收尾限制、产物优先和 assembly 投影，不是绝对路径纠正提示的真实端到端验证；后者目前仍只有离线测试证据。

当前分流：暂停跨主题覆盖和付费扩样。优先处理保存后立即进入最终回复、禁用工具的明确反馈，以及 provider 无视 `tool_choice:none` 时的有界恢复；随后再用新的预注册批次验证，不能改写本批 0/4 完整交付。assembly 默认继续关闭。

原始 `results.json` 的 `broadExplorationAttempts` 只匹配点号工具名，漏记了 provider 返回的 `shell_exec` wire 名；独立 `review.json` 已按 SQLite 与 wire 证据补记 O1/A1/A2/O2 分别 2/2/3/2 次，原始结果不回写，未来 runner 已同时识别两种名称。
