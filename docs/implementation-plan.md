# Kodo 实现方案

日期：2026-10-20  
状态：实施基线；P0/P1 单代理内核与 P2 完整本地内核 demo 已实现，包括协作、持久等待、共享预算、上下文压缩与原文追溯，以及有证据的不确定写入恢复。终端采用原生行输入；完整能力包、MCP 和 Web 尚未实现，实际支持与验证范围见 [README](../README.md)。
依据：[设计方案 v1.5](design.md)、[产品开发与上线方案 v1.2](product-launch-plan.md)。

公开实现的源码对照与采用边界见 [内核参考调研](kernel-comparison.md)。该调研区分默认分支实现、官方公开行为与 Kodo 自身选择，不表示已经验证第三方内核可直接替换本方案。

## 1. 实施结论

建议采用 **TypeScript + Node.js 的单进程本地应用**：先交付非交互 CLI 与统一执行内核，再接精简 TUI、能力包与案例验证，受邀试用通过后接本地 Web。主 agent 和子 agent 共用一个执行循环；模型负责分工，运行时负责权限、状态、消息、预算和恢复。

首发贯穿场景采用已有文档建议的“网站改动后的发布前验收”。先在公司内部一个真实项目中验证：完成验收 → 保存方法 → 换页面或改动再次使用 → 同事导入 → 根据反馈验证新版。这决定首批工具和案例范围，不把内核做成网站测试专用程序。

本方案编写时目录只有设计与调研文档。当前已建立源码、构建与测试入口，交付完整本地内核 demo；后续章节中的能力包、MCP、目录和 Web 仍描述产品目标，不代表已经实现。开发环境为 Node.js `v24.13.0`、npm `11.6.2`，其他平台需单独验证。

首个开发批次只需要证明四件事：

1. 真实模型能通过工具读取项目、生成可检查的产物，并完成多轮调用。
2. 参数错误、断流、取消和预算用尽时，状态与实际动作一致。
3. 重启后能保留任务与证据，结果未知的写操作不会自动重放。
4. 最小卡片格式能固定版本和资源摘要，为后续导入导出保留正确的数据基础。

先不建设完整社区、桌面外壳、远程执行、多级递归委派、向量数据库、全局记忆或任意生命周期钩子。以下接口、目录和命令描述阶段目标，已实现范围以 README 与可执行测试为准。

## 2. 技术选型与代码边界

| 验证与构建 | Vitest、TypeScript 检查、ESLint；CLI 构建与 Vite 页面构建 | 实际 npm 包安装后执行，而非只从源码启动 |

依赖精确版本在 P0 实测后锁定。协议若无法满足工具关联、取消或消息保真要求，在 P0 调整选型并记录原因；不要带着已知缺口继续做上层功能。SQLite 预编译安装失败、trigram 不可用或 Ink 无法可靠处理中文输入，同样是对应选型未通过，需要在该阶段解决。

保持一个 npm 包和一个源码工程，不提前拆 monorepo、微服务或独立 SDK：

```text
src/
  application/    用户命令、会话操作、决定变更、事件订阅
  runtime/        统一循环、调度、上下文、预算、取消
  messaging/      点对点消息、等待条件、超时和循环等待检查
  agents/         卡片解析、固定版本、绑定、包导入导出、案例比较
  discovery/      FTS5、短词匹配、浅层目录、检索预算
  tools/          内置工具、权限检查、项目写锁、自定义工具运行器
  providers/      首个模型适配器与能力声明
  mcp/            MCP 连接、身份绑定、工具过滤与调用
  storage/        SQLite 迁移、调用记录、事件、产物文件
  cli/            非交互命令与精简 TUI
  server/         P5 再新增：HTTP、SSE、本地访问控制
web/              P5 再新增：本地 Web 页面
tests/            确定性检查、故障注入、集成与端到端场景
examples/         可分发的官方能力包、固定数据和验收案例
```

依赖方向：CLI／TUI／HTTP → application → runtime 与能力包操作；runtime 使用模型、存储、工具和通信模块。界面不修改数据库，卡片解析与检索不启动模型。仅在第三方协议、资源执行与存储边界保留必要接口，不给每个函数再包一层服务。

## 3. 先固定的工程契约

### 3.1 应用命令与事件

CLI／TUI 直接调用应用层；Web 到 P5 再增加 HTTP 适配。应用层至少支持：创建会话、提交用户输入、取消运行、检查并恢复会话、获取快照，以及卡片管理与案例执行。

所有状态变更发出统一事件：`run.queued`、`run.started`、`run.waiting`、`message.created`、`tool.started`、`tool.finished`、`decision.updated`、`run.completed`、`run.failed`、`run.cancelled`、`run.interrupted`。事件封套包含递增序号、会话、运行、类型、时间和版本化载荷。

重要事件与状态在同一数据库事务提交后发布。文本 token 可临时推送，最终回复、工具结果和终态必须持久化。事件用于增量读取和排查，当前状态表用于快照；首版不实现完整事件溯源系统。

模型适配器统一输出文本增量、工具请求、结束原因、usage 和错误，保留供应商要求续传的协议字段。运行时保存请求快照与工具调用关联；不能只拼接文本而丢弃结构化内容。工具参数在完整接收且校验通过前不执行。

### 3.2 SQLite 与文件职责

按阶段建立必要表，不在首周一次建完：

| 表 | 核心职责与约束 | 引入阶段 |
| --- | --- | --- |
| `sessions` | 工作目录、当前决定版本、有效授权、总预算与消耗 | P1 |
| `decisions` | 不可覆盖的用户决定／约束记录，按会话递增版本 | P1 |
| `runs` | 父运行、后续运行、卡片摘要、模型绑定、状态、上下文引用；终态不重新打开 | P1 |
| `calls` | 模型／工具调用编号、请求与结果引用、状态、预算预留、操作影响、幂等键 | P1 |
| `events` | 递增游标及重要事件，与状态同事务提交 | P1 |
| `artifacts` | 来源运行、决定版本、内容摘要、受控文件位置与验证引用 | P1 |
| `card_versions` | ID、版本、摘要、来源、安装诊断、默认版本；同 ID／版本禁止不同内容 | P1 最小字段，P3 扩展 |
| `messages` | 问题／答复／通知、投递与模型输入关联；`reply_to` 与投递状态分开 | P2 |
| `waits` | 所等问题／运行、any／all 条件、截止时间与等待关系 | P2 |
| `case_runs` | 案例、卡片摘要、模型与环境、断言结果和原始证据引用 | P3 |
| `command_receipts` | 请求 ID、参数摘要与结果；重复提交返回既有结果，参数冲突拒绝 | P5 |

大文本、请求快照、工具输出和产物写入本地文件。先写临时文件并原子落位，再提交数据库引用；允许清理未被引用的孤立文件，不允许数据库先提交一个尚不存在的结果。更新卡片默认指针与检索索引在同一事务内完成。

用户数据保存在默认用户数据目录，提供 `--data-dir` 覆盖；实际模型绑定和凭据不进入工作项目或能力包。凭据优先引用环境变量或系统凭据存储，普通配置只保留变量名／凭据引用。

一个数据目录同时只有一个运行时所有者。P1 加互斥所有权标记，第二进程明确拒绝启动；不能凭锁文件年龄擅自接管。崩溃后由 `doctor` 核验原进程已退出再清理，避免两个进程共同调度。TUI 与 Web 同时在线在 P5 通过同一个运行时进程支持，不能各启一个内核抢读写。

### 3.3 运行循环与调度

```text
获取 queued 实例的唯一推进权
  → 读取最新授权、决定、待处理输入与必要上下文
  → 原子预留会话预算，记录模型请求
  → 调用模型并接收流
  → 保存完整且结束状态有效的响应，整批检查工具结构与控制调用位置
  → 各工具执行前做 Schema 校验、权限与资源检查
  → 写入调用开始记录，执行工具，保存结果与事件
  → 继续下一轮，或事务性进入 waiting／终态
```

同一运行只能有一个推进者。新消息到达时，已在运行的实例只登记新输入，在模型／工具边界读取；不会另起循环。模型一次返回多个工具请求时，首版按顺序执行，再完整回传调用结果，以降低取消、写锁和恢复的组合复杂度。

调度器独立控制子 agent 数量、在途模型请求、工具进程和会话总消耗。等待不占模型槽；为主 agent 保留请求余量，防止子任务占满额度后用户输入迟迟无法处理。取消和权限撤销直接设置运行时控制信号，不等待模型自行判断。

预算预留必须覆盖并发请求：调用前扣除估算输入与最大输出额度，结束后按可得 usage 结算。usage 缺失标记估计；断流费用不明时不释放全部预留而假装没有消耗。子任务和重试都计入会话总额，不通过新建实例重置。费用展示不足以充当供应商侧硬性账单上限。

### 3.4 消息、等待与问题升级

`send_message` 的发送者与会话由运行时注入；接收者、`reply_to` 和产物引用都检查会话归属与可读权限。已结束目标返回明确状态，由主 agent 决定创建 `continuation_of` 后续运行。

避免丢唤醒的关键是让以下两条路径经过同一个写入协调器：

1. **发消息**：事务内插入并去重 → 检查匹配等待并记录满足状态与待处理输入 → 已挂起的实例改为 `queued`，仍在收尾的实例保留唯一推进权 → 提交 → 通知调度器。
2. **登记并挂起**：先在短事务内检查已有消息、目标终态与超时，按检查结果保存等待记录和对应工具结果；需要挂起时，由协调器在另一短事务中复核控制信号、新输入与等待条件，仍需等待才提交 `waiting`，否则继续处理或取消。具体收尾规则见第 3.7 节。

因此，答复先到和等待先登记都能得到相同结果。进程重启后扫描数据库中的 `queued` 和到期待处理项，不依赖可能丢失的内存通知。

待处理消息按 ID 组装进持久化的模型请求快照，重试同一轮复用该快照，避免重复追加。请求送达与工具是否产生副作用分别记账，不从“消息已读”推断“任务已处理”。

初期检查明确的阻塞依赖环；对 any／all 条件只将必然无法推进的环判为死锁，不能把有其他可满足出口的等待误判。超时或死锁产生事件并升级主 agent，不用模型轮询维持等待。

`ask_user` 仅主 agent 可用。用户回答先持久化；涉及目标、约束或授权变化时形成新决定版本并通知相关任务，受影响的旧版本结果保留并标记需复核。普通资料补充作为任务输入处理。

### 3.5 最小内核接口与控制权

内核模块边界以设计方案第 3.4 节为准。以下是待实现的核心函数形状；字符串标识、错误与入参在实现中由 Schema 校验，不为每个函数再建设服务层。

```ts
type StepOutcome =
  | { kind: "continue" }
  | { kind: "wait"; waitId: string }
  | { kind: "complete"; resultRef: string }
  | { kind: "fail"; errorRef: string }
  | { kind: "cancelled" };

type InputMode = "steer" | "follow_up";

interface RunCoordinator {
  wake(runId: string): Promise<void>;
  cancel(runId: string): Promise<void>;
}

declare function executeStep(
  runId: string,
  signal: AbortSignal,
): Promise<StepOutcome>;
```

`wake` 只提示调度器检查已提交工作，不携带唯一输入副本。调度器取得实例唯一推进权后调用 `executeStep`，完成本步后按并发公平性继续或重新排队；其他入口不得直接调用它绕过推进权。普通失败返回结构化结果；持久化失败等无法可靠收尾的故障停止该执行并报告，由恢复检查处理，不伪造已提交终态。

`executeStep` 负责产生结果和必要的调用记录，最终 Run 状态由协调器在短事务中检查控制信号、新输入及结果后提交。取消优先于完成；晚到工具结果作为调用证据保存，不能重开已经取消的 Run。异常清理结束前不释放同 Run 的推进权。

主 agent 与子 agent 使用同一函数。`spawn_agent` 固定定义版本、任务资料包和有效绑定，事务性创建 `queued` Run 后返回标识；模型选择分工，调度器只控制执行资源。

模型适配器只返回结构化模型事件，不执行工具；所有内置、自定义与 MCP 工具经过同一执行入口。供应商 SDK 的自动重试默认关闭，或明确纳入内核预算与调用记录，不能由 SDK 和内核分别叠加不透明重试。

### 3.6 上下文转换与输入语义

```text
持久状态、当前决定、相关历史与产物引用
  → buildContext：筛选、预算与必要压缩
  → encodeRequest：供应商消息与工具协议转换
  → 模型请求
```

`buildContext` 不改变权限；`encodeRequest` 不自行丢弃历史、压缩消息或启动工具。保留供应商续传所需字段与调用关联，固定宿主规则、实际授权和最新决定重新注入；工具结果、同伴消息与卡片正文不能提升为宿主指令。

当前实现采用确定性历史压缩：按完整的 assistant／tool 轮次裁减已完成历史，保留宿主规则、初始任务、用户输入与决定和未解决问题。原文以内容寻址快照归档，并与 `context.compacted` 事件、当前上下文引用同事务登记；归档链保留上一次引用。只读 `history.read` 校验会话与运行归属，主代理可读取自己管理的子任务归档，子代理不能读取父任务私有上下文；支持消息游标与长消息字符分页。必要输入和工具 Schema 本身超过限制时明确返回 `CONTEXT_LIMIT`。压缩不额外请求模型，模型生成的语义摘要尚未实现。

当前 Run 的用户补充采用 `steer`；明确排到后面的任务采用 `follow_up`，当前 Run 终结后创建新 Run。二者均先持久保存输入，再通知调度。首版可用已持久化的输入事件及 Run 中的消费游标实现，不新增独立消息代理。决定版本只在目标、约束或授权确实变化时更新，不能把每条普通消息都当作全局需求变更。

同 Run 输入与终结的竞争由事务排序解决；终态后的用户输入转入后续运行，同伴消息返回目标已结束，主 agent 可按授权创建 `continuation_of`。取消／撤权可中断支持取消的在途调用。正在执行的旧响应在工具边界必须重新检查控制状态和最新决定；受变更影响且尚未启动的动作不继续沿用旧条件执行，并保存对应的未执行原因作为工具结果，保持调用关联完整。在途动作的真实结果或未知状态另行记录。

### 3.7 挂起、收尾与恢复位置

每个步骤至少保存模型请求引用、完整响应引用、工具调用 ID 与顺序、各调用状态，以及已消费输入位置。首版无需单独的 `steps` 服务或表，可以使用 `runs` 和 `calls` 的字段表达。工具调用记录区分尚未开始、执行中、成功、失败、取消及结果未知，不能只保存最终文本。

正常路径：完整响应落位 → 整批工具请求检查结构及控制调用位置 → 每个调用执行前再次检查授权和范围 → 记录开始 → 执行 → 保存对应结果 → 推进游标。已提交的结果不重复执行；未知写结果按第 4 节核实。只重试尚未产生工具副作用的模型请求，或在记录完整工具结果后继续下一轮。

`wait_for_events` 和 `ask_user` 是需要挂起的控制工具。在短事务中检查条件、保存等待记录与 `wait_registered` 工具结果；协调器随后用另一短事务检查等待是否仍有效再提交 `waiting`，否则继续排队。答复在两次事务之间到达时，消息事务标记条件已满足并保存输入，协调器不得再将实例挂起。挂起前响应中的每个工具请求都有对应结果；唤醒事件另行进入下一轮输入。

首版要求挂起／结束控制调用最多一个且位于调用列表末尾。违反约定的整批请求不执行工具，为每项记录协议错误供模型修正。这样无需先实现跨挂起保存一半工具批次的复杂续执行机制。

匹配答复、目标终态、超时或必须处理的新问题可以结束本次等待。提前处理新问题不会把原问题标成已答复，Agent 可在答复新问题后重新等待原问题。相关输入在同一短事务内消费并更新等待与排队状态，避免重复唤醒形成两个执行者。

以下故障检查是上述契约的验收要求：

| 检查 | 应观察到的结果 |
| --- | --- |
| 同一 Run 同时收到两次唤醒 | 只有一个推进者，无重复模型／工具调用 |
| 新输入在结束检查与终态提交附近到达 | 被当前运行处理，或明确转入后续运行／返回已结束，不静默丢失 |
| 答复先到、等待先登记 | 两种顺序均可继续，不永久等待 |
| 等待时同伴发来问题 | 可提前唤醒处理，原未解决问题仍可追踪 |
| 等待后继续模型调用 | 每个工具请求都有对应结果，关联 ID 不变，无历史协议缺项 |
| 响应内先挂起、后写文件 | 整批请求被拒绝，文件未修改 |
| 输出截断但工具参数看似有效 | 不执行该未完成响应的工具请求 |
| 外部写完成、结果未保存时终止进程 | 恢复后核实实际状态，不盲目重放 |
| 取消与工具启动／结果返回竞争 | 不启动新动作，晚到结果不把取消改为完成 |

借鉴来源：Pi 的上下文／协议分层、OpenCode 的协调器／步骤边界、Codex 的工具路由／执行边界，以及 Claude Code 的协作与渐进加载语义。Kodo 的 SQLite 等待事务和生命周期约定是自身设计，已由确定性协作、故障注入和 CLI 测试验证当前实现；覆盖范围见 README，不能据此推断所有模型的行为可靠性。不直接嵌套两套完整会话内核。

## 4. 工具执行、取消与恢复

每个工具声明名称、输入 Schema、所需权限、资源范围、超时和操作影响。操作影响至少区分只读、可确认幂等写、非幂等或未知写；由宿主工具定义，不能单凭包作者声明就降低风险。

所有调用在执行前重新检查有效授权与工作范围。文件工具校验真实路径、父目录、符号链接和 Windows junction，不仅做字符串前缀比较。任意 shell、自定义代码和本地 MCP 明确采用可信执行假设，应用层路径检查不能隔离这些进程。

首批内置工具为 `file.read`、`file.list`、`file.search`、`file.apply_patch`、`artifact.read`、`artifact.write` 和显式授权的 `process.exec`。进程接口使用程序与参数数组，避免拼接用户文本成为 shell 命令；只有确实需要 shell 语义时单独授予该能力。

写锁由工具执行层获取，覆盖同一项目内主／子 agent 和所有会话。先使用项目级锁，路径别名和重叠根目录归一到同一范围。任意 shell 与无法确定影响的本地代码按写操作串行；远程资源使用对应连接／资源锁，影响未知的有副作用调用保守串行。锁仅覆盖实际操作，不跨模型推理、同伴等待或用户询问持有。整合后另跑相关验证，运行过局部检查不等于整合状态已通过。

取消立即阻止新的模型与工具调度，并中断支持取消的 HTTP／子进程；在外部调用真正发出前还需检查一次。只终止本运行时创建的进程树，Windows 下验证子进程退出与输出收尾。无法取消的外部动作记录真实结果或“结果未知”，晚到结果不能把已取消运行重新变成完成。

| 中断现场 | 恢复动作 |
| --- | --- |
| 尚未开始的模型／工具请求 | 核对授权、决定与预算后重新排队 |
| 已发出的模型请求断流 | 保留部分输出与费用不确定性；不执行未完整生成的工具参数 |
| 已开始的只读调用 | 确认原调用不再执行后，在预算内重新读取 |
| 支持服务端幂等键的写调用 | 查询原操作或使用同一幂等键确认，不生成新键掩盖重试 |
| 本地补丁应用后未写完结果 | 比较目标内容、预期摘要和补丁前置条件，能确认则补记结果 |
| 无法确认结果的写调用 | 标记未知并暂停相关后续动作，由主 agent 查询实际状态；必要时向用户补充询问 |

进程启动时将遗留的 `running` 实例标记 `interrupted`。恢复不是回放历史命令；未知写操作未解决前，受影响范围不自动继续写入。

当前恢复入口为 `Application.reconcile`、`resolveCall` 和 `recover`，CLI 对应 `reconcile`、`resolve`、`resume`。文件补丁核实实际内容的 SHA-256 与预期新旧值：等于新值则确认成功，等于旧值则确认未应用；其他情况继续阻塞。外部进程写入没有通用自动验证器，须提供独立核实依据，不猜测完成。核实结论保存为不可覆盖的 `recovery.resolved` 事件，输出原调用记录、观察依据和恢复计划。

人工核实结果为 `succeeded`、`failed` 或 `not_applied`，依据须为 16 至 16000 字符；`not_applied` 额外要求 `retry:true`（CLI `--retry`）明确授权受控重试，其他结果禁止附带重试授权。中断运行从原步骤继续；已失败的 `UNKNOWN_WRITE` 运行通过 `continuationOf` 新建恢复运行，复制完整已保存响应与已核实的调用结果，原终态及原调用保持不变。重复恢复同一来源拒绝再次复制，未解决的同会话未知写入会阻止其他运行绕过恢复。

同一数据目录中的未知写入还阻止相同或父子嵌套工作目录的跨会话后续写入；其他会话仍可只读调查，无关工作目录可继续执行。该边界覆盖本地运行时能追踪的项目范围，不宣称约束外部程序在操作系统中的任意副作用。

会话总时长按至少一个任务正在推进的墙钟累计，主任务、并发子任务及延续任务共用同一额度；全部持久等待时暂停。执行起点 `activeSince` 先持久化，崩溃重开时保守计到重开时刻，含无法确认的停机时间并以预算上限封顶，避免重启重置消耗。该保守规则可能使较长停机后的运行耗尽时长预算，快照保留实际计入值供检查。

## 5. 能力包、MCP、检索与改进

### 5.1 从第一天固定身份，P3 再补全分发

P1 即实现 `AGENT.md` 最小 Schema、卡片不可变版本、运行绑定摘要；P2 的子 agent 也使用同一格式。P3 再增加完整资源清单、安装诊断和分享。这样不会到“做能力包”时才重构运行身份和历史记录。

卡片摘要采用规范化文件路径、逐文件 SHA-256 及排序后的文件清单计算，避免 ZIP 时间戳变化造成同一内容被当成不同包。`AGENT.md` 是身份和行为来源；`manifest.json` 仅描述资源完整性，不重复维护另一套提示词与权限配置。

导入分为四类状态：已导入、待配置、不兼容、可运行；候选／已采用版本与安装可用性分开记录。具体步骤为：

```text
只读检查归档 → 校验格式、路径、摘要、大小和引用
  → 注册未启用版本 → 检查模型、平台、绑定与许可
  → 准备已有授权内的依赖 → 启动必要能力并执行示例
  → 保存本机验证结果 → 按授权启用
```

归档先检查再安全解压到隔离的暂存目录；拒绝绝对路径、驱动器／UNC 路径、路径穿越、符号链接、重复或大小写冲突条目、Windows 保留名称及解压炸弹。同 ID／版本不同内容拒绝覆盖；注册阶段不能 `import` 工具模块、安装依赖或启动 MCP。

导出从显式允许分发的资源清单生成预览，不递归打包整个项目。检查 Skill 引用、工具依赖与 MCP 服务资源是否齐全；私人运行数据和实际绑定目录不在导出根内。关键词检查只作补充，不能作为隐私和分发许可的唯一依据。

Git 分享先通过既有 Git 托管交付固定提交和包文件，不开发任意仓库安装器。记录来源提交、派生版本和内容摘要；本地可运行版本不依赖公共目录在线。

### 5.2 扩展代码与 MCP 绑定

自定义工具使用固定的 `kodo-tool/v1` 契约：静态工具说明、输入 Schema 和运行入口。说明可在不加载代码时读取；启用后在独立子进程执行。TypeScript 源码采用固定构建步骤产出可执行模块，构建也属于显式准备阶段。独立进程用于超时、取消和崩溃处理，不宣称隔离恶意代码。

本地 MCP 优先分发源码、锁文件与运行要求，依赖安装默认禁止生命周期脚本；确实需要安装脚本时列为额外执行动作，按授权处理。远程 MCP 只分发模板和工具允许列表；目标地址与凭据由接收者绑定。

MCP 连接按服务定义摘要、凭据身份和授权范围决定是否复用；每个调用仍校验实例允许的工具，撤销时立即停止后续调用。工具很多时先暴露短描述和发现入口，选中后加载具体参数，避免工具列表挤满模型上下文。

### 5.3 检索与上下文

使用 SQLite FTS5 trigram 索引路由字段，中文短名称与一至两个字标签走精确／前缀匹配并设结果上限。启动用中文样例和短查询做能力探测，不仅检查是否支持 FTS5。全文正文与 Skill 内容不进入常驻上下文。

目录使用少量固定分类与标签，多入口引用并去重。第一次实验沿用设计文档的上限：5 个候选、3 次展开、2 张详情，同时限制累计输入 token；这些是实验初值。过滤严格禁止能力，缺少可补绑定的候选显示缺口，预算耗尽与“没有匹配项”分别返回。

上下文按“宿主规则与授权 → 用户目标与决定 → 当前任务与未解决问题 → 必要历史／工具结果／同伴消息”组装。当前内核已按第 3.6 节压缩历史并保存原文引用；授权与决定从结构化状态重新注入，不能只依靠模型摘要。确定性压缩不消耗额外模型调用，后续读取原文及实际模型请求照常计入会话预算。

### 5.4 保存方法与验证版本

“把这次做法保存为 agent”生成候选：提炼可变输入、方法、工具／Skill／MCP 依赖与验收条件；排除上次任务的凭据、临时路径和私有事实。先用不同输入验证，再允许将候选作为默认版本。

案例格式包含固定输入、环境要求、允许工具、预算、可检查断言和必要的人工验收项。优先用文件／Schema／命令退出码等确定性断言；开放结论保留人工核验，不能只用模型自评分。

版本比较记录模型标识、绑定配置摘要、工具依赖、案例数据摘要、预算、环境、结果与证据。尽量固定条件并重复运行，保留未用于修改规则的案例。只有目标问题改善且关键旧案例无不可接受退步，才按用户授权采用；否则保留旧默认版本。回退只切换默认指针，不改旧运行或撤销外部副作用。

## 6. TUI、本地 Web 与分发

TUI 只保留主对话、简短任务栏、待回答问题和按需详情；完整工具日志通过引用查看。非交互模式在 stdout 输出 JSONL 事件，诊断进 stderr，定义成功、执行失败、取消和需输入的退出码。非交互任务缺少必要用户信息时返回结构化缺口，不能永久挂起等待终端输入。

P5 增加本地 HTTP：会话列表／快照、用户输入、取消、恢复、卡片操作、案例执行、产物读取与 `events?after=<cursor>`。修改请求带幂等请求 ID，同 ID 同参数返回原结果，不同参数拒绝；SSE 重连按持久序号补事件，临时 token 丢失时用快照恢复最终内容。

本地服务只监听回环地址并提供同源静态页。使用一次性启动口令换取 HttpOnly、SameSite 会话 Cookie，启动口令不放查询参数、访问日志或长期浏览器存储。校验 Host、Origin 和修改请求的 CSRF 凭据；SSE 与产物读取也要求本地身份。产物只按标识和会话授权读取，不能传任意路径。Markdown 禁止原始 HTML，下载／预览内容按类型约束。

关闭浏览器不等于停止任务：只要应用进程仍在，任务继续；退出进程后按中断恢复规则处理。TUI 与 Web 读取同一快照和事件，不复制运行逻辑。

程序先通过 npm 包分发，官网使用公司已有静态托管；公开包名、域名、许可证和发布账户在发布阶段核实。官网、示例和反馈入口纳入 Beta；社区目录独立按需求建设，不进入内核关键路径。

若有两名工程师，A 负责模型、执行、调度和恢复，B 负责工具、卡片、MCP 与交互；每个阶段共同通过贯穿场景。文档、固定样例与测试数据可同时准备，应用命令和事件契约先共同固定，避免两套状态语义。

首周顺序建议：

1. 建立源码工程、锁文件、类型检查与测试入口，定义最小运行／调用／事件结构。
2. 在指定供应商上跑真实多轮工具请求，验证流结束、usage、参数错误和取消。
3. 实测 SQLite 安装、trigram 中文召回、数据目录互斥与事务写入。
4. 打通 `kodo run --json` 的读取项目 → 写产物 → 返回证据链；此时不做多 agent。
5. 注入断流、取消和进程中断，列出选型结果与 P1 剩余任务，校准后续排期。

`check` 包括类型和静态检查；`test` 检查状态转换、权限、预算等确定性行为；`test:integration` 使用临时 SQLite、受控工具进程和本地模型协议服务；MCP 测试在实现该功能后再加入。`test:e2e` 测试构建后的 CLI，P5 后追加浏览器；`test:provider` 使用选定协议验证真实模型，`test:protocols` 逐一验证三种协议的工具循环与认证负例，均使用已配置凭据和受限预算，不混入无凭据的默认测试。两个确定性 demo 分别验收完整协作链和上下文／核实恢复链，均保留实际证据；真实模型协作演示使用 `demo:kernel:local` 单独运行，该命令也可通过环境配置连接远程模型。

高风险检查必须能稳定安排时序或故障点，不能依靠多跑几次“碰巧不出错”：

| 验证对象 | 正常证据 | 必须覆盖的反例／边界 |
| --- | --- | --- |
| 工具循环 | 至少三轮调用保持调用 ID 和结果关联 | 不完整 JSON、无效 Schema、未授权工具；真实 SDK 断流 |
| 消息与等待 | 同伴问题与答复可定位原记录 | 答复先到／等待先登记、重复消息、终态目标、循环等待、超时 |
| 预算与取消 | 会话内各实例消耗可相加核对 | 并发请求争抢最后额度；取消与工具启动竞争；不可取消远程写 |
| 持久化与恢复 | 重启后状态与证据一致 | 外部写已完成但结果未落库时杀进程；不重复副作用 |
| 并发修改 | 同项目写操作被串行化 | 根目录别名、重叠目录、跨会话写；局部通过但整合检查失败 |
| 能力包 | 完整 Skill、本地 MCP 与远程 MCP 模板跨环境运行 | 路径穿越、链接、大小写冲突、缺资源、摘要篡改、版本冲突、无凭据、平台不符 |
| 导入／导出边界 | 注册零代码执行，导出清单可复核 | 包内恶意安装脚本不触发；私有日志和绑定不随包导出 |
| 版本改进 | 不同输入复用，新旧案例与证据并列 | 新案例改善而旧案例退步；旧实例仍绑定原摘要；回退不覆盖历史 |
| Web | 断线后恢复最终状态，重复请求只创建一次 | 伪造 Origin／Host、无凭据 SSE、越权产物、幂等 ID 参数冲突 |

评测沿用设计文档的至少 20 个任务，并留出未用于规则调整的案例。分别比较单 agent／协作、直接检索／目录辅助，以及用户原先配置好的工具流程。记录完成质量、人工纠正、复用配置时间、上下文、总 token、时延和费用来源；支持相同模型时控制模型条件，无法控制时标明混杂因素。

发布验证必须安装实际生成的 `.tgz`：版本显示、`doctor`、示例、取消、重启恢复、导入导出、采用与回退逐项检查。Windows／PowerShell 为首个明确目标；macOS／Linux 单独通过安装和进程／文件行为检查后再宣称支持。

## 9. 关键取舍与进入下一阶段的条件

最大的工程风险依次是：不可靠的副作用恢复、通信与等待竞态、扩展代码启用边界、跨平台安装，以及复用价值不足。前三项在内核与能力包阶段验证，不能留到 UI 完工后再补。

首个模型供应商及凭据只影响真实协议验证，npm scope／域名／许可证只影响相应发布动作，当前不需要把全部事项一次问清才能开始。P0 若没有可用凭据，可完成确定性内核和假适配检查，但该阶段的真实模型门槛仍未通过，不得据此宣布可用。

当前已建立完整本地内核 demo，协作、上下文压缩原文追溯、共享时长与核实恢复均有可执行验收。后续先用内部真实任务校验协作收益及模型稳定性，再推进 P3 能力包与 MCP；不要把确定性脚本模型的通过等同于真实模型完成同一任务。
