### 并行没有被额度充分利用

测试节点没有依赖，约 65 分钟后才真正派发；DAG 没有强制它等待。子代理仅存活 378.777 秒，实际模型请求重叠 117.391 秒，主代理主体工作仍然串行。

### 探索提示启用了，但没有触发

主卡和子卡均为启用 nudges 的 `1.1.0`。冻结分类器重放显示：主代理 170 次工具调用中，63 次计为成功读取；最长连续窗口为 7，未达 8 次阈值。首写前 40 次工具调用只有 13 次计入，27 次重置，其中 13 次是含分隔 `echo` 的读取组合。普通 `cd && sed` 已支持，`sed && echo && sed`、部分转义/管道与 Python 检查仍打断计数。

因此不能把“提醒默认开启”当成“已约束实际探索”。诊断上应区分未知操作与确有推进，避免把所有未知命令都当作推进而清零；此项只涉及诊断，不应放宽执行权限或副作用分类。

### 有效委派出现，但没有用到更高的容量

子代理约 34.927 秒开始写文件，195.060 秒完成，15 次模型请求、19 次工具调用，已知费用 2.80 credit；主代理则有 115 次物理模型请求（含两次重试）、152 次工具调用、已知费用 53.75 credit。其分工比基线中的测试子代理更早、更独立，但任务大小不同，不能把子代理耗时或费用差当作同任务提速。

运行期间的待办把核心路由、应用入口、OpenAPI 和总体验证都分给主代理，只有中间件分给子代理。双方只有短暂的双请求并行，子代理完成后主代理又运行约 45.4 分钟。分析脚本中的 `requestsAfterLastChild=89` 覆盖后续核心实现、测试和收尾，**不等于 89 次验收请求**。本轮没有超过默认的 2 个模型并发、1 个活动子任务，因此没有实际触及 2/8 档位的容量边界。

主代理两个读取命令被 `TODO_DELEGATED` 拦截：Python 统计路由源码，以及 `cd /app && sed -n 700,760p fastapi/routing.py`。执行分类未将它们识别为只读，按工作区级潜在写入处理，与子代理范围相交。这里的诊断读取分类与执行副作用分类是两套目的不同的规则，不能直接互换。改进可以从原生读取入口及明确的失败后替代动作开始；不能把任意 Python/sed 命令放宽成只读。

还出现一次未授权工具名 `shell_command`、一次子代理 `file.apply_patch` 参数误用，以及补丁匹配失败，后续均继续执行。主代理将实现任务标完成、尚未将验证任务标为进行中时，也有一次写入被 `TODO_PLAN_REQUIRED` 拒绝，更新待办后继续；这是任务状态摩擦，不是 DAG 依赖强制串行。没有触发 UNKNOWN_WRITE 或 NO_PROGRESS 终止。

### 费用与缓存需要单独调查

放宽组正常完成响应的输入缓存命中率为 91.50%，低于默认组的 96.22%。若将异常流上报的缓存 0 也纳入，原始聚合比率为 90.65%；这部分计量存疑，不能直接作为精确比较。

按同一 run 的前后请求核对，默认组有 3 次、放宽组有 8 次正常完成响应满足“输入超过 1 万 token、缓存命中不足 50%”；这些请求均只上报缓存 1077 token。它们的工具声明没有变化，之前的消息前缀也大体保持。最明确的例子：放宽组请求 117/119 的输入为 103,665/105,182 token，缓存均为 1077，费用为 3.06/3.03 credit；与各自前次请求相比，前 260/266 条消息、约 134/135 万字节相同，变化从末尾状态消息开始。请求 19 与其前次失败请求的全部消息都相同，缓存也只有 1077。

这些证据不能归因为工具列表变化或早期消息前缀重写，也不能证明上游具体故障。仍可能涉及网关路由、缓存有效期、计量或上游请求处理。需要上游日志才能区分。本轮不把历史“状态块导致缓存下降”的猜测当作已证实原因。

## 下一步优化方向

1. **优先收尾与验收范围。** 把任务明确要求的验证、提交和最终答复作为交付闭环，在预算中给它们留出余量。基线已经全量通过却继续清理直到超时；放宽组也在部分回归通过后继续清理、复测和核对约十分钟。必要修改后的复测合理，不能笼统删掉所有复测，但无新证据的追加检查应及时收束。
2. **优先改善分工和读取体验，不急于增加默认额度。** 在接口与文件边界足够明确时交出独立工作；中间件分工已有实际执行证据。读取失败应指向可用的原生读取方式；共享子代理活动时，应避免把常用读取变成工作区级写入冲突。测试进程应根据真实副作用与隔离能力处理，不能只靠改待办节点消除冲突。
3. **修正探索诊断。** 对常见组合读取补全诊断识别，用实际推进证据区分“未知”和“推进”；避免未识别命令轻易清空窗口，或创建过一次子代理后长期停止关注主代理的后续探索。诊断优化与权限、副作用判断保持独立。
4. **保留有界恢复，单独测网关稳定性与缓存。** 本轮两个缺失终态已恢复，失败用量仍可追踪；缓存低命中发生在稳定前缀下，先查上游证据，再决定是否调整上下文构造。
5. **暂不据此把默认档位升到 8/16。** 两组峰值都是 2，没有容量受限的证据。若后续评价并行上限，应在确有多个独立任务且出现模型排队时比较；固定分工实验与模型自主分工实验分开，重复样本并保持同等交付标准。

本轮只重跑并分析，没有继续修改 Kodo 产品代码，也没有追加付费替代格。

## 计量注意事项

- 子代理首次写入使用原生工具执行证据。现有 M2 的 10 秒“首次变化”实际看见了父代理已有 diff，且 `baselineKnownClean=false`，不能用作子代理首写。
- `writersWithObservedTools=1` 仅统计配置的 `fastapi` 根，漏掉测试目录，不能据此声称子代理未写文件。
- 推理 token 以网关上报为准；异常流中有推理字符而上报 0 的记录单列，不反推 token 或缺失费用。
- 默认组未完整交付，不计算两组完成时间提速或降费百分比；不能把默认组的超时时间当作它的正常完成时间。
