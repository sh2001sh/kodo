# Kodo D/E 消融：2026-10-30

四组均已结束并通过独立验证。本轮 RE（只开启 E）最快、已记录费用最低；D/E 同开是更快但更贵，D 单开则被长时间审查拖慢。只有一次样本，不能据此证明 D 必然有害或 E 稳定有效。

本轮按用户要求，将新会话 D/E 默认开启，再运行仅 Kodo、FastAPI 四种组合各一次。旧会话保留保存的因子；显式 `--agent-factors A,B,C` 仍关闭 D/E。未提交工作区中的混合改动。

## 实验条件与结论边界

- 顺序为 R0 → RDE → RD → RE，每组一次，串行；没有因失败重跑或替换样本。
- A/B/C 始终开启；D 是交接指导，E 将主代理的命令和部分专用工具下放给子代理。E 没有删除全部协调工具。
- 同一冻结构建、同一任务文本、同一基础提交；模型为 `deepseek-v4.1-flash`，上下文上限 1,048,576、输出上限 393,216，每格 5,400 秒、2 CPU、8 GB 内存。
- 任务是 `datacurve/fastapi-deprecation-response-headers`，外部验证器在独立无网络容器运行。任务还要求创建分支并提交代码。
- 墙钟是运行器计时，包含容器运行和退出后的录制收尾，不含外部验证。模型时间分别报告请求累计值和时间区间并集，不能把重叠时间重复相加。
- 每组只有一个样本，执行策略、上游响应和网关时段也有差异。以下结果只能描述本轮，不足以证明稳定的因果收益、成功率或对其他任务的优势。

原始证据根目录：`E:/sh/Coding/agent-harness/.kodo/handoff-ablation-fastapi-20261030`。各组的 `fastapi-kodo/relay` 保存请求、原始 SSE、逐请求计时和采样；`process` 保存工具计时、工作区快照、逐步记录和交互文本；`state` 保存原生状态；`git`、`git-state.json`、`artifacts`、`verifier` 保存提交及独立验收证据。

## 各组实际执行路径

### R0：先规划，再并行，发生等待环后由主代理接手

首次成功派发距主运行开始 1,001.774 秒。此前已发生 47 次工具调用、121,506 推理 token、9.03 credit。7 次派发尝试中只有 2 次成功，其他错误为 `SCOPE_REQUIRED ×2`、`WRITE_SCOPE_CONFLICT ×1`、`INPUT_SLOTS ×2`。

中间件子代理启动后台循环，等待另一子代理添加接口参数，同时持有整个 `/app` 的写锁 454.564 秒。实现者因此连续 6 次 `LOCK_TIMEOUT`，触发 `NO_PROGRESS`。全格共 10 次锁超时，累计等待 301.221 秒、区间并集 221.710 秒；这些时间与持锁、模型请求和主代理等待重叠，不能相加。

后台任务最终正常退出并释放锁，没有残余锁泄漏。主代理接手路由实现，期间批量修改曾因导入错误被回退，再修复并完成交付。每分钟快照会漏掉这种短暂修改与回退，必须结合逐请求工具记录分析。

### RDE：三个串行子任务，主代理验收仍产生较多往返

首次成功派发为 858.366 秒；此前仍消耗 97,224 推理 token、7.64 credit。首次产品源码修改为 1,044.171 秒，与 R0 的 1,115.557 秒相差约 71 秒，前期规划仍然明显。

前两个实现任务都申请了整个 `fastapi/tests` 写范围，尝试并行时被拒，随后顺序完成路由参数、统计中间件/OpenAPI，最后再创建一个子代理进行集成验证与提交。因此它避免了 R0 的等待环，但没有实际并行修改。

最后一个子代理结束后，主代理又用了 205.343 秒、13 次模型请求、1.18 credit 验收。其中 19 次 `inspect_run` 的实际工具执行合计仅 0.318 秒。查询对象不完全重复，问题是较长的模型往返链，而不是工具运行慢。集成子代理实际跑了两次完整测试；同一后台测试进程的多次 `process.read` 不算多次测试。

主代理工具数从 R0 的 39 降为 35；首请求工具定义字节数从 37,675 降为 33,256，约少 11.7%（这一比较同时包含 D 的描述变化）。每个运行内的工具定义均稳定。整体缓存率从 95.67% 降至 92.69%，但存在前缀完整却低命中的请求，不能据此归因于工具列表变化。

### RD：主代理实现后追加全面审查，收尾成本扩大

主代理先完成实现与测试，再派发只读审查。第一个审查的 relay 请求 92 返回 HTTP 200 和 `[DONE]`，但没有正常结束标记、正文或工具调用，原生状态记录 `MODEL_INCOMPLETE`；relay 的传输完成不等于模型响应有效。这也是缺少 credit 的请求。

主代理随后安排另一个审查运行。固定在该运行前 26 个已完成请求的分析显示：51 次工具全部成功，工具时间仅 7.332 秒；模型累计 634.070 秒，推理 75,420 token。它只暴露 13 个工具。读取重复正文约 1.6%，没有被强制小页或 8,000 字符上限截断；不能把它概括为重复翻完整个项目。

交接给出了变更文件、函数位置和既有测试结果，子代理也确实使用了这些信息。但要求同时覆盖 20 条功能、6 条继承规则、所有入口及静态检查，还要求使用 Git diff；选用的只读预设没有 shell/process，也没有收到 diff 工件。它用源码读取和字面搜索完成大范围静态核对，其中存在把 `^from datetime import` 当正则搜索、在受遍历上限限制的工作区查找外部依赖等调用语义问题。

第二次审查最终被主代理取消。它共有 45 次模型请求、260,016 推理 token、18.15 credit，85 次实际成功工具执行累计仅 12.278 秒。取消前没有正式交付报告；上游流在取消后仍继续，并生成了一个未执行的 `report_submit`。它不能算作已执行工具或已交付审查，也不能说模型从未生成报告。报告中的潜在判断未被主代理接收验证，不能把最终测试通过归为此次审查的收益。

两次审查是不同 agentId 的新运行，均无 `continuationOf`；没有复用首个审查者的会话。第二次审查中断后的续接尝试又返回 `AGENT_BUSY`。最终产品修改发生在首次审查期间，由主代理执行；第二次审查及取消后未再修改产品源码。RD 总推理量达到 507,727 token，其中首次源码修改前已有 166,409 token、10.70 credit。其墙钟比 R0 增加 48.2%，已知费用至少增加 105.0%。

### RE：较早派发完整实现，再用可执行测试独立验证

主代理在第 15 次请求、约 380 秒首次成功派发，此前用了 32,583 推理 token、3.01 credit。它把参数传递、运行时响应头、统计中间件、OpenAPI、测试和提交交给同一个实现者。首次源码修改约 802 秒，距执行者创建约 422 秒；虽然执行者仍需要读取与理解代码，端到端启动时间比其他组短。不能仅以子代理自己的首次修改速度评判交接：父代理提前做过多实现级探索，也会增加总耗时。

实现完成后，主代理另派具备命令执行能力的代理，在同一提交的 detached worktree 中编写独立测试。记录确认导入路径来自该副本；独立测试 32 项通过，并运行了全套项目测试。验证者修复的是自己初写验证脚本的问题，没有修改产品实现，最后删除副本并保持主工作区干净。两个子运行没有并行重叠。

这次交接也有缺口：验证者收到了 `slots.contract`，且有 `artifact.read`，却没有调用它，转而在文件系统找合同。其独立测试依据明文的 12 组要求，不能宣称与合同的 20 个场景逐条等价，也不能归咎于 artifact 权限。外部验证的 137/137 是另一份独立证据。

## 已有证据支持的优化方向

1. **先处理锁与等待的交互。** 避免用持有写锁的后台循环等待另一个写入者；资源竞争导致的未启动调用应与模型反复犯错分开计数。不能仅凭声明的写范围缩小无沙箱任意进程的实际影响范围。
2. **减少前期规划和验收往返。** 先确定任务边界、关键约束和执行所有权；实现者负责具体实现及验证。结果应直接带可核对的检查引用和简洁状态，让主代理集中检查缺失或高风险证据。
3. **交接内容匹配角色能力和读取入口。** 只读审查需要 diff、变更区段、测试结果和限定问题；需要运行检查的任务应分配给具备相应工具的执行者。共享 artifact 要明确可直接调用的读取入口，避免把 ID 当文件路径。交接文件名并不等于交接完整上下文。
4. **给审查明确的完成条件。** 区分必要验收与额外全面审查，避免把“简短输出”误当成“小范围工作”。覆盖无关静态规范或外部依赖的要求会扩大推理成本。
5. **核对取消与上游请求终止。** 原生运行被取消后，是否真正中止上游连接和计费，需要单独修复与验证。
6. **等待唤醒和进一步工具收缩排在上述问题之后。** 五分钟等待会产生额外请求，但本轮主要消耗在大量推理和验收链。13 工具的审查仍很慢，不能据此支持单纯按数量删工具。

这些是本轮日志支持的后续方向，未在运行中的冻结构建上混入修复。D/E 默认仍按用户要求开启。当前不建议继续按工具数量扩大收缩；RE 可作为后续复测候选，D 的文字需要优先检查是否真正缩短交接与收尾，而不是增加要求。不能因为本轮 RD 较差就直接将全部退化归因于 D。

## 复核入口

- `matrix.json`：执行顺序、各组保存的因子、运行结果与冻结构建。
- `analysis.json`：四组汇总、按运行拆分的用量/等待/错误/工具定义/缓存/交付条件，缺失值保留未知。
- `evidence-sha256.json`：运行器结束时原始证据文件的哈希清单；后续分析文件不属于原始哈希覆盖范围。
- `integrity.json`：原始哈希、请求/响应文件、因子、同构建和同任务文本的核对结果。
- `.kodo/scratch/handoff-{R0,RDE,RD,RE}-analysis-20261030.json`：补充人工核实的锁事件、首改时点、Git 分支、取消后输出、实际验证等证据。
- `.kodo/handoff-ablation-analyze-20261030.mjs`、`.kodo/handoff-evidence-check-20261030.mjs`：离线分析及完整性检查脚本，不调用模型。

模型提议的工具调用与实际执行分开计数：例如 RD 取消后生成的 `report_submit` 存在于原始 SSE，但没有执行。HTTP 200、SSE 结束、原生模型调用成功、子运行成功、最终验证通过也是不同状态。

## 后续复核补充（2026-10-30）

最终优化方案见 [效率与并行优化定稿](../kodo-efficiency-parallel-plan-20261030.md)。原实验数字与原始证据保持不变，新增复核发现如下：

- RE 请求 105 派发验证者时仍选中 implement 待办；143 已观察验证者完成，154 的 verify 验收仍被拒，155 改归属后结束。后续多活动待办必须配套显式任务关联。
- RE 请求 105 指定的 worktree 命令试图再次检出已占用分支，108 失败，110 改为 detached 固定提交成功。交接应减少未经验证的操作步骤。
- 全部 669 个请求按 run 比较，R0/RDE/RE 的历史差异均从末尾状态消息开始，工具定义也稳定。RD 请求 143/146/147/149 的同一历史位置在箭头字符和 Unicode 替换字符间变化。frontier relay 的 `raw += chunk` 入站读取存在跨块 UTF-8 损坏问题，本地分块检查已确认；日志没有保留入站网络分块，不能倒推实际边界，也不能据此解释全部缓存下降。下一轮实验须先修复传输保真。
- frontier relay 的上游 fetch 没有取消 signal，下游 close 只记时间；Kodo provider 已传 signal。RD 请求 149 没有记录 clientDisconnected，因此尚不能把延迟输出全部归因于 relay 或 Kodo。应核验完整取消链路，分别报告原生中断、取消与上游结束时间；中断后约 61 秒不等于取消后约 61 秒。
