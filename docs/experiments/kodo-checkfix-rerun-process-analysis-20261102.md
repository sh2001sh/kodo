## 7. 为什么重复提示仍没有触发

两版 `check.repeat_hinted` 都为 0。离线回放本轮冻结解析器确认：

- #117 可识别，但 #118 增加 `awk` 后无法识别，检查 key 不再相同。
- #121、151、157 也包含不支持的包装；#157 还在检查后接了 `; git diff --stat`。
- #162 可识别，但 #157 未形成相同的规范化检查 key，不能作为它的上次通过记录。

因此，“本轮没有重复提示”不能解释成“本轮没有重复检查”。成功提示的已知格式修好了，重复检查机制仍没覆盖模型实际使用的一部分命令。

不建议不断扩充 shell 命令白名单来猜测一切。优先让普通检查命令直接运行，由工具保留完整 stdout/stderr、真实退出码并给出简短预览与读取指针，减少模型自行拼接 grep/awk/echo。完整输出被 shell 先过滤掉后，现有 outputArtifact 也无法恢复丢失的上游内容。

## 9. 为什么多测试仍没完成要求

修复版独立失败是 deep/shallow history 各同步、异步两项。验收日志显示：恢复的子状态值已正确（`val == 77` 或 `x == 55`），但进入回调拿不到祖先键 `level` / `base`，报 KeyError。

对应过程缺口在 #79–80：模型发现恢复后回调会再执行并增加值，于是改为显式设置数据、恢复后查询 `get_state_data`。这避免了一个错误的加一预期，但新测试只验证存储恢复，没有验证“历史恢复 × 回调注入 × 祖先作用域”的组合。最终报告宣称历史恢复支持齐全，实际证据没有覆盖这个组合。

100% 分支覆盖率不保证输入组合正确；同一批测试反复跑也不会自动增加场景覆盖。本分析确定的是缺失断言与失败表现，未运行成果代码进一步复现进入顺序，因此不把更深的代码根因写成已验证结论。

对照的五项失败则是无数据状态的兼容语义三项、宏步变更清空两项。两版漏掉的行为不同，不应把 67→68 看成仅修好一个固定缺陷。

## 优化顺序

1. **先减少“为看输出而重跑”。** 普通检查直接运行；工具保留完整输出、返回简短结果和日志指针。先覆盖 #117/#118 这一类，收益明确且不削弱验证。
2. **同版本证据复用。** 让检查身份、真实状态和代码版本能够一起关联；无法确定的继续标未知。提交而未改代码不自动要求再全套；没有硬性次数限制。
3. **专项失败集中反馈。** 新测试组出现多个独立失败时，完整跑一次专项，集中修正夹具和实现；需要定位单个级联问题时仍可用 `-x`，不全面禁用。
4. **首次全套带齐已知项目检查。** 覆盖率缺口先读完整报告，专项补测后再统一全量。不要靠删覆盖率来获得速度。
5. **减少错误前提和无关修改。** 复用已存在的测试夹具、API 和图示断言；格式化只覆盖已改文件；避免为了找现成实现扫描外部环境。
6. **交付前核对组合行为。** 用公开需求交叉核对历史、作用域、回调、同步/异步等组合。这是补充已有验证内容，不新增交付硬门槛，也不向模型提供独立验收隐藏内容。
