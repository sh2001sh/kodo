# Kodo 精简版：默认与放宽并行上限对照

日期：2026-10-30。状态：两格均已结束，验证与记录完成。两格任务都失败，不能证明优化收益。改动未提交。

**结论：并行容量可以从 2 路模型 / 8 个活动子任务提高到 8 / 16，但这两次真实运行的峰值都只有一路模型、零子代理。** 两组都在修改源码前因不完整模型响应退出。当前证据指向过长的单代理探索与响应恢复问题，没有显示并行数量上限是瓶颈。不建议仅凭本次结果提高产品默认并行上限。

本轮“放宽”是提高有限上限，不是无限并发。模型请求上限包括主代理和子代理；活动子任务上限包含尚未结束的排队、等待任务。两层上限一起改变，不能单独归因于其中一项。提示模板和任务文本不变，工具说明中公开的活动子任务额度随配置变化。产品默认值仍为 2/8。

驱动器在每格结束后检查真实会话数据库中的并行上限、协议与工具视图，以及构建、任务文本、初始提交、记录完整性和脚本指纹。错误配置或记录缺失会使对照失效。网关预检 HTTP 200，耗时 1.181 秒；该预检只确认模型列表可访问，不保证后续生成稳定。

## 5. 下一步优先级

1. **先解决不完整响应的可恢复性。** 核对网关为何在只有推理、没有有效结束原因时发送 `[DONE]`。评估仅对没有执行工具、没有未决副作用的失败响应进行有界重试或恢复，保留原失败记录和未知计费；不能将半截响应当作成功，也不能通过放宽验收来消除错误。本轮未修改该行为或付费补跑。
2. **缩短首次实施前的探索，尽早交出独立工作。** 本次两组分别花了约 18 和 16 分钟、至少 9.7 万和 5.1 万推理 token，仍没有修改源码。后续应明确“已知入口、独立文件归属和接口边界足够时即可开始实施/交接”，避免主代理先设计完所有模块。提示是否是直接原因仍需消融，不凭这两格认定。
3. **在真正产生排队的工作负载上评估并行档位。** 保留当前 2/8 默认值；下一次先确保存在独立实施任务，再比较默认与放宽配置，观察实际请求重叠、写入冲突、质量和总费用。固定分工实验须与模型自主分工实验分开报告。
4. **工具入口数量暂不作为首要瓶颈。** 本次两个配置都只使用 shell，工具执行仅约 3–4 秒；继续删工具本身无法解释或解决已观察到的长模型请求。工具上下文、重复探索和任务调度应分别验证。

**已确认的直接原因**：网关返回的 SSE 内容本身缺少 `finish_reason`。两次都在推理增量后停滞，仍每约 10 秒收到 `: PING`，最后是 `choices: []` 的用量事件和 `[DONE]`；没有正文、工具调用、拒绝、过滤结束原因或封装的错误事件。34 次正常请求则都有 `tool_calls` 终态，最后有效内容至 DONE 的间隔最多 71 毫秒，其中两次正常请求总时长也超过 120 秒。

**可以排除或不支持的解释**：

- relay 改坏请求：37 次入站与转发请求指纹全部相同，输出上限也一致。
- relay 主动伪造 DONE：冻结脚本第 140–146 行先记录上游文本，再把原 chunk 转发；没有补发 DONE 的路径。证据文件经过 UTF-8 解码和凭据脱敏，严格说不是网络原始字节抓包，但目标文件没有脱敏替换，也没有 JSON 解析错误。
- Kodo 先超时断开、导致终态丢失：两次下游关闭都晚于 DONE 1–2 毫秒，符合 SDK 结束读取后的清理。relay 的 `CLIENT_DISCONNECTED` 是这次清理的结果。首字节分别只等了约 9/7 秒，后续心跳持续刷新本地 120 秒按字节计的空闲期限，没有 `FIRST_BYTE_TIMEOUT` 或 `STREAM_IDLE_TIMEOUT`。
- 撞上输出上限：两次末尾上报用量远低于请求上限，没有 `length` 终态；现有证据不支持该归因。两次也没有实际并行，不支持用“放宽并行把网关压垮”解释。

**较强线索、尚未证实的根因**：上游通道不再产生内容后，网关等待约两分钟，再以用量汇总和 DONE 收尾，可能是内部超时、上游连接终止或终态转发缺失。两次末尾统计都把已经出现的推理详情记为 0，并把先前增量中的缓存值 1,077 改为 0，形态与正常请求不同，可能涉及网关的兜底计量；不能据此认定具体软件或具体故障实现。

默认组请求 3 是另一条通道异常证据：HTTP 200 心跳约 126.6 秒后返回未加 `data:` 前缀的 JSON，错误类型 `new_api_error`、代码 `get_channel_failed`。冻结 relay 的 SSE 行解析器没有识别这段裸 JSON，因此其 `protocol=unknown/errorSeen=false` 不能解释为没有网关错误。此次离线审计已单列该错误，未覆盖原始记录。它支持当时存在网关通道问题，但不能证明与另外两次完全同因。

继续定位需要上游网关内部记录。对应 `x-oneapi-request-id` 为：默认组请求 21：`2026103003424024440945936468c0eSfOKfCke`；放宽组请求 16：`2026103003593922125909736468c0eK71hrjpS`；默认组请求 3：`2026103003275824671539636468c0eVYHRzaUA`。这些仅是请求追踪标识，未包含凭据。本地日志无法进一步区分底层模型、通道连接和网关自身的责任。

本轮 Kodo 的有界重试处理可恢复性，不会修好上游原因。后续若优化心跳空等，应把“收到字节”与“内容持续推进”分开观测；不直接把一次合法的长推理停顿当作失败，也不把 DONE 当作正常完成的替代证明。
