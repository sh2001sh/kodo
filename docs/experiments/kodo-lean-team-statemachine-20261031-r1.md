本轮选用 Frontier Harness Eval 的 `python-statemachine-state-data-scoping`。实际启动了 3 个子代理，观察到模型并发和 3 次自动集成；完整任务没有完成。主代理在处理集成回归时连续收到 3 次 HTTP 503，退出码为 1；独立验收也未通过。因此，本轮证明了委派链路可以运行，同时暴露了效率与质量控制问题，不能据此宣称并行比单代理更快或更便宜。

**为什么选择这个项目**

[任务定义](https://github.com/frontier-harness-eval/eval/tree/e837a70bd6beb4e72eeeda62dd06e3bd34f6cb63/tasks/python-statemachine-state-data-scoping)要求为状态机加入状态数据、生命周期管理、层级作用域、历史恢复、SCXML 导入和图示注释。目标项目是 [fgmacedo/python-statemachine](https://github.com/fgmacedo/python-statemachine)，基线提交为 `8d17ba9f6ba8420cf05fddb94013bc221ed9a222`。

生命周期、SCXML 和图示有独立文件边界，同时又共享公共数据接口，适合检查任务交接、并行修改、集成和回归处理。本轮模型确实按这三个模块拆分，三个子任务交付的文件范围没有交叉。因此它适合作为委派集成测试，但不是完全无依赖的并行吞吐测试。

**本轮暴露的具体问题**

1. **快照不兼容项目已有符号链接。** 第二次 delegate 参数校验通过后，三个节点都因 `snapshot supports regular files only: CLAUDE.md` 创建失败。模型把该链接替换成普通文件，再用三次 `task redo` 才启动成功。最终补丁仍包含这个无关的文件类型变化。源码位置：[execution-snapshot.ts](E:/sh/Coding/agent-harness/src/runtime/execution-snapshot.ts:58)。应支持在保持路径边界与链接语义的前提下创建快照，而不是让模型改项目文件来适配宿主。

2. **隔离检出没有消除 shell 串行化。** 当前无子运行级 OS 沙箱，写入类 shell 的副作用范围覆盖 `/app` 和全部子检出。日志中有 131 段这类全工作区写锁，合计持有约 569.270 秒；各调用方累计锁等待 733.331 秒，最长单次约 84.854 秒。等待之间可能重叠，不能当成可直接节约的墙钟时间。生命周期交付完成后等了 73.967 秒才集成；另外两项分别约 0.35 秒。源码明确采用这一保守策略：[index.ts](E:/sh/Coding/agent-harness/src/tools/index.ts:308)。优化应先建立可强制执行的进程/文件系统隔离，再缩小受保护的写范围，不能直接删锁或把 pytest 当作无副作用命令。

3. **先设计并实现公共基础再委派，串行阶段过长。** 第 46 次请求才首次尝试 delegate，而且把实现细节大量写入 goal，超出 4,096 字符被拒。下一次把内容移入 start 后又撞上符号链接问题。首次成功派发是第 50 次请求附近。当前主代理有 9 个工具，问题已经不主要是工具数量，而是何时停止探索、如何表达交接及运行时支持是否可靠。

4. **交接里出现错误工作目录和过细实现指令。** 两个子代理首次原生读取触发 `PATH_DENIED`，交接内容仍写“Workspace /app”，实际工作目录已经变成隔离检出。SCXML 的交接又明确要求移除既有全局初始化行为，与保留旧 W3C 行为冲突；子代理按指令执行后把冲突交回主代理。交接应强调可验收行为、接口和兼容要求，路径以子运行真实工作区或相对路径呈现。

5. **交付状态和质量状态没有可靠绑定。** SCXML 子代理最终答复明确写出“一个必需检查未通过”，并列出 10 项失败，但没有使用 `NEEDS_INPUT:` 前缀，于是运行完成并自动集成，节点变为 done。主代理阅读报告后发现问题并开始修复。运行时已有“子检出检查不等于集成后验证”的提示，这是正确的；仍需要结构化记录检查命令、退出码和未解决事项，区分已交付、已集成、已验收，不能仅靠正文前缀或完成状态。还不能直接把外层 shell 的 exitCode 当作测试退出码：请求 213、244、245 的 shell 均返回 0，但输出明确包含 `exit=1` 和 10 项测试失败，因为测试后还执行了 echo/grep/tail；需要保留实际测试进程的退出状态。

6. **重复验证与工具调用摩擦。** 40 次 shell 调用包含 42 个实际 pytest 命令片段（排除版本查询/环境探测，其中 2 次调用各包含两个命令；片段不保证前一个命令失败时后一个仍执行）。包含 11 个全套 pytest 命令片段，其余为专项、文档等检查。部分是代码修改后的必要重测，部分是基线与覆盖率比较；没有完整版本对应证据时，不把这些次数等同于浪费次数。项目 AGENTS.md 明确要求 100% 分支覆盖率。可优化检查安排和结果复用，不能取消真实质量要求。另外记录到 3 次 PATCH_MATCH、2 次 shell 读取不满足原生编辑观察要求的拒绝、2 次错误工作区读取。应让工具错误、路径和读取前置条件更容易一次调用成功。

7. **现有观测还存在盲区。** 通用 delegation-metrics 对 lean 别名的源码写入识别不完整，输出 `writersWithObservedTools=0`，不能据此说没有写入。本报告从数据库中的规范工具调用、结果、时间和副作用路径补充核对，主代理/三个子代理分别有 8/3/6/7 次成功源码文件写入调用。子检出还在运行终态清理中被删掉，最终归档目录存在但 clones 为空；以后应在清理前持久化检出证据或有明确保留策略。

**优化顺序**

- 先修快照对普通仓库符号链接的兼容性、子代理工作目录交接，以及验收状态结构化。这些直接决定能否顺利派发、是否将未通过交付误看成完成。
- 再补子运行进程隔离，让互不相交的命令具备真正并行条件；暂时继续保留未隔离命令的保守写锁。
- 把公共接口准备压到最小：目标与接口够明确就派发；交接给相关位置、接口约束和已验证事实，减少逐行实现命令。用首次派发时间、子代理首次修改时间和重复读取下界衡量效果。
- 子任务以必要的专项与覆盖率检查为主，由主代理安排集成后验证；只有代码版本和环境一致时复用已有结果。
- 暂不继续削减 9 个工具，也不先扩大并发上限。本轮已经达到 3 路模型并发，主要限制在准备时间、写锁、验证安排和集成质量。
- 上述修复后，再在同一任务运行 lean-solo/lean-team 同构建对照，保持指令与资源条件可比。当前单轮、中断、定向要求的数据不能计算并行加速比或费用优势。
