日期：2026-10-25。状态：已执行；最终 r4 在 D1 按预注册停止规则终止，矩阵有效但不完整。结果与原始证据见 [真实模型实验结果](ky-total-timeout-results.md)。

2026-10-27 使用最新版运行的无累计上限 v2-r10 在用户要求下于 B2 中止；5 个完成 trial 的结果见 [v2-r10 真实模型对照结果](ky-total-timeout-v2-r10-results.md)。

## 1. 选择和问题

选用 [sindresorhus/ky #848](https://github.com/sindresorhus/ky/pull/848)：增加 totalTimeout，并把 timeout 改为每次尝试独立计时。实际改动涉及运行逻辑、类型、文档和测试，共七个文件。该任务比常量查询有更多工程交付要求，同时可通过本地 HTTP 服务和可控 transport 独立验收。

不假定它一定需要多代理或足够触发摘要。完整任务仍只有一个，重复运行只估计本题波动，不能作为跨任务泛化证据。公开历史 PR 可能被模型见过，本题作为真实工程开发基准，不宣称无训练污染。

要回答三个问题：

1. 当前 Kodo 是否能正确交付这个工程功能？
2. 开放自主委派是否改变质量、费用和时延？
3. 当前摘要策略是否保持质量，并改变上下文、费用和时延？委派与压缩一起启用是否出现额外问题？

## 2. 当前 Kodo 基线

冻结时使用当前经过验证的 Kodo 构建，包括 r3 估算修复；不能将结果称为早期 T8 代码结果。记录源码内容哈希和 dist 哈希，单一旧 git HEAD 不足以标识当前含未提交修改的工作区。

这些检查只确认接口存在，不等同于新 Ky runner 的验收。准备阶段仍需验证该 runner 真正应用了分组策略、计入所有主/子/摘要请求并正确停止。

## 4. 分组：一个任务、四组、两次重复

首轮采用 2×2 对照，共 8 次完整运行：

| 组 | 自主委派 | 摘要 | 对应问题 |
| --- | --- | --- | --- |
| A | 关闭 | 关闭 | 单代理基线 |
| B | 开放 | 关闭 | B 对 A：开放委派的效果 |
| C | 关闭 | 当前 summary 策略 | C 对 A：单代理压缩的效果 |
| D | 开放 | 当前 summary 策略 | D 对 B：协作下压缩；D 对 C：压缩下委派 |

“关闭摘要”保留所有组共同的模型硬窗口保护与历史原文读取。两组摘要使用同一个冻结实现，assembly、structured exploration 与 exploreNudge 都显式关闭，不把提醒或相关性组装混入本实验。

开放组暴露 explore/spawn、现有临时配置及必要通信工具，主代理自主选择，主子使用同一模型。Solo 组移除委派入口和对应不可用工具提示；普通批量工具调用不受限制。业务工具、工具权限、总 session 预算相同，避免协作组独占专业能力。

不提供现成的任务专用卡片，不引入未验证 Skill/MCP，不强制委派、不设最低创建次数。临时配置是否使用作为观测项，本题不专门证明社区卡片收益。

B/D 未创建子代理时保留结果，称为“开放委派策略未采用”，不能把 token 波动归因于实际协作；C/D 未安装摘要时保留结果，称为“本题未暴露摘要路径”。

每个 block 含 A/B/C/D 各一次，分别使用全新 session 和工作区。拟定顺序 block 1 为 A→D→B→C，block 2 为 C→B→D→A，提供顺序反转以减轻时间漂移；最终顺序在注册中固定。所有 trial 顺序运行，同一 trial 内允许正常子代理并行。不声称反转顺序消除了上游缓存和负载影响。

两个 block 用相同冻结任务与验收集合，只改变运行重复编号；若模型支持随机种子，则同 block 使用相同种子，不声称不同策略能拥有相同生成随机轨迹。所有历史、知识目录和跨运行产物隔离。

## 5. 资源与环境建议值

> 2026-10-27 当前注册覆盖：从 v2-r5 起的完整工程对照不设置累计模型调用、累计 token、工具调用或 Agent 时长上限；以下数值保留为早期设计建议，不是 v2-r10 的停止条件。窗口、单次输出、子代理创建数、模型并发和单工具超时仍按注册冻结。

以下为设计建议，须在不调用付费模型的准备与 dry-run 后统一冻结；不能看到各组结果后再提高个别组上限。

| 项目 | 每个完整 trial |
| --- | --- |
| 模型 | `deepseek-v4.1-flash`，provider/返回 model 标识与参数冻结 |
| 输入输出总窗口上限 | 65,536 token，须由 provider 实际支持 |
| 单次输出上限 | 8,192 token |
| summary 工作软预算 H | 24,576 token |
| 总模型调用 | 80 次，含主、子和摘要 |
| 总 token | 2,000,000，含缓存输入、输出、主子与摘要 |
| 总工具调用 | 240 次，共享计量 |
| Agent 完整任务时限 | 25 分钟，含本地验证与等待 |
| 子代理创建数 | 最多 4 个，继承现有生命周期计数规则 |
| 模型并发 | 同一 trial 最多 3 个；不并发其他 trial |
| 单工具超时 | 120 秒，慢测试拆分执行，不用全局杀进程 |

矩阵最多 640 次模型调用和 16,000,000 token，最多 200 分钟 Agent 工作时长；这些是停止上限，不是预期消耗。独立验收使用单独可复现时限，分别报告 Agent 时长与包含验收的端到端时长。

宿主实际限制更小时，准备阶段统一调整全部组并更新注册。所有在途请求都需全局额度预留，不只是收到 usage 后才检查。主代理交付保留量继续沿用当前实现，不给某组额外兜底额度。

如果价格尚未确定，可以验证功能和记录资源；费用结论必须写“不确定”。本任务不把没有价格时的 token 比较改名为金额收益通过。

## 6. 独立验收矩阵

权威验收位于工作区外，在 Agent 完成或终止后将可提交文件放入干净基线、重新构建后执行。使用公开 API 与真实构建产物，不断言参考解的私有函数名或修改行数。

| 编号 | 公开契约对应的检查 | 主要能排除的错误 |
| --- | --- | --- |
| T01 | 普通请求成功，默认选项与 totalTimeout:false 不额外施加整体截止 | 新选项意外改变普通请求 |
| T02 | 多次重试每次独立获得 timeout，未设总限时可成功 | 仍将 timeout 当全局余额 |
| T03 | totalTimeout 跨尝试累计，次数未耗尽也按时结束 | 每次 retry 重置总计时 |
| T04 | timeout:false 时总体上限仍有效；两者 false 时有限慢请求可成功 | 把两个开关混为一谈 |
| T05 | 剩余总体预算小于单次限额时，以剩余预算限制尝试 | 只在重试前检查而放任尝试超时 |
| T06 | 退避和 Retry-After 等待消耗总体预算；耗尽不发送下一请求 | 只累计 fetch 时间 |
| T07 | retryOnTimeout 与 shouldRetry 保持规则，但不能越过总限 | 通过 retry 决策绕过终止 |
| T08 | HTTP 错误响应体持续不结束、错误解析挂起均受总预算约束 | 只限制收到响应头的时间 |
| T09 | totalTimeout:0 不发送；超安全计时上限抛 RangeError | 零值落回默认、参数溢出 |
| T10 | create/extend 继承、覆盖、false 关闭及父实例不变 | 配置合并遗漏和共享状态污染 |
| T11 | 用户取消及终止后无新的内部请求调度 | 前台结束但后台继续重试 |
| T12 | 原有非目标 HTTP/网络错误、重试次数、hooks 回归通过 | 为实现 deadline 破坏错误行为 |
| T13 | TypeScript 消费者可以使用 number/false，错误类型被拒绝 | 运行实现存在而类型缺失 |
| T14 | 文档、回归测试、DELIVERY.md、最终答复与实际日志一致 | 无文档、空交付、假称测试通过 |

T01–T13 为自动化为主；T14 用清单核对，不由关键词命中或单次模型评分决定。实现完全正确但验证不完整应明确区分“功能通过”与“完整交付未通过”。

测试设计约束：

- 首先复用上游相关回归的契约，但不能仅复制其固定数值；加入冻结的不同重试次数、延迟组合和配置继承组合。
- 优先使用可控 transport、单调计时与事件屏障，检查请求数量/顺序/错误类别。假时钟必须与实际生产代码使用的计时源一致。
- 再加入少量本地 HTTP 集成检查。网络循环与假时钟混用须先验证，不要求毫秒级精确相等。
- 提前固定合理时间容差，至少重复检查正常解；边界不设在刚好完成和超时的竞速点。测试调度波动不能直接算模型错误。
- 不要求自定义 fetch 无视 AbortSignal 时仍能被强行终止，也不在隐藏验收中要求任意用户 hook 必须可抢占。
- 旧测试中 timeout 整体语义随需求变化的断言允许明确适配；原有不相关行为用外部回归继续保护，不能要求参考实现也无法通过的旧断言。

## 7. 零付费入场验证

### G0：准备冻结环境

取得候选基线和相关参考实现，核对来源与许可证；锁定依赖/Node/系统；准备本地服务和隔离；生成内容清单。公开环境说明记录实际验证过的 build、定向 AVA、类型和 lint 命令。

### G1：证明验收有区分力

在相同环境运行：

1. 未实现基线：在至少一项 totalTimeout 新功能及 per-attempt 语义检查失败，其他预期基础行为可运行。
2. 参考实现：T01–T14 中适用于参考工件的功能/类型/文档检查通过；DELIVERY.md/最终答复用独立构造工件验证评分器，不要求上游 PR 原本包含 Kodo 交付文件。
3. 错误补丁 M1：每次重试重置总计时，应被 T03 拒绝。
4. 错误补丁 M2：只限制 fetch，不计退避等待，应被 T06 拒绝。
5. 错误补丁 M3：忽略内部错误体读取/解析，应被 T08 拒绝。
6. 错误补丁 M4：功能正确但遗漏导出类型/文档，应被 T13/T14 拒绝。

正确实现和代表性错误实现各至少重复验收三次，确认结论稳定。若参考解不满足公开任务，先诊断任务契约、上游参考范围与验收器，不现场给参考解放宽标准。

### G2：证明实验策略真实生效

脚本 provider 零付费检查：A/C 不存在创建入口；B/D 能创建、通信、等待和交付；C/D 的配置确实能触发安装与失败回退；全部组的业务能力和总预算一致；所有模型调用进入同一账本。

用模拟拒绝、未知 usage、取消和不完整矩阵验证停止及判定。安装事件、配置快照和 run 来源一一对应，不能只相信 CLI 参数。

### G3：冻结注册

保存任务/实现/构建/模型/提示/工具/依赖/验收/seed/预算/执行顺序/价格/停止规则的清单与哈希。所有必填值实际确定，运行目录为空，注册文件在第一笔模型请求之前写入。

G0-G2 已执行；r4 注册冻结了直接 runner 工件和生产构建，但遗漏三个共享 runner 依赖的逐项预哈希，严格 G3 依赖闭包不完整。实际记录和限制见结果报告，本方案本身不是注册文件。

## 8. 正式探索运行与停止

按两个 block、共八个 trial 执行，逐次持久化结果。共享预算和原始 evidence 覆盖主任务、子代理、摘要、重试及未知调用。

- 确定性的隔离/归档/记账/全局停止失效等契约错误出现，立即停止后续付费单元并离线复现。
- 正常任务验收失败保留原结果，不立即修提示重跑。若第一个 block 四组完整交付全失败，按预声明停止扩展 block 2，先检查任务难度、预算和环境；报告不完整且未形成收益结论。
- 提供方连续两次基础设施失败则停止矩阵；提供方内部允许的有限重试在注册中固定并全部计费，不追加替补 trial 掩盖失败。
- 任一全局额度不足时停止；记录已完成、正在运行和未开始单元。部分矩阵不能判整个实验通过。
- 单个任务超时/额度耗尽按任务失败记录，有可用产物仍进行独立验收；不得自动追加“免费收尾”模型调用。

不把所有摘要回退都视为致命错误：预期的可恢复失败应记录其代价及最终交付；不可恢复丢失、无界重试或违反预算契约才触发对应停止规则。

## 9. 结果与解释

每个 trial 记录完整交付布尔值、T01–T14 结果、约束违反、非空最终答复、工件哈希；再记录缓存/未缓存输入、输出、金额/未知量、请求和工具数、Agent 时长、独立验收时长、输入峰值及归档恢复成本。

委派项：是否创建、任务配置/范围/深度、创建时点、子任务完成与结果被采用的证据、主代理复查量。摘要项：触发/安装/失败、输入输出及缓存、发生在哪个 run、安装后重读成本。不能只统计主代理费用，或只统计最终成功安装调用。

按 block 列出 B−A、C−A、D−B、D−C 的质量与费用/时间差异，交互效果只作描述。不能把四个对比当作四项独立实验证据。

判定分三层：

1. 有效性：冻结、环境、矩阵、计量是否完整；未知费用保留，不按零处理。
2. 交付：每组几次完整通过、具体失败项。两组都失败不叫质量持平通过。
3. 代价：质量相当时描述实际费用与时延的取舍；只减少 token 不称省钱。失败试次资源仍进入全批成本，另列成功配对数据，不能只挑成功样本。

两个重复只是一个工程任务的探索证据，不做统计显著性、非劣效或默认开启结论。若八次全部成功但没有委派，只能说工具开放没有被采用；若没有摘要安装，只能说本任务在该预算下未检验摘要续做。不得事后增加强制分派或填充文本把它改成“成功触发”的同一实验。
