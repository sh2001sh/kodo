# Kodo 最新修改的单次 A/B 实验验证（2026-11-01）

结论：本轮当前版本通过全部独立功能验收，读取截断明显减少、开始修改更早，但总时间增加 28.4%，请求数增加 16.6%。新检查提示没有触发，且最终覆盖率证据缺失。因此不能把这次修改判为整体效率优化成功。

## 条件与证据

- 每版一次，顺序为修改前 → 当前修改。修改前是上一轮 optimized 的冻结版本，不是最早的原始 Kodo。
- 任务：`python-statemachine-state-data-scoping`，公共基线 `8d17ba9f6ba8420cf05fddb94013bc221ed9a222`。
- 同镜像、DeepSeek V4.1 Flash、1,048,576 上下文、393,216 输出上限、lean-team、ABCDE、协议 3、模型并发 3、活动子运行 8、2 CPU / 8 GiB。每格使用独立容器与新会话。
- 两格进程均正常结束、退出码 0，无 HTTP 失败；独立验收时间不计入墙钟。功能验收失败的对照仍保留，没有替换重跑。
- 完整证据：`.kodo/roundtrip-followup-ab-20261101/`。`batch.json` 保存条件与结果，`source-hashes.json`、`driver-freeze.json`、`analysis-freeze.json` 保存冻结信息。
- 每格 `statemachine-kodo/relay/` 保存逐请求记录与 SSE；`process/` 保存工具、原生历史及工作区采样；`state/kodo/kodo.sqlite` 保存原生事件；`artifacts/model.patch` 与 `verifier/` 保存成果及独立验收。
- 分析来自 `analysis/effect-review.json`、两版 `*-audit.json` 与 `*-visible-tools.json`。本报告修正严格命令解析器的统计盲区，没有改写原始日志。

## 修改是否生效

**读取体验有直接改善，但上下文并没有变小。** file.read 截断由 10/13 降到 6/15；shell 截断由 39/136 降到 5/139。首次原生写入提前约 158 秒。扩大输出上限与这些变化方向一致，但两格实际读取内容不同，无法把全部收益归于一个参数。累计输入增加约 68%，还包含更多轮次与不同实现路径的影响。

**检查提示本轮没有验证到收益。** 在两格 SQLite 中查询 `check.suite_passed` 和 `check.repeat_hinted`，计数都为 0。当前版本大量使用重定向后 `code=$?; tail ...; echo EXIT:$code`：打印测试退出码，却没有把它作为 shell 退出码返回。可人工从输出核对通过，但运行时的保守解析器没有据此发送提示。

另一个覆盖缺口是简单管道。`src/tools/shell.ts:194` 明确启用 `pipefail`，当前版本第 75 请求的 `pytest ... | tail` 实际失败，工具也返回 exitCode=1。不能把这种管道统称为掩盖失败；解析器需要结合宿主真实执行语义判断。以上是识别问题，不是放宽成功标准的理由。

**重复测试减少，但不能直接归功于提示。** 当前版本 9 次全套候选对应不同的调用前代码版本，并非同版本原样重复 9 次；仍存在修改—全套—再修改的循环。对照第 109/110、140/142 请求在相同版本上覆盖了全套测试，但检查参数含覆盖率差异，不能全部认定为无价值重复。当前版本也减少了覆盖率验证，节省时间中包含少做项目必需检查的部分。

严格解析器的 `firstSuiteElapsedEndSec: null` 和空的重复列表表示未识别，不能据此断言没有全套成功或没有重复。实际首次全套请求为对照第 76 次、当前版本第 58 次。

## 成果质量与实现差异

对照失败的是同步、异步两项 `test_changes_cleared_between_macrosteps`。其 `StateDataManager.initialize/remove` 把状态初始化、删除也写入变更记录；当前版本的 `enter_state/exit_state` 直接设置和移除状态数据，不在这两处追加变更记录，独立验收两项均通过。代码阅读副本在 `review-code/{baseline,optimized}/statemachine/data.py`。

当前版本没有简单地减少实现。`data.py` 从对照的 250 行变为 456 行，包含 `_StateData`、`ScopedStateData` 等字典行为；第 84–86 请求检查复制、序列化与历史，第 134/136 请求继续修字典赋值和转移，第 159 请求的回调数据传播测试失败后，第 160 请求修改同步/异步引擎并通过；第 164–169 请求还在修字典操作及类型问题。这些有实际反馈驱动，不能全部视作重复劳动，也不能断言全部是独立验收所必需。

整体补丁则由 22 个文件、1,203 行新增 / 19 行删除，变为 18 个文件、1,061 行新增 / 14 行删除。核心模块变复杂与整体补丁变小同时存在，不能只用行数判断实现优劣。两版均未出现上一轮讨论的额外 DataVar 别名，不能宣称本轮消除了该问题。

**独立功能验收全过，仍不等于项目交付要求全部满足。** 项目 `AGENTS.md:191` 明确要求 100% 分支覆盖率。当前版本只在第 102 请求留下专项覆盖率：data.py 67%、state.py 88%、汇总 77%；这只是当时该专项范围的结果，不是最终全仓覆盖率。之后的全套候选均使用 `--no-cov`，最终答复未披露覆盖率尚未验证。

对照第 140 请求有 `TOTAL ... 100%` 的全仓分支覆盖率输出。当前版本最后全套第 170 请求输出 `1567 passed, 1 skipped, 44 xfailed`，第 173 请求专项输出 `21 passed`，两者均不能替代覆盖率证据。

当前版本第 157 请求做过全包 mypy，之后仍有局部类型检查；不能沿用上一轮“后续修改完全没有类型检查”的结论。命令内修改后立刻测试的结果，也不能只凭调用前版本标签判为过期。

## 费用与结论边界

对照全部 151 请求的 credit 字段为 0；当前版本第 1–110 请求为 0，第 111 请求起出现非零，66 请求合计 12.10。字段存在但计量表现中途改变，原因未证实，因此不能比较实际费用，也不能把 0 当作免费。

每版一次且串行，缺少重复样本及随机化；同一对照构建上一轮曾达到 72/72，本轮为 70/72，说明结果存在波动。本轮只支持“当前样本功能验收更完整、总效率更差”，不支持稳定质量提升或稳定退化的因果判断。两版都未委派，本轮没有并行收益证据。

## 后续最小优化建议

1. 保留降低截断的改动，同时观察累计输入和额外读取；本轮不支持继续无条件扩大输出。
2. 校正检查证据对宿主 pipefail、退出码传播及命令内修改的处理，并用本轮真实命令做离线回放。无法确定的保持未知，不把外层 exitCode=0 当作测试通过。
3. 将“已通过可交付”的提示与项目实际要求对齐，覆盖率未验证时如实披露；保持提示性质，不新增交付硬门槛或固定次数上限。
4. 重点检查额外字典行为是否有任务依据，减少因此产生的修复链；不要把必要的复杂功能验证一并删掉。
5. 暂不提高并发。若继续测委派，应单独固定核心接口后比较委派与不委派，当前零委派样本无法回答并行收益。
