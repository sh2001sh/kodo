# python-statemachine 五组日志详细分析

本报告离线分析 2026-11-03 五组各一次的既有日志，没有重跑模型、修改实验产物或修改产品实现。结论依据请求内容、已执行工具、原生事件、验收器输出和最终补丁；不以模型自述替代执行证据。

最重要的结论是：这轮测到了 Kodo 在复杂代码任务中的执行路径、协作摩擦和供应商波动，尚未测到阶段挂载、方法卸载和动态工具的实际收益。无需据此否定产品方向，也不能把阶段标记组的较好结果当成阶段机制获胜。

主运行正常结束为 4/5；最终补丁通过全部独立验收为 3/5；两者同时满足为 2/5。这些是同一个任务、不同配置各一次的描述统计，不是总体成功率估计。active 的时间是中断时间，不能当作成功交付所需时间。

所有五组 skill.list、skill.load、task 调用均为 0；方法加载、结束、物理卸载、knowledge.saved 和压缩事件均未出现。每组主运行的工具定义只有一个版本。四个非预加载组的方法覆盖都是 0/3；分母是三张不同方法卡，并非三次独立的自主采用机会。按任务运行计，观察到加载的非预加载组是 0/4。

本轮还没有自然触发检查点：主 Agent 已知单次输入峰值分别为 227305、219895、215019、204264、136296 token，配置窗口为 1048576。累计输入数千万 token 是多次请求累加，不能解释成单次窗口被塞满。

## 方法为什么没被加载

marking、checkpoint、active 的首个请求均有标题 `Available session agents and inline methods (frozen)`；三张卡明确声明 `execution_modes: [inline]`，给出 `card-method/...` 句柄、`load: skill.load`，并说明加载到自身而非生成子 Agent。skill_list / skill_load 的工具描述也已明确。这三组不再是旧实验中“模型根本没有看到加载入口”的情况。

但是普通 skill 基线的首个请求只有技能工具，没有三张方法的名称、描述或句柄目录；模型必须主动调用 skill.list 才能发现内容。其发现条件比 inline 三组弱，仍不能作为仅比较生命周期管理的严格对照。resident 则把三张方法正文直接加入主卡提示，因此“resident 没调用加载”不代表它没得到方法。

方法内容仍是“理解代码、遵守项目抽象、检查并验证”这三类通用指导。主卡本身已经要求读相关代码、实现、验证、复用结果并在适当时委派。加载卡片能提供多少新增信息，没有由当前任务建立起来。这里的合理假设是方法增量价值低，但日志不能证明模型的内部选择原因。

主卡还明确要求在识别独立文件所有权与接口后委派实现；三张方法卡没有同等强度的加载要求。模型优先沿现有工作流调用 spawn_agent 是与可见指令一致的行为。这不是“不会用工具”：各组分别尝试委派 4、5、2、2、2 次，成功创建 3、3、2、2、2 个子运行。

另外，resident/skill 的首轮主工具为 22 个，inline 三组为 28 个，新增的是 task、artifact_write 及四个 knowledge 工具。三张方法卡本身又声明相同工具集合。因此：前两组与后三组包含工具入口、目录展示等多重差异；即使以后成功加载，这套卡片也不适合证明不同方法之间的动态工具裁剪价值。

### resident：图表子任务和后续验证占据较长路径

第 37 个请求同时派发 SCXML 和图表任务时，没有提供明确写入范围。第二次派发被 WRITE_SCOPE_CONFLICT 拒绝；模型在第 39 个请求取消第一个子任务，第 41 个请求用具体文件范围重新派发两者。

图表子运行用了 80 次请求、126387 个输出 token，占该组总输出 273680 的约 46.2%。它从会话开始约第 429 秒执行到第 1976 秒，跨度约 25.8 分钟；其中模型请求累计约 21.6 分钟。主运行记录的子任务等待为 1354 秒。

图表子任务包含环境检查、渲染器实现、测试和覆盖率补齐，最终主运行又进行了集成验证。该组含 pytest/unittest 字符串的 shell 调用有 57 个，其中主运行 24 个；这只是候选验证调用数，不等于 57 次完整测试执行，也不能据此断言所有复跑均多余。

因此它的较长时间有具体执行路径解释；不能断言是多放了三段常驻方法导致。该组确实成功交付了通过独立验收的补丁。

### skill：更多并行，但有路由和语义问题

该组先用了一个 explorer，再派两个 isolated implementer。两个实现子任务在约第 631 秒同时开始，分别在第 1346、1473 秒结束；主运行没有进入 run.waiting。243 次请求的墙钟时间短于 resident 的 236 次，说明请求数不等于串行轮数。

第 89 个请求把 SCXML 和图表任务分别发给 kodo/backend 和 kodo/frontend，被卡片的 server/、web/ 写入范围拒绝；下一请求改用 kodo/implementer 成功。这暴露了目录适配问题：名册显示“available”并不代表适用于当前仓库布局。应改善适用性展示与派发前校验，保留权限边界。

两个失败验收都是 get_data_changes 的契约问题，详见后文；它们不构成加载机制失败的证据，因为该组没有加载。

### marking：本轮正常完成且全通过的较短路径

其主运行 124 次请求，与 skill 的 122 次相近；主要区别是子请求仅 40 次，而 skill 为 121 次。marking 主运行自己完成核心和图表部分，只最终集成一个 SCXML 隔离子任务。期间取消过一个 shared SCXML 子任务，改用 isolated 执行。

相较 resident，时间减少约 44.9%，总输出从 273680 降至 123618。不过该组的 method.loaded、method.ended 都为 0，不能把这些差异命名为“阶段标记收益”。能够确认的是本次任务拆分和生成工作量更少，最终独立验收全通过。

### checkpoint：后半程的供应商异常非常集中

第 140–166 个请求共 27 次，全部属于主 Agent，占 2998.161 秒墙钟时间，约 50 分钟、全组时间的 66.9%；其中请求本身累计 2867.112 秒，已知输出仅 15239 token。

这段包含 5 次约 180 秒的无有效内容超时、1 次约 286.7 秒的流错误，以及多次等待一两分钟后才开始有效输出。全组原生 model.failed 7 次：1 次 HTTP 502、5 次内容进度超时、1 次请求/流断开，均出现后续重试，最终完成。

首输出中位数只有 7.02 秒，掩盖了后半程的集中长尾；因此不能只用中位数声称供应商正常，也不能把 74.7 分钟解释为检查点开销。此组既没有压缩事件，也没有物理卸载事件。没有足够证据计算“扣掉异常后应该耗时多少”，本报告不做反事实修正。

第 145 次异常流返回 deepseek-v4.1-flash-sg；请求指定的仍是 deepseek-v4.1-flash。该流没有有效工具调用，最终报协议错误且缺失 usage。严格模型标识审计应保留失败，但这也不等于已经证实后续成功工具步骤都由另一模型完成。

### active：串行排队加上最终中断

两个子任务都在约第 452 秒创建，SCXML 在第 460 秒开始，图表直到第 730 秒才开始，恰在 SCXML 完成之后。两者声明的共享写入范围都包括整个 tests/；这与宿主的冲突调度规则一致。图表创建到首请求等待约 277.7 秒。主运行另有四次 TODO_DELEGATED 拒绝，然后等待子任务约 595.3 秒。

第 133 个请求运行了全套本地测试，输出 1463 passed、143 skipped、44 xfailed。第 140–142 次请求连续 HTTP 502，第三次失败后主运行终止，没有主 Agent 的最终交付消息。外部验收对留下的补丁得到 72/72、1286/1286。

所以它提供了“已有补丁达到验收要求，但交付流程没有正常结束”的实例。20分50秒是被中断的观测值，不能作为完整交付速度冠军。更快的首输出中位数和更少输出也提示供应商时段、执行路径都影响比较。

## 验收失败不是覆盖率不足这么简单

### skill 的两项失败

测试先将 s1.count 从 0 改为 5，再转换到 s2。验收器要求新宏步后的 get_data_changes 为空；实际返回两条“退出 s1”和“进入 s2”的记录。

补丁表明它在宏步边界确实调用了 clear_changes，但随后把退出、初始化也记录为数据变更。因此不能简单概括为“忘记清空”。其新增测试也明确断言进入、退出会生成记录，自测与实现共享同一解释，因而能得到新模块 100% 分支覆盖而仍不满足独立契约。

### checkpoint 的五项失败

三个断言属于同一类：未声明 data 的活跃状态返回了空字典 {}，验收器要求 None。状态进入时无条件把 build_defaults 的结果放入存储，与失败输出一致。

另外两个是上述变更记录语义问题。同步测试返回两条记录；异步测试返回四条，连初始化和之前 set_state_data 的记录也保留了。最终补丁只在同步引擎加入 clear_changes，异步引擎的修改没有对应调用，说明还存在同步/异步实现不对称。

这几项应该归纳为“无数据状态的返回契约、生命周期事件是否计入变更、同步异步宏步边界一致性”三类问题，而不是五个互不相关缺陷。原始任务文字对若干边界缺少具体例子，报告评价的是与独立验收的符合程度，不把某一种语义解释宣传为所有场景下唯一合理的设计。

这也给方法包提供了可验证的价值方向：帮助模型识别有歧义的契约，记录所选语义，形成覆盖同步/异步和有/无数据边界的行为表。之后使用不同任务验证此流程，不把本次隐藏验收答案直接灌入后续比较来制造提升。

五组已有很高的缓存读取比例，本轮没有阶段切换破坏缓存的实例。累计输入下降也不是因卸载，因为从未卸载。父子前缀比较事件显示 canonical tools/messages 公共字符前缀仅 19 或 29、工具定义不同；这些是字符诊断，不能转换为缓存 token，但足以说明不能把高缓存率解释为已实现父上下文完整 fork 共享。

计费字段随串行时间段变化：resident 与 skill 已返回字段全为 0；marking 从第 113 次开始有正数；checkpoint 大部分请求有正数，末段又出现 0；active 已返回字段全为 0。可能的网关计费/路由原因不能从这些日志确认。34.29 只是已知字段合计，不能做跨组性价比排名。

relay 常把已完整收到协议终止标志的请求记为 cancelled / CLIENT_DISCONNECTED。这种传输关闭不等于原生模型执行失败；本报告以协议、原生 model.failed 和实际工具调用交叉核对，避免把数百次正常结束误算为故障。

## 对 Kodo 的直接启示

1. **先把方法选择测有效，再评价生命周期。** 统一 skill 与 inline 的目录名称、描述和加载入口；采用具有增量价值且可从任务自身推导的领域流程。自主采用和强制加载正控制分别统计。0/3 方法覆盖不能替代任务级采用率。
2. **给卸载和工具切换设置有效性门槛。** 必须观察到加载、结束、实际请求中的移除和工具视图变化，才将一次运行计入该机制的效果比较。用不同工具合同的方法卡测工具切换；用独立、明确标记的上下文压力场景测检查点，不混入历史任务成绩。
3. **把协作边界变成宿主可见的信息。** 派发前展示路径交集，优先给测试文件明确所有者，目录不适配的 backend/frontend 卡片应显示具体限制。权限拒绝是保护机制，优化方向是更早发现和更准确规划，不是取消约束。
4. **验证应面向行为契约，并绑定代码版本。** 覆盖率补齐不能替代边界语义检查。记录检查结果对应的文件或提交、测试输入和环境，区分必要复跑与重复取证。当前日志只支持指出验证路径较长，不足以把所有重复测试判定为浪费。
5. **区分补丁通过、Agent 完成和用户交付。** active 的例子应在产品状态里明确表达。对可恢复的供应商故障保留已有产物和检查证据，允许从持久化状态恢复；不要把重试耗尽等同于代码不可用。
6. **后续比较控制供应商和样本噪声。** 固定或核实后端模型、交错组别顺序、每格重复运行、保留模型/网络/工具/排队时间分类。对异常运行单独报告，不能删除不利样本后再宣布胜出。

现阶段更有日志支撑的竞争力方向，是让长期任务中的知识、方法、工具和检查证据能被可靠复用，并减少交接和重复工作。本轮证明了原有宿主能支撑复杂交付，也暴露了协作摩擦和完成状态问题；“热插拔方法带来更高质量或更低成本”仍需要机制实际参与后的实验。
