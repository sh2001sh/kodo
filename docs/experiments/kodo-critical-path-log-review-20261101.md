状态帧问题确实存在，但没有对照证据证明它导致了多少推理量，也不能据此说缓存大幅失效：两次状态机主代理输入缓存命中率都约 98%。这轮适合改进“当前状态”的准确性，而不是宣称又找到了一个巨大的缓存瓶颈。

本轮已出现正确的 `COVERAGE_FILE` 默认目录使用，以及 FastAPI applications 子代理跨命令保存转换脚本和原文件；说明持久输出机制本身可用。但同一能力对原生文件工具不可用、主代理仍沿用 `/tmp`，表明调用体验没有完全统一。

**7. 工具、并行和计划的验证情况**

| 问题 | 本轮结论 |
|---|---|
| 工具还很多吗？ | 主代理固定 9 个，工具 JSON 序列化 8,701 字符；实现子代理固定 5 个，3,411 字符。每个运行内逐字节稳定，已达到此前主代理 9k 字符目标 |
| 需要靠继续减工具提速吗？ | 暂无证据。当前反复用的 read/edit/bash/check 边界和环境契约更值得优化；不能把工具定义字符数直接换算成可省墙钟 |
| 并行是否真的发生？ | 原生模型峰值均为 3；至少两个模型同时执行的时间分别约 460.0、213.9、452.2 秒。子任务写入不同文件并分别集成，主代理期间也有自己的实现和验证 |
| 是否仍被全家族写锁串行化？ | 两次状态机没有 lock.waited 事件；FastAPI 仅观察到主工作区内两次后台全套测试与紧随 shell 的锁等待。没有本轮证据支持继续放大并发数 |
| FastAPI 为什么部分串行？ | applications 的 `after: routing` 是主代理声明的依赖，应用层检查确实消费 routing 新接口。可以研究更早确定共享签名/Doc 契约，但直接移除依赖会重演未实现接口检查失败 |
| P0 声明范围校验验证了吗？ | 本轮未发生 TASK_GRAPH_INVALID，也没有 scope 修正。因此只能说未再出现成果丢弃，不能说实测触发并证明了范围纠错规则 |
| P1 保留成果验证了吗？ | FastAPI 三次改 check 后复用原检出，同一代码版本重新验收并集成；没有丢弃成果。scope 扩改路径本轮未触发 |
| P2 重复检查提醒验证了吗？ | r2 仍有一次同版本、不同命令的重复；现有严格相同命令规则覆盖不到。不能宣称重复检查已经解决 |
| P3 环境交接验证了吗？ | 输出目录可跨命令使用，但 cache、Git、工具可用性、原生文件与 shell 边界还有缺口 |

本轮首个模型输出（推理、正文或工具参数最先出现者）的中位延迟为 **6.53、5.63、6.57 秒**，最大值为 **16.94、12.06、11.50 秒**。最长完整请求为 **65.41、41.59、45.32 秒**。没有重演此前 400～700 秒无模型内容的长等待，不能用本轮验证极端内容空闲超时的实际收益。

原统计的 relay 模型峰值为 5、4、4：部分流在原生 `model.finished` 后还延迟关闭，与后续请求重叠。例如状态机 r2 S2 原生调用约 4.16 秒，relay 流约 5.50 秒。该计数描述连接占用，不是调度器同时占用 5 个模型槽。原生事件配对后峰值均为 3，542 个调用均有结束事件。

所有 relay 请求 HTTP 200、协议完成，原生运行全部正常结束。`CLIENT_DISCONNECTED` 大多发生在协议终态后，不能当作网关失败统计。功能验收通过也不等于项目所有质量要求完成：状态机有 Graphviz 条件跳过，ruff/mypy 未执行；FastAPI 原仓库 Git 交付不完整。

**8. 建议的下一轮验收口径**

先修缓存和仅重验流程、真实仓库交付、持久日志读取三类确定性问题，再测量收尾改进。验收至少覆盖：只读源码下 pytest 正常保存缓存；check 更新且代码未变时不启动模型；代码变化后旧验收不能复用；长测试输出可跨命令读取；Git 交付核验原仓库；已恢复的无副作用编辑失败不持续显示为待解决写入。

下一轮仍记录模型调用、工具、后台进程、版本与验收证据，同时报告：首次派发时间、子任务首次有效编辑前的请求数、已知失败首次出现至上报的时间、无代码变更续接次数/费用、首次集成后全套成功至终态的时间、实际全套次数及原因、原仓库分支和提交状态。不能只依赖“同版本重复=0”这个单项指标。

速度上，两次状态机平均约 23.75 分钟，比历史成功格约 46.7 分钟短；但历史网关、模型输出和运行决策有差异，且本轮没有旧版对照。已能确认的是两次功能成功可重复、并行和保留成果路径正常；尚不能给各项优化分配独立的提速百分比。
