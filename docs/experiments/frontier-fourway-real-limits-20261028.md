# FrontierHarness 四方对比：真实模型上限（2026-10-28）

前几轮把上下文限制在 65536、单次输出限制在 8192。本轮不再人为限制，改用 `deepseek-v4.1-flash` 的公开上限：上下文 1,048,576、输出 393,216（[阿里云 Model Studio](https://help.aliyun.com/en/model-studio/deepseek-v4-1-flash)）。任务、网关、容器资源、外部验证器和权限配置都与[第二轮复测](frontier-fourway-repeat-20261028.md)相同。

## 口径

- 运行器新增 `--context-tokens` 和 `--output-tokens` 两个参数，同时传给四个 harness 的启动配置和中继。中继按 `outputTokens` 截断单次输出，本轮上限是 393216。不传这两个参数时默认值不变，旧实验仍可复现。
- Kodo 使用 `--kodo-local`，挂载本地 `dist`，构建清单哈希为 `9bbc1fb2…`，与[效率优化报告](frontier-kodo-merger-optimization-20261028.md)中改后的构建相同。
- 时限用任务原始值：数据题 900 秒，FastAPI 5400 秒，FastAPI 不再截到 1800 秒。
- relay 记录显示，四方请求的 `max_tokens` 均为 393216；没有任何响应以 `length` 结束。网关拒绝或中断的请求在下文逐格列出。

每格都有 1–2 次请求缺少 usage，所以 credit 都是下界。

- **两方全过。** OpenCode 与 Kodo 都拿到 reward 1。DeepSeek Harness 的补丁只差 1 项，但它在最后一次请求遇到网关 520 时以失败退出。
- **Pi 这一格无效。** 第 10、22 次请求流式中断，最后一次报 `malformed server-sent event JSON`，Pi 没有重试。留下的补丁只改了 `fastapi/routing.py`，引用了未定义的 `sunset`，导致 FastAPI 无法导入，原有测试也全部失败。这是网关故障加上不重试造成的半成品，不能算作它的能力结果。
- **放开上限确有影响。** 四方都没再碰到输出截断。前几轮首轮 Pi、第二轮 OpenCode 都是因为输出达到 8192 而没交出补丁。Kodo 单次输出最高到 16,235，已超过旧上限。
- **网关错误的恢复能力不同。** OpenCode、Kodo 遇到错误后都能继续；Pi、DeepSeek Harness 在最后一步遇错就直接结束。这本身是 harness 之间的差异，但这次是外部故障触发的，样本只有一次。

## Kodo 的成本问题

Kodo 与 OpenCode 都全过，但 Kodo 耗时约为 2.2 倍（2442.6 秒对 1092.8 秒），可见 credit 约为 5.7 倍（34.79 对 6.09）。

| 指标 | Kodo | OpenCode | DeepSeek Harness |
|---|---:|---:|---:|
| 平均单次输入 token | 183,321 | 64,738 | 72,526 |
| 单次最大输入 token | 287,392 | 114,548 | 116,393 |
| 首次写文件 | 第 24 次请求，628 秒 | 第 30 次，226 秒 | 第 22 次，227 秒 |
| 输入 token 明显回落（压缩或裁剪） | 0 次 | 0 次 | 0 次 |
| 模型产生的推理 token（全程） | 196,406 | 24,800 | 40,188 |
| 最后一次请求回传的推理内容（字符） | 819,053 | 101,945 | 162,590 |
| 最后一次请求中的工具结果（字符） | 196,693 | 240,658 | 202,410 |

Kodo 的请求数（106）和 OpenCode（110）接近，额外成本几乎全部来自每一步更大的输入。

**更正：** 本报告初稿把原因归为“Kodo 不压缩”，这个归因不成立。逐次请求统计显示，1M 窗口下四方都没有压缩：没有任何一步的输入比上一步少 20% 以上（DeepSeek Harness 第 2 次请求降到 1,009，是一次内部小调用）。OpenCode 和 DeepSeek Harness 的上下文同样一路增长，只是增长得慢。

差别在推理内容。三方都把历史 `reasoning_content` 原样回传，这是 DeepSeek 工具调用多轮对话的做法；工具结果的体量三方相近，Kodo 反而最少。但模型在 Kodo 里产生的推理 token 约是 OpenCode 的 8 倍，早期就有多步单步推理超过 24k 字符。四方请求参数相同（都只设 `max_tokens`/`max_completion_tokens` 和流式 usage，没有推理强度参数），所以推理变多更可能与 Kodo 的提示、运行时状态块或上下文长度有关。目前只确定了差在哪，原因还没验证。

据此，下一项优化不应是调压缩阈值，而是两件事：一是查清 Kodo 为什么引出更多推理，例如对比去掉运行时状态块或缩减工具定义后的单步推理量；二是确认 DeepSeek 是否只要求在同一轮工具循环内回传推理，若是，就可以裁掉更早轮次的推理内容。动手前应先在 FastAPI 上验证，这类改动会不会损失本轮的 137/137。

**后续：** 第一项的消融见[推理量消融报告](frontier-kodo-reasoning-ablation-20261029.md)。去掉状态块或缩减工具都没有降低每步推理，两格均超时、reward 0。另外，10-29 起网关不再把回传推理计入输入 token，很可能已丢弃历史推理，本报告各格的输入 token 与之后的运行不可直接比较。

## Pi 与 DeepSeek Harness 重跑

首轮这两格都受网关故障影响，因此用相同配置（1M 上下文、393216 输出、5400 秒、镜像内固定版本）各重跑一次。运行器的 `--harness` 现在接受逗号分隔列表，本次用的是 `--harness pi,dsh`。

| Harness | 运行 | 秒 | 请求 | 输入 token / 缓存 | 输出 token | credit | 新增测试 | 原有测试 | reward | 结束方式 |
|---|---|---:|---:|---:|---:|---:|---|---|---:|---|
| DeepSeek Harness | 首次 | 1022.3 | 91 | 6,527,351 / 6,457,600 | 63,840 | 至少 6.43 | 136/137 | 3134/3134 | 0 | 最后一次请求 520，退出码 1 |
| DeepSeek Harness | 重跑 | 987.3 | 114 | 7,378,092 / 7,307,776 | 60,674 | 13.12 | 136/137 | 3134/3134 | 0 | 正常完成，退出码 0，无请求出错 |
| Pi | 首次 | 239.7 | 22 | 561,916 / 516,480 | 21,545 | 至少 2.04 | 0/137 | 0/3134 | 0 | 流式中断，未重试 |
| Pi | 重跑 | 155.2 | 20 | 399,815 / 373,120 | 13,054 | 至少 2.47 | 0/137 | 3134/3134 | 0 | 流式中断，未重试 |

- **DeepSeek Harness 的 136/137 是稳定的规格偏差，与网关无关。** 重跑没有任何请求出错、正常退出，结果仍是 136/137，失败的是同一项 `test_nested_include_router_overrides_at_every_level`：多层嵌套 `include_router` 时，内层 `sunset` 没有覆盖外层（期望 `Sun, 15 Jun 2031 12:00:00 GMT`，实际 `Tue, 01 Jan 2030 00:00:00 GMT`）。首次那次 520 只是让进程以失败状态结束，没有改变补丁质量。第二轮 65536 窗口下 Pi 也只在这一项优先级上失败。
- **Pi 两次都在同一种故障上结束。** 重跑第 3 次请求 `fetch failed`（Pi 恢复了），第 20 次请求上游流被中断（relay 记为 `terminated`），Pi 收到半截数据后报 `malformed server-sent event JSON`，日志为 `willRetry: false`，随即结束。补丁仍只改了 `fastapi/routing.py`；这次能导入，原有测试 3134/3134 通过，但新增功能没写完，新增测试 0/137。Kodo 和 OpenCode 在同一网关上也遇到过 `terminated`、`fetch failed` 和 520，都能继续。两次采样里 Pi 都因这一点没完成任务，所以对“流式中断后不重试”的结论比首轮更有把握，但它仍只在这个网关上观察到。
- **上下文与推理。** 重跑同样没有压缩：DeepSeek Harness 最大输入 106,059，Pi 最大 36,649。按每次请求平均的推理 token 计：Kodo 约 1,889，OpenCode 约 228，DeepSeek Harness 两次约 447 和 251，Pi 两次约 783 和 576。Kodo 每步引出的推理仍明显最多。
- **credit 口径再次存疑。** DeepSeek Harness 两次输入 token 只差约 13%，credit 却从 6.43 涨到 13.12。重跑在次日 01:03 UTC 开始，与首次（15:22 UTC）相隔约 9.7 小时。同一 harness、相近 token 量下 credit 接近翻倍，说明网关计价随时段变化的可能性很大；跨时段的 credit 不宜直接比较，token 数更可靠。

## 局限

- 每格采样很少：Kodo、OpenCode 各一次，Pi 与 DeepSeek Harness 各两次。Pi 两次都因流式中断未完成，不能据此判断它在稳定网关上的能力；DeepSeek Harness 两次结果一致。仍不能据此排名。
- credit 是网关返回的额度单位，不是美元；跨轮计价是否一致仍未核实。
- Kodo 用的是本地构建，其他三方用镜像内的固定版本。
