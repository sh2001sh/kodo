# Kodo 效率与并行优化：实现及双构建对照

日期：2026-10-30。状态：方案实现及两格对照完成；实验暴露的三处小修复已应用，最终全量复测通过。改动未提交。

**结论：本轮未达到整体优化目标。** 优化版请求减少，但墙钟增加约 6.9%，已知费用更高、推理更多，外部功能验证从 137/137 降至 131/137。新的并行能力没有被本次模型策略实际采用。不能把机制测试通过、工具数量减少或主运行 completed 表述为效率与质量改善。

## 1. 范围与比较口径

按照 [效率与并行优化方案](../kodo-efficiency-parallel-plan-20261030.md) 完成 P0–P4。用户授权只运行 Kodo，旧版本与优化版各一次 FastAPI，不自动追加、补跑或替换失败格。

证据根目录：`.kodo/efficiency-parallel-20261030/`。基线构建在改动前冻结；两格均使用本轮修正后的 relay 和记录器，模型为 `deepseek-v4.1-flash`，上下文上限 1,048,576、输出上限 393,216，2 CPU、8 GB 内存、5400 秒任务时限。D/E 连同 A/B/C 在两格中均开启。

初始提交固定为 `11614be9021aa4ac078d4d0693a8b5250a1010d8`，初始分支统一为 `main`。两格收到相同任务文本，允许宿主管理的独立副本，最终交付必须集成到 `/app`。这与旧四格的任务环境不完全相同，不与旧四格直接计算优化因果收益。

顺序为基线再优化版。本轮衡量整包改动，不能区分各项改动的独立贡献；网关状态与模型选择的工作策略仍可能混杂。

## 3. 实现边界

- 独立 clone 不是 OS 沙箱。无沙箱任意命令仍保守锁住源仓库家族；Windows 原生沙箱仍有全局写进程互斥。代理生命周期或请求重叠不等于任意 shell 写入并行。
- 副本只包含提交基线，不自动复制源未跟踪文件。前置修改已集成但尚未提交时，后继继续排队并通知主代理；提交后才能准备副本。已准备副本与续接保持基线，依赖换代会通知，不静默改绑。
- 验收摘要来自真实记录，但不把退出码 0、子代理 completed 或报告齐全等同于语义验收。旧提交上的通过结果不能证明新提交。
- 本地取消关闭连接不能证明上游立即停止计算或计费。缺失费用不得记为零。

### 优化版逐日志发现

1. **前期实施没有更早。** 首次任意派发在 381.958 秒，但只是环境与分支任务。首次实际源码修改在 1049.583 秒，比基线晚 68.501 秒；首次成功实施派发在 1096.764 秒，比基线晚约 293 秒。主代理先写好约 100 行参数传播脚本，再交给子代理执行，主要设计仍集中在主代理。
2. **并行能力未转化为实际并行。** 11 个子运行依次启动，全部使用共享工作区，没有创建独立副本。主要源码由主代理使用文件工具修改；子代理主要负责命令、诊断、重复验证和交付。没有复现基线的 LOCK_TIMEOUT 连败，但这同时受分工策略不同影响，不能独立归因为调度修复。
3. **待办验收问题仍存在。** 标完成时补充描述触发新代次，出现模糊的 TODO_ACCEPTANCE。工具数量少了，任务所有权、派发参数及代次规则仍容易用错；错误反馈应直接指出所改字段与合法恢复方式。
4. **事件等待未被正确采用。** 主代理显式传入 300,000 毫秒超时；00:41:01 注册、00:46:01 超时、请求 197 再次调用模型。冻结实现只有省略超时才持续续期，工具说明未明确这一点。本轮没有 `wait.renewed`，不能宣称真实运行已消除定时轮询。
5. **交接没有充分复用事实。** 后续验证者再次收到已经确认不存在的测试文件路径。多次新建验证代理，没有使用续接；完整测试又为提取摘要或逐个确认已定位的同根错误被重复执行。第七个子运行针对缺失 `Message` 导入重复跑三次全套，其中后两次只为提取结果约 100 秒。
6. **通过后继续改动造成返工。** 新测试 24 项与全套 3158 项通过后，主代理又改写中间件与响应头逻辑，引入 `Message` 未导入的回归，造成全套 56 项失败。修复后通过不代表之前的重构成本可以忽略；最后修改、最后验证与最终提交必须分别核对。
7. **缓存不能凭尾部变化归因。** 优化版请求 252 发生接近全量未缓存输入，工具及前 340 条消息与前一主请求相同；基线请求 310 也有同类现象。flat 字段为 0 而 nested 字段仍有少量命中，应表述为接近全量未缓存。没有证据认定状态块改写了公共前缀；网关缓存选择或驱逐原因未知。

两格较长响应的推理流速相近（中位约 173.4 与 171.7 token/秒），不是优化版每个推理 token 明显变慢。全部请求耗时之和略降，但重叠减少使请求在墙钟上的并集增加约 429 秒；这与不同分工策略有关，不能归因于单个功能。

优化版最终源码修改发生于 00:47:09.517 UTC，提交于 00:54:13.407，最后全套验证于 00:56:45.120 结束，最后子运行于 00:57:09.756 结束，主运行于 01:00:18.793 完成（日期均 2026-10-30）。从最后源码修改到主运行完成还有 789.276 秒、72 次请求、11.15 credit；提交之后仍有 365.386 秒、29 次请求、7.32 credit。这些窗口包含关系明显，不可相加。后台测试完成使用实际进程结束事件，不能使用返回后台句柄的时刻。

### 外部质量为什么下降

六项失败集中于两个实现错误，见优化版 `verifier.log` 与 `model.patch`：

- **统计跨实例共享：五项失败。** `_stats` 被声明为类变量，初始化不创建实例统计，统计和重置方法都是类方法。不同中间件实例相互污染，导致 reset、再次统计、跳过非 HTTP、独立统计等检查失败。`get_stats` 实际复制了内层字典，不能误诊为浅拷贝问题。自写的五个中间件用例均先执行类级 reset，掩盖了实例隔离缺陷。
- **多层显式 include 覆盖次序：一项失败。** 每层新加入的显式配置被放到所有已有继承层之前，外层覆盖内层，违反“最近一层优先”的要求。自写测试覆盖单层显式覆盖及无冲突嵌套，却未覆盖多层都显式配置时的冲突。

这说明本轮 24 项自写测试的覆盖弱于任务合同要求。基线自写 115 项也不能仅凭数量判更好，但它通过了相同的外部 137 项功能验证。优化版主运行 completed 与自测通过都不能替代外部质量结果。

## 6. 实验后修复与未测量部分

- 验收委派待办时改写任务归属、描述或依赖，明确说明会更换代次，提示读取原任务并保留字段验收；真正新增工作仍需新代次证据，不放宽验收。

## 7. 后续优化优先级

1. 先恢复质量门槛：验收按合同的独立边界场景组织，重点覆盖实例隔离、嵌套优先级和重置等交互；不要让模型为证明自己当前实现而写测试。通过后只为具体未满足要求继续修改，避免无必要重构。
2. 把任务状态更新做得容易正确调用，优先消除已观察的代次、所有权和等待参数纠错；当前三处小修复只是第一步，真实模型是否采纳尚未验证。
3. 复用同一实施/验证 owner 的续接，把已知失败路径、有效命令和当前版本结果带入交接；一次执行保存完整输出与摘要，后续读取已有结果。
4. 分清直接执行与协作任务。普通命令不应为了形式上的角色划分反复创建新代理；真正独立的工作才提前派发，不先由主代理把完整实现写完再让子代理执行。先证明两个独立实施者产生有用重叠，再增加人数。
5. 工具继续按职责精简，保持每个运行的集合稳定，但不再把数量作为首要验收指标。当前主代理 24 个入口仍多于原目标 8–12 个；下一步应以完整交付、纠错轮数、总上下文与实际成本决定收缩，而不是继续增加通用工具。

本轮只做了授权的两格，没有自动补跑。进一步变更的稳定效果仍需后续独立对照验证，不能由本次失败样本反推已达到目标。
