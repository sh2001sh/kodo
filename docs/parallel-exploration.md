# Kodo 并行探索与项目知识方案

日期：2026-10-22  
状态：A–C 最小闭环已实现，按用户要求默认开启并保留宿主显式关闭选项；D 的确定性验收与对照脚本已提供，真实模型收益尚未验证。当前契约和启用方式见第 11 节。

## 1. 目标与设计结论

让主代理在值得隔离的问题上创建探索 Agent，把探索结果保存为可复核、可按需复用的项目知识，减少主代理重复阅读与后续任务重新理解项目的成本。

采用以下执行方式：

> 浅层定位 → 查询已有知识 → 识别独立问题 → 批量读取或分派探索 → 按需采用结论 → 实现与验收 → 更新受影响知识。

这些动作可以交错进行，不要求先探索完整个项目才能动手。主代理始终负责用户交互、关键取舍和交付；探索 Agent 负责有边界的调查。首版不增加独立规划 Agent、全仓预扫描、向量数据库、知识图谱、多级递归委派或通用工作流引擎。

核心决策：**值得拥有独立调查过程和上下文，且答案有明确用途的问题，才创建 Agent；只需读取几个已知文件时，批量调用工具。**

## 2. 依据与现有边界

依据 [前端对照报告](frontend-harness-comparison.md)、[协作收益对照](collaboration-benefit.md)及 2026-10-22 的代码核对：

- 指定委派已经证明创建、消息、等待、证据核验和子产物采用链路可用；自主委派仍未得到可靠验证。
- 前端实验长任务只安装了通用卡片，不能据此评价专用 Agent 的选择收益。
- 短任务多出的开销主要是模型往返、探索碎片化、测试返工和额外报告。并行探索不能成为小任务新的固定成本。
- 已有 `spawn_agent`、`send_message`、`wait_for_events`、`inspect_run`、卡片检索和有界 `update_progress`；复用这些能力。
- `artifact.read` 目前按会话授权，任务进度按运行历史维护；两者都不能直接冒充跨会话、可失效的项目知识。
- 本机已支持 Skills、MCP 和能力包，但实际探索能使用什么，取决于选定卡片、宿主绑定及授权。不能把支持扩展协议等同于已安装专家。

本方案将主代理选定的探索分工交给宿主落实，属于**宿主辅助的自主编排**。运行时不凭任务文字自行推测分工，不把这种模式的创建率与原生自主调用 `spawn_agent` 混为一谈。

## 3. 何时创建 Agent

### 3.1 三种执行粒度

| 输入形态 | 执行方式 | 示例 |
| --- | --- | --- |
| 路径已知，读取结果服务于同一个局部判断 | 主代理批量调用工具 | 读取分页函数、调用方和回归测试 |
| 一个问题需要连续搜索、阅读和判断，且可与其他工作隔离 | 独立探索 Agent | 追踪持久化格式及损坏数据恢复路径 |
| 后一个问题需要前一个问题的结论 | 先解决依赖，再决定执行者 | 先确认数据契约，再制定迁移方案 |

批量工具调用只减少模型往返，不保证现有运行时会同时执行每个工具。首版不为此放开任意工具并行；跨 Agent 的模型并发仍由现有调度器控制。

### 3.2 创建规则

先检查四个必要条件：

1. **问题有边界：**有明确问题、入口和停止条件。
2. **输入与能力齐备：**已知所需事实可以传入，读取权限和工具可用；不能把缺用户决定的问题交给子代理猜测。
3. **结果有消费者：**明确它将支持哪个实现、验证或取舍，或直接交付用户要求的调查结论。
4. **没有已有答案或重复负责人：**可用知识不存在或需要复核，也没有相同问题在运行。

满足必要条件后，出现以下任意一种理由，可以选择委派：

- **并行收益：**另有可推进工作，且本问题需要多步调查；不会创建后让主代理立即无事等待。
- **上下文隔离：**局部调查预计会引入大量与主任务其他部分无关的资料，只需返回少量约束。
- **专用能力：**已安装 Agent 拥有当前主代理未加载的技能、工具或专业方法，并适用于此问题。
- **独立核对：**存在具体高风险假设，需要由独立上下文核验；明确标记为复核，避免误认为普通重复工作。

以下情况默认直接处理：一两次定向读取即可解决；已取得所需答案；必须与当前修改高度交织；传递任务本身接近直接完成的工作量。并发或累计预算不足时明确返回限制，不静默创建、不静默改变执行者。

不按文件数、任务时长、上下文百分比设固定创建阈值，也不要求最少一个子代理。上述理由由模型判断，运行时只能验证可执行性，不能证明收益为正。

### 3.3 判断时机与可靠性边界

- 开始：主代理批量读取入口与必要配置，结合已有项目知识做浅层定位，避免先读完整个仓库再考虑分工。
- 出现多个独立未知问题时：提交一次结构化探索分工。
- 范围扩大、已委派问题出现新分支或持续受阻时：只重判新增问题。
- 已确定局部修复方法的小任务：不调用探索计划，不新增规划模型轮次。

复杂任务的“哪些问题值得拆分”仍依赖主代理。结构化分工消除的是**已决定委派却没有执行**的缺口，不保证模型一定发现全部机会。实测必须分别统计问题识别、委派选择、实际创建和结果采用，不能只看创建数。

## 4. 最小执行协议

### 4.1 提交探索分工

新增一个仅主代理可调用的 `exploration.plan`，用于有独立探索问题的任务。复用已有运行和事件体系，不新建规划 Agent。每次提交是一个增量批次，最多 4 个问题；这是输入边界，不是人数目标。

```json
{
  "batch_id": "storage-and-ui",
  "decision_version": 0,
  "questions": [
    {
      "id": "storage-contract",
      "question": "哪些存储格式和恢复行为必须保持兼容？",
      "inputs": ["src/storage.js", "src/model.js"],
      "consumer": "存储模块修改和集成验收",
      "deliverable": "接口约束、恢复路径、来源和未确定事项",
      "execution": "child",
      "reason": "需追踪独立读写链，可与主代理界面调查并行",
      "read_scope": ["src", "tests", "package.json"],
      "knowledge_refs": []
    }
  ]
}
```

字段契约：

- `execution` 为 `main | child | reuse | deferred`。`main` 由主代理直接调查；`reuse` 必须指定知识条目版本；`deferred` 说明缺少的输入或依赖问题 ID。
- `child` 必须具备当前可用输入，不允许携带未完成依赖。未就绪问题只记录，不创建占用名额的等待子代理。
- 专用 Agent 可提供已登记的 `card_id/card_version`；省略时使用受限的通用探索执行方式。`agent.route` 只负责候选发现，不必为了通用只读调查额外查询空专家库。
- 新执行方式给定权限不超过父运行；首版探索仅允许范围内的文件读取、搜索及已批准且可限制副作用的代码导航。默认不授予通用 `exec`、源码写入或联网能力。
- 除知识引用外，任务必须包含足以理解问题的具体输入，不复制完整主代理历史。

### 4.2 原子分派与恢复

`exploration.plan` 不是只保存一张计划表：对 `child` 项，内部复用 `spawn_agent` 的创建检查和初始上下文构造，在同一存储事务中记录分工、创建子运行并绑定问题 ID。不得绕过现有权限、卡片版本、预算及消息校验。

首版一个批次全部预校验后再提交；任一项非法则不创建任何子运行，返回明确原因。已提交批次按 `(mainRunId, decisionVersion, batch_id)` 幂等处理；相同 ID 不同内容拒绝，重复提交返回原子运行映射，避免重启重复创建。

精确问题 ID 的重复分派由运行时拒绝；语义相近的问题由主代理合并，首版不宣称实现语义级自动去重。并行复核使用独立问题 ID 并注明复核对象。

新子运行继续进入现有队列和共享预算，不能突破 `maxChildren` 或 `maxConcurrentModels`。当前默认并发为 2：主代理推进一支、一个探索 Agent 推进另一支；若主代理等待，空闲槽位可执行其他已就绪子运行。创建数上限与模型并发上限分别计算。

主代理不重复读取已分派范围来“等结果”。需要该答案时调用现有等待机制；只缺局部事实时通过消息询问。失败返回失败证据、已有发现及未解决项，主代理选择接手、缩小范围或重新分派；没有隐式无限重试。

用户改变目标后，旧版本未开始的探索停止分派；进行中的结果标为旧决定来源，由主代理判断是否仍相关。任何旧结果不能自动结束新任务。

### 4.3 探索结束契约

探索 Agent 的终态输出使用固定 JSON 结构，包含问题 ID、简短结论、事实、证据引用、推测及未解决项。运行时解析并校验后自动保存为候选知识，并向主代理发送条目引用和有界摘要；不再要求调用 `artifact.write` 重写同一份报告。

专用探索运行通过创建时的结果契约启用该格式；普通编码、问答运行保持现有最终答复格式。结构错误或引用不存在时复用有限纠正机制，耗尽后明确失败。能解析不代表语义正确；未解决项不能被标成已回答。

主代理通过 `inspect_run` 核实关键事实，采用时指定知识版本及用途。复用 `update_progress` 的可选 `knowledge_uses` 字段记录采用，不额外生成长报告，也不把知识正文注入进度快照。

## 5. 项目知识资产

### 5.1 保存对象与范围

首版保存接口契约、模块职责、入口与调用关系、验证方法和已知限制。任务进度、长日志、临时试错记录保留在原运行中；只有对后续任务有明确用途的发现才进入可复用知识索引。

```json
{
  "schema_version": 1,
  "id": "storage-contract",
  "revision": 1,
  "project_id": "host-assigned-project-id",
  "question": "持久化格式及恢复行为有哪些约束？",
  "summary": "loadTickets 负责加载和损坏数据回退；迁移要求尚未确认。",
  "scope": ["src/storage.js", "src/model.js"],
  "claims": [
    {
      "text": "损坏存档会回退到种子数据。",
      "basis": "source_observation",
      "evidence_ids": ["evidence-1"]
    }
  ],
  "hypotheses": [],
  "open_questions": ["旧版本存档是否必须迁移？"],
  "dependencies": [
    {"path": "src/storage.js", "sha256": "<runtime-recorded-content-hash>"}
  ],
  "source_run_id": "<runtime-assigned>",
  "source_decision_version": 0
}
```

示例中的宿主身份、版本、来源、时间和依赖哈希由运行时从实际读取及工具证据补全，不能相信模型自报的来源。`basis` 区分源码观察、执行证据和推测；没有匹配证据的事实退回纠正或列为推测。

知识条目使用不可变版本。相同主题的新发现生成新版本，旧版本不被覆盖。两份结论冲突时保留冲突，不能按“最后写入获胜”静默替换；采用某一版本需要记录依据。采用仅说明用于某个决定，不代表永久正确。

### 5.2 新鲜度与正确性分开

新鲜度派生为 `current | stale | unknown`，只描述依赖是否仍匹配，不代表结论正确。

- 使用前检查相关文件内容哈希，包括未提交改动；Git 提交号不足以代表当前状态。
- 已知文件被修改、删除或重命名，条目标为待复核；再次使用前定向核实。
- 外部修改可能绕过工具事件，因此写入通知只是提前标记的优化，不能代替读取时校验。
- 一个结论涉及多个文件时，收集结束前复核全部依赖；中途变化的结果标为 `unknown`，不能拼成“同一版本项目”的确定结论。
- “没有其他调用方”等否定结论须绑定搜索根、过滤条件及范围清单指纹；新增文件可能使其失效。无法取得完整范围证据时不提升为跨任务有效事实。
- 执行结果记录源码指纹、命令、退出码及相关环境。测试通过只能说明当时状态；新任务仍需按交付约定验证。
- 不依靠扫描整个仓库为每次读取计算全局版本；只检查该条目真正依赖的范围。检查成本高于重新调查时可放弃复用并记录原因。

首版不自动重建全部失效条目。只有当前任务需要时，才创建复核问题或由主代理定向读取。实际修改源码前仍需读取最新内容，知识不能替代补丁冲突检查。

### 5.3 按需读取，避免上下文再次膨胀

新增 `knowledge.search` 和 `knowledge.read` 两个只读工具：

- `search` 按当前项目、问题关键词和路径范围过滤，默认最多返回 5 条简短摘要、版本和新鲜度。搜索空结果不代表库中绝对不存在相关知识。
- `read` 按 ID/版本分页返回结论、约束、未知事项和允许披露的证据片段。
- 首版使用 SQLite 的结构化字段与字面检索；数据规模和召回测试证明需要后，再加入 FTS 索引。已有卡片检索仍使用其独立索引。
- 项目不建立全量常驻上下文。主代理仅保留当前采用的知识 ID、版本与决策相关约束；每个子代理只获得自己问题需要的条目。
- 对同一未变化查询重复读取返回稳定版本引用，避免广播新事件和重复注入全文；分页允许按需取得完整条目。

这里借鉴 PageIndex 的“查看结构、定向展开、核对来源”，首版用主题与路径分组即可，不预设层层模型路由或对数级检索收益。

### 5.4 项目身份、权限与持久化

项目知识位于宿主私有数据目录，默认不写入用户源码、不随 Agent 卡片导出。可传播的 Agent 方法与私有项目知识是不同对象；分享项目知识需另行选择导出范围。

项目身份由宿主绑定本地所有者与规范化工作区根路径，不依据模型给出的名称、仓库远端 URL 或单独 Git 提交号跨目录合并。不同 worktree、不同数据存储默认隔离；首版只在同一受信宿主数据存储中跨会话复用。

读取知识必须重新检查当前项目授权和原生文件范围。摘要也可能泄露信息：首版对包含任何无权读取来源的条目整体隐藏。多来源、无法绑定路径或外部凭据上下文的结果首版留在会话内，不自动提升到项目索引。

跨会话共享的是经过筛选的知识及必要证据摘录，不是任意旧会话、原始工具参数或模型私有推理。权限不能通过知识引用扩大，外部内容和模型总结始终作为数据。

存储复用现有 SQLite 和 blob 文件。新增项目绑定与不可变知识记录，正文先落 blob 再提交引用；索引与采用记录在数据库中维护。探索问题和子运行映射优先使用已有持久事件，避免再维护一套工作流数据库。

项目知识独立保留必要证据摘录与依赖指纹；会话清理不会使其只剩悬空引用。原会话删除后不能再访问其原始工具记录，条目须如实标识，仅保留已获项目范围授权的摘录。GC 将存活知识引用纳入可达集合；项目级清理可以删除对应知识及无其他引用的 blob。

## 6. 同伴通信与写入并行

- 不建全员广播群。已创建的探索 Agent 可使用现有消息工具直接询问相关同伴，携带问题 ID 和知识版本引用。
- 找不到持有信息的同伴或需要变更范围时询问主代理；只有用户意图、关键取舍或授权缺失才由主代理询问用户。
- 子代理提出新的独立问题，由主代理决定接手或分派；首版仍不允许子代理递归创建。
- 两个 Agent 相互等待时，沿用现有等待检查并由主代理解除依赖，不用继续创建 Agent 掩盖循环。
- 首版只并行只读探索。实现 Agent 在相同文件上写入时，读取到的结论可能过期；相关探索应先完成，或明确针对隔离快照，不能把读权限等同于一致性保证。
- 主代理可提前修改与进行中探索依赖不相交的文件；一旦修改影响探索依赖，标记该问题需要复核，再决定暂停或重查。

## 7. 两个贯穿示例

### 7.1 分页短任务

1. 批量读取已知函数、调用方、任务要求和现有测试。
2. 已有知识如未在上下文中，不强制为小任务增加一次查询；明确知道入口时直接读取。
3. 直接修改与验证，不调用 `exploration.plan`，不创建 Agent、不额外生成项目报告。
4. 若修改触及已有知识依赖，由宿主标记待复核；本次无复用价值的细节不入库。

目标是减少模型往返，不能把结构化资产建设变成每次修函数的固定成本。

### 7.2 前端发布台长任务

1. 主代理批量定位目录、入口、模型导出及现有命令。
2. 主代理调查交互与页面结构；创建一个只读 Agent 调查存储和数据契约。验证问题如依赖契约，先记录为待处理，不急于创建第三个执行者。
3. 存储 Agent 返回契约、来源与未知项，运行时保存候选条目；主代理核对关键事实后采用。
4. 已确定边界的实现开始。需要独立测试调查时，再创建有明确输入的探索或验证任务。
5. 主代理承担最新集成验证和最终交付；项目知识不替代验收。
6. 后续存储相关任务按需检索该条目，校验哈希后复用；源码变化只复核受影响结论。

示例不是固定前端流水线。真实任务可以选择全部直做，必须保留选择依据和结果，以验证规则是否有效。

## 8. 实施拆分与代码边界

| 批次 | 交付内容 | 主要代码位置 | 退出条件 |
| --- | --- | --- | --- |
| A：落实分工 | `exploration.plan`、只读探索任务契约、幂等创建及问题状态 | `src/messaging/index.ts`、`src/runtime/types.ts`、`src/runtime/coordinator.ts`；复杂逻辑按需抽出 `src/runtime/exploration.ts` | 一次主代理决定能可靠形成受限子任务；重启不重复创建；小任务入口不增加固定调用 |
| B：保存与采用 | 结构化结果解析、候选条目、依赖哈希、有限纠正、采用引用 | `src/runtime/coordinator.ts`、`src/runtime/context.ts`、`src/storage/index.ts` | 结果自动落盘，不需再写报告；无依据、冲突、过期结果不会成为已验证事实 |
| C：跨任务复用 | 项目绑定、知识检索和分页读取、授权、失效、GC | `src/application/index.ts`、`src/storage/index.ts`；知识规则集中在 `src/knowledge/` | 同项目后续任务可复用；无权项目不可读取；源码变化能阻止直接沿用旧结论 |
| D：实测与启用 | 原执行方式、并行探索、知识复用对照；CLI/Web 展示现有事件摘要 | `scripts/comparison/`、`tests/`、现有 CLI/Web 事件消费者 | 确定性验收通过，并如实报告真实模型的质量、成本及限制 |

新增探索处理模块是为了隔离分派和结果契约，新增知识模块是为了统一跨会话授权与失效规则；不引入独立服务。每批变更同步完成其调用方、Schema、持久化迁移和文档，不先暴露不可用工具。

按用户要求默认开启，宿主可用 `exploration: false` 显式关闭，不增加面向所有用户的大量策略参数。现有 `spawn_agent` 继续支持一般委派，`exploration.plan` 是同一创建能力的有界编排入口；是否使用由主代理按任务价值判断。

## 9. 验收方案

### 9.1 确定性测试

| 场景 | 必须观察到的结果 |
| --- | --- |
| 并发子任务与主任务 | 实际模型调用可重叠，且不超过共享槽位；不只检查存在两个运行 |
| 重复提交、崩溃恢复 | 相同分工只创建一次；中途失败不会留下一半未登记子任务 |
| 未就绪、预算不足、越权、无效卡片 | 不产生违规子运行；返回具体限制且无静默替换 |
| 只读探索 | 原生写工具、通用进程执行不能通过继承卡片重新获得 |
| 非法结果、伪造证据、连续失败 | 有限纠正；耗尽明确失败；未回答问题不伪装为完成 |
| 相同问题重复分派 | 拒绝或返回既有负责人；指定独立复核可保留 |
| 相关文件变化、外部修改、搜索范围新增文件 | 对应知识变为 stale/unknown，使用前复核 |
| 无关文件变化 | 不触发全库重建；相关条目可按其依赖继续使用 |
| 权限收窄、跨项目读取、会话 GC | 摘要和证据均遵循当前权限；存活知识无悬空 blob |
| 用户改变目标、取消、晚到结果 | 不自动采用旧决定结果，不恢复已取消运行 |
| 模型提供合法结构但错误事实 | 结构通过不等于事实验收通过；独立语义验收能够判错 |

### 9.2 真实模型实验

先做三类任务：已知入口的短修复；有独立调查分支的真实长任务；使用相同项目知识的后续任务。后续任务同时包含“依赖未变化”和“依赖已变化”两种情况。

对照方式：

- 基线：现有执行方式，不接入新探索编排和项目知识。
- 并行探索：接入结构化分工和本次探索资产，运行前清空可复用项目知识。
- 知识复用：使用同一前置任务形成的知识，执行新的后续目标；对照组在相同源码和目标上从空知识开始。

每种方式冻结模型、工具、源码、资源和任务验收；同一任务至少 3 次用于发现不稳定性，并交错顺序。单任务少量重复仅作探索，不宣称统计显著性。所有失败、恢复、额外调用和缺失用量保留。指定委派正控制单列，不计自主选择成功。

记录以下指标：

1. 交付质量、范围和最终答复完整性。
2. 独立问题识别、委派决定、创建成功、有用结果采用各自的数量；不以子代理数替代成功。
3. 端到端时间、模型请求数、累计费用和 token、主代理输入峰值。
4. 相同文件内容版本的重复读取、主子重复探索范围、等待期间可用工作是否被推进。
5. 资产生成、校验和复核成本；后续任务节省的读取与模型调用。
6. 错误或过期知识导致的错误决定；主代理是否需要重读全部资料才能采用结果。

上线判断：确定性检查必须全部通过；短任务不得出现机制强制新增的规划、资产写入或子代理调用；真实任务的隐藏验收不降低，并观察到可重复的定位时间或主代理上下文改善。若费用增加，必须同时说明换来的收益，不能只报速度。没有收益时先缩小探索边界和结果体积，不增加创建配额。

## 10. 完成定义与后续扩展

最小闭环是：**主代理识别独立问题 → 实际分派 → 子代理调查 → 结构化证据自动落盘 → 主代理采用 → 下一任务按需复用 → 源码变化后正确复核。**

探索资产不会自动变成通用 Agent 的能力改进。经过多个案例验证的方法可以另行提炼为技能或卡片版本；项目私有事实不随之传播。团队共享、多工作区知识映射、自动聚类、全局语义检索及递归委派，都等待当前闭环的收益和失败数据后再决定。

## 11. 当前实现与启用

应用 API、普通 CLI／Web 默认开启，无需传入探索选项：

```js
const app = new Application(dataDirectory, provider);
const run = app.createRun({ objective, workspace, binding, permissions: ['read', 'write'] });
await app.run(run.id);
```

省略 `exploration` 或传入 `true` 时，使用当前操作系统用户作为所有者；宿主可传入 `{ exploration: { ownerId: 'local-owner' } }` 指定所有者，或 `{ exploration: false }` 关闭探索与知识工具。同一数据存储、所有者和规范化工作区根目录的知识可跨会话读取；不同 worktree 默认隔离。启用后未指定卡片的主运行使用 `builtin/exploration-main@1.0.0`，自定义卡片需自行允许 `knowledge.search`／`knowledge.read`。已有运行保留其冻结卡片，不自动增加知识工具。`exploration.plan` 只对已启用宿主的主运行开放，不要求小任务调用它。数据库自动迁移到版本 4；知识正文及完整的有界读取页保存在私有 blob 中，不进入源码和能力包。

分派问题使用第 4.1 节的字段；延后项可在依赖就绪后以相同问题和消费者提交新批次转为执行，已有负责人不能重复分派。探索运行仅保留 `file.read`、`file.list`、`file.search`、`image.read`，并清除继承的技能；首版未开放专用 LSP、MCP 或执行证据的知识提炼。

探索终态必须返回以下 JSON，不使用 Markdown 围栏。`evidence_ids` 是通过 `inspect_run` 获取的本运行成功 `file.read` 调用 ID；模型请求内的工具 ID 不可替代它：

```json
{
  "question_id": "storage-contract",
  "summary": "简短结论及不确定性",
  "claims": [{
    "text": "直接观察的源码行为",
    "basis": "source_observation",
    "evidence_ids": ["runtime-model-call-id:read-source"]
  }],
  "hypotheses": [],
  "open_questions": []
}
```

非法结构或不匹配证据最多纠正两次，耗尽后明确失败。无证据结果必须说明未解决项，仅保留在源会话内。合法结果在运行完成事务中自动保存并通知主代理知识版本；正文一直标为 `candidate`，哈希匹配和结构通过均不等于语义验收。原会话被清理后，独立保留的来源摘录仍可分页读取，但不再暴露已删除的原调用记录。当前只保存源码观察；搜索结果不足以证明“没有其他调用方”，此类结论应保留为推测或未解决项。

采用时通过 `update_progress` 的 `knowledge_uses` 传入 `{id, revision, purpose}`。运行时重新检查项目、所有来源路径及真实路径权限、文件哈希和同会话决定版本；过期、未知或旧决定结果拒绝直接采用。宿主也可调用 `app.updateProgress`。所有版本都保留，首次相同用途采用产生 `knowledge.used`；它只表示本次用途，不提升为永久正确。宿主的 `app.coordinator.knowledge.clearProject(runId)` 可清理当前项目知识，后续 GC 回收无引用正文。

验证及对照入口：

```powershell
npm run check
npm test
npm run test:assessment
node 'scripts/benchmark-exploration.mjs'
node 'scripts/benchmark-exploration.mjs' --scripted
```

不带参数只打印实验矩阵，不访问模型。`--scripted` 在隔离的微型 ESM 源码任务上检验完整链路和独立行为验收，不代表真实模型收益。矩阵含短修复、独立分支、知识未变化和依赖变化的后续任务；基线、并行探索、知识复用交错运行，每组至少三次。复用前置调查属于指定委派正控制，成本单列并计入总开销。报告保留失败、缺失用量、创建与采用分别计数、原始证据和独立验收结果。

真实实验需显式选择模型和凭据环境变量，例如：

```powershell
node 'scripts/benchmark-exploration.mjs' --live --model 'MODEL' --endpoint 'https://provider.example/v1' --key-env 'KODO_API_KEY' --protocol 'responses'
```

当前按用户要求默认开启，但尚未运行上述真实模型矩阵；微型任务不能替代真实项目长任务验收，质量、费用和定位收益仍需真实模型实验验证。
