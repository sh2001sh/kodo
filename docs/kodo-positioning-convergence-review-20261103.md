## 0. 结论先行

1. **定位选 11-02/11-03 的方向**：面向重复性数字工作的本地 AI 工作台（技术上仍是通用 Agent harness）。10-19 的「以 Agent 为单位共享工作流」不能作为对外定位，应降为内核能力——证据是自主委派 7 轮 0 次、并行/团队配置无稳定收益（[handoff ablation](experiments/kodo-handoff-ablation-20261030.md)、[fourway-isolated](experiments/kodo-fourway-isolated-20261101.md)、[lean-team](experiments/kodo-lean-team-statemachine-20261031-r1.md)）。
2. **第一卖点应是「交付可信」，不是「多 Agent」也不是「方法复用」本身**。方法复用是情感钩子和长期资产；但现有代码里最扎实、用户最能感知、竞品最难直接复制的部分，是「结果旁边说清核过什么、没核什么、依据哪版方法」（已有 `quality.status`、`not_checked`、check + decisionVersion、冻结案例与采用记录）。三个特色建议按「可感知强度」排序：交付可信 > 纠正被记住 > 改前先验证。
3. **跑偏的根因不是文案，是两处结构性错位**：
   - **验证错位**：43 份实验 0 份是非编码任务；产品假设「第二次任务人工纠正下降」从未被测量（D2/D3/D10）。
   - **对象错位**：产品说「方法」，代码的一等对象是「Agent 卡片」；保存做法保存出来的是另一个子 Agent，不携带 Skills/MCP、也不声明 inline（D7）。
4. **当前最该做的不是继续建机制**：P1–P4 已实现且默认关闭，通用方法在真实运行中加载 0/8、0/4，专属方法 2/2——机制只有在「方法装了模型不知道的信息」时才可能被用到。冻结机制开发，先打通一个非编码闭环，用 4 期材料证明纠正次数下降。
5. **需要用户拍板的 5 件事**见 §8；未拍板前，工程上只做「不改变定位的 P0」：修 G7 稳定性、统一叙述与人设、冻结机制实验。

## 1. 三版定位的证据裁决

| 版本 | 原话 | 证据怎么说 | 裁决 |
|---|---|---|---|
| 10-19 设计方案 | 「以 Agent 为单位，共享和运行工作流的轻量 Harness」；主 Agent 组织子 Agent 协作（design.md:19,35） | 自主委派 7 轮实质任务为 0（[阶段能力设计](kodo-stage-capability-design-20261103.md):215 引 [team-lead retest](experiments/agent-delegation-team-lead-retest-20261028.md)）；指定分工能并行但更贵（RD 墙钟 +48.2%、费用 2.05×，handoff ablation）；团队配置快慢互见、不能宣称普遍更优（lean-team-fastapi） | **不作为对外定位**；多 Agent 保留为内核执行选择 |
| 11-02 通用任务定位 | 「处理重复性数字工作的 AI 工作台：把工作做成，把做法留下」；三个核心能力：一次工作形成方法 / 让用户知道为什么可用 / 工具输入变化后保留工作（p02:7,9,13,45-81） | 三个能力方向都有代码底座（卡片、案例、质量状态、恢复），但**核心价值假设（第二次及后续人工时间下降）0 次实验**；非编码任务 0 次 | **采用为定位**；价值假设待验证 |
| 11-03 阶段能力 | 专业能力随阶段加载、卸载（stage design） | 通用方法自主加载 0/8（五臂）、0/6（十格）；专属方法合成任务 2/2（[discovery](experiments/kodo-method-discovery-20261103.md)）；卸载/工具切换 0 次触发 | **是实现机制，不是定位**；只能作为「方法装什么」的设计原则 |

**一句话定位（建议对外固定）**：
> **Kodo 让 AI 学会你的做事方法——纠正一次，下次照做，改了能验证。**
> 产品类别：面向重复性数字工作的本地 AI 工作台。技术上仍是通用 Agent harness。

- 首批用户：每周反复整理多源资料、产出固定格式交付物、需要核对口径与来源的个人和小团队。编码用户由 CLI/TUI 继续服务，不作为首批验证对象。
- 首批场景（建议只选一个）：周期业务简报 / 客户反馈整理 / 报价比较。三者的可得材料、频率、验收可机械化程度差别很大，**建议先选「周期业务简报」**（材料易得、周期明确、汇总与来源检查可机械断言），另两个作为第二批。
- 品牌释义：Know · Organize · Do 保留；Organize 从「组织协作」改释为「把做法整理成方法」。
- 非目标（明确写进 README，防止再漂）：不做通用多 Agent 平台卖点；不做固定流程/可视化编排器；不做社区市场（后置）；不承诺自动正确、不承诺所有任务更便宜；不把 token 节省当卖点。

## 2. 产品特色（按可感知强度排序）

| # | 特色 | 用户看到什么 | 依赖的现有能力 | 现状 | 证据强度 |
|---|---|---|---|---|---|
| 1 | **交付可信** | 结果旁列出：已核对（总数/来源覆盖/字段完整）、未核对、用了哪版方法、哪些结论是判断 | `quality.status`、`not_checked` 标记、check + decisionVersion + 文件指纹、冻结案例断言 | 底座已交付；缺「按方法规则逐项展示」的交付卡（G6） | **强**：代码已实现、TUI `/check` 已有过期/覆盖提示；只差产品化展示 |
| 2 | **纠正会被记住** | 第一次交付后指出口径错误，系统问「以后同类任务都按这条吗？」；确认后第二次换材料不再犯 | 方法提炼、能力包、案例、采用/回退、inline 方法加载 | 链路断开：没有「纠正→候选规则→问适用范围」实现（G2）；提炼产物是子 Agent 卡且不带依赖（G3） | **弱**：机制片段有，产品链路无 |
| 3 | **改前先验证** | 方法改了，用旧案例和新材料各跑一遍，显示「4/5 → 5/5，可采用」，不合格可回退 | 冻结案例、比较、采用/回退 | 能力完整（CLI/TUI 双入口），但对象是 Agent 版本不是方法版本；Web 无入口（G5/G8） | **中**：机制已交付、未产品化 |
| 4 | **换材料就能复用** | 下一期替换输入直接跑，不重述要求 | 卡片运行、案例冻结输入、方法加载 | 缺业务文件格式（G1）、缺「复用这个方法跑新输入」的产品入口（G10） | **弱** |

基础保障（写在说明里、不作为首屏卖点）：断点续跑、预算上限、多供应商/备用线路、本地权限与沙箱、可追溯记录。

**明确不宣称**（有实验或文档反证）：
- 「多 Agent 更高效」：无稳定证据，指定并行更贵；
- 「更省 token / 更快」：机制未触发、计费字段不可用，无法判定；
- 「重复检查已解决」「委派消除轮询」「覆盖率=契约正确」：均已被实验文档收回；
- 「竞品没有此能力」：**收敛提案中「竞品没有面向普通用户的方法版本对比后采用」需要改写**——[产品上线方案 §6.1](product-launch-plan.md) 自己记录 Claude Code 已有插件评测入口，Pi 已有包分发/SDK。正确表述是：「各竞品有片段能力（插件评测、包分发、规则/记忆）；**面向非开发者、把业务交付＋方法沉淀＋版本验证连成一条可证明人工时间下降的体验**，没有被公开产品验证，这是我们的赌注，不是既有优势。」

## 3. 设计方案（收敛后）

### 3.1 分层

```text
产品面     Web 工作台（非开发者主入口）／TUI・CLI（开发者）／宿主 SDK（嵌入）
────────────────────────────────────────────────────────────
交付层     交付卡（检查结果＋方法版本＋未核对项）／案例与版本比较／采用与回退
方法层     方法（规则/检查/依赖/适用条件）· 能力包 · Skill/MCP 资源 · 项目知识
运行层     单主循环（共享预算、冻结名册、事件与记录、权限与沙箱、压缩与恢复）
────────────────────────────────────────────────────────────
基础设施   阶段挂载/卸载、动态工具视图、动态组装（全部默认关闭，非产品卖点）
```

### 3.2 对象模型的错位（本文最重要的补充）

| 概念 | 产品需要一个稳定对象 | 代码现状 | 后果 |
|---|---|---|---|
| 方法 | **Method**：方法版本、适用条件、必需输入、检查规则、依赖资源、来源纠正 | 没有；「方法」= Agent 卡片的 prompt + 案例 | 无法表达「我的做法」，只能表达「另一个人」 |
| Agent | 执行者配置（方法 + 工具 + 模型 + 报告契约） | Card v2（含 `execution.modes:[inline,child]`，2026-11-03 新增） | 已具备拆分基础，但没有产品流程用它 |
| 交付卡 | **DeliveryCard**：本次交付的已核/未核/依据/方法版本 | 分散在 `Run.quality`、事件、check 记录、artifact | 用户看不到「这一份结果为什么能用」 |
| 案例 | 方法版本的回归用例 | Case（file/json/output/command 断言）已交付 | 可复用，但只有 4 类断言，缺业务断言 |
| 知识 | 带来源/新鲜度的项目事实 | ProjectKnowledge 已交付 | 首次用户感知不到（TUI 无入口，运行中 0 保存） |

**结论**：不需要推翻现有内核；需要**把「方法」提升为一等对象**（或至少：方法产物一律生成 inline 方法卡，携带依赖与检查，案例挂在方法版本上），并把「交付卡」做成运行结束的标准输出。这是比收敛提案 G3「提炼结果是子 Agent 卡」更底层的判断。

### 3.3 闭环与现状

```text
完成任务 → 交付卡 → 用户纠正 → 候选规则(问适用范围) → 方法候选版本
   → 案例比较(旧/新输入) → 采用/回退 → 下一期换材料复用
```

| 步骤 | 现状 | 缺什么 |
|---|---|---|
| 完成任务 | 单主循环可用；编码场景可靠；非编码缺文件格式 | G1 |
| 交付卡 | quality/证据已有，展示未产品化 | G6 |
| 纠正→规则 | 无 | G2 |
| 保存方法 | 有 Agent 草稿/包/案例；不是 inline 方法，不带依赖 | G3、G8 |
| 验证 | 案例比较/采用/回退已交付（CLI/TUI） | G4 业务断言、G5 Web 入口 |
| 复用 | `--card`/`--package` 可重跑；无「同一方法换新材料」流程 | G10 |

### 3.4 产品面策略

- **Web 为主入口**（非开发者）：现状只有任务/证据/协作/恢复/上下文/知识/包诊断七块面板，缺 Agent 库、案例闭环、包导入导出、设置、后台任务——约为承诺的 40%（三套界面对齐表见下）。
- **TUI/CLI 服务开发者**：TUI 已覆盖全部产品能力但界面为英文；CLI 是功能最全的入口（21 主命令 + 5 组子命令）。
- 三套界面共享同一 Application/Store，不新建第三套业务逻辑——这一点代码已做到，不要破坏。

## 6. 收敛提案的核对意见

**同意（不改）**：11-02 为定位、11-03 为机制、10-19「组织协作」降为内核能力；D1–D6；G1–G7；冻结机制实验；先打通一个非编码场景再做 Web；停止条件（纠正次数不降就先改方法与加载）。

**修正（3 处）**：
1. **特色排序**：把「交付可信」提到第一（最能被验证、最贴近现有优势），「方法复用」是长期资产与钩子；不要用「竞品没有」的表述，改为「一体化体验未被验证」。
2. **G3 不够底层**：真正缺的是「方法」这个一等对象（G8），只改 authoring 输出格式而不建方法对象，复用的对象仍然是 Agent。
3. **「冻结机制实验」的边界**：冻结新的机制开发与机制矩阵；但核心实验里保留一次「强制触发的机制消融」（resident / 按需加载 / 无方法，`method.loaded>0` 才算数），用来决定 P1–P4 是保留还是删除。

**补充（新增 D7–D12、G8–G14）**：对象错位、轻量档切断能力、Web 面、度量口径、工具面/协议重做、术语不收敛、周期复用入口、分发与平台。

## 8. 需要用户拍板的 5 个问题

1. **第一卖点**：接受「交付可信」作为第一卖点（方法复用作为长期资产）？还是坚持「学习方法」为第一叙事、交付可信作为证据？
2. **首批场景**：选「周期业务简报」（推荐，机械检查最多）还是「报价比较」（更贴业务判断）？只选一个。
3. **方法对象**：是否同意把「方法」提升为一等对象（改对象模型/界面/包格式，成本中等偏大）？还是先用 inline 方法卡承载、只补依赖与版本（快，但概念仍偏向 Agent）？
4. **多 Agent 的去留**：保留为内核能力但不对普通用户暴露/宣传？还是收缩为「仅独立复核与并行探索」两种触发？
5. **编码用户的定位**：CLI/TUI 继续服务编码用户但不作为首批验证对象——是否接受「同一产品、两批用户、先验证非开发者」的策略？
