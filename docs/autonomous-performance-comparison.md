# Kodo 自主协作条件下的真实任务性能测试

日期：2026-10-20。CodeGo，`deepseek-v4.1-flash`，Chat Completions。四次真实任务均自然结束，未补跑替换，未启动本地模型。

**四次代码交付全部通过独立验收；两次开放协作的任务均未创建子代理。** 当前能证明此负载下的任务完成能力，尚不能证明设计要求的自主分工、同伴问答与并行执行效果。工具可用和模型实际使用必须区分。

## 对照条件

两组使用相同中性任务描述及公共契约：从零实现跨 runtime、Application、CLI 的历史归档目录，增加 README 与两份测试，只允许修改六个指定文件。任务不禁止、不强迫委派，也不指定子代理数量。冻结源码不包含待实现功能。

| 条件 | kodo-auto | kodo-solo |
| --- | --- | --- |
| 创建、列出、通信、等待、询问和取消工具 | 保留原生角色规则 | 不提供，作为单代理对照 |
| 子代理额度 | 产品默认最多 8 个 | 无可用创建工具 |
| 在途模型调用额度 | 产品默认 2 | 1 |
| 任务及验收 | 相同 | 相同 |
| 尝试次数 | 2 | 2 |

顺序为 auto1 → solo1 → solo2 → auto2，任务顺序执行。两组均为模型声明的 **1,000,000 token 输入与输出合并窗口、393,216 最大输出**，所有实际请求都发送最大输出参数。移除基准的请求次数、累计 token、小输出、独立字符、模型请求/响应字节和短任务期限限制；运行时必须为数字的预算使用安全整数或平台计时器上界。工具权限、角色规则、文件/进程输出捕获规则仍然生效。

实际最大单次输入 **134,398 token**，最大单次输出 **10,683 token**。这是使用最大容量配置的真实任务测试，没有填满窗口，也不证明网关的满窗口保持能力或最大输出生成能力。`promptCache: off` 表示不发送客户端会话缓存提示，不表示关闭供应商自动前缀缓存；缓存统计使用供应商实际 usage。

运行前构建、类型检查与 `eslint src tests scripts` 通过；45 项基准计量专项及 41 项协作/生命周期回归通过。测试期间未修改生产内核、任务或验收。四次结束且写入本报告之前，当前源码、冻结副本及 manifest 所列 **89 个文件**全部一致；四份结果和原数据库均未被审计改写。宿主审计子代理只做离线审查，没有调用测试网关，其活动不属于 Kodo 模型自主委派。

HTTP 请求区间峰值均为 2，但只是同一个 run 的响应传输尾部和下一请求重叠。依据可信 run 身份与 `model.started` 至 `model.finished/model.failed` 区间核验，实际模型调用峰值为 1，没有不同 run 的并行工作。不能把 HTTP 连接重叠写成多代理加速。

完整会话采集已经过真实本地内核的脚本供应商测试：主代理派生子代理，子代理执行长输出进程并遇到失败工具，主代理等待后结束；采集器正确还原子代理私有完整输出并包含失败调用、排除其他会话。它证明计量路径能收集协作证据，不能代替本轮真实模型自主协作证据。

本小样本中 auto 平均慢 **22.94%**、总 token 多 **26.77%**，每次贵 **¥0.04535～0.04742**，约 **24.55%～25.78%**。两组均全部成功，当前每次成功的均值等于每次尝试均值。没有丢弃返工或失败；以后若存在失败，应将其消耗另列，不能只平均成功样本。

**费用差不是开子代理导致的，因为子代理请求为零。** auto 的可测缓存率反而略高，差约 0.0674 个百分点；不能用缓存下降解释费用差。两组实现轨迹、输出量和额外自测不同，样本仅各两次，也不能把全部差异归因于工具 schema 开销或宣称稳定的因果关系。auto 的首请求输入均为 2,575，solo 为 1,664，额外工具条件下多 911 token 是可观察的首请求差异，不能代表全部额外成本。

按保存的公开充值价格，每百万非缓存输入 ¥0.50、缓存输入 ¥0.01、输出 ¥2.00：

```text
费用 = ((输入 - 缓存输入) × 0.50 + 缓存输入 × 0.01 + 输出 × 2.00) / 1,000,000
```

每次首请求缺少缓存字段，共四次；因此缓存率分母只使用输入和缓存都已报告的请求，完整费用按缺失部分全部命中到全部未命中给区间。没有将缺字段当成零命中，也没有获取账户实际扣费。HTTP 429 按用户规则为零，本批次实际没有 429。非 429 缺输入或输出 usage 时应保留完整费用未知，本批次未出现。

审计比较同一 run 的相邻请求，204/204 对保留旧消息、工具定义和系统提示；已有思考字段 196/196 对保留、预期的上一响应思考回放 151/151 对齐。未观察到前缀被反复重写导致缓存损失的证据。

## 执行中遇到的问题及结论边界

auto1 曾三次测试非零退出后自行修复，最终全部验证通过。auto2 有一次 `FILE_CURSOR`、两次 `ARTIFACT_CURSOR`；solo1 有一次 `FILE_CURSOR`，均为字符分页位置非法，之后继续完成。工具错误共四次，没有静默吞掉。成功执行的 `process.exec` 即便子进程非零退出，仍可能记为工具执行成功；因此工具失败数不等于测试失败数。非零进程还包括刻意验证 CLI 拒绝路径，不能全部判成缺陷。

solo2 最终报告有一处测试总数排版残留，实际完整输出为 64 项；其功能、验证和范围均通过。没有复现旧批次的空正文提前完成，但本轮没有修复生产结束判定，因此不能据此认定旧缺陷已经修好。

当前设计的“能提供协作工具”有实证，“在合适负载下能主动选择协作并带来收益”仍缺真实证据。优先待验证的是任务分解和委派策略，而不是先增加并发额度。若调整主代理提示或委派策略，应使用新的冻结版本和同负载对照，单独标记受引导的协作实验，不能把强制创建算作本轮自主成功。

本轮直接覆盖真实编程工具闭环、失败后修复、交付及验收；设计中的双子代理直接问答、同伴失败收敛、循环等待、用户中途变更、取消、权限撤销、故障恢复、卡片发现与跨供应商协议性能没有在这四次真实模型任务中完整触发。已有确定性回归可以证明各自检查覆盖的行为，不能把它们汇总成“全部内核真实性能已达标”。

此前的 Pi core / OpenCode 结果仍保留在 [历史最大容量竞品测试](complex-code-comparison.md)。它们是另一冻结版本和明确单代理条件，不能与本轮混合计算胜率、速度或协作收益。
