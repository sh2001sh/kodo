# Kodo 最终产品定位与执行方案

日期：2026-11-03。状态：定位定稿，执行方案待按阶段推进。本文取代同日的 [产品定位收敛](kodo-product-positioning-20261103.md)，并更新 [减法方案](kodo-subtraction-plan-20261103.md) 的加法部分；减法清单仍以该文为准。设计依据包括 Kodo 实测数据和 Anthropic 2026-10-22 文章《Building agents: When to fold subagents into your main agent loop》。

已确定的约束：

- 面向学生和办公人群，覆盖科研与日常工作，不做垂类；
- 与 CodeGo 保持独立；
- 技术特色以动态上下文为主体延伸；
- 手机端打通属于体验优化，和技术创新分开推进、分开验证。

## 1. 产品定位

### 1.1 一句话

> **Kodo 是装在电脑上的 AI 工作助手：在长期、多文件的工作里，它一直记得住、找得到、说得清。**

- **记得住**：一个项目跨天、跨会话、跨设备持续推进，已经读过的材料、做过的决定不会丢，也不会因为压缩而变形。
- **找得到**：几百份文件的项目，用 128k 窗口的便宜模型也能做，因为模型每次只取当前需要的内容。
- **说得清**：每条结论都能追溯到原文位置；每次任务都列出这次用到了哪些材料和决定，哪些已经过期。

### 1.2 用户与场景

| 人群 | 典型任务 |
|---|---|
| 学生与科研人员 | 几十篇文献的方法与结论对比、综述初稿、实验数据整理与作图、论文修改跟踪导师意见 |
| 办公人群 | 多份材料汇总成报告、周期性表格统计、会议纪要与待办整理、方案和报价对比 |

共同特征：材料多、周期长、需要反复回到同一件事上，而且结果要能核对来源。

### 1.3 竞争位置

| 现有选择 | 局限 | Kodo 的位置 |
|---|---|---|
| 云端对话助手 | 文件要逐份上传；会话之间各自独立；长项目靠摘要接续 | 直接处理本地文件夹，项目上下文持久保存 |
| 办公软件内置 AI | 只处理当前这一份文档 | 跨文件、多步骤 |
| 编程 Agent | 能力足够，但门槛高，上下文以线性会话为主 | 不需要懂技术；上下文是可寻址的存储 |

诚实的边界：单项能力别人都有局部实现。Kodo 的特色在于上下文存储这个工程组合，以及面向非技术用户的本地工作体验。这是窗口期，不是技术壁垒；最大的风险是国内大厂推出同类本地桌面 Agent。

## 2. 技术特色：可寻址上下文存储

### 2.1 核心思想

主流 harness 的上下文是一份线性记录：不断追加，窗口快满时压缩，压缩后细节就永久丢失；子 Agent 交回来的也只是摘要。

Kodo 把上下文看作一个**持久、可寻址、可校验新鲜度的存储**。主上下文只放少量必需内容和一份索引，其余内容由模型通过工具按需取用。这与 Anthropic 文章主张的渐进披露一致：harness 负责建立索引和保证正确，选什么由模型自己决定。

### 2.2 四个性质

| 性质 | 含义 | 已有基础 | 待实现 |
|---|---|---|---|
| **无损** | 移出主上下文的内容换成指针，原文随时可以取回 | 内容寻址归档、`history.read/search`、压缩时保留原文引用 | 指针清单进入状态帧；取回后能重新编入上下文 |
| **新鲜度** | 每条事实带来源哈希，来源一变就标记为过期，不拿过期事实推理 | 项目知识带文件哈希；决定带版本 | 主 Agent 的普通观察也写入知识；`file.patch` 接受“本会话已读且哈希未变”的读取证据 |
| **跨运行共享** | 子运行和后续会话查询同一个存储，不再重复探索 | `inspect_run`、知识检索 | 子运行的上下文包从存储生成；子运行结果写回存储 |
| **缓存友好** | 执行过程中只追加内容，只在压缩检查点集中重建 | 状态帧位于请求末尾；system 缓存断点 | Anthropic 历史缓存断点；检查点重建前比较重建成本与后续节省 |

### 2.3 主动放入和按需拉取的分工

| harness 主动放入上下文（少量，几乎每次都要用） | 模型按需拉取（工具） |
|---|---|
| 用户的决定与约束（带版本） | `history.read/search`：原始对话与工具记录 |
| 状态帧：进度、预算 | `knowledge.search/read`：带来源的项目事实 |
| 项目索引：文件、产物、知识条目及其新鲜度 | `skill.list/load`：方法 |
| 已移出内容的指针清单 | 文件与产物读取 |

上次 assembly 实验的做法是每轮由代码按关键词挑选证据并替换进上下文。新方案放弃这种做法，原因有两个：它替模型做了选择，而且会破坏缓存。

### 2.4 子运行只用于三种情况

| 情况 | 场景 | 方式 |
|---|---|---|
| 并行处理独立任务 | 几十篇文献分别阅读 | fresh 子运行，返回结构化结果，证据写回存储 |
| 上下文膨胀 | 长项目的大范围检索 | fork 子运行，共享主干前缀，结论折回主干 |
| 独立复核 | 黑盒检查交付物 | fresh 验证器，不提供实现者的结论 |

三种情况都由主 Agent 把子运行当作工具调用，对话始终由主 Agent 掌握。删除点对点通信和完全交接。

### 2.5 可量化的目标

已有实验数据（README 中的大上下文压缩复核）：

- 闭卷：只看压缩后的上下文，得分 30%–60%；
- 开卷：可以回读全部原文，得分 97.5%，但输入是闭卷的 4.8–9.2 倍。

**目标：质量接近开卷，成本接近闭卷。** 验收线（2026-11-04 用户确认）：深埋事实 QA 得分达到开卷的 90% 以上，输入不超过闭卷的 2 倍；黄金评测的成本门槛在中位数之外补充 P90，防止长尾失控被中位数掩盖。

## 3. 体验设计

| 体验 | 内容 | 对应技术 |
|---|---|---|
| 整个文件夹交给它 | 读写 PDF、docx、xlsx、pptx、csv；可以跑 Python 做统计和作图 | 文件工具、并行子运行 |
| 结论可点回原文 | 交付物中每条结论都标注来源文件和位置；没有出处的内容明确标注 | 上下文存储的来源记录 |
| 上下文清单 | 每次任务列出用到的材料、决定和历史，标出过期项，可以点开原文 | 存储索引与新鲜度 |
| 改坏了能撤回 | 每一步都有检查点；删除或覆盖前确认；可回到任意一步 | 文件检查点、`rewind`、哈希校验 |
| 手机和电脑打通 | 手机负责发任务（文字、语音、拍照、分享）、收提醒、回答问题、审批、看结果；电脑负责执行，文件留在本地 | 持久等待、`ask_user`、逐次审批、Web 工作台 |
| 一键安装 | 内置运行时和预编译原生插件，用户无需安装构建工具 | 打包与分发 |

费用控制（自选模型、预算上限）和断点续跑作为基础保障，不作为首屏卖点。

## 4. 不再做的事

- 多 Agent 协作作为卖点；自动分工、任务图、名册路由、角色卡体系；
- 用编码任务跑委派、卸载、工具视图这类机制消融矩阵；
- 社区、作者后台、市场；能力包和案例保留，作为方法分发和验证单位，冻结扩张；
- 新增工具档位、实验开关或角色；新的机制必须先有评测证据才能进入默认配置。

## 5. 执行方案

总原则来自文章，也是 Kodo 过去缺的那一条：**度量，一次只改一处，留下经得起检验的。** 每个阶段都有进入下一阶段的门槛，不承诺固定周期。

### 阶段 0：基线与评测（所有改动的前提）

1. **提交当前状态作为基线。** 仓库目前只有 `28a5cd7 first commit` 一个提交，几乎全部改动都未提交，不提交就无法回退。
2. **建 10 个黄金样例。**

   | 类别 | 数量 | 示例 |
   |---|---:|---|
   | 文献与科研 | 4 | 多篇论文对比表、综述初稿（引用必须真实）、从论文抽取实验数据、按导师意见修改 |
   | 数据与表格 | 3 | 统计并作图、多表清洗合并、周期报表 |
   | 报告与文档 | 2 | 多材料汇总报告、会议纪要与待办 |
   | 编码 | 1 | 沿用 statemachine 任务，作为回归 |

   目前还不能读 PDF 和 Office 文件，所以阶段 0 的材料先用文本化版本（md、csv、txt，PDF 预先转成文本）。阶段 3 完成后，同一批样例换回原始格式。
3. **每个样例写评分标准**：可以机械检查的项（字段、汇总数、引用是否真实存在、文件是否产出）加上需要人工判断的项。不能违反的规则单独列出。
4. **用当前默认配置每个样例跑 3 次**，记录合格率、费用、耗时、缓存读取占比和重复读取率。
5. **评测基础设施**：逐请求记录响应模型和计费字段，出现线路变化时把对应结果格标为受污染；第一格冒烟时如果目标机制触发次数为 0，自动中止。

**门槛**：基线数据完整，评分标准经过人工复核。

### 阶段 1：减法

按子系统分批删除。每删一批，重跑黄金评测，并检查有哪些样例的结果翻转了，不能只看总分。

| 批次 | 内容 | 约计行数 |
|---|---|---:|
| 1a | 任务图与 lean-team 调度（`runtime/task-*`、`messaging/task-*`、`delegate.ts`） | 1,854 |
| 1b | 隔离检出与集成（`runtime/execution-*`） | 1,156 |
| 1c | 名册、路由、留存、派生、预设与角色卡 | 1,159 |
| 1d | 协作工具精简为 spawn、wait、inspect、cancel、ask_user；子运行只保留 fresh 和 fork；todo 去掉依赖与派发 | 约 1,500（精简） |
| 1e | 5 套工具档位、A–E 因素、3 个任务协议收敛为一套默认配置；P1–P4 并入上下文存储的加载策略 | — |
| 1f | 提示词审计：删除为旧模型和单次实验加的规则；默认身份改为通用工作助手（`src/runtime/lean-prompt.ts:13`） | — |

同期修复两个内核问题：共享执行下的写范围冲突（在保留的 spawn 路径上，要求写任务声明 `scope.write`，或者把同一批派发作为整体校验），以及“无内容时 25 秒内 3 次 502 即判失败”（改为分钟级退避）。

产品尚未发布，旧会话不做兼容恢复；恢复旧会话时明确报出版本不兼容，不静默降级。

**门槛**：

- 黄金评测合格率不低于基线，按 3 次运行判断；
- 不能违反的规则没有新的翻转；
- 费用和耗时的退化不超过 10%；
- `npm run check` 与全量测试通过。

### 阶段 2：上下文存储（技术核心）

1. 状态帧加入项目索引和指针清单；
2. 主 Agent 的普通观察写入知识（复用已规划的 P3 来源校验）；
3. `file.patch` 接受“本会话已读且哈希未变”的证据；
4. 子运行上下文包从存储生成，子运行结果写回存储；
5. 检查点重建加入成本判断；补上 Anthropic 历史缓存断点，断点必须打在状态帧之前的最后一个稳定内容块上；
6. 上下文清单通过事件和 API 输出，供阶段 3 的界面使用。

**专项评测**，每项都和 off、summary 两个基线比较：

| 层 | 测什么 | 数据来源 |
|---|---|---|
| 深埋事实 QA | 准确率和输入 token | 现有 362k token 测试集 |
| 目标切换 | 已移出的原文能否被正确取回 | 新增 |
| 128k 长任务 | 完成率、费用、缓存命中 | 黄金样例中材料最多的 3 个 |

**门槛**：达到 §2.5 的验收线；黄金评测不退化；子运行重复读取率明显下降（基线为 42%）。如果没有达到，先改工具描述和索引，不扩展其他功能。

### 阶段 3：办公能力

可以在阶段 2 期间并行推进，两者改动的文件基本不重叠。

1. 读取 PDF、docx、xlsx、pptx；输出 docx、xlsx、md 和图表；
2. 交付物的来源标注与上下文清单界面；
3. 检查点与撤回的界面；
4. 黄金样例换回原始格式后重跑。

**门槛**：原始格式下的合格率不低于文本化版本。

### 阶段 4：桌面与手机

1. **一键安装包**：内置运行时和预编译原生插件，覆盖 Windows 和 macOS。
2. **主界面**：以现有 Web 工作台为基础，做成桌面窗口；TUI 留给开发者。
3. **手机端第一版**：局域网扫码配对，形式为 PWA，复用 `kodo serve` 已有的 Cookie、CSRF、幂等回执和 SSE 重放。需要注意：局域网 HTTP 不是安全上下文，Service Worker 和推送都不可用，所以第一版在页面打开时提醒；系统推送随第二版一起做。
4. **第二版**：远程中继，端到端加密，服务器不保存内容；同时加入系统推送。中继需要自建服务器，单独评估成本和合规。

**门槛**：一名不懂技术的用户可以独立完成安装、配置模型、在手机上发出一个任务并收到结果。

### 阶段 5：用户验证

招募 5–10 名学生和办公用户，用他们自己的材料，同一任务分别用 Kodo 和他们现在常用的工具完成，记录：

- 完成时间和人工操作步数；
- 产出中的错误和编造出处的数量；
- 跨天继续同一项目时，重复解释和重复上传的次数；
- 是否愿意继续使用。

**判断**：如果长项目和多文件任务上没有可重复的改善，回到阶段 2 调整存储和工具，不扩大推广。

## 7. 证据与边界

- 交接成本（42% 和 41% 重读率）来自五组复测，每组一次、单一编码任务，统计脚本为 `.kodo/scratch/reread/reread.mjs`，见 [减法方案](kodo-subtraction-plan-20261103.md) §2。
- 专属方法自主加载 2/2 来自小型合成任务；通用方法 0/8 来自编码任务。
- 开卷与闭卷数据来自现有压缩复核实验。§2.5 的阈值为提案值。
- Anthropic 文章的结论基于企业部署和 Claude 5 一代模型；Kodo 的验证模型是 deepseek-v4.1-flash，结论能否迁移需要由阶段 0 和阶段 2 的评测回答。
- 本文的定位与体验均为待验证的产品假设，没有用户访谈或市场数据支撑。
