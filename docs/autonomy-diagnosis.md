# 自主协作没有触发的原因分析

后续只读复核与优化建议见 [自主委派优化方案](autonomy-optimization.md)：原事实成立，但可观察断点不等于已分离根因；补充了子运行证据读取缺口和终态／唤醒重复携带结果的发现。本文原实验数据与结论范围保留。

日期：2026-10-20。基于上一批四次真实任务、当前源码，以及本轮新增的 10 次真实 API 请求。模型和协议仍为 CodeGo / deepseek-v4.1-flash / Chat Completions，使用 1M 合并窗口与 393216 最大输出参数。诊断没有修改生产内核。

**已确认可观察的断点在首次委派请求之前；尚未分离提示、模型和任务结构的因果贡献。原版本主代理方法存在配置缺口，但主代理保留完整编程工具本身不是缺陷。** 同时，新的真实委派对照暴露了卡片选择和结果引用理解两个具体问题。它们影响实际协作质量，但不能倒推为上一批零次创建尝试的直接原因。

## 已确认的事实

| 检查对象 | 证据 | 结论 |
| --- | --- | --- |
| 工具是否送到模型 | 两次 auto 的 104 个请求均含六个原生协作工具 | 不是评测漏装工具 |
| 是否尝试创建后被拒绝 | 原批次 spawn_agent 调用为 0，主模型继续执行读写与验证 | 未进入创建校验及子任务调度阶段 |
| 并发、子任务额度 | auto 使用 maxChildren=8、maxConcurrentModels=2，最大预算模式 | 没有由额度为零或并发为一直接禁用协作 |
| 工具选择参数 | 原请求未设置 tool_choice=none，也未硬编码只可调用文件工具 | 模型可以选择协作工具 |
| 实际模型能否调用创建工具 | 新的明确委派对照创建了一个子任务，真实读取随机标识，主代理等待并交付 | 当前模型、协议和内核的这条链路可以成功工作 |
| 加强一段提示是否立即触发委派 | 同一原始决策点重放，只替换主代理系统指导，其他消息、工具和参数完全相同；两次都选择 file_read | 没有证据声称补一句提示即可解决 |

这里的链路成功只有一个只读子任务的范围，不能推广为所有协作、取消、恢复或并发场景无缺陷。104 个请求来自同一种任务的两次 auto 运行，并非 104 次独立实验；这不能证明该模型在所有任务上都不会自主创建子代理。

## 1. 默认主代理方法与设计职责存在差距

[设计职责](design.md)要求主代理理解目标、选择执行者、解决跨任务取舍、协调变更、核验并交付。[运行时边界](design.md)又明确不把固定业务步骤硬编码到调度器，因而模型的方法配置需要承担任务分解和委派选择。

原诊断时的 [initialContext](../src/runtime/context.ts)中主角色的直接指导仅为：

```text
You are the main agent. Delegate only useful independent tasks.
Only you can spawn/cancel children and ask the user.
```

[默认卡片](../src/agents/card.ts)让通用执行者用可用工具完成任务、检查事实、保存证据；[本批评测卡片](../scripts/compare-harnesses.mjs)也主要强调读文件、修改、验证和简洁交付。主代理同时拥有所有编程工具，因此独自完成全部功能完全符合现有提示。

缺少的具体方法包括：如何识别值得委派的独立工作，何时在任务推进中重新评估，如何传递输入/约束/范围/验收，何时主代理继续其他工作，如何处理子结果及验证证据。协作工具说明主要描述参数和权限，没有把这些操作组织成可靠的使用方法。

这支持“默认导演式方法不足”的工程判断，但不能从源码和两次样本中精确分离提示、模型倾向和任务特性的贡献。调度器不应为提高创建次数而无条件派生任务。

## 2. 任务与验收没有区分任务成功和自主协作成功

上一批虽跨三层源码，但仍是同一历史目录功能的六文件交付，核心 API、CLI 和测试有共享契约。它可以划出测试设计、只读审查等独立工作，也可以由一个模型有效串行完成；不能仅凭“文件多、调用多”认定必须产生协作。

[原始验收](../scripts/compare-harnesses.mjs)检查完成、行为正确、验证、改动范围和子任务收敛。auto 不要求最低子任务数，这对于不强迫委派是合理的，但其通过只说明任务交付合格；它不是“遇到有价值的分工机会时是否正确选择协作”的行为验收。

[协作单元测试](../tests/collaboration.test.ts)及[全会话计量测试](../scripts/comparison/autonomy.test.mjs)通过脚本供应商或宿主操作生成创建调用。它们检查创建以后的机制，不能验证真实模型会自主决定创建。原来机制测试通过、实际任务不使用，可以同时成立。

后续需要独立记录两种结果：产出是否合格，以及自主委派机会是否被利用。既要有适合分工的独立模块/分析/审查任务，也要有应保持单代理的小任务作为对照，不能简单把“创建越多”定为通过。

## 3. 明确委派对照复现了卡片选择问题

本轮以随机内容的 proof.txt 做只读能力对照：明确要求主代理创建一个子任务读取文件，主代理不能自己读取，然后等待并返回完整标识。主角色使用现有系统规则，卡片只提供文件读取/列出，协作工具由当前内核原生装配。

实际过程：

1. 模型调用 spawn_agent，编造 `card_id=readonly-proof-reader`、`card_version=1`。
2. 内核正确返回 `CARD_NOT_FOUND: card version is not registered`。
3. 模型去掉这两个字段重试，继承现有卡片，成功创建一个只读子任务。
4. 子任务真实读取随机文件并完成。

[spawn_agent 描述与参数](../src/messaging/index.ts)提供可选 card_id/card_version，却没有明确告知“未知已注册卡片时省略二者即可继承；不能通过填写名字创建新卡片”。[实现](../src/messaging/index.ts)确实要求指定卡片已注册；当前模型操作面也没有卡片搜索/浏览接口。

因此，需要把“创建运行实例”和“选择已注册能力卡片”讲清楚。默认通用子任务应能无须猜卡片 ID 地创建。专业卡片发现是后续能力，不能当作通用委派的先决条件。

这个错误发生在本轮明确委派对照中；原批次从未调用 spawn_agent，不能宣称原批次也被 CARD_NOT_FOUND 阻断。

## 4. 子结果已经送达，引用类型仍让模型误用

同一对照中，主代理等待子任务完成后，又调用 list_agents，拿到子结果的 resultRef，随后把它当作 history.read 的 ref：

```text
HISTORY_DENIED: history reference is not indexed for this run or its managed children
```

这个拒绝是正确的。resultRef 是内部结果 blob 的引用，不是已经登记的 context archive。与此同时，[终态消息](../src/messaging/index.ts)和[等待唤醒](../src/messaging/index.ts)已经把完整子结果送入主代理后续输入；没有丢失子结果。

[list_agents](../src/messaging/index.ts)暴露 resultRef，但工具描述没有说明其引用类型和消费方式；现有多层 JSON 字符串封装也增加了识别结果的负担。模型在已有子结果的情况下仍进行了无效读取。

这不仅是说明不足：该对照没有上下文归档事件，主代理缺少读取子任务原始工具证据的可用入口。宿主审计能核对数据库，不等于主代理独立核验。完整子结果还被终态与唤醒重复注入。修复需要受管运行证据入口及通知去重；仍不开放任意 blob 读取。

## 新增诊断的原始结果

两次单轮探针重放同一份原请求 19，源 SHA-256：`40a3b243fbbb327adb941944803fcce31ce76ed663f5bf1b2adcfc7d5e368f1e`。只改系统提示中的主代理指导，工具清单、其余消息、模型参数及原任务不变。探针返回的工具没有执行，不能把它们算作完成任务或修复后的性能成绩。

| 探针 | 返回操作 | 可得出的结论 |
| --- | --- | --- |
| 原始指导 | file_read | 本次仍继续串行收集信息 |
| 补充分工、资料包、等待及验收指导，无最低子任务数 | file_read | 单段指导未在这个执行中的决策点立即改变选择 |

这是一个历史中段、每种一次的选择探针，包含此前已经串行推进的上下文，不是从任务开始的完整 A/B；不能排除随机性，也不能证明新的指导永远无效。

真实明确委派对照共 **8 次模型调用：主代理 6 次、子代理 2 次**；包括失败创建、成功创建、等待、子读取、结果引用误用及最终完成。主子均 completed。宿主独立读取真实工具结果核对随机文件，主代理没有独立读取原始工具证据；七项检查全部通过，进程退出 0：

```text
passed: true
exactlyOneChild: true
childCompleted: true
childReadActualRandomFile: true
mainDidNotReadFile: true
finalContainsActualMarker: true
waitOccurred: true
```

本轮合计 10 次 API 请求，114,092 输入、3,848 输出 token，全部 HTTP 200 且有完整结束标记；包括探针与能力对照，不混入上一批性能或自主创建率。

## 修复应解决什么

1. 补全现有主代理方法中的任务分解、委派资料包、并行工作及验收策略，让通用子任务成为实际可选择的执行方式；保留简单或紧耦合工作直接完成的判断。
2. 澄清现有 spawn_agent 的继承语义和已注册卡片条件，澄清 list_agents、等待唤醒和各类结果引用；以本次两项真实失败作为针对性验证案例。
3. 用从任务起点开始的新冻结实验验证行为：保持中性任务，不指定创建数量；覆盖值得委派和不值得委派的负载，同时比较实际委派、质量、等待、并发、成本与最终验收。更强提示或更多创建次数都不能单独作为修复成功依据。

当前定位支持先修主代理方法与面向模型的协作接口，再检验模型在合适负载上的选择。更换模型、增加并发额度或硬编码始终创建两个代理，都没有得到本次证据支持。
