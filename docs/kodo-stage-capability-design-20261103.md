# Kodo 最终设计与实施方案：阶段驱动的能力挂载

日期：2026-11-03，历史评审修订版。评审时仅实现 P1，原计划先验证现有 skill.load 之外是否存在增量价值，再决定是否建设显式阶段协议；下文的排期措辞均描述这个历史计划。当前已实现 P1–P4，入口与限制见 [实现说明](inline-methods.md)，真实模型收益仍须由实验判断。本文记录了对 [前版可插拔 Agent 设计](kodo-pluggable-agent-context-design-20261102.md) 的修订依据。

## 1. 最终架构

**一个主 Agent 持续负责目标和交付；按需加载专业方法，切换时使旧方法失效，检查点再物理移除；完整工作过程默认连续保留。**

- 默认：通过 skill.load 加载兼容的卡片方法，隐式记录当前方法阶段，不要求先调用 declare、activate、done。
- 阶段结束只追加失效标记，方法正文和历史暂时保留。物理卸载方法与收拢执行过程分开处理，后者不因方法切换自动发生。
- 例外：大量独立探索、并行工作、独立评审、不同模型或执行环境，启动子 Agent。
- 两种模式都使用已有项目知识，不要求复制全部父级历史。
- todo 可以提示后续需要的能力；显式阶段协议保留为后续精确控制方案，首个验证闭环不改 TaskGraph。
- 小任务直接执行，不强制规划或挂载专家。

产品表达：**按需接入专业能力，延续已有项目理解，适时释放不再需要的方法上下文。** 延迟失效没有立即释放 token，也不能保证模型完全停止遵循旧方法，需要实际验证。

```text
用户任务 → 自主发现 → skill.load 加载卡片方法 → 主 Agent 连续执行
                         ↓                         ↓
                   隐式记录方法阶段        换方法或实际结束运行
                                                   ↓
                                    追加旧方法失效说明，保留过程
                                                   ↓
                                    原有压缩检查点 → 物理移除方法

独立探索/并行/独立判断 → 沿用子 Agent 路径
```

## 2. 复用现有结构，不增加第三套调度器

| 对象 | 负责什么 | 实现决策 |
|---|---|---|
| Agent 定义 | 方法、Skills、工具/MCP、输入和报告要求 | 复用 Card、能力包与现有资源版本 |
| 隐式方法阶段 | 当前方法身份、加载调用、版本与失效原因 | 首版复用事件/调用记录，不创建任务节点 |
| 显式阶段节点 | 目标、依赖、能力需求、验收与进度 | 验证有效后才扩展 TaskNode |
| 阶段绑定 | 本次卡片/资源版本及已有有效合同 | 宿主记录；首版不动态扩大工具或权限 |
| 项目知识 | 观察、假设、来源、适用范围和未决问题 | 复用 ProjectKnowledge；决定沿用 decisionVersion |
| 当前上下文 | 实际发送给模型的内容与工具 | 扩展 context-assembly、attachments、请求组装 |
| 完整记录 | 原始调用、材料、结果、切换历史 | 复用 history、工件与事件 |

当前 todo 协议和 lean-team TaskGraph 是两套实现。首版两者都不改变，隐式方法状态不拥有任务目标、调度、验收或依赖，不能变成第三套计划。后续确需显式阶段时统一扩展 TaskGraph，不双写计划。

第一版不迁移会话，不新增任务协议版本，不同时改造三套界面。后续显式阶段采用宿主持久化的协议版本，旧会话继续原语义；如需迁移，在空闲边界一次转换。实验必须使用可实际到达 skill.list/load 的工具视图，各组配置相同。

## 3. 首版入口与后续显式计划

首版用 skill.list 发现、skill.load 加载。宿主把已注册、声明 inline 兼容的卡片方法映射为可加载目录项，返回同样的方法正文，并在成功加载时隐式记录当前方法；模型无需额外规划调用。

现有 skill.load 只接受预加载且在 run.card.skills 中获准的 Skill ID，尚不支持加载卡片。实现时必须显式增加卡片方法目录项类型及宿主映射，使用可区分且通过现有 ID 校验的稳定句柄，检查命名冲突，并绑定卡片版本/digest。不能按名称猜测任意 Skill 是 Agent 卡片，也不能因为加载普通参考 Skill 就切换主方法。

保留原 skill.load 参数与普通 Skill 行为；卡片方法句柄映射和可读资格由宿主建立。正文分页及同方法重试不新建阶段；卡片依赖 Skill 属于补充资料，不替换主方法。必要操作规则未完整加载时，明确要求继续读取，不能把第一页当作完整方法。

以下显式计划结构只作为后续候选，P1 不实现。若隐式方式已满足需要，不要求引入它。

后续可沿用节点 id、goal、after、acceptance，增加 needs。以下是拟新增接口，当前不可调用：

```json
{
  "action": "declare",
  "tasks": [{
    "id": "compare",
    "goal": "比较供应商报价并形成推荐意见",
    "after": ["requirements"],
    "needs": {
      "capabilities": ["按统一口径比较报价和服务条件"],
      "knowledgeQueries": ["预算上限、采购数量、交付期限"],
      "requiredRefs": [],
      "execution": "auto"
    },
    "acceptance": "输出比较表，包含来源、有效期、缺失条件与推荐依据"
  }]
}
```

- capabilities 描述需求；用户明确指定 Agent 时可保存精确卡片引用。
- requiredRefs 是必需的知识/工件版本；knowledgeQueries 用于查漏。写了查询不等于已经具备输入。
- execution 支持 auto、inline、child，auto 默认倾向 inline；宿主条件不满足时返回原因，不能绕过。
- 无 needs 的节点保持普通工作方式。产物复用现有工件与报告结构，不增加重复的交付物模型。
- 显式模式下节点声明后不自动派发；activate 才绑定执行方式。该操作不作为默认能力加载的前提。
- 同一主运行一次挂载一个主方法包，包内可引用多个 Skill；不同主方法顺序切换，独立子运行可并行。

能力检索复用 agents/discovery 的目录、关键词、routing 和显式引用。先给主 Agent 能力摘要，再加载选中方法。宿主验证输入、依赖和运行条件；不增加选择 Agent、向量库、全项目预扫描或每轮自动检索。

无匹配时明确显示缺口。主 Agent 能用原有能力完成时可以显式改为普通执行；缺少必要工具或资料时补齐条件，不静默采用不相关专家。

## 4. 一份能力定义，两种执行方式

继续使用 Card 的方法正文、skills、tools、mcp、inputs、report、constraints。拟增加可选字段 execution: { modes: ["inline"] }；支持两种执行方式的卡片可同时声明 child。纳入 schema、digest、导入导出和版本比较。

旧卡片没有此声明时保留独立运行语义。支持 inline 的卡片由作者明确声明并验证；不能自动剥掉旧卡片的身份、规则或报告要求后声称等价。

首版只支持方法与资料加载：卡片需要的工具、资源和范围必须已由当前运行提供，所有可执行约束能在现有合同中满足。若需要动态加工具、收窄范围而宿主尚不支持，返回不兼容原因，不假装挂载成功。独立运行沿用现有路径。

有效工具合同以宿主/用户已授权资源为上界，包含必要的基础控制入口与选中能力依赖，并应用阶段/卡片限制。能力包只声明需求，不自行授予权限。主 Agent 的原始卡片不被改写。

后续动态工具模式中，多处直接读取 run.card 的校验需要统一读取有效合同。实际执行始终按合同检查；工具展示可比较“精确活动集合”和“稳定的已授权候选超集”两种策略。后者允许描述仍可见但当前不可执行，返回明确的未激活原因，不自动越权执行。仅在提示词增加名称不构成工具挂载；只读专家不能借主 Agent 的更宽权限写入。

不同模型、独立判断或无法在主运行满足的执行环境要求使用 child；缺的是宿主授权/资源时，创建子运行也不能解决。独立评审接收必要事实与原始材料，不默认注入主 Agent 的推荐结论。

## 5. 阶段生命周期

P1 的隐式生命周期：

1. 成功加载卡片方法 A，宿主记录其精确身份、方法实例和来源调用；加载失败不切换。
2. 加载 A 的下一页、重试或补充普通 Skill，只追加资料，不重复开启阶段。
3. 成功加载主方法 B 时，追加“A 方法已结束，不再作为当前工作指令”的宿主说明并启用 B；仍保留 A 的所有执行历史。切换结束的是方法适用期，不代表 A 的任务或产物通过验收。
4. 实际运行终止时记录方法结束。提问、等待、工具回合结束或暂时回复不视为任务完成；不靠扫描“完成”字样判断。
5. 加载动作与生命周期事件复用现有工具提交、调用身份和幂等处理。取消/失败按真实状态记录，不标成成功；恢复不能凭缺少标记默默清空方法状态。

首版不承诺从任意自然语言准确推断所有方法边界。不换方法又未终止时保留当前方法，记录边界遗漏；若实验显示这是主要问题，再引入最小显式结束动作，而不是一开始要求完整阶段协议。

以下完整生命周期及 task 扩展均推迟到增量价值验证之后：

复用 TaskNode 的 pending、running、needs_input、done、stale 等状态，不另建状态机。扩展现有 task 工具：

| 操作 | 主要输入 | 行为 |
|---|---|---|
| declare | 节点及 needs | 声明工作，校验依赖；复用任务声明逻辑 |
| activate | node_id、expectedGeneration、选中的能力引用 | 核查依赖，准备知识与合同，挂载或启动子运行 |
| extend | node_id、expectedGeneration、当前包的资源引用 | 追加获准资料或 Skill，不重排历史 |
| done | node_id、expectedGeneration、resultRef | 核对产物与检查记录，保存成果、完成任务并标记方法失效；物理卸载等到检查点 |
| inspect / resume / redo / drop | 既有标识与原因，适用操作增加代次检查 | 复用检查、恢复、重做与放弃，补齐主阶段支持 |

这些是拟新增/扩展接口。需同步参数 schema、工具版本、SDK 与界面；已有 task accept 处理 stale 结果，不改作任意验收。

阶段执行规则：

1. activate 核查前置阶段最新代次已完成，先取已有知识，再确定调查缺口。
2. 必需约束、方法、证据与输出余量必须放得下；超限则明确要求分阶段或调整输入，不能静默截断。
3. 固定本阶段卡片、Skill、MCP 与工具绑定版本。重复 activate 返回现有绑定，不重复创建子运行。
4. 主运行只有一个活动 inline 阶段；子运行各自持有上下文和绑定。
5. 阶段内允许补充资料；更换方法默认追加失效说明。只有确需重建投影/变更执行合同的检查点才形成新的物理上下文版本。
6. done 必须引用真实产物及检查记录。可机械检查的条件由宿主检查；业务判断标明是模型评阅还是用户确认，不能伪装成客观验证。
7. 依赖代次或有效决定变化使受影响成果待复核，不能当作新输入的完成证明。
8. 暂停、失败与放弃记录方法状态，默认延迟物理卸载，保留未完成工作与外部操作状态，不标记为成功。

当前 completeSelfTask 主要检查依赖后标记完成；结构化检查又偏向 Git 子运行。必须补齐主运行成果记录和本地文档/表格检查，不能直接把现有 done 当作充分验收。

## 6. 方法失效、物理卸载与过程收拢分开

当前模型输入由以下部分组成：宿主规则和有效用户约束、相关项目理解与前置成果、当前阶段方法和必要资料、当前阶段追加历史、末尾状态帧。

完整历史持久保留，方法切换不自动重建投影，也不要求把执行过程替换为成果摘要。

| 操作 | 处理内容 | 默认时机 | 代价与首版范围 |
|---|---|---|---|
| 方法逻辑失效 | 追加带方法实例引用的失效说明，旧正文仍在 | 换方法或实际结束运行 | P1 实现；不减少输入 token，也不保证模型必然忽略旧指令 |
| 方法物理卸载 | 从请求移除失效方法和不再需要的领域参考资料 | 原本就需重建的压缩检查点 | P2 验证；可回读恢复，不随意删除包含项目证据的资料 |
| 执行过程收拢 | 对读取结果、尝试、可见解释和中间产物做选择/压缩 | 仅上下文压力或压缩检查点 | 有损，推迟独立验证；不以阶段切换触发，也不要求访问模型内部推理 |

P1 保持现有压缩策略在所有实验组相同，不新增过程摘要。P2 先只移除已失效方法，不改变原有过程保留策略。领域参考资料可能承载后续判断依据，应按内容和依赖决定保留，不能按“来自旧阶段”一删了之。

标记沿用方法实例、卡片版本、资源 digest 与来源调用；未来显式阶段再关联 nodeId/generation。对方法加载的工具调用/返回保持协议配对；物理移除时使用既有合法历史投影和回读指针，不能留下孤立调用。

后续若验证过程压缩，仍必须保留用户约束、必要依据、有效成果、未决问题和未结束外部操作；以真实后续任务检查信息损失。记录中的“方法已失效”不能覆盖用户决定、领域硬约束或仍有效的项目事实。

现有 assembleEvidence 主要筛选工具证据，P1 不修改它。P2 复用历史引用和消息配对机制，仅为失效方法增加检查点处理；不把方法卸载与整段工作历史摘要绑定实现。

缓存按提供方的实际请求结构与规则判断。Anthropic 的工具定义处于缓存层级前部，改变工具通常影响后续 system/messages 缓存；不能把“所有提供方每次切换必然全部失效”写成通则。P1 保持工具 schema 和历史稳定，只追加方法及失效说明；这有利于保留可复用前缀，不保证其已建立、未过期或必然命中。

原有压缩检查点先作为唯一物理卸载触发器。可卸载内容阈值不是 P1 新配置；以后有数据证明值得额外重建时再添加。阈值应由剩余上下文、预计后续调用和提供方实际读写价格评估，不任意写死 token 数。

后续单独比较精确活动工具集与稳定候选超集，测量缓存读/写 token、未缓存输入、实付费用、延迟、误调用次数和恢复轮数；工具描述本身的输入开销也计入。实际执行都使用同一有效合同，稳定超集不包括宿主未批准的资源。无真实缓存用量时标记未知，不能用前缀相似率代替命中率。

## 7. 项目理解的保存与复用

本节是后续独立改进，不进入 P1/P2；首轮各实验组使用相同的现有知识能力和完整历史，避免把知识入口升级的收益误算为阶段机制收益。

ProjectKnowledge 已有不可变修订、来源调用、文件哈希、假设与未决问题；但 prepare 入口依赖结构化 exploration 和该运行成功的 file.read，普通主 Agent 发现不能直接用这条入口。

抽出来源校验和候选知识生成，使主 Agent、普通子 Agent 可提交自身真实来源引用；保留探索入口兼容，复用现有存储，不新增记忆数据库。不能凭模型填写的任意 callId 接受无权限或不属于允许来源的内容。

观察与推断分开；新鲜度不代表正确性。用户决定保持原始消息/decisionVersion 依据，不交给摘要覆盖。冲突结论保留双方证据并定向复查。项目资料不随通用能力包导出。

首先支持已有文件证据及工件，覆盖本地业务材料；实际需要网页/应用时再添加来源适配，无法检查更新则标为 unknown。修改前阅读、来源变化核实和独立评审不计为无效重复探索。

## 8. 原子切换、恢复和真正热插拔

P1 不新增上下文重建事务：仅复用工具调用结果与既有事件提交，保证成功加载、隐式方法标记和重试身份一致。至少验证失败加载不结束旧方法、分页不重开、重启可重建当前方法身份。这里是必要的记录一致性，不是完整阶段切换框架。

以下完整事务与资源热插拔推迟；只有实际替换投影或动态修改执行合同后才需要实现：

切换在模型/工具调用边界发生：事务外准备输入、验证资源和生成投影；短事务内重新核对节点代次、决定版本及绑定版本，一次提交绑定、成果引用、上下文引用与事件。准备期间有新输入则重新校验，不能覆盖新决定。

依据运行、节点、代次与操作身份识别重试。提交前中断恢复旧状态，提交后恢复新状态，禁止节点已完成但成果未保存、工具已收回但请求仍宣称可用等半状态。外部操作沿用现有调用记录与恢复机制，不因阶段恢复自动重放。

首版只加载冻结名册内且与当前运行合同兼容的卡片方法。会话内安装新能力属于另一步：安装 → 校验绑定 → 提交名册新修订 → 后续阶段可发现。registerCard 本身不等于热插拔。

在途阶段固定原版本；停用阻止后续挂载，当前使用完再释放。重启按确切身份恢复资源，缺失时明确报告，不能悄悄换最新版。

## 9. 实施批次与代码落点

| 批次 | 主要修改位置 | 可验收结果 |
|---|---|---|
| P1 最小实验闭环 | agents/card.ts、runtime/types.ts；extensions/skills.ts；application/index.ts 的目录注入；既有工具结果提交/运行终止处的必要事件处理 | 卡片声明 inline；skill.load 加载并隐式记录方法；切换只追加失效说明；自主采用率和三组对照可测 |
| P2 检查点方法卸载，仅收益成立后 | context.ts、context-assembly.ts、attachments.ts 中实际必要位置，以及既有提交/恢复入口 | 原有压缩检查点真正移除失效方法；执行过程不按阶段收拢；请求合法、恢复一致 |
| P3 按证据选择后续工作，不捆绑 | 共享知识：knowledge/index.ts 与交接入口；显式阶段：TaskGraph/task 工具；动态工具：tool-view/执行合同入口 | 只解决实验暴露的具体瓶颈，各自有单独基线；可以只做知识而不做显式协议 |
| P4 通用体验与真实热插拔，按需求 | agents/roster.ts、derive.ts、storage/cards.ts、application/index.ts 及必要界面消费者 | 名册修订不替换在途资源；只修改实际需要展示新行为的界面 |

首个闭环仅 P1，不先实施原方案横跨约二十个文件的 P1+P2。使用同一任务包含两个专业方法切换，分别运行常驻、现有 skill.load、隐式失效三组。每组首次各一遍只做可行性冒烟；不能从单次结果判断稳定优势。

P1 不增加 TaskGraph 操作，不创建 stage-context 协调器，不改变主卡片/模型/动态工具权限，不引入新的投影原子切换框架，不同时升级三套界面。必要的卡片字段解析、序列化和现有消费者必须改完整；不能为了人为限制文件数量留下不兼容代码。

P1 固定同一可到达 Skills 的现有工具 profile。若目标 profile 隐藏 skill.list/load，工具可达性应作为所有组共同的前置条件修复，不能只修实验组。必要的工具版本/指纹变化按现有规则处理，但首版不做全量 SDK/UI 重构。

若 P1 与普通 skill.load 持平，停止扩展显式阶段协议，优先改进已有目录/方法质量。若 P1 无短任务收益但长任务测量明确显示失效方法造成窗口压力，可进入 P2 的独立方法卸载实验；不能声称标记已经省 token。过程收拢保持独立的后续验证，不默认进入 P2。

## 10. 验证与发布门槛

### 10.1 先验证模型是否会主动使用

[负责人模式复测](experiments/agent-delegation-team-lead-retest-20261028.md) 记录 codego1 / deepseek-v4.1-flash 的 7 轮实质任务自主委派与待办调用均为 0，显式正控制可用。这是对“机制可用不等于会采用”的证据，不是对所有模型的结论，也不能据此断言 skill.load 必然无人使用。

实验前标注任务中适合使用专业方法的机会点，并准备无需专业方法的负控制。给模型正常目录和工具说明，但任务提示不出现“调用 skill.load/阶段/activate”等要求，不按模型实际有没有调用来事后改变分母。

- 自主采用率：合适机会点中，模型自行选择并成功加载相关方法的比例；同时报告分子/分母、误选、不必要加载、首次有效使用前轮数。
- 实际利用：检查产物是否应用方法要求，不能只数调用。宿主自动生成阶段事件不计为自主采用。
- 生命周期可靠性：分页/重试重复开阶段、加载失败误结束旧方法、漏标方法结束、失效后继续套用旧方法的次数。
- 显式要求加载的正控制只证明链路可用，单独报告，不混入自主采用率。若只有正控制成功，P1 不通过默认采用验收。
- 冒烟样本不设伪精确的成功率门槛。进入默认发布前，用预先固定的多任务/重复次数方案评估采用率、质量和开销；不能以一次主动调用通过验收。

### 10.2 分阶段合同测试

合同测试查看实际 provider 请求、持久状态、真实产物和调用记录：

| 验证对象 | 必须观察到的结果 |
|---|---|
| P1 加载 | 只加载选中方法；普通 Skill 不触发切换，分页/重试不重复开启，失败加载保留旧状态 |
| P1 延迟卸载 | 换方法只追加失效说明；既有历史/工具 schema 不因切换改写；过程和旧正文仍在；不声称已减少输入 |
| P2 物理方法卸载 | 检查点后的实际请求移除失效方法，保留必要依据及过程；原文可回读，工具消息配对合法 |
| 知识 | 有效主运行观察能复用；过期/矛盾/无来源内容不能直接成为已核实依据 |
| 完成 | 无产物、检查失败、依赖失效不能报告已验证完成；主 Agent 自评与宿主检查分开 |
| 边界 | 超限、无匹配、缺工具、中途补资料、无新知识、重复 activate、取消均明确处理 |
| P1 记录恢复 | 已成功加载的方法身份可恢复；不因重试重复标记；不新增外部操作重放 |
| 后续完整恢复 | 投影/合同提交前后分别恢复一致状态，外部操作不重放，在途子任务不丢失 |
| 兼容 | 旧卡片/会话保持语义；不同工具 profile 展示与实际执行一致 |
| 热插拔 | 后续阶段采用新名册，在途阶段不被替换，缺失旧资源明确报告 |

P1 扩展现有 agent-card-v2、extensions 及应用能力集成测试，覆盖相关加载/失效边界；不为尚未实现的 TaskGraph/上下文事务创建空测试。P2 再扩展 context-assembly、请求快照和恢复测试。知识、热插拔与完整任务验收测试随对应功能实施。

现有可执行命令：

```powershell
node 'node_modules/vitest/vitest.mjs' run 'tests/agent-card-v2.test.ts' 'tests/extensions.test.ts' 'tests/application-capabilities.test.ts'
npm run check
npm run build
```

各批运行受影响测试与类型检查；完整实施最终运行 npm test，区分已有失败与本次引入失败。

### 10.3 三组基线和后续单因素实验

| 组别 | 行为 | 用途 |
|---|---|---|
| A 常驻组 | 所有相关方法正文常驻，无新增阶段协议/失效标记 | 衡量按需加载本身的作用 |
| B 现有 Skill 基线 | 现有 skill.list/load 按需加载相同方法，无阶段记录/失效说明/新增卸载 | 判断已有能力是否足够 |
| C 隐式方法阶段 | 相同 skill.list/load 接入卡片方法；加载后隐式记录，换方法追加失效说明；不新增物理卸载 | 隔离阶段标记的增量价值 |

B/C 使用逐字相同的方法正文、等价的目录描述、方法句柄、分页策略、候选范围和模型可见工具 schema；B 的正文以普通 Skill 注册，C 额外挂接宿主卡片映射。避免把更好的目录或更多知识当成阶段收益。A 加载同一批方法正文，其他工具/输入条件一致。

同模型、预算、工作区初始状态、现有知识能力、压缩策略和工具集合。不得只对 C 增强加载提示。正文按需加载差异是 A 与 B/C 的处理变量，失效说明是 B 与 C 的处理变量。缓存实验记录冷/暖状态、有效期和执行顺序，防止后运行组偶然复用缓存获得优势。

P1 不新增物理卸载，因此 C 的输入甚至可能略长于 B；能验证的是自主采用、方法边界、旧方法干扰和成本，不能验证压缩收益。

后续单独实验：C 与 C 加检查点方法卸载；稳定工具超集与精确活动集合；保留过程与压力下过程压缩；普通交接与共享项目知识。每次只改变目标因素，不把全部能力同时开启比较总分。

场景覆盖报价比较与预算、周期简报、编码回归，包含资料变化、跨阶段证据依赖和中断续做。每条件重复多次、交错运行顺序，保存轨迹和盲评产物。现有 eval:tasks 有强制 solo/child 的任务，先改成中立要求再作对照。

主要指标：合格交付率、关键事实遗漏/错误、人工纠正、无新增信息的重复探索；同时记录所有运行及摘要的费用、耗时、回读和输入峰值。缓存命中只解释结果。

推进门槛：P1 合同测试通过，未提示条件下能观察到相关方法的自主选择和实际使用；相对 B 有可重复的质量/方法干扰改善，或测得足以支持 P2 的长任务方法积累问题。若 C 与 B 持平且没有明确后续问题，保留 B，不为已有按需加载收益建设完整阶段协议。物理卸载、动态工具和过程压缩分别通过自己的质量/成本门槛再发布；样本不足时保持实验状态。
