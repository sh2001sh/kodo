# Kodo 效率与并行优化定稿

后续方案入口：[简洁设计与轻量 DAG 优化方案](kodo-pi-simplicity-review-20261030.md)。该方案基于本轮实验结果调整主代理能力分配，并明确 DAG 动态更新、任务与展示信息分离、下一轮实施批次和验收条件；后续实施内容与验证记录见该文第 9 节。本文保留原 P0–P4 的设计与实验状态，不用后续修改重写历史实验结论。

日期：2026-10-30。本文是逐日志复核后的实施方案。P0–P4 的代码机制已实现，D/E 保持默认开启。**性能与质量验收未通过**：两格实测基线 4088.423 秒、功能 137/137，优化版 4369.720 秒、功能 131/137；优化版 11 个子运行均串行，未使用独立执行副本。实验后追加了待办验收反馈、等待说明与流结束分类修复，最终全量复测 176 个文件通过、2076 项通过、9 项跳过，类型与 ESLint 检查通过。原始记录在 `.kodo/efficiency-parallel-20261030/`，完整结论见[实验报告](experiments/kodo-efficiency-parallel-20261030.md)。

## 1. 结论与证据边界

目标是减少用户等待时间和完成任务的总费用，同时保留交付质量。方向是：少量稳定的基础工具、明确的任务所有权、可并行的待办、事件驱动等待，以及一次可核对的交付。工具数量、代理数量和首次修改时间都是解释指标，不单独作为成功条件。

本轮扫描四组全部 669 条 steps 和对应请求 JSON，核对工具使用与每个 run 的历史前缀；再逐组检查关键派发、等待、错误、验收及原生工具计时，并核对当前源码。并非人工逐字阅读约 900 MB 的全部文本。统计结果保存于 `.kodo/scratch/handoff-efficiency-recheck-20261030.json`，原始证据未改动。

原报告：[Kodo D/E 消融](experiments/kodo-handoff-ablation-20261030.md)。下文请求编号是各组 relay 全局 index，也对应 `process/steps.jsonl` 行号，不是单个代理自己的 step。

| 组别 | 墙钟 / 已知 credit | 首次产品修改 | 实际运行方式 | 主要优化点 |
|---|---|---|---|---|
| R0：ABC | 3237 秒 / 20.48 | 1116 秒 | 两个子运行重叠，其中一个失败，主代理接管 | 前期规划、派发参数纠错、持锁等待造成竞争 |
| RDE：ABCDE | 2819 秒 / 23.71 | 1044 秒 | 三个子任务串行 | 宽写范围、阶段式待办、交接间隔和验收往返 |
| RD：ABCD | 4798 秒 / ≥41.98 | 1288 秒 | 主代理实现，追加审查失败后重新创建审查，后者被取消 | 审查范围与能力不匹配、结束条件不清、恢复和取消 |
| RE：ABCE | 2292 秒 / 18.89 | 802 秒 | 完整实现后独立可执行验证，两个子任务串行 | 更早交接、准确待办绑定、验证输入与验收聚合 |

四组均通过外部 137 项新功能和 3134 项回归验证；这不证明所有语义约束均满足。原任务要求从 main 建分支，但初始环境只有 master；后续夹具须统一。每组一次且顺序运行，网关延迟、策略和异常不同，不能把差异解释为 D/E 的独立因果效应。RD 有一次费用缺失，不能把其已知费用当完整总额。

## 2. 逐组复核

### R0：并发存在，但工作安排产生等待环

- 首次派发前约 1002 秒、121,506 推理 token、9.03 credit。主代理先完成大量实现设计，再交给执行者。
- 请求 24 两次缺少结构化 scope；25 第二次派发写范围冲突；27、33 又遇到 INPUT_SLOTS。七次尝试只有两次创建成功。应改进入口说明和参数反馈，不能把所有往返都归于模型选择。
- 请求 51 用后台 shell 循环等待另一实现者补接口，持有整个工作区写锁约 455 秒。另一实现者连续锁超时，最终 NO_PROGRESS；全格共 10 次锁超时，但其中一次早于这段循环，不能全部归为同一原因。
- 主代理接管后仍交付成功，说明恢复路径有价值；不能将“多建代理”直接当作速度收益，也不能称这次问题为残留锁泄漏。

### RDE：串行来自多层约束

- 请求 25 两个任务都声明 `scope.write=["fastapi","tests"]`，第二个被拒；后两位分别到请求 110、147 才成功派发。
- 三位子代理生命周期无重叠。前后两次交接间隔约 101.8、88.6 秒，其中含必要核验，不能全部承诺消除。
- 首次派发前已消耗 97,224 推理 token、7.64 credit。主代理占全格费用约 52.2%（12.38 / 23.71），值得优先减少前置设计与协调往返。
- 最后子任务结束后还有 205 秒、13 次请求、1.18 credit。19 次 inspect 的工具时间合计仅 0.318 秒；问题主要在每次读取后再请求模型。

### RD：少工具没有解决审查失控

- 请求 95 让只读 explorer 覆盖 20 条需求、所有 API 入口、6 条继承规则及静态规范，还要求 Git diff，却没有 shell 或 diff 工件。
- 第二个审查者仅 13 个工具，仍产生 45 次请求、260,016 推理 token、18.15 credit；85 次实际工具只用 12.278 秒。抽样重复读取比例低，不能把它描述成反复读整个仓库。
- “输出简短检查表”并未约束检查工作量。应给明确的变更范围、风险问题、证据与停止条件；需要执行检查时选择具备对应能力的代理。
- 第一个审查因不完整模型响应失败；第二个是新 agent，没有继承前者进度。后续恢复应先判断原 owner 是否可续接，不把每次异常都变成从头再做。
- 请求 149 在原生中断/取消期间继续流出未执行的报告提议。提议不等于执行，未送达的报告不计交付价值。取消链路须分层核验，见第 3 节。

### RE：可复用的是完整所有权与可执行验证

- 约 380 秒派发完整实现，早于其他组；实现者承担代码、测试和提交，再由另一代理在固定提交副本验证。
- 两个代理仍然串行，速度改善不能称作并行收益。实现者启动到首改约 422 秒，包含必要理解，不能一律算无效探索。
- 请求 105 同时传合同 artifact 和另写的 12 组要求；验证者没有调用 artifact.read。32 个独立测试通过不能自动等同于覆盖合同全部 20 场景。
- 同次交接指定检出已占用分支的 worktree 命令；请求 108 失败，110 改为固定提交的 detached worktree。过细操作指导会传播错误，应交接目标与约束，复用经过验证的工作副本创建机制。
- 请求 143 已观察到验证子任务 completed；154 的 `verify` 完成更新仍被 TODO_ACCEPTANCE 拒绝；155 改成 executor=main 才完成。派发时仍选中 implement，隐式关联不能表达模型真正想验收的 verify。
- 最后子任务结束后还有 161 秒、14 次请求、1.54 credit；11 次 inspect 仅 0.190 秒。这些读取不都是重复，应聚合已有证据，保留发现缺口后展开原文的能力。

## 3. 新增发现：先保证实验与传输可信

### 3.1 relay 入站 UTF-8 解码会改变请求

`scripts/comparison/frontier/relay.mjs:90` 使用 `raw += chunk` 拼接 Buffer。UTF-8 字符跨网络块时，每块独立转换可能产生替换字符；损坏后的 JSON 同时被记录并转发到上游。stdin 配置读取也采用同样方式，应一起修正。

RD 请求 143、146、147、149 相较同 run 上次请求，历史第 52 条消息的 reasoning_content 在同一位置出现 U+2192 与两个 U+FFFD 的切换，长度在 18071/18072 间变化。本地分块解码检查证明当前拼接方式不能保持字符。现象与代码缺陷吻合，但日志没有原始入站字节分块，无法倒推出四次实际网络边界。

修复采用 Buffer 收集后统一 UTF-8 解码或流式解码器；检查中文、箭头、emoji 在各字节边界分块的保真性。原始证据保留，不修饰历史数据。新增记录至少区分收到的请求与限制处理后实际转发的请求，便于验证代理是否改变内容。

四组逐 run 请求比较：R0 155 次、RDE 186 次、RE 153 次转移都只在末尾消息开始变化；RD 有 158 次同类转移和上述 4 次更早变化。各 run 的工具定义都未改变。当前 `context-progress.ts` 已采用追加快照，不能再把旧版 todo 前缀替换直接当成本轮根因。解析后 JSON 相等并非原始网络字节全等；缓存实际命中也受上游影响。

### 3.2 中断需要核验整条连接

当前 OpenAI provider 已传入 signal；实验 frontier relay 的 fetch 没有 signal，response close 仅记录时间，没有中止上游。普通 `scripts/comparison/relay.mjs` 与 frontier relay 是不同实现，不应混淆。

这证明 frontier relay 缺少取消传播，但尚不能断言本次延迟输出全部由它造成：RD 请求 149 的 relay 记录 `clientDisconnected=false`。要分别记录原生中断、provider abort、下游连接关闭、relay abort、上游连接结束和收到的用量。约 61 秒属于中断后继续流出的区间，不能写成 cancel 后仍持续 61 秒。

补离线假上游端到端检查：客户端中断后连接结束、部分输出保留、最终状态不是正常完成；保留未知用量。本地关闭连接不保证远端立刻停止计算或计费。SIGTERM 也应处理活跃上游连接。首包与流空闲超时独立于总任务时限，活跃长推理不应因固定短总超时被杀掉。

## 4. 最终设计：基础工具与并行协作同时保留

### 4.1 主代理先定边界，不先写完实现设计

只需要确认用户目标、关键约束、代码入口、工作所有权和验收标准，就可以启动合适执行者。复杂接口协作先确认最小接口，不要求主代理先推演所有实现细节。小任务直接完成，不为一个命令专门创建代理。

交接复用现有 objective/context/inputs：提供已知事实与来源、尚未解决的问题、负责文件、依赖、完成条件。函数级实现设计属于执行者；必要的用户契约不能删。把卡片模板拼接改为明确的提示段落组装，消除精确字符串替换静默失效。

合同只有一个权威版本：小内容有界注入，大内容提供 artifact ID、版本/摘要及准确读取方法。执行者按需读取当前代码，验证者按合同场景对应检查证据；不复制主代理完整历史，不要求所有角色从零重探，也不禁止合理独立审查。

### 4.2 将 todo 从单阶段开关改为可并行任务记录

当前限制分别位于 `src/tools/todo.ts:123`、`src/runtime/todo-execution.ts:13` 和 `src/runtime/agent-factors.ts:16`。底层已有异步子运行调度，默认 8 个活动子代理、2 个模型请求并发，不重建另一套引擎。

最小完整改动必须一起交付：

1. 多个独立待办可以 in_progress，保留 ID、修订号与 generation。
2. spawn_agent、followup_task 和 explore 的任务项显式关联 todoId。代次由宿主在事务中确认并记录，不让模型手填内部 generation；校验、创建和关联原子完成。
3. 没有待办也仍可派发。旧会话保留原关联；新协议省略 todoId 就表示未关联，禁止暗中选第一个活动项。无关联子任务仍受全部直接子运行的完成检查约束。
4. 添加可选 dependsOn，仅支持任务完成依赖：前置项被明确接受后才就绪。拒绝缺失 ID、自依赖和环；依赖失败、取消不能视作完成。宿主冻结本次执行接受的依赖 generation/交付版本：前置项重开时，尚未启动的后继重新判定就绪；已启动后继保留原绑定并标记依赖变更，由 owner 决定继续、重验或重派，不能静默改绑。暂不增加中间里程碑协议。
5. 子运行结束与任务被接受分开；某项被接受即可推进其后继，不必等同阶段所有任务结束。已提交、就绪的执行请求可由现有队列启动，调度器不自行编造子任务。
6. 主代理操作按实际目标和活跃所有权检查冲突，独立文件可以修改，不因别的 agent 待办运行就全局禁写。E 仍限制主代理工具可见性，todo 修复本身不会重新赋予 shell。
7. 正常接管、重派和取消有明确记录，不靠改 executor 掩盖未交付工作；保留失败确认、最新续接结果及终态提交前的子任务重检。

旧会话按持久版本恢复，新协议随会话冻结；迁移不重写历史关联。多任务事务并发冲突通过已有 revision 重读重试，不能生成重复子运行。

### 4.3 有效并行还需要资源与写入边界

原生文件工具可以用真实目标做冲突判断。共享工作区里两个拥有不相交文件的代理可并行读写这些文件；同文件冲突继续排队或要求重分工。

任意 shell 是另一层约束。`src/tools/index.ts:252–271` 在无沙箱时将进程影响范围视作整个工作区。仅声明更小 scope 或只改 cwd 不能缩小真实影响；不能提前释放仍在运行进程的锁来换取并行。

独立 shell 工作采用实际受约束的独立执行环境，或已明确管理共享资源的独立 checkout；worktree 本身不构成 OS 隔离，Git 共享元数据、端口、缓存与外部输出仍可能冲突。分支创建/集成由一个 owner 执行，冻结每个任务基线，交付提交或补丁后统一集成并验证。当前共享无沙箱模式暂保守串行任意写命令。

独立副本必须成为该 run 所有工具的实际执行根。当前文件和命令工具主要使用 session.workspace；不能只设置 shell cwd，否则 file 工具仍会修改主树。执行根解析、scope、锁、工件来源与验收路径要一起适配，核对文件读写和测试导入均来自指定副本；不能让执行根变化扩大原有权限。

依赖等待交给调度器，不使用 sleep/文件轮询占住写锁。锁竞争且未启动的调用进入资源等待，不计入模型纠错连败；仍有取消、总截止时间和死锁诊断，不能无限重试。

先验证 2 个真正独立工作者的收益，再评估并发上限。增加代理人数不自动增大模型吞吐量，也可能争抢 2 CPU 的测试资源。

### 4.4 工具收缩为稳定的小集合，不牺牲操作能力

可以接近用户希望的基础工具体验，但保留并行协作就不能只剩四个文件/命令工具。下表是目标设计，不代表当前 Pi 的精确工具清单或已经实现的 Kodo 接口。

| 视图 | 常驻能力 | 处理方式 |
|---|---|---|
| 直接执行 | 读取、写入、补丁、命令；命令执行包含已登记后台句柄的查询/停止 | 约 4–5 个清晰入口；是否增加独立搜索，以调用成本衡量 |
| 协作主代理 | 读取/搜索、写入/补丁、委派、发送消息/续接、事件等待、验收检查、询问用户、简明计划 | 目标约 8–12 个；单独 cancel 或能力发现有必要时保留，不追求硬性数量 |
| 专项代理 | 基础集合加该任务必需的浏览器、LSP、图像或其他能力 | 创建时确定，运行中保持稳定 |

读取入口可以支持有界文本文件、目录和搜索，但须明确 literal/regex、路径、行号与分页；工件读取必须有清楚入口。不能以合并名字代替减少参数和描述，也不把所有能力塞入一个巨大的万能工具。

默认移出普通编程视图的候选：卡片创作/保留/派生、广泛知识浏览、通用进度录入以及重复的发现入口；高级工作流通过专门配置使用。四组主代理 39 个已暴露名称中共有 21 个未被提议调用，这是简化候选证据，不是删除依据：ask_user、取消、恢复及历史读取虽低频，仍须有可达路径。

第一步复用已有稳定角色视图与预设，不增加动态工具搜索平台。保留旧工具 ID/卡片版本用于旧会话恢复；新会话选择精简预设。当前 D/E 默认先不变，新视图完成并验证后再调整默认映射。

### 4.5 将等待与验收中的机械工作交给运行时

等待以子任务完成、失败、提问、用户输入、取消或总预算到期唤醒。五分钟内部状态检查不自动触发模型重新决定“继续等”；显式由用户要求的定时提醒另行保留。进程等待同样使用登记句柄与事件，不能恢复到 nohup 后自行 tail 轮询。

扩展已有 inspect_run，返回有界验收摘要：提交/文件状态、实际检查命令及调用引用、退出码、结果摘要、失败后修正与重跑关系、未覆盖项。必要时一次批量展开几个引用，避免为了查几条输出连续请求模型。

摘要由已有实际记录生成，不相信子代理自报“全部通过”；日志仍可展开，旧提交的验证不能证明新提交。主代理判断风险与缺口，成功任务不再逐一重演所有检查。独立全量测试原则上由集成/验证 owner 负责；代码、环境或测试配置变化后应重跑受影响检查。

### 4.6 推理与上下文优化放在正确位置

先减少不必要的工作量：前置全设计、宽泛审查、协调纠错和逐条验收。不能用删除协议要求的历史推理或盲目降低 max_completion_tokens 来代替这些修复，否则可能产生截断、失败和重做。

随后单独评估模型支持的推理强度或输出预算；不把生成上限等同实际推理量。长审查在已有共享预算内预留交付资源，达到边界时返回已证实结论、证据和未覆盖项，不能伪装全面完成。使用现有预算设施，暂不另建复杂预算系统。

保持系统文本、工具 schema 与历史前缀稳定；状态增量置于尾部。模型上下文只带当前工作所需内容，完整 relay/原生历史仍留在本地供分析。日志完整与每次请求全量重放是两个不同目标。

## 5. 实施顺序与验收

| 批次 | 内容 | 可证伪的验收 |
|---|---|---|

P1 的原生读写并行不依赖 P4；任意 shell 的广泛并行必须满足 P4。P2/P3 设计可并行审阅、机制独立测试。本轮按已授权范围只做冻结基线与整包优化各一次，不能分离各项改动的因果贡献；分项消融未执行。

必须覆盖：依赖缺失/环/失败/取消、同路径竞争、主子修改不同文件、等待中重启、重复事件不重复派发、跟进任务代次、全部直接子任务完成检查、终态前迟到派发，以及失败后的明确接管。机制测试使用离线 provider，完整套件也要重新跑；之前只有相关复测全绿，不能当作本版本完整全量通过。

## 6. 后续测量

旧四格仅保留作问题证据。当前授权规模为旧版本与优化版各一次，均使用修正后的 relay、同模型、同预算、同初始 main 分支及相同任务文本。旧构建在实现前冻结，运行顺序为旧版本再优化版；不自动补跑或增加格数。

本轮衡量整包优化，不能分离调度、交接、工具精简和独立副本各自的贡献。单次顺序试跑可发现回归，不能证明稳定收益。进一步分项消融不属于当前两格实验范围。

主指标始终是完整交付、外部质量、墙钟、真实总费用。解释指标包括首次有效修改前费用、任务 ready→started 等待、按 task/run 的模型排队与执行区间、锁持有/等待、取消传播延迟、末个执行者交付后的模型轮数、实际 schema 字节、未缓存输入和推理量。

并行分别统计子运行生命周期重叠、模型请求重叠和有用工作重叠，不以“创建两个代理”代替加速。读取重复需比较文件版本、区段和目的；跨代理读同文件本身不是浪费。验收往返 13–14 次可把常见完整交付目标设为 1–3 次，但这是待验证目标，异常与证据缺失不受此硬限制。

复用现有 relay/steps/tools/原生状态/工作区快照。增加 taskId、generation、dependsOn、执行副本基线和就绪/排队/阻塞/终态时间，便于还原关键路径；不复制一套状态系统。保留失败、取消、缺失用量与原始输出，不只统计成功请求。

## 7. 实现边界与兼容性

- 新会话默认 `taskProtocol: 2`、`toolProfile: compact-v1`，内置成员为 `1.2.0`。缺少版本字段的旧会话保持原行为；完整工具视图与旧任务协议可以分别显式选择。TUI 在活动会话中按名称启动成员时优先使用冻结名单版本。
- 实验前冻结优化实现的默认主代理工具实测为 24 个（完整视图 35），schema 为 20,285 字节（完整视图 32,483）；普通子代理为 15 个（完整视图 21），schema 为 13,001 字节（完整视图 17,719）。实验后的描述修复会改变 schema 字节，不改变工具数。没有达到 8–12 个入口的设计目标；保留了恢复、工件、文件操作与必要协调能力。隔离执行者另有 `workspace.commit`。显式专项配置及自定义卡片可增加工具，仍受角色与权限检查。
- 多活动待办与显式关联已实现；依赖等待、内部等待续期和资源竞争均由运行时处理。验收摘要来自真实调用记录，批量证据最多 8 条，不把成功退出码等同于语义验收。
- 独立执行采用各自拥有 Git 元数据的 clone，所有工具使用同一执行根。在依赖接受后、首次执行前创建副本；源已跟踪改动未提交时继续排队并通知主代理，未跟踪文件不自动复制。提交和集成由宿主管理，集成冲突保留主树。副本留作恢复，续接复用原副本。
- 原生文件和模型请求具备并发条件；无沙箱任意命令仍按源仓库家族互斥，Windows 原生沙箱保留既有全局写进程锁。这些模式的任意 shell 写入并发不在本轮已实现承诺内。
- 实验结束前保存主树、原生状态和 `/.kodo-executions` 副本；未集成、失败或取消的副本也保留。实验任务允许宿主管理副本，但最终必须集成到 `/app`，因此不与旧四格直接计算因果收益。
