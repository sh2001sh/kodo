# Kodo 差异化分析（终版）：功能全商品化，但竞品源码里空着五件事（2026-11-03）

> 缘起：先被指出「交付可信/纠正记住/改前先验证」是现有 harness 已有的东西（成立）；随后两轮竞品核查（Claude Code 源码 1902 文件 + [竞品问题处理](competitor-problem-handling.md) 的 Pi/OpenCode 源码对照）显示：**功能全部商品化，但同类产品在源码/文档层面明确空着五件事**，恰好是 Kodo 投入最深、也最难被"顺手补上"的方向。
> 一句话：**把功能当特色是死路；Kodo 唯一的机会是把「方法可验证、交付可审计、失败保守、业务文件原生、模型不锁定」做成一个复合承诺，钉在错误成本高的重复业务上。**

## 0. 结论

1. **功能层面没有空位**：记忆（含团队记忆）、Skills、插件市场、hooks、checkpoint/rewind、子 Agent、Agent Teams、定时任务、worktree、压缩、权限沙箱、会话恢复、TUI/Web/IDE、成本统计——Claude Code 源码全部有且成熟；OpenCode/Pi/Codex 各有等价。
2. **源码层面明确空着五件事**（§2）：
   - 方法/Skill 的**行为验收 + 版本采用/回退**（Claude Code 只做静态 manifest 校验，`rubric`/`grader`/`testPlugin` 源码命中为 0）；
   - **交付物审计对象**（无 deliverable/auditTrail 数据模型，无"已核/未核/依据"的交付记录）；
   - **保守失败语义**（Pi/OpenCode 无未知写入阻断、无完成≠验收、无硬预算预留账本、无压缩可溯源）；
   - **本地业务文件**（Claude Code 42 个工具全是代码/Git/shell/MCP，无 Office/PDF/表格）；
   - **非厂商锁定 + 本地私有**（Claude Code 只有 Anthropic 家族）。
3. **单独任一项都撑不起产品；五项的复合才构成定位**：业务文件 → 业务交付；方法行为验收 → 换材料复用不退化；交付审计 → 用户敢用；保守失败 → 出错代价可控；本地+模型自由 → 中文中小团队的成本与数据要求。
4. **Kodo 已有其中三项的地基**：案例冻结输入 + 比较 + 采用/回退 ≈ 方法行为验收；check 记录 + `quality.status` + `not_checked` ≈ 交付审计；effect/reconcile/预算预留/原文归档 ≈ 保守失败。缺的是业务文件与产品化流程。
5. **不要再比功能，改比可靠性**：用陷阱任务对照测「错误宣称完成率/未知写入恢复/预算透明度/第二期纠正次数」，这是唯一能证明差异化的实验（§6）。

## 3. 为什么这五项可以构成差异化

- **单点是功能，复合是产品**：业务文件（场景）+ 方法行为验收（复用不退化）+ 交付审计（敢用）+ 保守失败（出错可控）+ 本地模型自由（成本/数据），合起来回答的是同一个问题——**"这份工作能不能放心交给它，而且下个月还能用"**。竞品做其中一两点容易，同时做需要牺牲它们的产品指标（流畅度、云端数据、厂商锁定）。
- **与竞品默认哲学相反**：大厂默认"推进优先"（agent 不停、少打断、数据上云、绑定自家模型）；Kodo 的默认"停下核实、本地留证、模型自选"。这不是能力差距，是取舍差距——结构性、可长期占位，但会被"strict mode"追赶，窗口有限。
- **我们已经投入在内核**：事件溯源、effect 状态与 reconcile、决定版本、预算预留、原文归档、包 SHA-256、案例冻结/比较/采用/回退——这些不是演示层，正是五项空位的底座。
- **符合中文中小团队的现实**：本地部署、数据不出机、用国产/自有模型、错误代价高（财务/合规/交付）、需要交接。竞品是英文、代码场景、云端账号。

## 4. 修正后的定位 / 特色 / 设计方案

### 定位

**给「错误成本高、需要交接」的重复性业务工作，提供本地、私有、可验证方法、可审计交付的 AI 工作台。**
首批场景候选（只选一个）：周期经营简报/对账、合规材料整理、代账交付、招投标资料核对。共同点：错一个数就有代价、需要留痕、换人要做。

### 特色（承诺，可观测）

1. **方法改完先验证再用**：用旧材料+新材料各跑一遍，给出"4/5 → 5/5，可采用"，不合格可回退；不是静态检查插件格式。
2. **不把"跑完"当"做对"**：交付物旁逐项列出已核/未核/依据版本；未核的明确标出。
3. **不确定就停下**：外部写入/命令结果不确定时阻断核实，不自动重放；预算硬上限、未知用量单列。
4. **交付可交接**：产物 + 来源 + 口径 + 方法版本 + 检查记录打包，换人可复核可续做。
5. **本地、私有、模型自选**：无账号、数据不出机、可用国产模型，单位任务成本可算。

### 设计方案（四层；引擎冻结，不再加机制）

```text
场景层   业务文件（xlsx/docx/csv/PDF）· 口径库 · 检查器 · 模板 · 案例集
交付层   交付包 = 产物 + 已核/未核清单 + 来源 + 口径版本 + 检查记录 + 方法版本
方法层   方法（inline）+ 行为案例（冻结输入）+ 比较 + 采用/回退
引擎层   单主循环 · 本地执行 · 权限沙箱 · 事件溯源 · effect 核实
         · 预算预留 · 原文归档 · 能力包 SHA-256（已完成 → 冻结）
产品面   中文 Web 为主（业务用户）；CLI/TUI 服务技术用户
```

### 明确不做

多 Agent 卖点、阶段挂载继续开发、通用功能竞赛、社区市场、token 节省叙事、追求"更快的 agent"。

## 5. 四问检验

| 判据 | 结论 |
|---|---|
| 竞品结构上不愿做 | 通过：审计/阻断/本地/模型自由与其云端、流畅、锁定策略相反 |
| 用户一次就感知 | 部分通过：仅在错误路径和交接场景强感知，需场景与受众匹配 |
| 越用越值钱 | 通过：口径库、案例、审计记录、方法版本随使用增厚 |
| 我们有不对称优势 | 通过：内核已投入 8 个相关子系统；相对开源竞品是深度，相对大厂是取舍 |

## 6. 证明方式：两组实验，不再比通用编码分数

**实验 1（可靠性对照，2–3 天）**：陷阱任务 + 独立验收，Kodo vs OpenCode vs Claude Code（可选 Pi）：
| 陷阱 | 指标 |
|---|---|
| 命令退出码 0 但输出错/缺字段 | 错误宣称完成率 |
| 写入中中断/进程超时 | 未知写入发现率、重复执行次数、恢复人工干预 |
| 验收只覆盖部分要求 | 部分通过是否被报成通过、未核项披露率 |
| 429/流错误/供应商波动 | 预算超支、未知用量单列、中断恢复 |
| 方法升级前后 | 旧案例回归是否被发现、能否回退 |

**实验 2（产品假设，1 周）**：同一用户、同一方法、4 期业务材料；第 1 期纠正并保存方法，2–4 期测人工纠正次数、复核时间、合格率；硬门槛：方法加载事件>0。
**判定**：实验 1 显著优于对照 → 五项空位成立，可对外宣称"更可靠"；打平 → 转 §7。

## 7. 如果两项实验都不成立

- **C 开源引擎/组件**：把"核销、预算、归档、方法验收、包校验"做成可嵌入执行内核，进中文开发生态；无产品护城河但可持续。
- **D 服务内部引擎**：选已有服务业务（代账/咨询/招投标代理），卖"服务+软件"，行业口碑是特色。
- 共同点：不再以"通用 AI 工作台"和功能竞赛进入市场。

## 8. 需要拍板的三件事

1. **场景**：接受"错误成本高 + 需要交接"作为首批场景？具体选哪一个（对账/经营简报/合规材料/代账/招投标）？
2. **实验**：是否同意先跑 §6 两组实验（比编码矩阵便宜），用结果决定差异化是否成立？
3. **资源**：这个场景里你手里有没有不对称资源（客户/渠道/领域专家/服务业务）？没有的话，五项空位也只能做成开源组件，撑不起独立产品。

**证据边界**：竞品"未做"来自静态源码副本与对照文档（2026-10-20/26），非实时产品体验；官方文档与源码副本存在矛盾处已标注；市场判断未做用户访谈与规模研究，均为待验证假设。
