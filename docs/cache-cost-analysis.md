# 缓存命中率、优化实测与任务费用

日期：2026-10-20。模型：CodeGo `glm-5.3`，统一 Chat Completions。费用基线沿用[上一轮 256k token 目标窗口的 12 次真实任务](harness-comparison-256k.md)，不混入本轮探针或新任务。

本页“成功”沿用原自动验收口径；报告事实复核及加入质量门槛后的摊销，见[产物质量对比](quality-comparison.md)。结构通过不等于无需事实修正。

## 为什么 Kodo 的命中率低

上一轮全部尝试的加权输入缓存命中率：Kodo **33.55%**、Pi core **53.92%**、OpenCode **58.39%**。分母是实际输入 token，缓存是其中的子集。

对 Kodo/Pi 的 **58 份请求、50 对相邻请求**复核后发现：旧消息全部逐条保持为下一次请求的前缀，工具定义和系统决定消息均未变化。两类任务的四份首次请求，在仅归一化运行 ID、工作区后，完整 JSON 一致。因此，没有证据表明本轮差距源于 Kodo 在任务内破坏前缀；OpenCode 使用自身提示和工具，不能只比较循环。

具体反例：Kodo 报告 2 的第 6 次请求保留 39369 字符前缀，缓存仍为 0；第 7 次则命中 23332/25640（91.00%）。Pi 修复 1 同样出现 92.00% → 0 → 86.89%。字符共同前缀只用于检查文本稳定性，不能换算为精确 token 前缀。

这些数据证明缓存行为存在波动。路由、缓存有效期、驱逐和底层匹配机制都不可见，不能把其中任何一项断言为根因。

## 已实现的优化和实测边界

`src/runtime/context.ts` 将通用宿主规则和主/子代理静态规则放在首条 system 开头，将工作区、权限、运行 ID 后置。只变化运行 ID 时，首条消息的共同前缀由 **42 字符增至 864 字符**；不同主/子代理共享 579 字符通用规则。消息仍为原有 3 条，方法配置仍是 user，恢复身份替换、决定状态、执行权限校验保持原行为。

这是增加跨任务可复用前缀的改动。动态身份仍位于首条 system 尾部，不能宣称其后的整个任务或方法配置都可跨任务复用。

线上对照固定同一份真实请求的历史和工具，仅变化宿主布局与等长运行 ID。采用旧/新/新/旧、新/旧/旧/新的顺序，两种身份、每种布局各两次原样重复，共 8 次。输出上限统一为 32，只测输入缓存，不执行工具，不作为任务完成费用。目标窗口 256000 token；实际输入最多 25642，未测试满窗容量，也未执行 20k 字符组。

| 布局 | 请求数 | 输入 token | 缓存 token | 命中率 | 公开充值估算费用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 优化前 | 4 | 102562 | 27200 | 26.52% | ¥0.1652200 |
| 优化后 | 4 | 102562 | 26787 | 26.12% | ¥0.1658395 |

**本次没有测出缓存收益**，不能把前缀变长写成线上命中率提升。优化后同一请求原样重发，缓存仍从 1600 降至 0；旧布局另一份请求则从 0 升至 25600。小样本不能估计长期效果，耗时变化也不能归因于布局。继续提高真实命中率，需要核实网关支持的缓存及路由机制；现有公开信息不足以选择有依据的客户端参数。

## 按什么价格计算

CodeGo [公开价格元数据](https://codegoai.com/api/pricing)中 GLM-5.3 的输入倍率为 4、输出相对倍率 3.5、缓存读取倍率 0.25。站点前端公式为每百万输入 `2 × 模型倍率 × 分组倍率`。默认分组倍率为 1。

需区分站内余额显示和充值现金折算：[公开状态](https://codegoai.com/api/status)的 `price=0.25`、`usd_exchange_rate=7.3`；前端开启充值价时再乘 `price / usd_exchange_rate`。不能把余额显示的美元直接当成现金美元价格。

| 每百万 token | 站内余额显示价 | 公开充值折算人民币 |
| --- | ---: | ---: |
| 未缓存输入 | 8 美元余额 | ¥2 |
| 缓存读取输入 | 2 美元余额 | ¥0.5 |
| 输出，含推理 | 28 美元余额 | ¥7 |

账户实际分组、个人充值优惠未知，以下都是**公开默认分组、公开充值价的估算**，不是账户账单。公开模型行没有提供长上下文分档或缓存写入单价。价格版本为 `9d31d94c6e1ec64de1cf66f93783919fa08f15504215145e869f095730c9f728`。

```text
人民币费用 = ((输入 − 缓存输入) × 2 + 缓存输入 × 0.5 + 输出 × 7) / 1000000
```

缓存输入不重复计入输入，推理不重复计入输出。按用户要求，HTTP 429 为零 token，但计请求和时间；其他缺失 usage 的响应保留未知。仅当账户采用相同倍率和兑换口径时，上表现金估算才对应其购买成本。

## 完成一次任务相差多少

成功均值只计通过固定验收的尝试；摊销费用则将同组失败和重试开销除以成功次数。上一轮每组只有两次尝试，不能由此预测长期成功率。报告通过指结构及证据条件，人工复核仍发现部分事实错误，详见原报告。

| 任务 | 内核 | 成功/尝试 | 成功任务平均费用 | 含失败的每份成功交付费用 |
| --- | --- | ---: | ---: | ---: |
| 仓库报告 | Kodo | 2/2 | ¥0.1381975 | ¥0.1381975 |
| 仓库报告 | Pi core | 2/2 | ¥0.1091675 | ¥0.1091675 |
| 仓库报告 | OpenCode | 1/2 | ¥0.1401630 | ¥0.1401630 |
| 分页修复 | Kodo | 2/2 | ¥0.06200375 | ¥0.06200375 |
| 分页修复 | Pi core | 1/2 | ¥0.06277850 | ¥0.21107300 |
| 分页修复 | OpenCode | 2/2 | ¥0.09994075 | ¥0.09994075 |

- 仓库报告：Kodo 比 Pi 每份贵 **¥0.02903（26.6%）**；比 OpenCode 便宜 ¥0.0019655（1.4%）。Kodo 同时有更多累计输入与输出，差价不能全归因于缓存。
- 分页修复：仅比较成功任务，Kodo 比 Pi 便宜 **¥0.00077475（1.2%）**，比 OpenCode 便宜 ¥0.037937（38.0%）。缓存比例低，仍可能因总输入更少而成本更低。
- 计入失败：Pi 错误修复额外消耗 ¥0.1482945，使修复的每份成功交付成本高于 Kodo ¥0.14906925；Kodo 低 **70.6%**。这是本批摊销，不是稳定优势。
- OpenCode 报告失败的 6 次请求均为 429，按约定费用为零，所以其摊销费用不变；交付耗时仍从成功样本的 73.0 秒增至 155.8 秒。

## 优化后的真实任务复测

另外执行 Kodo 两项任务各一次，保留 256k token 目标窗口、原预算和验收；该组源码已含本次前缀优化及新增回归，不能与旧组混合取均值。

| 任务 | 结果 | 请求/工具 | 输入/缓存/输出 token | 公开充值估算费用 |
| --- | --- | ---: | ---: | ---: |
| 分页修复 | 通过 | 4 / 4 | 16435 / 0 / 1619 | ¥0.044203 |
| 仓库报告 | 网关通道不可用，失败 | 6 / 10 | 已知 32868 / 10837 / 126，另 1 请求未知 | 已知 ¥0.0503625 + 未知部分 |

修复任务仅修改目标 `history.ts`，实际完整通过 **16/16** 上下文测试，独立 Unicode 无损分页、非法页界拒绝、跨会话拒绝检查均通过。缓存为零，但调用和输入量更少；不能把较低费用归因于缓存优化，也不能由单次样本证明长期费用下降。

报告的第 6 次响应为 HTTP 200，网关先发 SSE 心跳，随后裸写 `new_api_error / get_channel_failed`，提示当前模型服务暂不可用。没有正常结束事件或 usage。内核以 `MODEL_INCOMPLETE` 拒绝执行这次响应的工具；不是输出上限截断。该次费用保持未知，不能套用 429=0 的规则，也不能把预算预留当真实消费。错误分类可进一步细化，本次未扩展修改。
