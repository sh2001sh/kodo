# 256k token 目标窗口下的真实任务效率比较

日期：2026-10-20。模型为 CodeGo `glm-5.3`，统一 Chat Completions。只跑 Kodo、Pi core、OpenCode 的大窗口配置，没有执行 20k 组，也没有启动本地模型。

缓存前缀取证、优化实测及按 CodeGo 价格计算的任务费用，见[缓存与费用分析](cache-cost-analysis.md)。该分析保留本报告为费用基线，另列优化后的新任务。

五份报告的独立事实核验、六份补丁的追加行为验收见[产物质量对比](quality-comparison.md)。本报告的 10/12 是原自动验收结果；加入报告事实门槛后为 8/12，原始样本与结果不覆盖。

12 次任务的固定验收共通过 **10 次**：Kodo 4/4、Pi core 3/4、OpenCode 3/4。Pi 一次错误补丁耗尽时间；OpenCode 一次全部请求遇到 HTTP 429。总计 **82 次远程请求、96 次工具调用、810859 token**。按用户明确要求，**HTTP 429 = 0 token**，但请求次数、重试和耗时照计；本组有 7 次 429。

## 256k 的具体含义

本轮目标窗口为 **256000 token**，没有把 256000 字符改名为 token：

- OpenCode 模型配置为 `limit.context=256000`；Pi 模型元数据为 `contextWindow=256000`。
- 当前 Kodo 仅有字符预算。本次将 Kodo/Pi 字符阈值设为 `Number.MAX_SAFE_INTEGER`，关闭字符裁剪，并移除转发器的 256000 字符截断；未修改生产内核。
- 用成功响应的供应商 `prompt_tokens + outputLimit ≤ 256000` 事后核对窗口。429 按零消耗结算，不把拒绝请求当作已实测输入。所有实际生成响应均有 usage，并满足该条件。
- **本组实际最大输入为 25640 token**，加 3072 输出预留为 28712。这是目标窗口配置下的任务效率测试，**没有填满 256k，也没有验证满窗记忆能力或供应商的实际最大容量**。CodeGo 的模型列表未提供窗口元数据；Kodo 此方式也不等于已实现发送前的精确 token 限额。

保留 500000 累计预算、26 次远程请求、240 秒任务执行、单次 3072 输出预留；Kodo/Pi 还有 70 次工具预算。现有预算账本会按 UTF-8 字节作保守预留，429 也可能留有内部预算占用，这不是本表的消费量。本组没有触发本地调用、token 或上下文预算拒绝。OpenCode 的工具数从原生记录核对，不宣称具有与 Kodo 相同的 70 次工具硬闸门。

## 验收与事实复核

修复任务从同一个冻结源码注入游标回归，要求仅修改 `src/runtime/history.ts`、完整运行 `tests/context.test.ts`，并通过隐藏的独立行为验收。每组先有未注错正例与已注错负例。五个成功修复都真正完整执行 **15 passed (15)**、退出码 0；独立验收覆盖 Unicode JSON 无损分页、非法页长拒绝、跨会话读取拒绝。五份最终补丁均与冻结正确源码字节一致。

Pi 修复 1 把 `position=0; break;` 改成裸 `break;`，遗漏 `position=end`。随后四次完整测试达到宿主 30 秒工具超时，一次使用无效 basic reporter，最后一次被总体时间耗尽取消；独立 oracle 报 `cursor did not advance`。没有 OOM 或上游 429 证据。这次失败不能归因于上下文裁剪，也不能由此断言 Pi 循环必然劣于 Kodo。

五份成功报告都实际读取 5–6 份项目文件、包含源码，列出至少两条真实限制，保存 Markdown，并明确说明本轮没有运行验证；与执行记录一致。人工审核发现 Kodo 1 泛化恢复延续行为、把归档 marker 的 ref 写成 archivedRef；Pi 1 有引用定位及未验证/未实现混淆；Pi 2 错述 offset 上限与 file.search 的大文件/编码行为。Kodo 2 与 OpenCode 2 未发现明显实质性错误。因此报告结构验收通过不能解释为逐句完全准确。
