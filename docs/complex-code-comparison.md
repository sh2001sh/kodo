# 最大容量模型下的复杂代码任务对比

日期：2026-10-20。网关 CodeGo，模型别名 deepseek-v4.1-flash，Chat Completions。三套内核各两次，六次全部自然结束，没有补跑替换失败。未启动本地模型。

**缓存下降不能归因于本轮开子代理：321 次真实模型请求、400 次工具调用中，子代理工具调用为 0。** 三套内核的可测加权缓存率分别为 Kodo 95.70%、Pi 96.86%、OpenCode 97.53%。本次复杂任务的缓存表现明显高于旧 GLM 小任务，但模型、任务、容量和思考历史回放都发生变化，不能据此认定单一优化的因果收益。

**解除长度限制解决了截断障碍，但没有解决交付完整性。** 原自动验收为 Kodo 1/2、Pi 2/2、OpenCode 1/2；统一追加边界复核后，严格公共契约合格为 **Kodo 1/2、Pi 1/2、OpenCode 0/2**。Pi 首轮仅错误码偏差；OpenCode 首轮有异常索引引起的查询崩溃。不能把这些不同严重性的问题合并解释为“都不会实现功能”，也不能只看原 86 项检查就宣称完全正确。

## 容量与对照条件

- 按用户最新要求使用模型声明的最大容量：**1,000,000 token 输入与输出合并窗口，最大输出 393,216 token（384K）**。所有 321 次出站请求都明确发送这个输出参数；Kodo/Pi 使用 max_completion_tokens，原生 OpenCode 使用 max_tokens。两者受合并窗口约束，并非允许 100 万输入再叠加 384K 输出。
- 移除了基准的请求次数、工具次数、累计 token、10 分钟任务、120 秒请求及 2MB 请求/模型响应限制。Relay 与 OpenCode 外部任务计时器停用；必须使用数字预算的 Kodo/Pi 使用安全整数与平台计时器技术上界。模型窗口、协议完整性、取消信号和工具自身输出/文件限制仍有效。
- 实际最大输入为 **131,929 token**，实际最大单次输出为 **11,649 token**。已出现超过旧 8192 输出和 2MB 流大小的成功响应。没有人为填满窗口，**不证明 100 万 token 满窗保持能力，也不证明网关能实际生成 393,216 token**。容量依据是官方声明，网关探针只证明接受参数。
- 同一冻结源码、公共任务与验收；单代理执行。首轮 Kodo→Pi→OpenCode，第二轮反序；远程任务顺序执行。准备和独立审查的宿主子代理没有调用本次网关 API，不进入测试用量。
- Pi 为官方 Agent core 1.3.0，共用 Kodo provider、工具、提示与私有思考回放，**不是完整 Pi coding-agent**。OpenCode 为 1.19.3 原生 Windows CLI、提示和工具；因此不是只有主循环不同的纯对照。
- 当前任务不是报告任务，Kodo 的报告专用完成纠错钩子不为此实现任务兜底。实现是否合格在结束后统一核验。
- 试验结束、维护前，manifest 中 87 个文件在冻结副本与当时主仓库均逐项 SHA-256 一致。随后只修改命令证据识别器及清单说明、增加本报告；六份候选、原始结果、manifest 和冻结源码均未改写。

官方容量依据：[价格与容量](https://api-docs.deepseek.com/quick_start/pricing/)、[Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)、[官方 harness 默认窗口](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/src/defaults.ts)。保存的网页与来源在本批次 official-capacities/ 中。

## 任务与独立验收

从零实现历史归档目录：runtime 的 listHistory、Application 公共入口、CLI history 命令、README、两份新测试，只允许六个指定文件。覆盖持久索引、恢复链授权、全局排序与去重、超过 100 个归档、分页安全整数、严格 CLI 数字、只读和持久重启；不是修复一条预置错误。

冻结的 86 项隐藏行为验收有独立正负控制：原始未实现源码仅 17/86，隔离正确实现 86/86。候选还须完整运行两份新测试及原有 context/recovery/cli 三份测试，完成 build、TypeScript noEmit 与 ESLint，不得改旧测试和配置。独立验收另在隔离副本执行，不能代替模型自己按要求执行。

六份候选均通过冻结的 86 项行为检查；独立五文件测试均为 62 或 63 项通过。但 Kodo 第二轮的新增测试存在类型与 lint 错误，而且模型没有完成全部交付要求。追加探针统一作用于六份：精确非 history 命令错误码、JSON null 无效归档索引；不改原成绩，不向后续任务模型透露隐藏结果。该复核未盲化，且仍不是所有输入的正确性证明。

## 真实执行问题

1. **Kodo 第二轮提前空答完成，属于当前内核尚未补齐的完成判定。** 第 37 次响应 HTTP200、完整终止标志、finish_reason=stop，无正文、无工具，只有私有思考内容；输出 685 token，远未达到上限。内核将其记为 completed，最终文本为空。只改了五文件，README 未更新；自己只跑新增两文件 14 项测试，没有完整五文件回归、noEmit 和 lint。独立检查发现 tests/cli-history.test.ts 的 env.KODO_DATA_DIR 推断类型错误（TS2339，exit2），以及 history-catalog.test.ts 的无用赋值（lint exit1）。功能 86/86 与运行终态都不能抵消交付失败。完整终态后的 CLIENT_ABORTED 记账标记不是本次失败原因。
2. **Pi 首轮的 CLI 错误分类偏差。** run history --offset -1、run history --limit -1、inspect history --offset -1 均须返回精确 ARGUMENTS，却返回 HISTORY_ARGUMENTS。原因是把参数列表中出现 history 当作当前命令。请求仍提前拒绝，未发现权限扩大或数据副作用。原隐藏验收使用宽泛的 ARGUMENTS 正则，漏掉此差异。带空格的数字另列解释边界，不用于主要判错。
3. **OpenCode 首轮有异常索引查询崩溃。** 索引指向合法 JSON null 时，在保护范围外读取 snapshot.version，导致整个 listHistory 抛 TypeError；应排除无效快照。相同 fixture 其他五份均正常返回有效条目。它还存在与 Pi 首轮相同的 CLI 错误码偏差。旧验收测了无效对象形状而未测 null，原 86 分保留。
4. **OpenCode 第二轮留下额外文件。** 额外 smoke 中 Windows 变量未展开，在工作区生成 %TD%/err.txt 与 %TD%/run.txt，违反六文件范围；原 scope 不合格保留。它的功能、追加边界和真实静态检查通过。原 buildAndCheckRun=false 是证据识别器对 && echo BUILD_OK/TYPECHECK_OK/LINT_OK 的误伤，已离线更正为 true；总体仍不合格。原生 shell 还使用固定外部临时目录做 smoke；文件范围事后检查不是操作系统沙箱，不能将现有工具权限称为强隔离。未据此推断发生既有数据删除。
5. **整文件替换工具容易被误当局部补丁。** Kodo 首轮曾将测试文件暂时替成短片段；Pi 第二轮也将约 11k 字符测试替成 510 字符片段，随后恢复。均无最终残留，额外修复已计费。这是共享工具契约的交互问题，不能仅归因于某个循环。候选还经历断言、CLI 位置参数、测试超时、lint 和 Windows ESM 路径返工。

当前明确未修复的是：空最终响应被当作任务完成，以及实现任务缺少可执行的交付验收回路。这里没有以事后人工补齐候选来掩盖失败。测试中生成的新历史目录功能只存在候选副本，未自动并入主产品源码。

## 缓存与费用解释

全组 315/315 对相邻请求的旧消息、tools、system 均稳定；304/304 对旧思考历史保留，207/207 处上一响应思考完整回放。前缀稳定但零缓存、至少 50 个百分点波动、思考历史丢失均为 0。没有模型子代理调用，不能用多代理上下文分叉解释这批命中率。

三者完整任务缓存率仍只能给区间：Kodo **95.6419%～95.7057%**，Pi **96.8261%～96.8658%**，OpenCode **97.4264%～97.5298%**。表内 95.70%/96.86%/97.53% 是排除缺缓存字段首请求后的可测加权值。未知缓存不是零缓存。

KODO_PROMPT_CACHE=off 表示不发送客户端缓存提示键，不是关闭上游自动缓存。不同模型和网关路由、TTL、驱逐不可见，客户端相同文本前缀也不等于已知的底层 token 缓存前缀。旧 GLM 批次已经发现稳定前缀仍零缓存的反例，本批没有复现，不能据此倒推旧批次的唯一原因。

公开价格：每百万非缓存输入 ¥0.50、缓存输入 ¥0.01、输出 ¥2.00。计算为（非缓存输入×0.50＋缓存输入×0.01＋输出×2）/100万。缺缓存字段的请求按全部命中与全部未命中给费用边界；缺输入/输出时须标未知。429 按用户约定零 token，但仍保留请求和耗时。

按相同 22,550,202 输入和 310,630 输出，假设输入全部未缓存，公开价反事实估算为 ¥11.896361；本次按已知缓存得到 ¥1.194206～¥1.201974。它说明缓存对费用的影响，不是核实的账户扣款，也不是一次缓存优化的因果实验。即便总 token 更大，缓存输入单价低、输出量较少时费用仍可能更低；不能用总 token 单独推算费用。
