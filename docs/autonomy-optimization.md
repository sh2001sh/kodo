# 自主委派诊断复核与优化方案

日期：2026-10-20。状态：P0/P1 已实现并通过回归；新增真实委派正控制通过。P2 的 A/B/C/D/Solo、三类任务、每组每任务两次探索性重复已完成：按规格验收27/30，开放协作的24次运行全部零创建，尚未达到自主分工收益标准。结果见 [实现与分组实测](autonomy-optimization-results.md)，冻结目录 `.kodo/autonomy-factorial-1792500488622`。以下原诊断与实验建议保留；执行结果另见后续实测报告。

依据：[原诊断](autonomy-diagnosis.md)、[原自主协作评测](autonomous-performance-comparison.md)、`src/runtime/context.ts`、`src/messaging/index.ts`、`src/runtime/history.ts`、`src/tools/index.ts` 与诊断数据库／请求快照。

## 1. 复核结论

原分析总体正确，尤其正确地区分了机制可用、模型主动选择、最终交付合格这三件事。应将“根因已定位”收窄为：已确认可观察的断点在首次委派请求之前；默认角色方法不足是有源码依据的改进方向，但提示、模型和任务结构的因果贡献尚未被分离。

| 原结论 | 复核判断 | 限定条件 |
| --- | --- | --- |
| 创建与等待链路可用 | 成立 | 只证明一个明确要求的只读子任务；不是任意协作场景都正确 |
| 主代理缺少具体委派方法 | 成立 | 可以确认配置欠缺，不能直接证明它是零委派的唯一或首要原因 |
| 卡片与结果引用误用增加成本 | 成立 | 错误发生在新的明确委派对照，不能反向解释原批次的零创建尝试 |
| 原任务不足以验收自主分工 | 成立 | 一种紧耦合任务的两次 auto，不是 104 次独立决策实验；4/4 是交付通过 |
| 单段提示没有立即改变选择 | 成立 | 每种提示仅一次中段探针，下一步读取文件可能是合理的分解准备，不证明后续永不委派 |

主代理拥有编程工具本身不是错误。禁用这些工具来制造委派，会改变产品的可用能力，也会让简单任务付出无必要的通信成本。导演式主代理应有分工与整合责任，同时保留小任务直做和必要核验能力。

## 2. 独立复核到的证据与新增发现

本次用只读 SQLite 连接与已保存请求检查以下事实，没有读取或输出凭据，没有调用外部模型，也没有改写原始评测证据。

- 原 auto 两次分别有 50、54 个请求，全部提供六个协作工具；工具调用记录中的 `spawn_agent` 均为 0，未设置 `tool_choice=none`。
- 明确委派对照有 8 个模型调用、1 个子代理；子代理实际工具结果包含随机文件标识，主代理没有调用 `file.read`，最终输出包含真实标识，主子均结束。
- 两个失败调用分别是 `CARD_NOT_FOUND` 和 `HISTORY_DENIED`；原诊断列出的错误与数据库结果一致。
- 两份决策探针请求仅第一条系统消息不同，原始组与原请求内容一致，原文件 SHA-256 与报告一致。

新增发现一：结果读取存在能力缺口，不只是描述不清。`list_agents` 给出内部 `resultRef`，`history.read` 只允许通过 `context.compacted` 事件登记的归档引用。本次对照的归档事件数为 0，所以即使模型改用正确的历史发现方式，也没有归档可供核验该子任务原始调用。宿主审计能读取数据库，不代表模型拥有同等证据入口。子结果转述成功也不等于主代理独立核验了原始证据。

新增发现二：结果在上下文中重复。`Mailbox.onTerminal` 投递完整子结果，`refresh`／`settle` 的唤醒事件又包含相同结果。读取 `request-8.json` 确认首次唤醒请求同时含两份相同结果，后续请求继续携带。它可能增加通信和上下文成本，但没有证据说明它导致原批次不委派。

新增发现三：当前通用子代理继承父卡片、模型绑定和不超过父级的粗粒度权限。只修改一个共享卡片的提示可能把“导演职责”同时传给子代理。优化应明确主／子角色方法的装配位置，不能靠所有 Agent 共用一段强制委派提示。

## 3. P0：先消除协作操作歧义

### 3.1 创建运行与选择卡片分开

修改现有 `spawn_agent` 的描述与字段说明，不添加新的创建框架：

- 不知道已注册卡片 ID 和版本时，省略二者，创建继承当前卡片的通用子任务。
- `card_id` 和 `card_version` 只选择已存在的不可变版本，不能通过命名创建卡片。
- `objective` 说明可验收交付；`context` 提供资料位置、已确认约定、约束、负责范围与验收方法。
- 子代理没有父会话历史，但共享工作目录；禁止在相同资源上做未经协调的并发修改。
- 无效卡片仍返回错误，并附可执行修正方式；不能静默回退为其他卡片。

保留显式卡片字段供已知注册卡片使用；专业卡片检索随后按真实需要实现，不能成为通用子任务的先决条件。`scope` 目前主要是任务约定，不能将提示中的文件范围宣传成操作系统强隔离。

### 3.2 提供可消费的结果与证据

`list_agents` 保持轻量，只列 ID、职责、状态、决定版本及结果可用性，不再向模型暴露无法消费的裸 blob 引用。内部存储仍保留这些引用用于恢复和审计。

优先落实设计中已有的 `inspect_run`，用途是受限查看运行摘要与核验依据，不是任意 blob 读取：

- 主代理可以按运行 ID 查看自己管理的子运行、终态结果及相关工具证据；必要的恢复链授权沿用已审计规则。
- 同伴只得到获准的状态或显式共享产物，不因同会话就自动获得另一执行者全部历史。
- 证据按运行 ID／调用 ID 查询，数据库解析真实归属；支持分页和输出上限，返回实际工具状态、退出码或工具输出，而非只返回模型自述。
- `completed` 与 `quality: not_checked` 分开显示，进程工具“执行成功”与进程退出码也分开。
- 隐去密钥与不必要的私有输入，保留当前任务授权；拒绝跨会话、非受管运行及伪造调用 ID。

这是新增一个面向模型的工具入口，但它补的是已有设计要求的核验能力。不要开放 `read_blob(ref)` 来修复 `HISTORY_DENIED`，也不要要求每个只读子代理额外获得 `artifact.write` 才能交付证据。

### 3.3 一份结果正文，一种读取路径

终态事件携带有上限的结果摘要、运行 ID、决定版本与证据入口；等待事件只描述条件、原因及相关运行 ID，详细内容按需读取。上下文压缩后仍可按运行 ID 再读取，不能要求模型只能依赖曾经出现过的通知。

历史归档、产物与运行结果明确区分：`history.read` 读取归档引用，`artifact.read` 读取产物 ID，`inspect_run` 读取受管运行及证据。协议允许的工具结果仍可用 JSON 字符串传输，但内部不要反复把 JSON 正文塞入字符串字段，增加无意义的转义层。运行时控制字段与不可信子代理正文保持分离。

## 4. P1：补全可执行的导演方法

主代理方法放在角色专属装配处，通用卡片继续表达领域方法。首版使用一份简短固定策略，不新增规划 Agent、每轮强制反思或专门的委派打分服务。

建议主角色指导：

```text
你对整体交付和验收负责。开始任务并完成必要的初步了解后，判断是否存在
目标清楚、输入可提供、结果可核验、与当前工作少冲突的独立任务。
当独立调查、实现或验证有望改善交付质量、缩短关键路径或减少主上下文负担，
且收益值得额外启动、通信和整合成本时，使用 spawn_agent。
小任务、紧耦合修改、必要输入尚不明确或剩余预算不足时直接处理。

委派时提供目标、必要资料、约束、负责范围、验收条件和结果形式。
未知已注册卡片时省略卡片字段，不编造 ID。子代理不会继承你的完整对话。
委派后推进其他不冲突的工作；确实依赖结果才调用 wait_for_events，不轮询。
允许协作者直接问答，跨任务约定变化由你统筹。
收到结果后检查证据和整合状态，不能只凭 completed 宣布验收通过。

发现新的独立工作、范围明显扩大或现有方法连续失败时，重新判断分工。
不要按文件数、工具次数或固定人数机械创建代理，也不要把全部工作再做一遍。
```

不要求每次模型调用都输出完整规划理由。可以给用户一句实际分工说明，评测主要观察任务划分、调用与交付证据，不依赖不可见推理或自我评分。

初期优先委派只读调查、测试设计和独立审查。并行实现必须先确认契约和文件责任；当前同目录共享、写锁与哈希前置条件能控制部分冲突，不能保证业务整合正确。

有子代理不等于有收益。主代理启动子代理后立即等待，可能仍通过上下文隔离或独立验证获得价值；只有同时存在独立工作且关键路径缩短，才称为并行加速。

## 5. P2：从任务起点做可归因的实验

先用离线测试检查协议与授权，再用明确委派的真实正控制验证操作摩擦是否减少，最后才验收自主选择。真实任务不写“必须委派”“至少两个 Agent”等要求，任务起点使用干净历史与相同项目状态。

### 5.1 对照组

| 组别 | 协作接口 | 导演方法 | 用途 |
| --- | --- | --- | --- |
| A | 旧 | 旧 | 当前行为基线 |
| B | 新 | 旧 | 识别工具语义与结果消费改善 |
| C | 旧 | 新 | 识别角色方法改变；策略不引用尚不存在的工具 |
| D | 新 | 新 | 验证组合效果及交互影响 |
| Solo | 关闭协作工具 | 使用对应的通用执行指导 | 判断实际任务质量、耗时与消耗是否值得协作 |

这是实验配置，不新增五种用户产品模式。最小预试可先运行 A、B、D；如果要声称是哪种改变有效，则补齐 C。接口变化会改变工具 schema 和输入长度，记录这是干预的一部分，不假装只有正文提示发生变化。

模型、协议、任务、工具权限、任务数据、输出容量、预算、并发和验收条件在对应组内冻结。先沿用现有容量配置，不能为了触发协作单独压低主代理上下文或撤掉工具。实验顺序交错或随机分块，记录网关、限流、缓存与供应商返回的模型标识；无法控制的变化明确列出。

每组至少多次重复作为探索性验证，例如每任务 3 次；这仍不足以声称统计显著。用预试观察波动后再决定样本量和可接受的质量／成本差异，保留全部失败、无委派和返工记录，不选择最好的一次。若需检查模型倾向，在接口和策略固定后追加模型因素实验，不在第一轮同时换模型。

### 5.2 任务集合

| 类型 | 示例 | 观察重点 |
| --- | --- | --- |
| 明显独立的工作 | 两个互不依赖模块的缺陷调查，最后整合结论 | 能否在早期识别分工，避免主代理先把全部工作做完 |
| 有契约依赖的工作 | 接口约定确定后，独立实现与测试设计 | 能否先澄清契约，再开展有用的局部分工 |
| 不宜委派的小任务 | 单一配置或边界明确的小修复 | 是否保留直接完成能力，避免无收益通信 |

在实验前由人按依赖、输入可获得性、写入冲突和验收条件标注可委派机会，允许多个合理分工，不把模块数量等同于必须创建人数。另留未用于调提示的任务检查泛化。

“存在可分工机会”和“委派具有净收益”分别验证。必要时增加单独标注的受引导对照，测量某个分工是否真的改善结果；其成绩不计为自主选择成功。

### 5.3 指标与接受条件

- 交付：相同隐藏验收、整合测试与范围检查；独立记录失败和遗漏。
- 自主选择：可委派任务中是否产生有内容、有边界且被使用的子交付；小任务中是否有无效委派。两者都报告，不以创建总数排名。
- 时机：首次有用委派发生在主要工作完成前还是之后，防止“最后补一个审查代理”虚增分工指标。
- 协作成本：参数错误、无效读取、重复结果字节、等待、人工介入与主代理重复工作。
- 收益：端到端耗时、全会话 token／费用、主上下文峰值、真实跨 Run 并发和关键路径。主上下文下降不等于总 token 下降。

P0 的确定性验收要求非法卡片可明确修正、无归档子任务的证据可合法读取、越权读取被拒、结果正文不重复注入；真实正控制检查模型能否无误使用，不把单次成功当作保证。

P1／P2 的接受条件是在保住交付质量与小任务直接执行能力的前提下，对预先选定的目标场景观察到可重复的委派利用和至少一项实际收益，并报告增加的成本。阈值在查看新实验结果前根据预试基线确定，不能事后挑指标宣布成功。

## 6. 修改范围与实施顺序

| 顺序 | 主要位置 | 交付 |
| --- | --- | --- |
| 1 | `src/messaging/index.ts`、受管运行证据查询、相关工具 Schema | 卡片语义、明确错误、`inspect_run`、轻量列表与去重结果 |
| 2 | `src/runtime/context.ts`、必要的默认卡片说明 | 主／子角色分离的导演方法与证据消费指导 |
| 3 | `tests/collaboration.test.ts`、上下文／历史／授权相关测试 | 正常和拒绝路径，挂起／终态顺序与结果消费回归 |
| 4 | `scripts/compare-harnesses.mjs` 及现有评测辅助模块 | 冻结对照、独立任务集、行为与质量分开计量 |

先保存可复现的旧版行为，再修改；当前目录不是 Git 仓库，应延用现有源码冻结与摘要机制，避免覆盖旧证据。生产默认只在新验证通过后更新。接口和策略分别记录版本，以便退回旧策略而不回滚历史数据。

暂不做：硬编码始终创建两个 Agent、删除主代理全部工具、单独增加规划 Agent、直接换模型、放大并发额度、开放任意 blob 读取，或用提醒循环反复逼模型委派。这些做法没有得到本轮证据支持。
