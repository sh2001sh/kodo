# 阶段 2 设计：可寻址上下文存储（2026-11-04）

依据 [最终定位与执行方案](kodo-final-positioning-20261103.md) §2、§5 阶段 2。本文先给出深埋事实 QA 的基线数据，再据此排定实现增量与验收口径。

## 1. 基线：深埋事实 QA（`scripts/context-store/dfqa.mjs`）

任务：阶段 0 基线提交的文档切成 54 页（约 36 万 token），16 个虚构事实埋在 25%–75% 深度，每个答案只能在对应页找到。第一阶段回放“主 Agent 已逐页读完”的历史，在 128k 窗口上跑一步，默认策略触发压缩（摘要每次都安装成功）；第二阶段在同一对话里一次问 16 题。代码：`main` 的 1f（`cf0939e`）。证据：`.kodo/context-store/dfqa-baseline-1f/`、`dfqa-baseline-1f-archive/`。

| 条件 | 答对 | 答题阶段输入（均值） | 其中未命中缓存 | 模型调用 | 模型怎么找 |
|---|---|---|---|---|---|
| 闭卷（答题时不能调工具） | 1/48 | 20,049 | 约 1.8 万 | 1 | — |
| 开卷（默认工具，材料文件仍在） | **48/48** | 78,528（3.9×） | 约 3,000–4,400 | 2–3 | `file.search` 搜工作区，每次只返回命中行 |
| 归档（默认工具，答题前删除材料文件） | 2/48 | 928,923（r1 达 2.67M） | 约 18.7 万 | 1–52 | r1 盲翻 `history.read` 124 次、耗尽预算、0 分；r2/r3 搜不到文件后放弃 |

另有两组无效测量保留为排查记录：`dfqa-baseline-1f-failed-nowire`（中转日志目录缺失，请求没发出）、`dfqa-baseline-1f-noread-instruction`（第一阶段“不要再读取文件”的指令留在对话里，抑制了开卷回读）。

### 1.1 结论

1. **原文还在工作区时，现有产品已经能完整找回**：`file.search` 一次命中一行，16 题全对。定位方案引用的“开卷是闭卷的 4.8–9.2 倍”来自更早的实验条件（整段重读）。
2. **原文只在本会话历史里时，现有产品基本找不回**（2/48）：
   - 压缩摘要让模型“用 history.search 查细节”，但默认卡的工具视图把 `history.search` 隐藏了；
   - `history.search` 本身是逐字扫描、每页最多 12.8 万字符，36 万 token 的归档每个问题要翻多页；
   - 剩下的 `history.read` 只能按位置翻页，模型只能盲翻（r1：124 次、267 万输入、0 分）。
   这正是“无损”性质（移出的内容随时可取回）目前缺的那一块，也是上下文存储的第一个目标场景：工具输出、网页、已改动或删除的文件，原文只存在于会话历史里。
3. **输入总量的“≤ 闭卷 2 倍”无法作为模型按需拉取的口径**：任何由模型自己取证据的做法至少两次调用（一次取、一次答），每次都带着同一段基础上下文，总量天然超过 2 倍（开卷第二、三次调用 95% 以上命中缓存）。只有由 harness 在模型开口前替它塞证据才能压到 2 倍内，而这是定位方案明确放弃的做法。

## 2. 验收口径（需用户确认的调整）

| 项 | 原提案 | 建议 |
|---|---|---|
| 质量 | 达到开卷的 90% 以上 | 不变：归档条件 ≥ 开卷条件的 90%（开卷当前 100% → 至少 14.4/16） |
| 成本 | 输入总量 ≤ 闭卷的 2 倍 | **按未命中缓存的输入计**：归档条件 ≤ 闭卷的 2 倍（闭卷约 1.8 万 → 不超过约 3.6 万）；输入总量与调用次数同时报告，另设绝对上限：单次答题阶段输入总量 ≤ 30 万（防止盲翻） |
| 黄金评测 | 不退化 | 不变：同时段对照、样例中位数成本 ≤ 1.10、P90 ≤ 2.0 |
| 子运行 | 重复读取率明显下降（原基线 42%） | sub-01 中“子运行重读主运行已读文件”的比例从约 0.6 降到 0.3 以下 |

## 3. 实现增量（每步单独评测，一次只改一处）

| 增量 | 内容 | 判定 |
|---|---|---|
| **P2.1 归档检索** | 归档时为历史消息与工具结果建全文索引（SQLite FTS5，trigram 分词以支持中文），`history.search` 一次查询覆盖全部已授权历史并返回带精确读取指针的命中片段；默认视图开放 `history.search`（与摘要里的指引一致） | 归档条件达到第 2 节质量与成本线；开卷/闭卷不退化；默认请求变化经黄金评测 |
| P2.2 指针清单 | 状态帧加入“已归档来源”清单（读过的文件路径与对应归档、工具调用），让模型知道哪些内容可以取回 | 若 P2.1 后归档条件仍有“不知道能查而放弃”的格子才做 |
| P2.3 读取证据 | `file.patch` 接受“本会话已读且哈希未变”的证据，免除强制重读 | 黄金评测重读率与成本 |
| P2.4 子运行上下文 | 子运行上下文包从存储生成（父运行已读来源的指针与摘要），子运行结果写回存储 | sub-01 子运行重读率与成本 |
| P2.5 缓存与重建 | 检查点重建前比较重建成本与后续节省；Anthropic 历史缓存断点打在状态帧之前最后一个稳定块 | 黄金评测缓存读取占比与成本 |
| P2.6 上下文清单 | 通过事件与 API 输出本次任务用到的材料、决定、历史与新鲜度，供阶段 3 界面使用 | 接口测试 |

顺序：先做 P2.1（它直接对应基线里最大的缺口），再按 P2.1 的数据决定 P2.2 是否需要，随后 P2.3–P2.6。
