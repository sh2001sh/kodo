# Kodo 精简与并行方案（lean 配置）

日期：2026-10-30。当前修订 5：在修订 4 的宿主专项检查基础上，优先减少范围声明错误、续接返工与重复检查。L1、L2、L3 已接入运行流程，`lean-team` 可显式选择；默认仍为 `compact-v2`。修订 5 仅运行确定性验证，新的付费模型实验须另行确认；功能验证不能作为速度与费用改善的结论。

实现入口：新会话使用 `--tool-profile lean-team --task-protocol 3`；单人模式使用 `--tool-profile lean-solo`。活动子任务额度和模型并发额度分别由 `--max-active-children`、`--max-concurrent-models` 控制；节点总数使用会话冻结的 `maxTaskNodes`，默认 32。

实现边界：

- 声明任务和节点操作在数据库事务中持久化；快照、提交、集成及释放由宿主在事务外推进。`task release` 返回释放已排队，结果另有持久记录，不能当作已经删除检出。
- 主代理固定 9 工具，子代理按角色使用精简视图。自定义卡片必须能使用自由文本任务包和最终答复：具有必填命名输入或结构化报告契约的卡片会明确标为不兼容，不删除原卡片约束。
- `task inspect` 支持原始工具证据分页；续接已集成结果时保留检出，将新运行的交付基线推进到上次集成提交，避免重复应用之前的补丁。
- 恢复主运行产生新 ID 时迁移图和宿主交付记录；旧终态运行保持不变。暂停子任务的续接保留检出，实际执行和最终交付均受模型并发与未结算效果检查约束。
- 定向测试使用脚本模型驱动真实 coordinator、SQLite 与 Git，覆盖并发额度 1/3、自动集成与依赖、需要输入、续接/重做、冲突、暂停恢复；它们验证行为，不衡量真实模型速度或费用。
- 调度器取快照、集成和释放检出时只尝试获取工作区锁；被占用则保留节点与派发准备记录，由宿主重试，不阻塞下一次主模型请求、不把锁等待记为任务失败。锁释放没有会话事件时也会重试，等待期间不会为此唤醒模型。
- 共享工作区退化（6.7）：主运行第一次 `delegate` 时检测工作区是否为 Git 仓库根目录，结果作为 `task.workspace_mode` 事件冻结，之后不随 Git 状态变化。共享模式下，可写节点缺少 `scope` 时整个调用被拒；子运行直接写入工作区，不取快照、不提交、不集成；`scope` 重叠的写节点按声明顺序串行，主代理写入活动子任务的范围时被拒；`reviewer` 只读、不能执行命令。`delegate` 返回 `workspaceMode` 和共享模式说明。
- 显式 `task wait` 只对选中节点及其阻塞依赖作就绪判断，未选中的独立 `self` 节点或失败节点不会使它提前返回；最终完成判定仍检查全图。完成通知整体不超过 50 KiB（UTF-8 字节，与 OpenCode 工具截断和 DeepSeek harness `spill-policy` 的量级一致）；超出时完整通知保存为工件，模型收到保留决策字段的预览、长文本首尾摘录、`read` 指针，以及“委派 explorer 检索、不要整段读取”的提示。`stale` 的未集成交付通过状态机转入 `integrating`；子运行额度缺失时回退为 8，与节点总数无关。

### 修订 5：按关键路径减少返工

按 P0 声明校验、P1 保留成果修正参数、P2 重复检查计量、P3 依赖与环境交接排序。并发额度不改。声明时拒绝不存在且包含空白的范围，保留已有合法文件名；检查命令中的缺失相对文件目标必须可在写范围内创建。已有只读测试、内联代码及已识别的选项值不因此要求写权限。

## 1. 目标与原则

**模型在每个阶段只看到当前阶段需要的东西；可以独立推进的工作由运行时按依赖图自动并行；安全约束留在内核里执行，不写进提示。**

判断收益只看三项：墙钟时间、实际费用、结果质量（外部验证、是否提交、是否给出最终答复）。工具数量、代理数量都只是手段。

原则：

1. **默认按 Pi 的形态工作。** 单人编码时，模型只看到短系统提示和少量核心工具。
2. **规则按需出现。** 委派、集成、收尾的规则，分别放在对应工具的描述、工具返回结果、子任务完成通知和运行时提示里，用到时才进入上下文。这些内容都追加在历史末尾，不改写前缀。
3. **名册按需查询。** 不在初始上下文注入 agent 名册，创建子代理时再查询。
4. **依赖图由运行时调度。** 模型一次声明任务和依赖，运行时负责启动就绪节点。
5. **并行写入靠隔离，不靠规则。** 写代码的子代理在当前工作区的快照检出中工作；子运行结束后，由宿主提交和集成。
6. **内核安全不放松。** 写入冲突、未知写入和解、子任务生命周期、崩溃恢复全部保留，并扩展到任务图节点和集成过程。
7. **新配置独立冻结。** 新增 `toolProfile: 'lean-solo'` 和 `'lean-team'`，按会话保存，会话内工具集合不变；现有 `full`、`compact-v1`、`compact-v2` 的请求字节不变。

**Kodo 首次请求的组成（compact-v2）**：两条系统消息共 5,776 字符，其中主代理指导约 4.3k 字符，涵盖委派、交接、任务图、契约工件、审查和验收规则；agent 名册 2,838 字符；环境信息 707 字符；任务本身 3,349 字符；状态帧 1,205 字符。工具定义中最大的几个是 `spawn_agent` 4,109、`todo_write` 2,586、`followup_task` 1,731、`inspect_run` 1,400 字符。8/16 组的 20 个工具里有 10 个从未被调用。

**现有并行机制的问题**（源码核实）：

- 任务图的 `dependsOn` 只用于判断已派发的子运行能否开始（`src/runtime/todo-dependencies.ts:26`）。节点就绪后不会自动派发，必须由主代理调用 `spawn_agent`。两组实验各只派了 1 个子代理，所以并发峰值都是 2。
- 共享工作区里，子代理运行期间主代理的 shell 命令会被当作工作区级写入，与子代理的写范围冲突（`src/runtime/todo-execution.ts:27`）。隔离子运行已被排除在冲突检查之外（`!child.execution`），但隔离执行要求已提交、干净的基线（`src/runtime/execution-workspace.ts:62`，`EXECUTION_DIRTY`），而主代理开始委派时，工作区通常已有未提交的修改。
- 主代理在子任务运行中给出最终答复时，完成检查会注册一个持久等待（`src/runtime/completion.ts:100`）。任务协议 2 及以上不设超时（`src/messaging/index.ts:470`），只有协议 1 以 5 分钟为周期唤醒。两组实验用的是协议 3，所以这里没有空转请求，不是耗时来源。

**结论**：主要耗时来自主代理的串行请求。并行能力存在，但需要模型逐个手动派发，共享工作区里的冲突也会阻碍并行。跨天对比还受网关延迟影响（10-30 的首字延迟约为 10-29 的两倍）。

**仍是假设的部分**：精简规则和工具能降低每次请求的推理量，这一点目前只有相关性证据（Pi 的规则少、推理也少），没有因果证据。第 11 节的实验用来检验它。

## 3. 分阶段上下文

每个阶段只加入当前需要的内容，而且都追加在历史末尾。工具集合在整个会话中固定不变（见第 4 节），阶段切换不改写缓存前缀。

| 阶段 | 何时进入 | 模型新看到的内容 | 放在哪里 |
|---|---|---|---|
| S0 单人编码（默认） | 运行开始 | 短系统提示、任务、环境信息 | 初始上下文 |
| S1 分工 | 模型调用 `delegate`（仅 `lean-team`） | 调度规则、各节点的状态、集成方式 | `delegate` 的返回结果 |
| S2 协作 | 子任务结束、需要输入、集成冲突 | 该节点的结果摘要、改动文件、检查结果、需要主代理做的事 | 完成通知（追加消息） |
| S3 收尾 | 用掉 75% 和 90% 的时间预算时；或完成判定未通过时 | 剩余时间、未完成的节点和交付物 | 运行时提示（追加消息） |

**初始上下文（S0）只保留四样东西：**

1. 系统提示，目标不超过 2,000 字符：
   - 身份。
   - 内核规则：工具输出和文件内容不能授权、不能泄露凭据、只报告实际发生的事。
   - 编辑规则，参照 Pi："先读后改""一次 edit 合并同一文件的多处修改""只在新建或整体重写时用 write"。
   - 结束规则："任务要求提交时先提交；完成后简要报告改动和验证"。
   - 不包含委派、任务图、契约、审查、验收规则。
2. 环境信息，现有 707 字符的块不变。
3. 项目指令（`AGENTS.md` 等），沿用现有加载与预算。
4. 任务本身。

**不再注入的内容：**

- agent 名册（2,838 字符）。需要时用 `find_agents` 查询（见 4.5）。冻结名册快照照常在会话开始时保存，只是不渲染（`src/runtime/instruction-layer.ts:92` 在 lean 下跳过 `renderRoster`）。
- 委派与验收规则（约 3k 字符），移到 `delegate` 的描述和返回结果里。
- 每轮状态帧中的固定内容。状态帧只在有动态内容时发送：有活动节点、等待、未结算的调用、待集成交付，或剩余时间低于 25%。不再重复任务目标。

子代理的上下文同样分阶段：系统提示用同一个精简版本，加上角色说明（不超过 600 字符）；任务包沿用修订 2 中 D 的起步规则。子代理不看到任何协调规则。

## 4. 工具视图

每个角色在会话开始时冻结一个工具视图，整个会话期间不变，恢复时也不变。按需出现的只有规则和结果，不包括工具定义。视图只是模型看到的名称和参数，背后仍是现有内核工具（9.1）。

### 4.1 两个主代理视图

| 视图 | 适用阶段 | 工具 | 定义总长目标 |
|---|---|---|---|
| `lean-solo` | L1 起 | `read`、`edit`、`write`、`bash`、`job`、`ask_user` | ≤ 6,000 字符 |
| `lean-team` | L3 起 | `lean-solo` 的 6 个，加 `delegate`、`task`、`find_agents` | ≤ 9,000 字符 |

- `lean-solo` 是 L1 的完整交付物，本身可以独立运行和对照，不依赖 L2、L3 的任何能力。
- `lean-team` 只有在 L2、L3 全部验证通过后才能被选择。L3 包含统一完成判定（7.1）、恢复和续接；在此之前不存在"会自动派发和集成、但完成判定不完整"的可选配置。会话创建时如果选择它而能力未就绪，直接报错，不会降级成 `lean-solo`。
- 会话没有 exec 权限时，`bash` 和 `job` 换成以下 5 个工具，沿用 compact-v2 的做法（`src/runtime/role-view.ts:13` 的 `canExecute` 分支；有 exec 时它隐藏 `file.list`、`file.mkdir`、`file.rename`、`file.delete`，没有 exec 时保留）。这在会话创建时就确定，同样冻结。

| 模型工具 | 内核工具 | 说明 |
|---|---|---|
| `search` | `file.search` | 字面文本搜索 |
| `list` | `file.list` | 列目录 |
| `mkdir` | `file.mkdir` | 一次建一级目录；`write` 要求父目录已存在，所以新建多级路径前先用它逐级创建 |
| `move` | `file.rename` | 不覆盖已存在的目标 |
| `delete` | `file.delete` | 只删普通文件 |

`move` 和 `delete` 与 `edit` 一样不需要模型传 `expectedHash`，改由内核按观察版本检查（4.3）。有 exec 时这些操作由 `bash` 完成，不进入视图。

| 模型工具 | 内核工具 | 说明 |
|---|---|---|
| `read` | `file.read`、`history.read`、`history.search`、`artifact.read` | 按参数区分，见 4.4 |
| `edit` | `file.patch` | 现有 `edits` 数组已支持多处修改；版本检查改由内核承担，见 4.3 |
| `write` | `file.apply_patch` | 只用于新建文件或整体重写 |
| `bash` | `shell.exec` | 长命令自动转后台，现有行为 |
| `job` | `process.read` | 读取后台命令的输出和退出状态 |
| `ask_user` | `ask_user` | 不变 |
| `delegate` | 新增，复用 `spawn_agent`、`followup_task` 的创建逻辑 | 第 5 节 |
| `task` | `inspect_run`、`wait_for_events`、`send_message`、`cancel_agent`、`interrupt_agent`、节点操作 | 按 `action` 区分：`inspect`、`wait`、`send`、`cancel`、`interrupt`、`done`、`drop`、`accept`（5.5）、`release`（6.3） |
| `find_agents` | `agent.search`、`agent.route` | 见 4.5 |

主代理视图里不再出现：`todo.read`、`todo.write`、`recovery.inspect`、`file.search`、`file.list`。被阻塞的未知写入已由运行时在交接前自动调用恢复检查（`src/runtime/tool-step.ts` 中阻塞写入的分支），不需要模型手动调用 `recovery.inspect`。

### 4.2 子代理视图

| 角色 | 工具 | 工作区 |
|---|---|---|
| `explorer` | `read`、`search`、`list` | 共享，只读 |
| `implementer`、`tester` | `read`、`edit`、`write`、`bash`、`job` | 快照检出（第 6 节） |
| `reviewer` | `read`、`search`、`bash`、`job` | 快照检出：可以运行测试，结束后丢弃，不集成 |

- 子代理没有任何协调工具，也没有提交工具。提交由宿主在子运行结束后完成（6.4）。
- 结构化报告（`report.submit`）在 lean 视图下不提供。子代理的最终答复就是报告；内核另外从检出的 diff 中采集改动文件，从工具记录中采集检查命令和退出码，一起放进完成通知。
- 子代理需要外部信息时，最终答复以固定前缀 `NEEDS_INPUT:` 开头，见 5.5。

### 4.3 编辑：取消手工传递哈希，保留内核版本检查

现有 `file.patch` 已支持 `edits` 数组的多处修改，问题只在于模型必须先 `file.read`，再把哈希复制进 `expectedHash`。日志里因此出现过 `FILE_UNREAD` 和多出的往返。内核本身已经按运行记录观察过的文件版本（`src/tools/read-state.ts` 的 `recordSeen`、`recordWritten`），并在写入前用 `staleState` 判断是否过期（`src/tools/index.ts:152`）。

lean 视图下的 `edit` 和 `write`：

- 参数里没有 `expectedHash`。模型不需要搬运哈希。
- 内核仍然检查版本，规则按目标是否存在区分：
  - **目标已存在**：文件必须被本运行的 `read`、`edit` 或 `write` 观察过；当前内容与最后观察的版本不同时，返回 `FILE_STALE`，要求重新读取。错误信息写明"用 `read` 读取，shell 读取不算"。
  - **目标不存在**：`write` 走创建路径，不要求先观察，内核在写入时确认"目标仍不存在"（沿用现有 `staleState` 对 `currentHash === null` 的处理，`src/tools/read-state.ts`）；如果写入前目标已被别人创建，返回 `FILE_STALE`，不覆盖。`edit` 不能用于不存在的文件。
  - 父目录必须存在，沿用现有规则；有 exec 时用 `bash` 建目录，没有 exec 时用 `mkdir`（4.1）。
- 每处 `oldText` 必须在应用时唯一出现，沿用现有规则。唯一匹配只用来定位，不当作一致性保证：片段唯一不代表文件其余部分没有变化。
- 自动集成（6.5）和其他运行的写入都会改变文件内容，但**不会**更新主代理的观察版本。所以主代理在集成后编辑同一文件，会收到 `FILE_STALE`，用 `read` 读到新内容后才能继续。这是预期行为。
- 工具定义在共享模式和快照模式下完全一致，不会因为执行方式不同而改变冻结的工具定义。版本检查在两种模式下也一致。

**弱一致选项（不在 L1 默认启用）**：Pi 的做法是不要求先读，只靠 `oldText` 匹配。它接受的语义是"片段仍存在且唯一时就应用，不保证文件其余部分与模型的认知一致"。如果以后要测试这种做法，作为会话级冻结选项 `editConsistency: 'match-only'` 单独加入，调用记录标注 `consistency: 'match-only'`，结果里返回修改前后的哈希。它不进入 L1，避免和其他变量混在一起。

### 4.4 历史、摘要与工件的读取入口

现有的裁剪结果、摘要和集成结果都会返回读取指针，例如 `{ tool: 'history.read', args: {...} }`（`src/runtime/tool-result-prune.ts:41`、`src/runtime/summary-schema.ts:63`、`src/runtime/context-assembly.ts:141`），集成结果还会返回 `diffArtifact`。`history.read` 也被默认加进每个运行的可用工具（`src/tools/bindings.ts:10`）。删掉这些工具而不改指针，长任务就只能重新探索。

lean 视图下由 `read` 承接这三类读取：

| `read` 的参数 | 映射到 |
|---|---|
| `path`（可带 `offset`、`limit`） | `file.read` |
| `history`（引用）加 `offset`、`limit` | `history.read` |
| `history_query` | `history.search` |
| `artifact`（工件 ID） | `artifact.read` |

- 四种参数互斥，校验失败时返回具体错误。
- 产生指针的地方不再写死工具名，改为调用一个按会话视图渲染指针的函数。lean 视图下渲染为 `read({ history: ..., offset, limit })`，旧视图保持原样，所以旧配置的请求字节不变。
- 摘要读取的格式校验（`src/runtime/summary-read.ts:57`）同时接受两种渲染形式，内部统一为 `history.read` 再校验。
- 子代理的 `read` 有同样的能力；`task inspect` 返回子运行内容时，指针同样按视图渲染。
- 恢复读取的统计（`src/runtime/context-inspection.ts:67`）按规范调用名计数，不受改名影响（9.1）。

### 4.5 名册按需查询

- `find_agents` 的输入是一段任务描述，可以带所需能力；输出最多 5 个候选卡片（ID、版本、适用场景、需要的输入）。数据来自会话冻结的名册快照，查询复用 `agent.search` 和 `agent.route`。
- `delegate` 的描述里直接列出 4 个内置角色，每个一句话。只有使用自定义卡片时才需要查询。

## 5. 任务图与调度（`lean-team`）

### 5.1 `delegate` 的输入

一次调用声明一批节点，主代理自己负责的部分也可以作为节点写进来。

```json
{
  "tasks": [
    { "id": "core", "owner": "self", "goal": "在 routing.py 中实现响应头的计算与注入" },
    { "id": "middleware", "role": "implementer", "goal": "新增 DeprecationTrackingMiddleware 及其单元测试",
      "start": ["fastapi/middleware/__init__.py", "已确认的接口：get_stats() 返回副本"],
      "scope": ["fastapi/middleware/deprecation.py", "tests/test_deprecation_middleware.py"],
      "acceptance": "get_stats 返回副本；保持原中间件行为",
      "check": { "program": "python", "args": ["-m", "pytest", "tests/test_deprecation_middleware.py", "-q"], "timeoutMs": 120000 } },
    { "id": "tests", "role": "tester", "goal": "为 core 编写回归测试", "after": ["core"],
      "scope": ["tests/test_deprecation_headers.py"], "check": { "program": "python", "args": ["-m", "pytest", "tests/test_deprecation_headers.py", "-q"] } }
  ]
}
```

- 每个节点必填 `id` 和 `goal`。`start` 写相对路径、符号和已知事实，`scope` 写负责的文件，`acceptance` 写可验收行为、公共接口与必须保留的旧行为。宿主明确传入子检出实际路径，交接里的父工作区路径不能作为切换目录的依据。
- 可执行快照子任务使用 `check: {program, args, timeoutMs?}` 声明专项检查；默认总时限 600 秒，并受剩余会话预算约束。宿主按字面参数执行单个程序，不拼接 `| tail` 等后缀。程序本身仍须正确传播测试退出码；运行时不能证明任意脚本的语义。
- 新的模型调用中，`check` 只接受结构化命令，文字验收条件放在 `acceptance`。`check` 仍可省略；已持久化的旧字符串继续可读，但这两种情况均标为 `unverified`，不提供宿主测试门禁。旧说明不会自动变成可执行命令。共享模式的结构化检查在声明时拒绝，避免在无法绑定快照版本时承诺验收；只读 explorer 和 self 节点也不能声明宿主检查。
- 子代理在开发中跑自己负责的模块和回归测试，避免反复跑全套；主代理在所有改动集成后统一跑全套及项目要求的覆盖率。代码未变且已有成功结果时复用证据。此分工是提示指导，不是对任意 shell 命令的强制拦截，也不取消项目的验证要求。
- `after` 写依赖的节点 ID，省略表示可以立即开始。
- `owner: "self"` 的节点由主代理完成，运行时不会为它创建子代理。主代理用 `task done` 标记完成，或用 `task drop` 放弃并写明原因。
- 再次调用 `delegate` 可以追加节点，修改或删除尚未开始的节点，或者对已结束的节点执行 `resume` 或 `redo`（5.5）。

### 5.2 节点状态

节点状态和运行状态分开记录。节点是任务图里的一项工作；运行是一次子代理执行（现有 `RunStatus`，不新增值）。一个节点可能先后对应多次运行。

| 节点状态 | 含义 |
|---|---|
| `pending` | 依赖未满足 |
| `queued` | 依赖已满足，等待额度 |
| `running` | 当前运行在执行 |
| `needs_input` | 子代理要求澄清，或宿主检查未通过，需要主代理处理（5.5） |
| `integrating` | 运行已结束，宿主正在检查、提交或集成（第 6 节） |
| `conflict` | 集成未通过，等待主代理处理 |
| `failed` | 运行失败、被中断，或集成出错 |
| `done` | 改动已集成或没有改动；`self` 节点已标记完成 |
| `stale` | 结果基于已失效的前置代次（5.5），不算完成 |
| `dropped` | 被主代理放弃（写明原因），或被取消 |

节点状态写入新事件 `task.node.updated`，带节点代次，从事件可以完整重建任务图。内部复用任务协议 3 的依赖与代次逻辑（`todo-dependencies.ts`），但不再要求主代理维护待办列表。

### 5.3 调度

- **校验**：ID 唯一、`after` 引用存在、依赖图无环、`role` 有效；`scope` 是字面写路径，解释放入 `goal` / `acceptance`。不存在且含空白的范围条目返回 `TASK_GRAPH_INVALID`，已有合法空白/括号文件名不改写。检查中的缺失相对路径必须位于写范围；已有只读回归测试可在写范围外。新文件名确需空格时，由主代理先创建，或明确声明其所属目录。校验失败时整个调用不生效。
- **节点数与运行额度分开**：节点总数受新的会话预算 `maxTaskNodes` 约束（默认 32），只是图的大小，不占运行额度。同时在跑的子运行数由现有 `maxActiveChildren`（默认 8）控制；模型请求并发由 `maxConcurrentModels`（默认 2）排队控制。`pending` 和 `queued` 节点不占任何额度，也不占文件锁。
- **自动启动**：节点进入 `queued` 后，有空余额度时由运行时派发。派发涉及 Git（快照引用、克隆）、文件系统（检出目录）和数据库（运行、事件），三者不能一起原子提交，所以按"准备记录 + 幂等恢复"处理：
  1. 一个数据库事务写入派发准备记录 `task.dispatch.prepared`：节点 ID、节点代次、预分配的子运行 ID、快照引用名、检出目录路径、所依赖前置节点的代次。此时还不创建运行。
  2. 事务外取快照、写引用、建立检出（6.2）。每一步都以准备记录里的名字为准，并且可以重复执行：引用已存在且指向同一快照提交时直接沿用；检出目录已存在且 `HEAD` 等于快照提交时直接沿用；否则删除半成品后重做。
  3. 第二个事务创建子运行，写入 `todo.dispatched` 和 `task.dispatch.committed`，节点进入 `running`。提交前复核依赖代次（5.5），不一致就放弃这次派发。
  4. 恢复时扫描有 `prepared`、没有 `committed` 的记录：依赖代次仍然有效就从第 2 步续做；已失效就删除引用和目录，写 `task.dispatch.abandoned`，节点回到 `queued` 或 `pending`。预分配的运行 ID 只会被创建一次，所以不会重复派发。
- **依赖满足**：前置节点处于 `done`，并且它的当前代次就是后继准备记录里登记的代次。后继的快照在前置节点集成之后才取（6.2），所以后继能看到前置结果。
- **失败传播**：前置节点处于 `failed`、`conflict`、`needs_input`、`stale` 或 `dropped` 时，后继保持 `pending`，但归为"需要主代理处理"（7.1），不会让主代理进入等待。主代理收到通知后可以重做前置节点、放弃后继，或者把后继改成 `self` 自己做。
- **返回值**：每个节点的 ID、状态、运行 ID（如有），以及一段不超过 800 字符的调度说明。说明只在第一次调用时完整返回，之后只返回状态。

### 5.4 完成通知

每个节点离开 `running` 或 `integrating` 时，追加一条运行时消息，不超过 50 KiB；超出时按上文“实现边界”保存完整通知并返回预览：

- 节点状态和运行状态，以及最终答复的摘要（截断；完整内容用 `task inspect` 读取）。
- 改动文件列表和行数统计（来自检出的 diff）。
- 检查命令、退出码，以及该命令运行时的代码版本（6.6）。数据来自工具记录，不依赖子代理自述。
- 集成结果：已集成（给出集成后的工作区版本）、冲突文件列表，或没有改动。
- 因此变为 `queued` 并已自动启动的后继节点。
- 失败、冲突或需要输入时，写明需要主代理做的一件事。

### 5.5 需要输入与续接

- **需要输入**：发现需求与现有行为冲突或缺少关键输入时，子代理立即以 `NEEDS_INPUT:` 结束，提供证据和选项，不继续打磨。运行仍为 `completed`，节点进入 `needs_input`，不集成。正常答复进入交付流程，但有结构化检查时仍须通过宿主门禁。
- **检查失败**：节点进入 `needs_input`，保留检出，通知与 `task inspect` 暴露宿主结果。查看记录不会当作通过；主代理可 `resume` 修复、`redo` 换当前快照，或带原因 `drop`。前两者清除旧验收结论，在新子运行结束后重新检查。集成后的跨模块问题优先 `redo`，因为 `resume` 的旧检出没有兄弟任务的改动。
- **`resume`**：用于 `needs_input` 的节点，或需要小修正的节点。创建新运行，保留代理身份、模型和上下文（现有续接行为），并复用原检出，追加主代理提供的信息。适合原检出仍然有效的情况。原检出因此必须保留到会话结束或显式释放（6.3）。节点代次不变。
- **修正续接参数**：仅 `needs_input` / `failed` 可在 `resume` 中提供替换的 `scope` / `check`；父权限、卡片约束和节点冲突检查继续生效，旧检查结论清空，新运行结束后必须重新执行宿主检查。运行中不得改参数，`done` 的普通续接不得借此修改范围。移动已有文件时，显式保留源与目标路径直到移动完成，不静默扩大范围或丢弃检出。`input` 说明具体修正工作。
- **`redo`**：用于冲突，或前置节点代次已变化的情况。在当前工作区重新取快照，建立新检出，创建新运行；代理身份保留，上下文只带上次的结果摘要，不复用旧检出。旧检出按 6.3 延后清理。

**代次与失效**：

- **何时换代**：主代理对节点发出 `redo` 并被调度接受时（写入 `task.node.updated`），节点代次立即加一，原代次标记为 `superseded`。不再等到重做集成后才换代，所以不存在旧结果仍被当作有效的窗口。
- **原代次已集成的改动**：已经进入主工作区的改动不会自动回滚，因为回滚可能覆盖主代理之后的修改。通知写明"原代次的改动仍在工作区；新代次在包含它们的快照上重做"。
- **后继的处理**：依赖被换代的节点的每个后继，按当前状态处理：
  - `pending` / `queued`：保持等待，直到前置的新代次 `done`；之后按新代次取快照。
  - `running`：继续运行，但它的结果被标记为基于失效代次。主代理收到 `dependency_changed` 通知，可以等它结束后 `redo`，也可以 `drop`。
  - `integrating` / `done`：节点回到 `stale` 状态（新增节点状态，含义是"结果基于已失效的前置代次"），不再算作完成。主代理收到通知，选择 `redo`，或者用 `task accept` 显式确认旧结果仍然有效（写明原因，记入事件）。
- **复核点**：以下三处都重新读取依赖代次，不信任之前的判断：后继集成开始前（不一致则不集成，节点进入 `stale`）；启动下游节点前（派发准备与提交时，5.3）；主运行终态事务内（7.1）。
- **`dropped` 的节点**不能续接，只能新建节点。

### 5.6 等待

- 主代理有独立工作时，子运行在后台进行，模型不需要等待。
- 主代理没事可做时，用 `task wait` 等待任意或全部节点离开 `running` 和 `integrating`。
- 主代理给出最终答复而完成判定未通过时，按 7.1 处理。

## 6. 并行写入：快照隔离、宿主提交与集成

### 6.1 现状

`createExecutionWorkspace`（`src/runtime/execution-workspace.ts:57`）用 `git clone --no-local` 建立独立检出，再 `checkout --detach` 到 `HEAD`。限制有三：

- 工作区有未提交的已跟踪修改时，直接返回 `EXECUTION_DIRTY`（第 62 行）。主代理通常是改了一部分代码之后才委派。
- 检出基于 `HEAD`，看不到主代理尚未提交的修改。
- 交付读取的是子检出里已提交的 `baseCommit..commit` 差异（`executionDelivery`）。子代理要自己调用 `workspace.commit`，而沙箱可能隐藏 `.git`。

集成用 `git apply --check --index` 再 `git apply --index`（`applyExecutionDelivery`，第 124 行），会改动用户的暂存区。

### 6.2 取快照

快照在主代理工作区的写锁下取，保证取到的是一致的工作区版本。现有写锁同时覆盖原生写入和受管理的写入 shell：写入类 `shell.exec` 在开始前取得写锁（`src/tools/index.ts:457`），转入后台后继续持有，直到进程退出（`src/tools/index.ts:601`，`onSettled: releaseExecution`）。所以取快照直接复用这把锁，不另外判断 shell 是否在运行：有写入 shell 在前台或后台运行时，快照自然排队，节点保持 `queued`，状态帧显示"等待取快照"（12）。

写锁管不到的是 Kodo 之外的进程（用户的编辑器、外部构建工具）。对它们的处理：

- 取快照时同时记录文件哈希清单（6.6 的代码版本）。
- 快照写完、释放锁之前，按清单里记录的大小和修改时间复核一遍；有变化就丢弃这次快照并重取，连续 3 次失败时节点进入 `failed`，通知写明"工作区在取快照期间被外部进程修改"。
- 这只能发现取快照期间的外部修改，不能阻止它，与现有未知写入的定位一致。

步骤：

1. **确定文件集合**：`git ls-files -z --cached --others --exclude-standard`，得到已跟踪和未被忽略的未跟踪文件。先按现有 `protectedPart` 规则（`.git`、`.kodo`、`.env*`、密钥文件等）过滤，被排除的文件不会进入暂存区或对象库。普通文件保存工作区字节；2026-10-31 兼容性修正后，目标存在且位于项目非受保护区域内的相对符号链接按 Git `120000` 保存原链接文本。其余链接与特殊文件明确报错。子任务交付仍沿用 `commitExecutionWorkspace` 的普通文件变更检查，未修改的链接保留在基线中。
2. **写入对象**：用临时索引文件（`GIT_INDEX_FILE` 指向 `.kodo/snapshots/<节点>-<代次>.index`），对过滤后的文件列表执行 `git update-index --add --remove -z --stdin`，再 `git write-tree` 和 `git commit-tree -p HEAD`。不使用 `git add -A`，避免受保护文件先进入暂存再被删除。用户的 `HEAD`、索引和工作区文件不变。
3. **持久引用**：写入 `refs/kodo/snapshots/<会话>/<节点>-<代次>`。有了引用，对象不会被 `git gc` 回收，也能被 fetch。
4. **建立检出**：`git clone --no-local --no-checkout`，然后在检出里显式 `git fetch <源> refs/kodo/snapshots/...:refs/kodo/base`，再 `checkout --detach refs/kodo/base`。不依赖普通克隆会复制哪些引用。
5. **记录**：`execution.snapshot` 事件，包括快照提交、引用、源 `HEAD`、文件哈希清单的摘要和被排除的文件数量。快照提交作为 `baseCommit`。

`HEAD` 是空仓库（没有提交）时，`commit-tree` 不带 `-p`。

### 6.3 清理

检出的保留期限以"还会不会被续接"为准，不以节点是否 `done` 为准：

- **可续接的检出**（实现类节点的当前代次）：节点 `done` 后仍保留，因为 `resume` 会复用它（5.5）。保留到会话结束，或主代理用 `task release` 显式释放。释放后该节点只能 `redo`，`resume` 返回明确错误。
- **`redo` 替换的旧检出**：新检出建立、新运行创建（5.3 第 3 步提交）、并且旧代次的交付证据（提交、diff 工件、检查记录）都已持久化之后，才删除旧检出。在此之前崩溃，恢复时两个检出都还在，按准备记录决定保留哪一个。
- **`dropped` 节点和 `reviewer` 检出**：不可续接，节点结束且交付证据持久化后即清理。
- 临时索引在快照写完后立即删除，不随检出保留。
- 会话结束时清理该会话 `refs/kodo/snapshots/<会话>/` 下的全部引用和全部检出。
- 清理失败只记录 `execution.cleanup_failed` 事件，不影响节点状态；下次启动时按会话状态补清理。
- 引用存在用户仓库里，但不在 `refs/heads` 或 `refs/tags` 下，不会被普通 push 带走。文档和 `delegate` 返回值写明这一点。

### 6.4 宿主提交

子代理视图里没有提交工具，也不需要用 Bash 提交。子运行正常结束（`completed`，且不是 `NEEDS_INPUT:`）后，节点进入 `integrating`。声明了结构化 `check` 时先执行检查，再执行提交：

- 检查复用既有工具执行路径，遵循权限、审批、范围、写锁、进程管理和未知写入和解。后台宿主任务不占模型请求槽，也不会让调度轮次等待整个命令；未提供进程隔离时，测试仍持有保守的工作区家族锁，因此不承诺文件操作能与测试并行。
- 命令正常退出且退出码为 0、无超时/取消/信号终止/输出上限错误，才记录检查通过。在子工作区写锁下，提交前再次比较检查开始时的代码版本；变化或无法确认时阻止交付，进入 `needs_input`。
- 进程中断后不将未知结果当作通过，也不自动重放命令。未启动调用可明确记为未执行；已启动但未记录结果的调用保留未知写入，先完成现有和解流程，再续接。
- 宿主检查作为主运行的 `host.task.check` 调用持久化，记录子运行、节点代次、命令参数、实际退出信息、开始/结束时间和代码版本；输出较长时保留工件指针。主运行停止时会取消并等待在途检查收敛，然后清理检出。

1. 复用 `commitExecutionWorkspace` 的检查：收集已修改、已删除和未被忽略的新文件；受保护路径、写范围外的文件、非普通文件都让节点进入 `failed`，通知里列出违规路径。
2. 通过检查后，用宿主管理的 Git 身份提交，得到 `commit`，记录 `execution.committed`。
3. 检出里被 `.gitignore` 忽略的新文件不提交，在通知里列出，提醒主代理检查。
4. 没有改动时，节点直接进入 `done`。
5. `reviewer` 的检出不提交、不集成，结束后直接丢弃。

宿主提交和集成同样作为主运行的副作用调用记录（`host.execution.commit` 和 `host.execution.integrate`）持久化，不属于模型工具视图。主代理仍只有 9 个工具。

### 6.5 集成

集成在主代理工作区的写锁下进行，步骤和副作用记录如下：

1. **复核依赖代次**（5.5）。不一致则不集成，节点进入 `stale`。
2. **计算预期后像，不改动工作区**：把受影响文件的当前内容复制到 `.kodo/integrate/<调用>/` 下的暂存目录，在暂存目录里执行 `git apply --check --binary` 和 `git apply --binary`。预期后像基于主工作区的**实际前像**算出，所以已经包含主代理和其他节点在快照之后的并行修改；不从子检出推导。应用失败时节点进入 `conflict`，调用以 `effectOutcome: 'not_applied'` 结束，主工作区没有被碰过。
3. **持久化计划**：一个事务里写入调用记录（`effectState: 'not_started'`）和集成计划。计划对每个受影响文件记录：
   - 前像：是否存在、内容哈希、文件模式；
   - 预期后像：是否存在、内容哈希、文件模式；预期后像的内容本身存为工件，恢复时可以直接写回。
4. **应用**：将 `effectState` 置为 `started`，按计划逐个文件原子替换（写临时文件再 rename）、删除或修改模式。不在主工作区运行 `git apply`，因此不碰用户的暂存区。
5. **结束**：校验每个文件已等于预期后像，计算集成后的工作区版本（6.6），调用以 `effectOutcome: 'applied'` 结束，节点进入 `done`，记录 `execution.integrated`。**主运行的文件观察不更新**：主代理之前观察到的版本保持原样，只给主运行记录一条外部变更（文件列表和新哈希，与现有 `changedSinceSeen` 的通知机制一致）。主代理之后编辑这些文件时，因观察版本与当前内容不同而得到 `FILE_STALE`（4.3）；用 `read` 读取后，观察才更新为新版本。

**中断恢复**：调用停在 `not_started` 时，主工作区没有被改动，删除暂存目录，从第 1 步重新集成。调用停在 `started` 时，属于未知写入，按持久化的计划逐文件比较存在性、哈希和模式：

- 全部等于预期后像：判定为已应用，补写第 5 步的结果和事件。
- 每个文件要么等于前像、要么等于预期后像（部分应用）：用计划里存的预期后像内容补完剩余文件，再按"全部等于预期后像"处理。前像和后像都由计划确定，所以补完是幂等的。
- 有任何文件既不等于前像也不等于预期后像（集成期间被写锁之外的进程修改）：判定为 `unknown`，不再写入，节点进入 `failed`，交给主代理处理；这次未知写入会阻止主代理完成（现有 `unresolvedCompletionWrites`）。

**非原子边界**：Git、文件系统和数据库不能一起提交。本节和 5.3 的做法相同：先持久化完整计划，再执行可重复的步骤，最后写结束记录；恢复只依赖计划和磁盘上的实际状态。

**完成失效**：集成会改变工作区写入的指纹。主代理的完成验收如果在集成之前做出，终态事务会发现指纹变化，按现有规则（`src/runtime/coordinator.ts:463` 的 `completion.invalidated`）让主代理重新验收。

### 6.6 检查证据绑定代码版本

补丁能应用不代表合并后的代码通过测试。

- **代码版本**：取快照时、集成后各计算一次工作区版本，即 6.2 文件集合的哈希清单再取摘要。子检出里的检查记录子检出版本。
- 完成通知里的每条检查结果都带上它运行时的版本。子代理在子检出中通过的检查，只证明子检出版本，不证明集成后的主工作区。
- 集成后的主工作区版本与子检出版本不同（例如主代理在此期间改过其他文件）时，通知明确写"子任务检查基于快照版本；集成后尚未在主工作区验证"。
- 运行时不自动在主工作区重跑检查，因为何时、用什么命令验证是主代理的判断；只是不让子任务的结果被误认为集成后的证据。
- 同命令提醒只面向主代理：命令、工作目录、代码版本相同，前次有完整成功结束记录，且没有中间写入或集成时，显示前次成功时间。命令照常执行；环境变化或证据要求仍可成为重跑理由。
- 离线审计按运行、工作目录、`check.started` 版本统计广域 pytest 的重复次数和调用区间。不同参数也可计入“同版本广域重复”，但不等于命令相同或检查无效；混合命令不能拆出精确 pytest 耗时，后台耗时未知时保持未知。目前其他测试框架不在该分类器覆盖范围内。
- 每个运行有跨命令保留的临时输出目录，通过 `KODO_RUN_OUTPUT_DIR` 使用，`COVERAGE_FILE` 默认放在其中。目录与工作区、私有存储隔离，不影响代码版本；显式环境覆盖保留。运行结束后直到宿主清理临时目录前保留，长期证据需转为 artifact。

### 6.7 退化情况

- 工作区不是 git 仓库的根目录时，快照检出不可用。写代码的子代理退回共享工作区：`scope` 必填，沿用 strict 写范围冲突检查；主代理命令与子代理写范围重叠时仍会被拦下。`delegate` 的返回结果写明当前处于共享模式。`edit` 的定义和版本检查在两种模式下相同（4.3）。
- 克隆不是操作系统沙箱。子代理的 `bash` 仍然可以写检出之外的路径，与现在一致，按现有的进程策略和未知写入和解处理。

## 7. 完成判定与收尾

### 7.1 统一完成判定

现有 B2（`childCompletionState`，`src/runtime/child-completion.ts:7`）只检查已经创建的子运行：活动、中断、未查看的失败。它不知道尚未派发的节点、未完成的 `self` 节点和待集成的交付。lean 视图下主代理没有待办，`todoCompletionFeedback` 也不参与。所以新增 `taskGraphCompletionState`，与 B2、未知写入检查一起组成完成判定：

未完成的节点分两类，处理方式不同：

- **可自主推进**：存在不需要主代理参与就能让它前进的执行者。包括 `running` 节点（子运行在跑）、`integrating` 节点（宿主正在提交或集成）、`queued` 节点（调度器会在有额度或拿到写锁后派发），以及依赖链上游全部属于以上三种的 `pending` 节点。
- **需要主代理处理**：没有任何后台执行者能解除阻塞。包括 `needs_input`、`conflict`、未处理的 `failed`、`stale` 节点；未完成的 `self` 节点；以及上游含有 `failed`、`conflict`、`needs_input`、`dropped`、`stale` 或未完成 `self` 节点的 `pending` 节点（沿依赖图向上判断）。

| 条件 | 未通过时 |
|---|---|
| 没有需要主代理处理的节点 | 先返回反馈，列出节点、阻塞原因和可选操作（`resume`、`redo`、`drop`、`task done`、`task accept`）；计入纠正次数。即使同时还有可自主推进的节点，也先返回这条反馈，不进入等待 |
| 没有可自主推进的节点 | 只剩这一类时：延后完成并持久等待，不计入纠正次数（沿用 B2 等待语义）。每次被唤醒后重新分类，有节点转为"需要主代理处理"时立即返回反馈 |
| B2 的子运行条件 | 沿用现有反馈 |
| 没有未结算的写入（含宿主集成调用） | 沿用现有 `UNKNOWN_WRITE` |

这样，持久等待只发生在确实有执行者能推进的时候。前置任务已放弃或失败、或者在等主代理自己的 `self` 节点时，不会进入无限等待。

- `failed` 节点用 `task inspect` 查看后算已处理，规则与 B2 相同：查看确认失败，不代表任务成功。
- `dropped` 节点不阻止完成，但最终答复之前，运行时把被放弃的节点和原因追加给主代理，避免答复遗漏。
- 判定在两个地方执行：主代理给出最终答复时；以及终态事务内部。终态事务里重新计算任务图状态并复核每个 `done` 节点的依赖代次（5.5），与验收时的结果比较，不同则记 `completion.invalidated`，主运行回到 `queued`（与现有子运行检查在 `src/runtime/coordinator.ts:468` 的做法相同）。这样，验收后才到达的节点结束、集成、换代或新派发都不会被漏掉。

### 7.2 收尾提示

两组实验都在收尾阶段浪费了时间。默认组全量测试通过后还剩约 312 秒，主代理一直在清理和复测，最后超时、没有提交；放宽组在部分回归通过后又额外核对了约 10 分钟。

- **时间提示**：用掉会话时间预算的 75% 和 90% 时，各追加一条不超过 300 字符的提示：剩余时间、未完成的节点、任务要求但尚未完成的交付物（例如分支或提交），以及"优先完成提交和最终答复"。每条只发一次，发送记录写入事件，恢复后不重发。
- 时间提示只依赖会话时间预算和事件记录，属于 L1。
- **重复检查提示（L2 起）**：它依赖 6.6 的工作区版本，该能力在 L2 实现，所以这个提示也放到 L2，L1 不包含它，保持 L1 独立。只在以下条件全部满足时追加一次提示："代码版本与上次相同，上次结果仍然有效"：
  - 同一命令字符串、同一工作目录；
  - 两次运行开始时的工作区版本（6.6）相同，且期间没有任何写入，包括 shell 写入和集成；
  - 上次运行**成功**（退出码 0）且没有超时。
  - 上次失败时不提示，因为重跑失败的命令可能是在确认偶发问题，或者收集更多输出。证据不足（例如有无法确认的 shell 写入）时也不提示。这只是提示，不拦截命令。

## 8. 不变的内核

以下机制在 lean 视图下全部保留，只是不出现在提示里：

- 文件写入串行化、写范围检查、受保护路径、按运行的文件版本检查。
- 无沙箱写入的超时和解（P1）、未知写入在交接前自动做恢复检查；宿主集成也纳入这套机制（6.5）。
- 子任务生命周期：运行中的子任务会延后主代理的完成；失败的子任务必须查看或重做；中断的子任务必须恢复或取消。
- 崩溃恢复与不重放；会话冻结（工具视图、名册快照、因子、配置）。
- 每个子运行仍有完整的事件和调用记录，`task inspect` 可以读取。

## 9. 兼容

### 9.1 工具视图的解析位置

运行时在校验之前就已经按工具名做了多处判断：

- 模型响应落库时，按名称计算副作用（`src/runtime/model-step.ts:191` 的 `host.tools.effect(call.name)`）。
- 按名称判断控制调用和协作入口（`controlTool`、`collaborationTool`，`src/messaging/index.ts:58`），后者决定走 `Mailbox` 还是 `Tools`（`src/runtime/tool-step.ts:60`）。
- 批次规则：只读调用能否并行（`concurrencySafe`，`src/runtime/tool-batch.ts:15`），控制调用必须单独且排在最后。
- 执行时按名称判断能否转入后台（`src/runtime/tool-step.ts:113` 的 `movable`）。

所以名称映射不能只放在 `Tools.validate` 前，而要在模型响应解析之后、上述所有判断之前，一次性完成：

1. `src/runtime/tool-view.ts` 的 `canonicalRequest` 按运行和会话选取视图，并调用 `resolveToolCall` 得到规范调用。`read` 这类一对多的工具按参数选择内核工具，参数不合法时返回结构化错误，不执行。
2. `model-step.ts` 落库时，`requestRef` 继续保存规范内核调用；改名时另存 `modelRequestRef`，保留模型原始名称和参数。副作用计算、控制和协作判断、批次规则、后台判断、权限校验、恢复、指标继续读规范调用，无需迁移旧记录。
3. 发回给模型的工具结果用 `tool_call_id` 对应，模型看到的始终是它自己调用的名字。
4. 旧视图下 `resolveToolCall` 是恒等映射，不写 `modelRequestRef`，旧会话的调用记录和请求字节不变。
5. 历史重放、恢复和指标脚本统一读 `requestRef`；需要模型原始调用时读 `modelRequestRef ?? requestRef`，所以新旧记录可以混合读取。
6. `delegate`、`task`、`find_agents` 注册为新的协作入口；`task` 在宿主中复用原检查和消息能力。控制调用属性按 `action` 决定：`task wait` 是控制调用，必须排在批次最后；`task inspect` 不是。

- `toolProfile` 增加 `'lean-solo'`、`'lean-team'`，按会话保存。现有的 `full`、`compact-v1`、`compact-v2` 的请求字节保持不变，用确定性重放测试验证。
- 任务协议：lean 视图固定使用任务协议 3 的依赖、代次和派发记录（`todo.dispatched`、`todo.dependencies.ready`），节点状态另用 `task.node.updated` 事件；主代理不使用 `todo.*` 工具。
- 内置卡片：lean 发布新版本（`1.4.0`），只改工具列表和提示，旧版本照常注册，沿用 B3 的做法。
- 指针渲染（4.4）和名称映射（9.1）都按会话视图决定，旧会话不受影响。

## 11. 实验设计

只有用户确认之后才运行付费实验。下面的规则在第一格开始前固定，运行期间不调整。

### 11.1 分组与可得结论

| 组别 | 配置 | 能回答的问题 |
|---|---|---|
| P | Pi | 同一时段的网关状况基准 |
| R0 | compact-v2（现有默认） | 对照 |
| L1 | `lean-solo` | 精简配置的**整体**效果 |
| L3 | `lean-team` | 精简加并行的整体效果 |

- L1 同时改变了提示、工具和编辑行为，只能衡量整体效果，不能归因到其中任何一项。需要拆分时，另行设计消融实验，比如只换提示、保留旧工具。
- "规则变少会降低推理量"仍是假设。L1 相对 R0 的推理 token 变化是对这一假设的观察，不当作结论的前提。

### 11.2 任务

- **FastAPI**：现有基准。单模块、耦合较强，能检验 L3 会不会出现"为了委派而委派"的退化。
- **可拆分任务**：3 个互不相关的模块各加一项功能，各自有测试，另有一个独立验收脚本。L3 的并行结论以它为主，不只依赖 FastAPI。任务资产与验收在实验前单独完成并验证，确认 4 组都能跑通。

### 11.3 重复次数与顺序

- 每个任务每组跑 3 次，即每个任务 12 格，两个任务共 24 格。
- 执行顺序按区组轮换：每个区组依次跑 P、R0、L1、L3 各一格，3 个区组的组内顺序分别为 P→R0→L1→L3、R0→L1→L3→P、L1→L3→P→R0。
- 这是**不完整的轮换**：4 组只有 3 个区组，各组出现在每个位置的次数不相等，顺序效应不能完全抵消。报告里写明每格所在的区组和位置。
- 每个区组只有一个 P 样本，**无法估计同区组内的波动**。P 只用来粗略标记区组之间的时段差异（例如某个区组的 P 明显变慢），不作为显著性判断的依据。
- 同期交错只能减少时段偏差，不能消除。3 次重复的结果只用来判断方向，不做统计显著性的结论。
- 两个任务分批执行：先跑可拆分任务的 12 格；看到明显负面结果（例如 L3 完整交付率低于 R0）时停止，不继续跑 FastAPI。

### 11.4 指标与失败计量

- **主要指标**：完整交付率（外部验证全过、按要求提交、给出最终答复，三项都满足）、墙钟时间、已记录费用。
- **失败计量**：
  - 运行开始后的任何失败都计入主要指标，包括网关失败（HTTP 5xx、流中断未恢复）。不完整流的恢复能力本身就是被比较的内容。计入方式：该格不算完整交付，墙钟按会话时间上限计入，费用按已记录值计入。
  - 另外报告一个**辅助结果**：剔除基础设施失败格之后的完整交付率和墙钟。辅助结果只用于解释，不参与判定。
  - 运行开始前的失败（容器没起来、环境准备失败）不算该组的结果，按预定顺序原位重跑一次，并在报告里记录。
  - 费用有缺失请求时只报告下界，不估算缺失部分。**任何一组存在费用缺失时，都不对费用做"下降"的判定**，即使两组缺失的请求数相同：缺失请求的费用可能差别很大，下界之差不等于真实费用之差。这种情况下，费用一项只报告下界，判定改为"费用无法判定"。
- **判定**（以中位数为准，3 次中至少 2 次满足；只判断方向）：
  - L1 相对 R0：完整交付率不下降，墙钟下降；费用在两组都没有缺失时下降，否则标为"费用无法判定"。
  - L3 相对 L1：在可拆分任务上墙钟下降 30% 以上，完整交付率不下降，费用在可判定时增加不超过 20%；在 FastAPI 上墙钟不超过 L1 的 110%，费用在可判定时也不超过 110%。
  - 结果不满足，或关键项"无法判定"时，不进入默认配置。
- **解释性指标**：主代理请求数、每次请求推理 token、首字延迟、子代理并发峰值、节点数、自动集成和冲突次数、主代理空转请求数、`FILE_STALE` 次数、重复检查提示次数。

## 12. 风险

- **快照检出的成本**：每个写节点一次克隆，加一次 fetch。大仓库要改用 `git worktree` 或部分克隆，L2 时实测 FastAPI 规模下的耗时。
- **取快照被 shell 写入推迟**：主代理长时间运行写文件的后台命令时，节点会一直排队。完成通知和状态帧要显示"等待取快照"，避免看起来像卡住。
- **自动集成冲突**：两个节点的 `scope` 重叠时容易冲突。`delegate` 校验时对重叠的 `scope` 发出警告，但不拒绝，因为 `scope` 是可选的。
- **快照引用留在用户仓库**：`refs/kodo/snapshots/` 下的引用在会话结束时清理；清理失败时下次启动补清理。
- **模型不调用 `delegate`**：精简后委派规则只剩工具描述，模型可能完全不委派。L1 和 L3 分开测量；如果 L3 在可拆分任务上也不委派，先调整 `delegate` 的描述，不把规则加回系统提示。
- **旧会话**：lean 是新配置，冻结在会话里；旧会话和旧证据不受影响。
