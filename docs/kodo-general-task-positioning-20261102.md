# Kodo 通用任务定位与竞争力重建提案

日期：2026-11-02。用户已明确产品应为通用任务 harness，不限于开发者或编程场景。本文是基于当前实现和公开资料的产品建议，不表示路线已获确认、功能已经实现或市场需求已经验证。本次仅新增提案，不更改运行时及既有产品承诺。

## 1. 建议的产品决策

技术定位：Kodo 是以任务结果为中心的通用 Agent harness，支持模型调用、能力发现、持续执行、结果检查，以及工作方法的保存与再次验证。

面向使用者的定位：**Kodo 是处理重复性数字工作的 AI 工作台，帮助你完成任务，并把有效做法保存为下次可以使用的工作方法。**

推荐表达：**把工作做成，把做法留下。**

核心价值假设：对于需要跨资料和工具反复完成的工作，Kodo 可以减少用户重复配置、解释要求、检查结果和纠正执行的时间。必须用第二次及后续真实任务验证，不能由第一次成功推出复用有效。

默认采用完整的单主循环，按需使用 Skills、工具和独立子任务。多 Agent 是执行选择；不同任务可以采用不同的组织方式。工作方法不绑定固定代理数量，也不必对应一个独立子 Agent。

2026-11-03 评审更新：保留可插拔 Agent 定义，先通过 skill.load 按需加载兼容的卡片方法，隐式记录方法阶段；切换时只追加失效说明，完整执行过程继续保留，方法物理卸载推迟至压缩检查点。独立探索、并行工作与独立判断继续使用子 Agent。先与现有 skill.load 基线及常驻方法组比较自主采用、质量和费用，只有证明增量价值才建设显式阶段协议及更多动态能力。见 [阶段驱动的能力挂载设计](kodo-stage-capability-design-20261103.md)。[P1 实验入口](inline-methods.md) 已实现并默认关闭，真实模型收益仍未验证。

初期采用本地工作台作为主要产品入口，SDK 保持为嵌入接口。选择现有 Web 工作台承接非开发者的主要流程，CLI/TUI 继续服务熟悉它们的用户，不同时重做所有界面。

## 2. 为什么需要调整，哪些旧判断仍然成立

原《产品开发与上线方案》已提出“调好一次，下次少重复配置和纠正”，并规划方法提炼、换输入验证和版本采用。这条方向值得继续，但“以 Agent 为单位分享工作流”仍然偏向技术对象，不能充分解释选择 Kodo 的理由。

当前问题是产品主张、实现重心与验证任务尚未对齐：通用方法复用写在方案里，运行体验和实验大量围绕代码仓库、Git、命令及测试展开。需要改变投入顺序和首批成功案例，不只是替换品牌文案。

2026-11-02 直接读取的 Pi 官方 README、Packages 和 SDK 文档确认：Pi 已支持扩展、Skills、提示模板、包分发、SDK、持久会话和会话分支。以上能力不能独立成为 Kodo 的差异化依据。Pi 可被扩展用于更广泛的任务，也不能把“通用”本身当作竞争壁垒。

Kodo 有机会竞争的是完整使用体验：用户无需自己组装评测、方法提炼、能力绑定与版本比较，就能把经常做的工作交给系统，并判断方法更新是否值得采用。这是尚待证明的产品假设，不能宣称其他产品绝无此能力。

## 3. 通用能力与首批用户

架构服务多类任务；首批获客按工作特征聚焦：每周反复整理多源资料、产出固定格式交付物、需要核对来源和数字的个人与小团队。运营、项目协调、咨询和商务支持可以作为招募来源，不要求用户会写代码。

初期选择“资料整理与业务交付”作为验证范围，是为了得到可比较的结果，不把内核固定成报表工具。

| 首批工作方法 | 用户输入 | 交付与检查 | 复用价值 |
|---|---|---|---|
| 周期业务简报 | 本期表格、上期报告、说明材料 | 汇总表与简报；核对总数、来源、时间范围、缺失项 | 下次替换材料，沿用口径与模板 |
| 客户反馈整理 | 反馈导出、既有分类规则 | 去重分类表、问题汇总；可追溯到原记录，保留不确定分类 | 分类纠正经过验证后用于下一批 |
| 方案或报价比较 | 用户提供的报价、产品说明和偏好 | 同口径比较表与建议；区分事实、缺失条件与判断 | 复用比较维度，换供应商与需求 |

先用用户提供的文件和明确来源完成任务，再接入真实应用读取。外部写入、周期触发和更多连接器应随具体需求增加；不以接入应用数量作为首版目标。

## 4. 三项需要建立并验证的核心能力

### 4.1 一次工作形成可继续使用的方法

目标体验：用户完成任务并纠正结果后，选择“保存这种做法”；系统提取可变输入、适用条件、操作方法、必要能力、输出要求和检查方式。再次使用时只需补充变化的信息。

现有基础：Agent 草稿、从运行提炼方法、能力包、案例与版本比较。

关键缺口：当前作者入口主要生成方法文本，并不会自动携带所需 Skills、自定义工具和 MCP 配置。不能将它宣传为任意成功任务的一键复制。方法与任务资料也要分开，具体客户资料和历史答案不应成为通用方法正文。

首版做法：复用现有包与案例结构，只处理宿主已经识别的能力依赖；在界面列出需要重新绑定的资源。方法更新先形成候选版本，使用不同输入比较后再采用。用户纠正不是无条件追加的新规则，必须判断适用范围及是否与旧规则冲突。

衡量：第二次及后续任务的人工操作时间、纠正次数、输入配置时间、合格交付率。保存数量、生成提示词长度、包下载量不代表复用成功。

### 4.2 让用户知道结果为什么可以使用

目标体验：交付物旁边显示实际检查结果、来源、未解决问题和适用输入版本；用户不必阅读模型日志判断是否完成。

现有基础：真实工具记录、输出工件、完成验收回调、冻结案例和采用记录。

关键缺口：通用任务不能只用命令退出码或文件存在判断质量。现有案例支持 output/file/json/command，可由工具转换结果接入，但面向文档、表格和资料来源的现成检查与用户操作尚未形成完整体验。

首版做法：围绕三个场景实现字段、汇总数、来源覆盖和输出结构检查；表达质量与业务取舍保留人工判断。模型评阅作为辅助证据，不能因为模型给自己打高分就显示客观验证通过。只核对已声明的要求，不承诺自动证明任意任务正确。

衡量：关键错误率、人工发现的漏项、检查覆盖范围、错误宣称完成的次数，以及用户检查交付物所需时间。

### 4.3 工具或输入变化后，保留已经完成的工作

目标体验：资料缺失、服务暂时不可用或任务中断后，保留产物和已确认事实；补充资料后从适当位置继续。不同子任务之间只交换后续执行所需的信息。

现有基础：持久运行、等待、预算、恢复、失败记录、依赖代次和部分任务续接。

关键缺口：Git 检出和文件写范围主要服务代码与本地文件，不能等同于跨应用事务。外部服务的执行结果需要工具自身提供明确回执、查询能力及重试语义。某次请求超时后，不能仅凭超时就认定没有执行。

首版做法：只为首批场景必需的连接器定义结果和恢复语义；复用现有运行与效果记录，不先建设通用分布式事务系统。无法确定的外部结果明确留待核对，不能假装全部可回滚。

衡量：恢复后的重复操作、已完成工作损失、人工接管次数，以及恢复到可继续状态的时间。

## 5. 核心资产如何处理

| 现有资产 | 建议 | 原因及具体落点 |
|---|---|---|
| 单主循环、预算、事件和输出存储 | 保留 | 跨场景执行基础；避免再建另一套运行时 |
| 多 Agent、依赖图、续接和集成 | 保留为按需能力 | 独立工作受益时使用，不增加强制委派或固定角色流水线 |
| lean 工具视图 | 优先调整 | 接通已授权的 Skill、MCP 和扩展能力；少量基础工具不应等于固定能力上限 |
| 编码系统提示与角色 | 从通用入口中分离 | 当前 lean 明确写着 coding agent；编程方法作为按需能力保留 |
| Git 独立检出与提交集成 | 保留在代码任务中 | 普通文档与应用操作不应被迫使用 Git 语义；非 Git 共享模式不等于完整跨应用隔离 |
| 能力包与案例比较 | 提升到核心体验 | 用户从真实任务保存方法、用新输入比较、选择采用版本 |
| Web、CLI、TUI | 共用现有应用层 | 先在 Web 完成非开发者最短路径，不新增桌面外壳或第三套业务逻辑 |
| 社区、市场和作者分成 | 后置 | 先证明同一使用者反复使用，再证明跨用户交接有效 |
| 自动模型路由、更多角色、全连接器目录 | 暂缓扩张 | 暂无证据证明这些比首批任务成功率和复用体验更重要 |

源码依据：`src/runtime/lean-prompt.ts`、`src/runtime/tool-view.ts`、`src/extensions/skills.ts`、`src/runtime/task-workspace.ts`、`src/agents/authoring.ts`、`src/cases/schema.ts`、`src/runtime/completion.ts`。

先修改具体断点，再决定是否需要抽象。让第二个不同场景复用同一机制后，再提取公共接口；不预先制造全场景工作流框架。

## 6. 首版体验应当是什么

一次完整示例：用户提供本期业务材料和一份认可的上期报告，请 Kodo 生成本期报告与核对表。系统发现缺失字段后集中询问，完成产物并显示已核对和未核对的部分。用户纠正一个统计口径，系统修改本次结果，并询问该规则是否适用于以后同类任务。用户保存方法后，下一期替换材料再次执行。

界面围绕三个对象组织：任务、工作方法、结果。协作图、模型与工具记录属于可展开详情；用户无需先创建 Agent、写 JSON 案例或维护角色名册。

首次使用必须能直接完成任务，不要求先提炼方法。保存和改进发生在有实际复用意图时，避免把每次一次性任务都包装成资产。

这条体验与传统固定自动化流程的区别，在于方法可描述目标、约束和判断，模型可根据本次输入调整步骤；确定性工具继续处理计算和固定操作。不为每个流程都加入模型判断。

## 7. 如何证明对 Pi 有选择价值

不能只比较默认 Pi 与配置完整的 Kodo，也不能把 Kodo 的方法、工具和历史纠正信息独占后宣称内核更强。

| 对照 | 条件 | 回答的问题 |
|---|---|---|
| 端到端产品体验 | 新用户获得相同任务、材料和可用服务，分别完成必要配置；记录全部人工操作 | Kodo 是否降低开始使用和再次使用的负担？ |
| 执行能力 | 相同模型、预算、输入与方法；尽量提供等价工具，冻结版本并交错重复运行 | 差异是否来自运行时，而非额外知识或能力？ |
| 方法复用 | 首次任务后使用此前未用于修改方法的新输入；对照相同信息的 Pi Skill/扩展方案 | Kodo 的保存、验证与采用是否减少反复纠正？ |
| 恢复能力 | 普通任务中安排可控的服务暂不可用或用户补充输入；保留失败记录 | 是否减少损失和人工重启成本？ |

起步采用三个场景，每类至少四份不同输入，包含普通、缺失字段或冲突信息的情况。开发方法使用的输入与验收输入分开；小样本只用于选择方向。不能把十二个案例通过等同于通用市场优势。

主要指标：每次合格交付所需的人工操作时间，同时报告合格交付率、模型成本和总耗时。人工时间包括配置、解释、检查、修改与接管；自动执行等待单列，避免把较慢运行伪装成人工节省。人工计时与介入定义在实验前固定。

招募第一批 5—10 名具有重复任务的使用者，观察至少两轮新输入使用。这是建议的探索规模，不是已招募人数或统计显著性承诺。先寻找明确、重复的收益，再扩大样本。

判断规则：只在提示中运行得更好、换输入即失效，不算复用竞争力；检查负担没有减少，不算交付竞争力；多代理更多但质量、人工时间及成本没有改善，不算协作竞争力。

## 8. 产品推进顺序与停止条件

| 阶段 | 工作 | 进入下一阶段所需证据 |
|---|---|---|
| A：确认真实重复任务 | 收集经授权的任务材料、当前做法、交付要求与人工负担；选出首批三种方法 | 至少存在愿意再次提供新输入的使用者；否则调整场景 |
| B：打通一个非编码交付 | 在现有主循环接通必要能力，完成输入、产物和结果检查 | 普通与缺失输入情况都能诚实结束；不依赖用户理解内核配置 |
| C：验证第二次使用 | 保存方法、绑定依赖、换输入复跑、候选版本比较 | 质量不退步，人工操作出现可重复的下降；否则先改方法和体验，不扩展社区 |
| D：跨场景复用与竞争对照 | 第二、第三类场景复用现有机制，与等价 Pi 配置比较 | 收益不只来自单一模板；限制和失败样本明确 |
| E：小范围产品化 | 精简安装、连接、错误处理、方法交接与版本管理 | 用户愿意持续使用，并有明确付费或部署需求 |

不承诺在未知团队规模下的固定周数。每一阶段只补阻碍真实使用的能力，不以框架完整度作为退出条件。

如果收益主要来自方法与图形界面，且自研执行器没有表现出额外价值，应评估把 Kodo 产品层放在现成执行器之上；如果恢复、交付记录和协作明显降低用户负担，则继续投入当前内核。先做一个边界明确的适配试验再决定，不能仅凭 Pi 更轻量就重写，也不能因既有投入拒绝比较。

## 9. 商业与长期积累

早期卖点是完成具体工作和降低重复劳动；收费候选是团队共享方法、集中维护与验证、托管执行或部署服务。先验证使用和支付意愿，不先决定单次任务抽成或建交易市场。

长期可积累的资产包括：用户认可且经过新输入检验的方法、场景特定的检查方式、稳定的应用连接和恢复经验，以及任务交付的产品体验。用户数据与方法归属应清晰，支持导出；不能把不能迁移当作壁垒。

单个功能可复制，以上组合也不天然形成护城河。只有持续减少真实用户的操作负担、提高合格交付率，并形成稳定的使用与分发渠道，才能把技术能力变成竞争力。
