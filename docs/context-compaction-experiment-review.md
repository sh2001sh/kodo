# 上下文压缩实验复核：结果、归因与下一轮设计

日期：2026-10-22  
范围：离线复核 `.kodo/qa-deep2-20261022-180811/` 的原始 SQLite 事件、模型请求/响应、逐题答案、dry-run，以及当前压缩实现和评测脚本。本次未调用模型、未重跑付费实验、未修改生产代码或原始成绩。

> **2026-10-24 更新：** §14 记录了摘要预算闭环修复后的真实模型复跑。§11～§13 保留为历史证据，当前决策以 §14 为准。

## 1. 结论

**实现有具体缺口，实验也存在测量与归因问题。当前结果支持“这套配置的闭卷保留不够好”，不支持“可溯源压缩方案整体失败”，也不能把失败主要归因于摘要长度不够。**

本轮有价值：它揭示了不同策略实际保留的区域、来源引用协议不稳、预算与语义保留目标不一致。但它是一次超窗口批量历史的闭卷压力实验，尚未测到按引用恢复、知识自然沉淀、正常增量压缩和压缩后继续完成真实任务。

数值应保留，解释应修正。尤其 summary 第二次在 phase-1 失败后，phase-2 又发生了一次成功摘要；10% 不是纯硬容量回退的成绩。

## 2. 从原始请求确认的事实

### 2.1 hybrid 实际没有摘要调用

| 组别 | 压缩前估算输入 | 首次装配后估算输入 | 实际路径 |
| --- | ---: | ---: | --- |
| off | 386,443 | 114,550 | 硬容量裁剪 |
| mask@16384 | 386,443 | 33,449 | 隐藏 41 个旧工具结果 |
| summary@65536 | 386,447 | 114,554 | 先形成硬容量兜底投影，另有摘要计划 |
| hybrid@65536 | 386,446 | 33,452 | 隐藏 41 个旧工具结果，无摘要计划 |

这些是 `dry-run.json` 的输入估算，不是供应商实际 token。报告的约 361,864 token 是 seed 内容估算，加入消息协议等后的原始请求估算约 386k，两者不可混用。

`src/runtime/context.ts` 只有在隐藏正文后仍超过工作预算时才创建摘要计划。hybrid 隐藏后约 33k，低于 65,536，因此没有调用摘要模型。两个 hybrid trial 的模型调用均只有 phase-1 确认与 phase-2 答题。

所以 mask 与 hybrid 都得到 10% 并不说明“摘要也无效”；这批数据没有触发 hybrid 的摘要分支。它说明以 token 占用作为唯一触发信号，可以达到容量目标而没有保留足够闭卷事实。是否必须保留那些事实，还要看当前任务及是否允许恢复。

mask 的 16k 与 hybrid 的 64k 不构成相同工作预算对照；off 保留区又明显更大。可以比较这些配置的产品表现，但不能据此孤立比较算法优劣。

### 2.2 成功摘要没有看过全部历史

`src/runtime/compaction.ts` 从最早的旧消息组依次加入摘要请求，遇到下一个完整组超过容量便停止。本批 phase-1 两次请求均只覆盖归档偏移 5–38，共 34 条消息、17 个工具轮次；实际输入分别为 73,685 和 74,018 token。

检查真实请求正文，指定事实标记只包含 **KF-1 至 KF-8**。中后部的指定事实并未全部提供给这次摘要模型。

成功的 r1 摘要保留了 KF-1 至 KF-8 标记；最终 Q1–Q8 中七题通过，Q4 受到第 2.4 节的冲突影响，另有 Q19/Q20 通过，总计 9/20。不能把中部题未答对全部解释为“摘要模型看见后遗忘”：不少信息根本没进入其摘要请求，未覆盖的旧工具正文又在后续投影中被隐藏。

这暴露的是**部分摘要覆盖与最终保留策略的组合效果**。保留原文引用在产品设计上允许这种行为，但报告必须区分“已总结”“只归档”“仍原文可见”，不能统称为已语义压缩。

也不能用“压缩必然有损”解释所有低分。19 条短事实本身可以容纳在数千 token 内；真正困难的是在未知后续问题的大量材料中选择它们、确保材料实际被处理，并让来源可检索。本轮需要优先区分输入覆盖、摘要提取、后续隐藏与答题利用这四个损失环节。

### 2.3 phase-1 失败的直接原因是引用 ID，不是正文超长

r2 第一次摘要调用：

```text
finishReason = stop
request maxOutputTokens = 9338
usage.input = 74018
usage.output = 6573
raw response characters = 3335
extracted JSON characters = 3324
allowed JSON characters = 20968
source reference occurrences = 28
invalid source reference occurrences = 28
```

JSON 可解析，八个顶层字段齐全；引用却为 `"2"`、`"3"`、`"6"` 等数字字符串。宿主目录要求的是 `history:<归档哈希>:<消息偏移>` 形式。运行事件因此记录 `SUMMARY_INVALID: summary structure, length or source references are invalid`。

这足以确认拒绝安装的直接原因。返回正常结束，正文长度远低于限制，因此本次失败不能归因为输出截断。不能排除其他任务存在长度问题，但本次样本不支持优先继续扩大摘要 token 或无条件重试。

建议使用宿主分配、请求内唯一的短来源 ID，例如 S1、S2；每段原文旁明确标注对应 ID，宿主维护它到原始授权引用的精确映射。模型不得猜测完整哈希。不要把当前失败返回的数字自动“修正”为偏移，因为它们可能指列表序号，存在歧义。校验应区分解析、字段、预算、未知来源等具体错误。

### 2.4 Q4 有相互矛盾的输入

评测脚本的 `DEEP_FACT_TEXT[4]` 人工插入“任务摘要输出预算的固定上限是 4096 token”，判题也要求 4096。

但 r1、r2 的实际摘要输入正文都含有：

```ts
const summaryTokens = Math.min(8192, Math.floor(built.workInputTokens * 0.08), budget.maxOutputTokens);
```

r1 最终回答 `Q4: KF-4 8192`，被判错。问题明确要求按 KF-4 回答，因此不能直接将这题改判为正确；同样不能据此认定模型没记住实现。它混入了“按指定标记取值”与“依据实际源码理解现状”的冲突。

处理方式：保留原始成绩，标注冲突；新一轮冻结源码、事实和答案，保证彼此一致。若专门测试冲突处理，则应将“指出冲突、区分版本或请求证据”写入验收，单独计分。

### 2.5 phase-2 并未冻结压缩投影

r2 的原始事件顺序为：

```text
phase-1 context.summary.started
phase-1 context.summary.failed      # 不合法来源 ID
phase-1 普通模型确认
phase-2 context.summary.started
phase-2 context.summary.installed   # beforeTokens 114516 → afterTokens 50022
phase-2 普通模型答题
```

phase-2 摘要实际使用 66,350 输入 token。`step=1` 跳过了初始后续任务重建，却没有关闭请求前的再次压缩。其输入还已经包含问答要求。

因此，r2 的 2/20 是“第一次失败、第二次压缩成功后的答题”结果；summary 的 27.5% 是这条路径与 r1 路径的混合成绩。原报告关于“失败直接回退硬容量后只剩 10%”的因果解释不成立。

如果研究的是 phase-1 压缩保留率，phase-2 应使用冻结投影并禁用再次语义压缩，预先给问题与输出留空间。如果研究真实运行行为，就允许继续压缩，但要将全部压缩次数、覆盖变化、题目是否参与摘要及费用纳入实验定义，不能叫严格的单次压缩保真测量。

## 3. 实验合理之处与不能推广的结论

### 3.1 闭卷压力测试有价值，但关闭了产品的恢复路径

隐藏正文的设计保留读取指针，工具禁用时无法使用这些指针。因此 10% 能证明该投影不适合闭卷记忆全部事实，不能证明可追溯恢复不可用。

仍然应保留闭卷测试：当前目标、有效用户约束、下一步行动和未知副作用不能全依赖事后检索。但应将“执行必须立即知道的状态”与“可以按需找回的细节”分开评分。

读取不可变历史与重新探索当前仓库也是两件事。恢复当时证据通常只需读取定位页；不应把所有 open-book 工具调用都计作“从头重新探索”。需要分别统计历史读取、当前文件读取和重复执行。

### 3.2 一次灌入 42 轮不等同于增量工作的长期记忆

脚本把 42 个工具轮次一次写入上下文，然后触发首次压缩。摘要器必须立即面对大于运行窗口的历史，只能选择其中部分；此前没有在工作预算附近持续沉淀任务状态。

这适合检验导入超长历史、窗口缩小和恢复极端条件，但不能代替正常过程：探索或工作一段 → 达预算压缩 → 继续 → 再压缩。当前实验也没有给出真实的执行目标，phase-1 只要求简短确认已掌握，任务摘要缺少选择相关信息的具体依据。

下一轮应同时保留批量压力组和增量任务组。增量组问题仍可事先保密，但要给代理一个真实任务目标，检查它在压缩后能否继续完成工作。

### 3.3 “96.7% 是窗口内假象”措辞过重

能放入窗口时，全量上下文获得较好表现，是一个有效的可行容量基线，尤其能衡量提前压缩牺牲了多少准确率、节省了多少成本。它无法回答超窗口后的退化问题，但不能仅因未触发压缩就废弃。

事实在多处重复，对“来自指定页的精确恢复”是混杂，对“理解项目事实”却可能是正常冗余。应按研究问题解释，而非将二者一概判为无效。

### 3.4 KF 唯一性没有证明答案一定来自指定页

问题本身包含对应 KF 编号，模型可以从问题复制编号，再从其他页面的重复事实获得数值。检查 seed 中标记只出现一次，不能排除这条路径。因此编号和数值正则都命中，并不等价于证实来源保留。

建议将事实准确率与来源正确率分开计分；来源正确要求合法引用定位到真正支持答案的内容。纯记忆定位测试可使用未在问题中泄露的随机值与随机实体映射，避免把公开给模型的编号当作反猜测保障。

### 3.5 每组 40 个答案不是 40 个独立样本

每组只有同一 seed 的两条运行轨迹，每条轨迹中的 20 题共享同一次压缩。安装失败会同时影响多题，所以这些题高度相关。

扩样本要增加独立任务、源码快照、事实位置和目标，重复运行用于测波动；区间和非劣效判断以任务或轨迹为聚合单位。不能把两次运行的 40 个答案作为 40 次独立成功/失败计算稳定胜率。

### 3.6 单次费用不能代表多轮收益

当前费用包含压缩、一次确认和一次答题，反映的是短评测生命周期内的代价。长任务中摘要开销可能被后续较小输入摊销，也可能被恢复读取抵消。只有实际持续执行的总账本能区分。

不只比较理论 token：计入所有摘要尝试、缓存未命中、检索结果输入、重规划后的重复工作和最终交付时间。当前数据不证明降本，也不证明所有长任务都无法降本。

## 4. 实现优化应对准具体问题

1. **先修来源接口。** 使用明确短 ID 映射，记录可诊断校验错误；保持权限与不可变来源校验，不以放宽引用合法性换安装率。
2. **公开覆盖缺口。** 记录拟折叠、实际总结、只归档、保留原文各自范围；界面和交接数据明确“未总结部分”，不能只报告摘要安装成功。
3. **优先正常增量压缩。** 验证达到软阈值时是否及时整理状态。批量超窗口导入走明确降级路径：部分摘要加可搜索档案，按需恢复；只有实测需要，才增加有预算的分段摘要。
4. **用执行需要约束隐藏。** 当前任务依赖的决策、失败原因、下一步和未知写入必须保留；资料细节可引用。不能只按旧正文是否可缩短判断全部语义价值，也无需为每个工具输出额外调用一次模型。
5. **验证计划复核行为。** marker 是提示，不是行为验收。构造压缩期间用户修改约束、子代理返回结果的任务，检查下一次动作是否正确调整、是否重复委派或重做已完成操作。

对当前大历史实验，不建议先做无条件重试、扩大摘要上限或强制 hybrid 每次总结：这些动作没有对准已确认的引用问题，也可能明显增加费用。

## 5. 下一轮最小实验矩阵

| 实验 | 控制条件 | 回答什么 |
| --- | --- | --- |
| 固定投影闭卷诊断 | phase-1 后禁止新压缩；冻结一致事实；同工作预算 | 实际进入摘要的事实保留了多少，关键状态是否可直接使用 |
| 同投影开卷恢复 | 相同历史与起点，仅开放授权历史读取/搜索 | 丢失细节能否恢复，恢复增加多少调用、输入、时延 |
| 目录检索机制 | 已知正确的知识条目与来源 | 目录、搜索和证据读取是否能运行 |
| 自然知识沉淀 | 真实探索生成条目，未知后续问题；记录建库成本 | 系统是否会留下有用知识，而非只会读取人工答案库 |
| 增量任务继续 | 相同任务从起点推进，至少三次压缩，有要求变化 | 计划、协作和完整交付是否保持，累计成本是否改善 |

目录脚本当前按问题答案预置五个条目，并在摘要中写入事实。它适合作为读取正控制，不能证明自然探索具备同等知识保留能力。应将该组标为人工正确知识库，对自动沉淀另设组，纳入建设和维护成本。

算法对照使用同预算的 off/硬裁剪、mask、summary、hybrid；预算取不同档位作为第二个维度。保留实际模型输入量与覆盖范围，不能仅因为参数 H 相同就假定信息量相同。若 hybrid 没有触发摘要，报告实际路径；用更长的增量运行验证是否触发其第二级，不靠强行调用冒充生产行为。

执行优先级：先修正上述评分与阶段污染，降低来源协议失败；再做小规模闭卷/开卷/目录正控制及增量任务。机制结果可靠后再扩 C4 的独立配对任务。直接扩大当前脚本样本，只会更精确地重复现有混杂。

## 7. 后续实验复核：自动知识沉淀、配对布局与三方比较

本节对应后续证据 `.kodo/knowledge-deposition-run3-20261022-200131/`、`.kodo/qa-independent-run-20261022-195521/` 与 [三方比较报告](context-compaction-third-party-comparison.md)。前文保留的是此前实验的历史复核，本节不将已经修正的旧问题描述为仍未修复。本次仍只做离线检查，未新增模型请求。

### 7.1 自动沉淀链路通过了受控验证，但探索目标已提前指定

`knowledge-deposition.mjs` 的 BUILD_QUESTIONS 已指定文件、每个需要提取的事实类别、KF 编号和用途；例如明确要求读取默认工作预算、目标比例、近期消息上限、摘要上限和超时。后续 15 个问题基本沿用这些提取目标。

这不是人工写入答案：真实模型读取文件并产出来源观察，宿主持久化，后续运行读取知识，链路具有实际意义。但准确命名应是“定向探索后的自动知识沉淀与复用”，尚未证明未知未来问题下的自主知识选择、自然任务副产物沉淀或长期维护。

`kfHitRate=15/15` 的实现检查 claims/summary 中是否出现 KF 标记，不校验每个事实值正确且证据充分，不能将标记覆盖率当作知识准确率。五个条目中检索限制条目包含的 KF-16/17 不在这次 15 题评分内，后续应检查真实问题对探索成本的利用率。

### 7.2 Q10 实际答对，原评分是正则假阴性

原答案为：

> KF-10，RAPTOR 未被首版采用；原因涉及递归聚类、向量索引、自动父节点摘要这类做法——代码频繁变更时上层摘要需失效重建，带来写入成本、遗漏传播与调试难度，且尚无证据表明这些成本必要。

评分正则仅接受“不采用/未采用/未被采用/没有采用/不引入/未引入”，没有接受中间插入“首版”的表达。知识条目本身也包含相符解释。因此应保留原自动评分 14/15，并补充“人工复核 Q10 后为 15/15”；不能把这道失败归因为知识遗漏。此处只核对并说明，不修改原始结果文件。

还有一处提示不对称：原 qaInput 的格式示例直接包含 `Q1: KF-1，默认 workInputTokens 是 65536`，controlInput 没有这个例子。当前脚本已移除答案示例，并让两组使用相同的 `Q<id>: KF-<id>，` 占位格式；原始运行和成绩不重写，Q1 仍不能作为独立的知识获取证据。修正单题评分后的 15/15 也不是已消除提示混杂后的重跑成绩。

Q14 还同时询问“默认是否启用”和“64k 的定位”，原评分正则却只检查“默认关闭”。本次原答案经人工复核基本覆盖两问，但自动成绩不能证明复合问题的每个子项都经过校验；当前脚本已改为同时检查默认关闭、64k 数值及“实验起点/未验收”定位。

无目录且无文件工具的 0% 是负控制，能排查部分答案泄漏和凭空作答，不能作为效率或产品竞争基线。应增加“可以正常读文件”的同任务对照，以及“相同内容的平面笔记/搜索”对照，区分知识存储、目录结构和多代理探索各自的贡献。

### 7.4 三个 task 是三种相关布局，尚非三个不同领域任务

脚本三组从同一仓库、同一 19 条事实目录各选 16 条，再改变页序、插入位置、填充和编号。两两事实交集分别是 14、14、13 条，即每组 16 条中的约 81%–88% 重叠。

以 task 为单位汇总优于把所有题目当独立样本；但此处更准确的描述是“三种相关事实布局的配对压力测试”。它能揭示位置敏感性和单 seed 的 60% 不稳定，不能代表跨仓库任务泛化。

coverage 的三组结果分别为 22/68=32.4%、18/72=25.0%、20/68=29.4%，合计 60/208=28.8%；统计单位为消息数，不是 token 数或事实数。应同时报告输入 token 覆盖、关键事实是否进入摘要请求、摘要是否保留以及最终是否正确利用；不能只凭三组结果宣称事实准确率与消息覆盖率已建立强相关或因果关系。

### 7.5 OpenCode 对比混合了文档规格、源码默认与降级路径

核对本机 `.kodo/opencode-src`，提交为 `b42c31613fdcbd220e859bea357fea48260a6c7a`：

- `packages/core/src/session/compaction.ts:202` 的默认 keep 是 15,000；8,000 应标作重放选择或另一个版本的文档值，不能在该源码版本下称为默认。

- `deliver` 优先发送可容纳的原请求或历史请求；需要缩减时才进入 `flattenAndDropOldest`。1250 字符截断来自对应文本序列化工具，不能概括成每次摘要必然截断到 1250 字符。
- 持久会话历史、扩展、文件记忆和外部工具的恢复能力，不能仅凭不存在 Kodo 式目录就排除。

`get_channel_failed` 是上游通道失败的直接证据；长请求挂起还可能涉及重放器、超时或请求兼容，未经隔离不能将全部失败归因于某一方。正式比较应保存各工具的有效配置、失败分类和请求是否实际到达模型。

### 7.6 下一步应优先验证 Kodo 自身的质量—成本收益

目前已支持的结论是：定向探索产生的知识能自动持久化并被后续任务读出；原文恢复可显著提升这批问答准确率，但读取开销不可忽略。尚未证明目录相对普通笔记/文件搜索具有优势，也未证明新压缩策略改善实际编码任务交付。目录的 93.3% 与相关布局摘要的 12.5% 来自不同材料、目标提示和信息访问条件，不能直接作为目录优于摘要的量化对照。

优先顺序建议：

1. 已修正判题假阴性、Q1 示例泄漏、QA/对照费用归属，以及三方机制描述；保留旧记录，后续重跑生成无上述混杂的新成绩。
2. 用真实开发任务自然产生知识，之后提出事先未给探索器的相关问题，并加入一次源码修改、失效检测和更新验证。
3. 同任务比较直接读文件、平面笔记/搜索、Kodo 目录；将建库、检索、更新和完整交付成本一并计入。对保留正确答案的负控制继续保留，但不拿它当竞争基线。
4. 将来源恢复限制在小范围分页，记录命中前扫描量、重复读取和成功恢复代价；检查压缩后是否根据新状态实际调整计划。
5. 再做版本和配置冻结的三家 CLI 任务对照。原生默认配置回答产品体验问题；同模型/预算及相同外部知识工具的对照回答内核机制问题，两者分开报告。

Kodo 可主张“内置可追溯的项目知识沉淀和跨 Agent 复用”，当前不能主张“只有 Kodo 能长期记忆”或“已经比同类省 token”。默认关闭新压缩策略的决定仍有依据。

## 9. 动态组装四组实验独立复核（2026-10-23）

复核对象为 `.kodo/context-assembly-real-tasks-20261023/` 的 results、trace、只读 SQLite 调用记录、不可变请求/结果 blob 和各组 REPORT.md；没有重新调用付费模型或修改生产代码、原始成绩。该实验冻结的 `src/runtime/context.ts`、`src/runtime/coordinator.ts` 与复核时工作区版本逐字节一致。

### 9.1 默认关闭合理，但低分原因尚不能归结为相关性

| 组 | 原始初筛分 | 实际运行终态 | 报告文件 |
| --- | ---: | --- | --- |
| off | 70 | completed，有最终答复 | 存在，30,307 字节 |
| hybrid | 70 | MODEL_BUDGET | 存在，21,834 字节 |
| assembly | 10 | UNKNOWN_WRITE | 不存在 |
| assembly+hybrid | 50 | MODEL_BUDGET | 存在，22,764 字节 |

assembly 的 10 分仅来自“未修改不允许的项目文件”，不代表一份已完成报告保留了 10% 的知识。最后调用是全量 Vitest 命令，工具参数 timeoutMs=300000、内部 timeout=280 秒，但宿主 toolTimeoutMs=120000；trace 显示约 120.387 秒后取消，shell 被按可能写入处理，运行以 UNKNOWN_WRITE 停止。结果中的 timedOut=false、cancelled=true 与宿主取消路径一致，不能仅看 shell 自身的 timedOut 字段判断有没有超时。不能为提高成功率而把所有测试命令视为无副作用、绕过未知写入保护。

hybrid 的会话已计费 token 为 1,972,280/2,000,000；assembly+hybrid 的会话预算账本为 1,942,523/2,000,000。下一次输入估算与输出/收尾预留还要占额度，故尚未到 200 万也可能触发 MODEL_BUDGET。后一账本不等于 provider 实测 usage，需继续分列实际用量、未知用量的保守预留与可用余额，不能只用累计 input 判断是否应可继续。

这些是有效产品失败，必须保留在端到端结果里；但不能据此单独估计“相关性选择导致质量降低 60 分”的因果效应。

### 9.3 选择器有可定位的问题，值得修复

1. **评分依赖上一次投影，候选不稳定。** coordinator 把 built.messages 安装为后续 contextRef；下一轮 assembleEvidence 对当前 group 的 JSON 提取词项并估算体积。正文隐藏后，候选变成更短、词项不同的指针；恢复后又变长。原文与指针没有稳定的候选摘要/大小，容易产生自反馈。实际 53 次组装中有 50 次发生恢复，共记录 145 条恢复消息；最近六条 user 输入的内容哈希始终相同。18 次组装使总输入估算增加。恢复增加输入本身不是错误，且新证据也可能合理触发替换，但这些数据与末段反复隐藏/恢复支持优先排查抖动，而不能把恢复次数解释为成功响应用户目标切换。
2. **词项被前部文本挤占。** assemblyTerms 对中文连续文本生成相邻双字词，最后只取前 128 个不同词项。本次真实任务输入产生 218 项，保留区包含大量工作区说明；平台、范围、限制、引用、计划、报告等目标后部词项在该条输入的截断区。这是选择器的目标表示缺陷，不表示原始用户约束从主模型上下文被删除。对候选使用 JSON.stringify(group) 也让协议字段、命令包装和正文前部挤占配额。
3. **全文组竞争 6,553 token，不适合直接充当多主题覆盖器。** 当前按整个工具组贪心选入，超额就跳过，无分主题覆盖约束。一个长源码响应即便重要也可能放不下；两个近期工具轮次只能保护最近活动，不能确保内核、分发、依赖、MCP、沙箱、恢复等全部交付主题都有证据。
4. **恢复预算与候选体积不一致。** 隐藏候选先按指针组的长度扣额度，再读取最长 32,000 字符原文；最终只检查总工作预算和硬窗口。因此 evidenceInputTokens 不是恢复原文后的严格额度。应先按拟注入片段核算，而非先按占位符收费再恢复。
5. **未达到软容量也可能提前隐藏。** 当前 assembly 在满足容量时仍会执行证据筛选。对宽泛任务，相当于提前用不成熟的相关性判断替换可直接保留的证据。模型没有主动调用 history.read：本批恢复计数为零指的是工具调用，不能与宿主自动恢复的 145 条消息混为一谈。

### 9.4 评分与任务副本还存在混杂

`real-tasks.mjs` 给 source factual review completed 固定 false，等待独立人工复核；本批目录没有 report-audit.json。因此四组 acceptance.passed=false 不能直接作为四组均被事实审查判错的证据。

命令评分只识别五条 npm 命令，但 START_HERE.md 明确推荐直接运行 node/tsc/vitest。off 报告列出了构建、类型检查、静态检查、doctor、平台验证和 demo 的直接调用，仍被判“没有三条可用命令”。应依据任务要求核对实际命令，保留原分并生成另列复核分；没有全面审查前不自行宣布新总分或整份报告通过。

freezeSource 的根文件清单漏掉 LICENSE，冻结副本也缺少 .github；assembly 执行 verify-installation 时实际遇到打包缺少 LICENSE，并继续调查环境与打包问题。这不是从本次证据可推断的真实仓库缺陷。下一轮应使任务副本具备其所宣称支持的验证前提，或明确哪些验证不可用。统一缺陷影响四组，并不保证对不同执行路线没有不同影响。

### 9.5 下一轮保持简单，先辨认原因再扩样本

先修评分和副本完整性、展示真实工具时限、保证预算不足时有可用的收尾路径。未知写入仍须先核实，不能通过伪造成功或盲目重放恢复。报告类任务应阶段性落盘已有证据，避免把全量测试变成产出报告的前置条件；“产物保存”和“任务完成”单独记录。

选择器最小改进：复用已有来源/归档记录，为候选保留不随隐藏变化的来源 ID、路径/符号、简短预览、原始体积与新鲜度；从稳定记录生成请求投影。没有新增相关信息或目标变化时尽量复用选择；容量有余量且无法可靠判断相关性时保留证据。明确的交付主题从已有计划/待办取得，综合报告阶段给各未完成主题保留最小证据；按片段分页并按实际注入量计费。不增加图数据库、强制全量知识分类或每轮辅助模型调用。

优先执行低成本证伪检查：相同源记录与相同任务状态反复组装应稳定；目标尾部新增要求应影响选择；一次超长读取不能挤掉所有其他必需主题；同一来源从原文变指针不应改变相关性排序和原文预算；恢复来源失效应显式记录且不越权。

## 14. 摘要预算闭环修复后的真实模型复跑（2026-10-24）

### 14.1 条件与控制

原始证据位于 `.kodo/qa-retention-budget-repair-real-20261023-235818/`。实验使用 `codego1/deepseek-v4.1-flash`，比较 `off` 与 `summary@65536`，每组 2 次并交替运行；deep seed 目标约 360k token，运行窗口 131,072 token。phase-2 为闭卷、禁用工具并冻结压缩，窗口仅为容纳冻结投影提升到模型声明值，未发生二次压缩。

付费运行前的 dry-run 满足 20/20 事实检查、19/19 深埋锚点唯一性与 phase-2 freeze 控制。当前源码生成 44 页证据；每次 summary 计划用 4 块处理 86 条拟折叠消息，未触发 8 块上限。源码与旧批次已有变化，因此只把本批的 off/summary 作为配对比较，不跨批比较绝对成绩。

### 14.2 结果：没有安装摘要，闭卷处理效应仍未测到

| arm | 闭卷正确率 | 摘要安装 | 模型请求 | 输入 token | 输出 token | 估算费用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 12/40 = 30% | 不适用 | 6 | 272,124 | 2,618 | ¥0.07507 |
| summary@65536 | 12/40 = 30% | 0/2 | 12 | 526,375 | 49,604 | ¥0.26386 |

两次 summary 的 30% 都来自摘要失败后的确定性 fallback 投影，与 off 恰好答对同一组近期事实；`accuracyWithInstalledSummary` 为 `null`。因此本批不能报告摘要使准确率持平，也不能计算摘要保留率的变化。只能报告：summary 请求数为 off 的 2 倍、输入约增加 93.4%、估算费用约为 3.52 倍；费用仍标记为不完整，因为失败请求存在未知 usage 预留，不能视为账单。

覆盖应分三层解释：

| 层级 | r1 | r2 | 能说明什么 |
| --- | ---: | ---: | --- |
| 计划消息覆盖 | 86/86 = 100% | 86/86 = 100% | 分块计划包含全部拟折叠消息 |
| 实际进入摘要请求的 KF 事实 | 12/19 = 63.2% | 12/19 = 63.2% | 两次都处理到第 2 块后停止 |
| 已安装摘要中的 KF 事实 | 0/19 | 0/19 | 没有摘要通过最终安装 |

所以“计划 100%”不等于“实际处理 100%”，更不等于“事实保留 100%”。当前安装 coverage 为 0，而不是 42.9% 或其它部分安装比例。

### 14.3 两次失败的直接原因

`summary-r1` 的第 1 块正文为 4,229 token，低于 5,242 的正文硬预算；第 2 块为 7,848 token，正确进入一次有界缩写。缩写请求遭遇 provider HTTP 525，随后该块的一次瞬时重试也遭遇 HTTP 525。宿主保留第 1 块并尝试部分安装，但由 4,229-token 正文、24 条解析后的不可变来源记录、coverage 和状态包装组成的可见 marker 为 10,793 token，超过 10,484 的注入预算 309 token，最终以 `SUMMARY_INJECTION_BUDGET` 失败。

`summary-r2` 的第 1 块首次请求遭遇 HTTP 525，一次瞬时重试成功，正文为 4,903 token。第 2 块返回 7,744-token 内容但结构不合法；实现按契约没有对非法结构调用缩写。第 1 块的部分 marker 为 11,250 token，超过注入预算 766 token，同样无法安装。

事件中的 6 条 `context.summary.failed` 包含同一 trial 的块级失败、重试失败和最终安装失败，不是 6 个独立根因。正文预算修复已经改变了真实路径：r1 确实进入了“仅正文超额时缩写”的分支；但唯一一次真实缩写被 HTTP 525 阻断，尚未验证缩写能否端到端安装。r2 的非法结构属于另一条预期拒绝路径。

### 14.4 当前判断

本轮把阻塞点从“正文预算契约必然失败”推进到了两个可分离问题：provider 的 HTTP 525/非法结构，以及注入预算公式没有充分覆盖来源和外壳开销。后者在两份合法部分摘要上只差约 3%～7%，但这是确定性安装失败，不能通过放宽正文校验或忽略外壳来绕过。

下一步只应修正注入预算闭环：由确定性可计算的外壳、解析后来源记录、coverage 和状态字段形成硬上界，并增加复现 24 个来源、10,793/11,250-token marker 的离线回归。修复后先运行 1 次最小 summary；只有成功安装，才恢复 paired off/summary 闭卷比较。

本批闭卷 fixture 没有工具和委派入口，因此没有新增自主委派数据；§12.4 的历史结论不变。summary 与自主委派继续默认关闭，暂停付费扩样。

## 15. 架构复核：收缩职责，再修预算契约（2026-10-24）
