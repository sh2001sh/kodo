# Kodo 上下文压缩：大上下文项目认知保持对比（真实模型，闭卷问答）

日期：2026-10-22（第三轮：大上下文 + 均匀深埋事实 + 唯一标记；含离线复核修正）  
状态：大上下文对照实验完成。离线复核见 [《上下文压缩实验复核》](context-compaction-experiment-review.md)：本文数值保留，但归因按 §0.1 修正。样本小、题目非独立，不能做统计显著性判断。

> **最新复跑（2026-10-23）：** 修复摘要截断与共享 token 竞争后，闭卷 summary 仍为 0/2 安装，原因已变为字符预算与 token 安装预算不一致；自主委派两组均为 1/2，子任务仍为 0 完成。§15 是当前结论，§14 保留为修复前历史证据。

> **重要修正（2026-10-22 复核）：** 原始请求/响应/事件显示，hybrid 本次并未调用摘要模型（只走遮罩）；成功摘要只收到 17 个工具轮次（KF-1～KF-8），不能代表全部历史；summary 的 r2 在 phase-2 又成功安装了一次摘要，10% 不是纯硬容量回退；Q4 的 4096 与当前源码 8192 冲突。因此本文结论从“摘要模型保留不足”改为“输入覆盖、来源协议、阶段冻结与评分口径共同造成当前结果”。

## 0.1 复核修正（以 [review 文档](context-compaction-experiment-review.md) 为准）

1. **hybrid 没有摘要调用**：遮罩后约 33k，低于 64k 工作预算，未创建摘要计划；mask 与 hybrid 本次实际是同一路径，不能据此比较摘要算法。
2. **摘要输入覆盖不全**：phase-1 两次摘要请求约 74k input token，只覆盖归档偏移 5–38（17 个工具轮次，KF-1～KF-8）；中后部事实从未进入摘要请求，随后在工作上下文中被隐藏。不能把中后部失败归因为“摘要模型读过但总结丢了”。
3. **summary r2 的 phase-2 再次压缩**：phase-1 摘要因来源引用不合法失败后，phase-2 又成功安装一次摘要（此时题目已在上下文）。因此 r2 的 2/20 不是“纯硬容量回退”，27.5% 是混合路径。
4. **来源引用协议是失败直接原因**：失败响应正常结束、JSON 仅 3324 字符（上限 20968），但 28 个来源引用全是 `"2"`、`"3"` 等裸数字；宿主需要明确短 ID 映射，不能自动猜数字含义。
5. **Q4 冲突**：人工事实/答案写 4096，但实际源码已改为 8192；保留原判并标注，下一轮冻结一致源码、事实与答案。
6. **闭卷只测“不可重读时的记忆”**：mask 的设计路径是按指针恢复；闭卷低分不能证明可溯源压缩整体不可用。96.7% 是**窗口内的有效容量基线**（衡量提前压缩的准确率代价），只是不能回答超窗口表现，不应一概称为“无效”。
7. **KF 唯一性 ≠ 来源正确**：问题本身含 KF 编号，模型可从问题复制编号、再从其它页重复事实取数值；需要把“事实准确率”与“来源正确率”分开计分。
8. **20 题不是 20 个独立样本**：同一轨迹的题目共享同一次压缩；统计聚合应以任务/轨迹为单位。

## 0. 为什么重做实验（效度修正）

| 轮次 | 设计 | 结果 | 解释 |
| --- | --- | --- | --- |
| 标准窗口 | 86k 上下文，全部塞进 1M 窗口 | off 96.7%、mask/hybrid 32–33%、summary 83.3% | **有效的窗口内容量基线**：off 未触发压缩，回答不了超窗口表现，但可衡量提前压缩的准确率代价 |
| 大上下文 v1 | 361k 上下文、128k 窗口，事实页均匀分布 | off 92.5% | **效度缺陷**：事实在 docs 等其它页重复出现，off 从保留页兜底答对 |
| **大上下文 v2（本报告）** | 361k 上下文、128k 窗口，**19 个事实页深埋 + 每页唯一 KF 标记**，问题只能由指定页回答 | off 30%、mask/hybrid 10%、summary 27.5% | 可用对照，但需按 §0.1 修正归因 |

唯一标记机制：每个事实页在页面中部（token 深度 25%–72%）插入一行 `【项目事实 KF-{id}】...`，问题要求答案带对应 `KF-{id}` 标记；dry-run 断言每个标记在全 seed 中恰好出现 1 次。这样其它页即使重复真实数值，也不能冒充“保留了该页”。

| arm | 准确率 | 预算类 7 题 | API/存储 6 题 | 设计取舍 5 题 | 约束 2 题 | 输入/输出 token | 估算费用（2 trials） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **off（旧版硬容量）** | **12/40 = 30.0%** | 0/14 | 4/12 | 4/10 | **4/4** | 270,628 / 2,540 | ¥0.140 |
| mask@16384 | 4/40 = 10.0% | 0/14 | 0/12 | 0/10 | **4/4** | 83,152 / 2,103 | ¥0.026 |
| **summary@65536** | **11/40 = 27.5%**（phase-1 安装 1/2） | 4/14 | 3/12 | 0/10 | 4/4 | 354,304 / 23,958 | ¥0.214 |
| hybrid@65536 | 4/40 = 10.0% | 0/14 | 0/12 | 0/10 | **4/4** | 83,234 / 3,259 | ¥0.028 |

summary 细节：r1 phase-1 摘要安装成功，准确率 **9/20（45%）**；r2 phase-1 摘要失败（`SUMMARY_INVALID`）后回退硬容量投影，只答对 Q19/Q20 = 2/20。所以 summary 的 27.5% 是“一次安装 + 一次回退”的混合值，不能当作稳定保留率。

## 3. 位置分析：压缩到底丢了哪里

| 事实页位置 | 内容（token 分数） | off | mask/hybrid | summary（安装 trial） |
| --- | --- | --- | --- | --- |
| Q1–Q8 头部（1%–17%） | 预算、CLI、存储/目录 API | 基本全丢（0/16） | 全丢 | **Q1–3、Q5–8 答对（7 项）** |
| Q9–Q14 中部（24%–58%） | user_version、RAPTOR、PageIndex、分工、摘要触发、默认关闭、64k 定位 | 全丢 | 全丢 | 全丢（Q4 还答成 8192） |
| Q15–Q20 尾部（68%–98%） | README/文档尾部事实 | **Q15–Q18、Q20 答对**；Q19 固定约束保留 | 仅 Q20（最后页） | Q20 答对；尾部其余在摘要安装后未保留 |

结论：旧版 off 只保住了**最后一个完整近期窗口附近的尾部事实**（约 6/20），头部/中部事实全部被归档省略；mask/hybrid 更极端，只保住最后一页与 kernel 固定的用户约束；summary 安装成功时可从交接摘要中恢复一部分**头部**事实，但中部/尾部的深埋事实仍大量丢失。

## 4. 关键发现

1. **“旧版不压缩更好”只在上下文仍装进窗口时成立。** 在 361k vs 128k 窗口下，旧版硬容量裁剪也只能保留约 30% 的项目事实；此前 96.7% 的结果必须废弃，原因是窗口内 + 事实重复。
2. **mask/hybrid 在大上下文下只剩 10%**：它们把旧观察替换成指针，闭卷（不重读）时仅最后一页和固定用户约束可用；**本次 hybrid 未调用摘要模型**（遮罩后低于工作预算），mask 与 hybrid 实际路径相同，不能据此比较摘要算法。
3. **summary 的 r1 只覆盖了部分历史**：r1 摘要请求只收到 17 个工具轮次（KF-1～KF-8），因此 45% 不能代表它对全部历史的保留能力；r2 在 phase-2 又成功安装一次摘要（题目已进入上下文），10% 不是纯硬容量回退。来源引用协议失败（裸数字而非短 ID）是 phase-1 摘要失败的直接原因，不是输出长度。
4. **在“闭卷且只接受指定事实”的条件下，所有策略都丢失大量项目认知**：off 30%、summary 27.5%、mask/hybrid 10%。但这里混合了输入覆盖、来源协议、后续隐藏与答题利用四个损失环节，不能把低分主要归因于“摘要模型能力不足”；项目知识若要求长期可用，应依赖知识目录/原文按需读取。
5. 用户约束（Q19）在所有 arm 都保留，验证了“内核固定状态不交给压缩”；但这不等于项目知识保留。
6. **实现修复仍然有效**：摘要围栏解析、推理 token 余量、摘要内容上限 8192（8% 公式）让大上下文摘要从“0 安装”变为可安装；但默认启用门槛远未达到。
7. **open-book 证明“可恢复”，但穷举重读代价过高**（探索性 n=1）：off 19/20、mask 20/20，但单 trial 输入 0.68–1.21M token、13–46 次工具调用；summary/hybrid 因工具循环触发 `TIME_BUDGET`，未产出答案。见 §9.1。
8. **知识目录是决定性补足**（2 repeats）：预置 5 条知识目录后，closed-book 准确率从 10–30% 提升到 **92.5–97.5%**；mask+catalog 是成本最低的高保留组合（输入约 176k token / 2 trials）。这验证了设计“目录保留知识、原文可追溯”的核心主张。见 §9.2。

## 6. 局限

1. 每 arm 仅 2 次、单模型/单端点/单 seed；无统计显著性。
2. KF 标记是真实事实上的唯一标识，属于受控 needle 设计；它避免重复兜底，但也意味着问题只测“指定页是否被保留”，不测跨页综合推理。
3. 闭卷禁止重读；mask/hybrid 的真实产品路径允许按指针重读，本实验只回答“不重新探索”目标。
4. phase-2 继承是 harness 显式 pin（产品 `followUpContext` 不原生继承），见前份报告方法学说明。
5. 费用为历史费率估算，非账单；summary 失败/重试的 token 已计入。
6. 样本中摘要 phase-1 安装只有 1 次，summary 的 45% 仅作方向性参考。
7. open-book 仅完成 1 次重复（工具循环接近时间预算后停止）；summary/hybrid 失败原因为 `TIME_BUDGET`，不是答案错误。
8. knowledge catalog 由 host 人工预置 5 条知识条目（19 KF 事实），只是**读取正控制**；不证明系统能从真实探索中自然沉淀出同等知识，也不证明维护成本。
9. open-book 未设置单 trial 工具调用上限；token/时延被 search/read 循环放大，这本身是需要产品约束的发现。
10. KF 编号出现在问题里，模型可从问题复制编号；即使 seed 中标记唯一，也不能完全排除从其它页重复数值获得答案。下一轮应把“事实准确率”与“来源正确率”分开计分，并使用未在问题中泄露的随机实体/值。
11. 同一轨迹的 20 道题共享同一次压缩，不是 20 个独立样本；区间与非劣效判断应以任务/轨迹为聚合单位。
12. Q4 存在事实冲突（人工 4096 vs 源码 8192），原成绩保留并单独标注；本报告不据此判定模型记忆。Q4 的 harness 事实/答案已在下一轮冻结前修正。

## 7. 后续建议

1. **扩样本**：每 arm ≥5–10 次重复、多 seed/多窗口比例（2×/4×），才能判断 summary 45% 是否可复现，并向 C4 §11 的每组 ≥20 对靠近。
2. **open-book 需要有界检索预算**：本实验的穷举 search/read 让单 trial 达到 0.7–1.4M 输入 token 并触发 TIME_BUDGET；产品应限制每次问题的检索次数/字符，并把“按指针一次定位”与“全库扫描”区分开。
3. **知识目录 arm 已补做并验证核心主张**：下一步应测“目录自动生成/维护”质量，以及目录与压缩策略组合的成本曲线（mask+catalog 目前最便宜）。
4. **摘要可靠性与成本**：catalog 模式下摘要 2/2 安装，优于 closed；但仍需更多样本确认。摘要失败应保留回退并在 UI 明示。
5. **C4 正式验收仍未完成**：需要编码任务 + 开放读取 + 目录 arm 的 A/B/C/D 每组 ≥20 配对、预注册与统计检验；在那之前 `--compaction` 保持默认关闭。

## 9. 补充对照：open-book 与 knowledge catalog

> 说明：复核指出这两组实验仍偏弱——open-book 未加有界检索（工具循环可耗尽时间预算），catalog 是人工正确知识库的读取正控制。以下是保留的探索性数据，不能单独证明“可溯源压缩整体可用”或“系统会自然沉淀知识”。

### 9.1 open-book（允许 history.read / history.search，探索性 n=1）

phase-2 运行卡提供 `history.read`、`history.search`，指令要求优先按压缩投影中的 read 指针恢复原文；其余与 closed 相同（deep seed、128k 窗口、KF 唯一事实）。

| arm | 准确率 | 请求 | 输入 token | 工具调用 | 恢复字符 | 估算费用 |
| --- | --- | --- | --- | --- | --- | --- |
| off | 19/20 = 95% | 9 | 680,153 | 13（search 12/read 1） | 29,210 | ¥0.091 |
| mask@16384 | **20/20 = 100%** | 36 | 1,205,602 | 46（read 17/search 29，2 错误） | 164,312 | ¥0.120 |
| summary@65536 | **0/20（TIME_BUDGET）** | 22 | 1,403,399 | 45（search） | 30,996 | ¥0.561 |
| hybrid@65536 | **0/20（TIME_BUDGET）** | 35 | 1,279,336 | 48（read 15/search 33） | 152,624 | ¥0.194 |

结论：**允许重读时，被压缩的内容确实可以恢复**（off 95%、mask 100%），但穷举式 search/read 会把单 trial 推到 0.7–1.4M 输入 token，summary/hybrid 甚至耗尽会话时间预算。设计文档的“按来源引用读取”必须配合有界检索，否则不能作为常规路径。

### 9.2 knowledge catalog（人工预置 5 条目录，读取正控制；2 repeats）

每个 trial 在 host 侧按知识管线预置 5 个条目（覆盖 19 KF 事实与 Q19 约束）：知识由真实 `file.read` 证据生成，phase-2 通过 `knowledge.browse/search/read` 检索后闭卷作答。

| arm | 准确率 | 摘要安装 | 请求 | 输入 token | 目录工具调用 | 估算费用 |
| --- | --- | --- | --- | --- | --- | --- |
| off | 39/40 = 97.5% | — | 11 | 768,468 | 9 | ¥0.150 |
| **mask@16384** | **37/40 = 92.5%** | — | 10 | **175,939** | 12 | **¥0.058** |
| summary@65536 | 39/40 = 97.5% | **2/2** | 10 | 333,746 | 5 | ¥0.155 |
| hybrid@65536 | 39/40 = 97.5% | — | 11 | 267,751 | 13 | ¥0.056 |

结论：**知识目录把“压缩后项目认知”从 10–30% 拉回到 92.5–97.5%**，且 mask+catalog 是成本最低的组合（输入约为 off+catalog 的 23%，准确率仍有 92.5%）。这直接验证了设计文档“目录保留知识、任务摘要用于继续当前任务”的分工：项目知识不应寄望于工作上下文本身，而应沉淀到目录并按来源读取。注意目录由 host 预置，目录自动生成/维护质量不在本实验范围内。

## 10. 复核后的修正实验（固定投影 + 增量多次压缩）

复核后实现了短来源 ID、覆盖范围遥测、phase-2 freeze、Q4 事实一致化，并新增增量实验脚本。以下为**修复后的重新测量**，用于替代 §2 的混合归因。

### 10.1 固定投影闭卷（phase-2 freeze，不再发生第二次压缩）

| arm | 准确率 | 摘要安装 | coverage（planned/covered/uncovered） | 输入 token（2 trials） | 估算费用 |

- summary 从旧混合路径的 27.5% 变为 **60%**，且 **2/2 安装**（短来源 ID 修复后没有出现来源引用失败）；两次 trial 分别为 8/20（40%）与 16/20（80%），波动仍大。

| --- | --- | --- | --- | --- | --- | --- | --- |
| off | 17/32 = 53.1% | 6/8 = 75% | 23/40 = 57.5% | 3 次 hard（每 trial） | — | 630,309 | ¥0.255 |
| mask@65536 | 4/32 = 12.5% | 6/8 = 75% | 10/40 = 25.0% | 3 次 mask | — | 187,080 | ¥0.078 |
| summary@65536 | 15/32 = 46.9% | 6/8 = 75% | 21/40 = 52.5% | 3 批均触发；**6/6 安装** | 3/3 每 trial | 611,120 | ¥0.344 |

- 事实保留的区域性明显：mask/hybrid 只剩最后批次（Q16 等）可答；off/summary 能保留部分早期批次，但两次 trial 波动大（off 13/16 vs 4/16；summary 10/16 vs 5/16）。

### 10.4 归因更新（相对 §2/§4）

1. 旧 summary 27.5% 混入了 phase-2 二次摘要；固定投影后为 **60%**，且 2/2 安装。不能把旧低分主要归因于“摘要模型能力不足”。
2. 新测量仍有明确上限：coverage 只有 39%，且增量场景中后期摘要覆盖降到 50–64%；中后部事实仍大量丢失。这是**输入覆盖 + 保留策略**问题，不是单纯输出长度问题。
3. 闭卷低分只描述“不重读时的记忆”；同投影开卷 97.5% 证明恢复路径有效，但代价是 0.75–1.29M input token / 2 trials，且必须设检索预算。
4. 增量任务的执行状态基本保留（修复 Q20 口径后应为 4/4），而事实细节仅约五成；因此“压缩后继续工作”可以依赖投影中的状态，但**项目资料必须依赖目录/按需读取**。
5. C4 仍未通过：本组只覆盖单 seed、2 repeats、人工预置目录、无自然知识沉淀与独立配对任务；默认关闭不变。

## 14. 真实模型复跑：事实链路与自主委派（2026-10-23）

使用冻结模型 `deepseek-v4.1-flash` 和 provider `codego1` 重跑。闭卷实验采用 phase-2 freeze，答题阶段禁用工具且没有二次压缩；off、mask@65536、summary@65536 各 2 次。自主委派实验使用同一 onboarding 任务，off 与 summary@65536 各 2 次，协作工具可用但提示不要求也不禁止委派。原始证据分别位于 `.kodo/qa-retention-rerun-real-20261023/` 和 `.kodo/compaction-delegation-rerun-real2-20261023/`。

### 14.1 闭卷准确率变化

| arm | 本轮准确率 | 相对 §10.1 | 摘要安装 | 输入 token | 估算费用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| off | 12/40 = 30% | 30% → 30% | — | 259,998 | ¥0.07121 |
| mask@65536 | 4/40 = 10% | 10% → 10% | — | 107,336 | ¥0.03276 |

summary 聚合值比本轮 off 高 10 个百分点，但不能判定为稳定提升：唯一成功安装摘要的运行答对 10/20；另一次摘要失败、未安装，回退投影后答对 6/20，与 off 单次结果相同。相对 §10.1，summary 的安装成功率从 2/2 降为 1/2，闭卷准确率下降 20 个百分点。其输入比 off 高 53.6%，估算费用高 148.7%。mask 输入比 off 少 58.7%、费用少 54.0%，但闭卷准确率下降 20 个百分点。

### 14.2 覆盖率与 KF 事实链路

成功安装的 summary 运行中，`context.summary.installed.coverage` 为 42/98 = 42.9%。§10.1 为 64/164 = 39.0%；表面增加 3.9 个百分点，但本轮只有 1 次安装，分母、候选布局和成功样本数均不同，不能解释为覆盖能力稳定提高。

| 阶段 | KF 事实数 | 比例 |
| --- | ---: | ---: |
| 预置于事实页 | 19/19 | 100% |

| 最终投影可见 | 9/19 | 47.4% |
| 闭卷答对 | 9/19 | 47.4% |

最终投影多出的 1 条是近期保留的 KF-20，不是摘要补回。加上固定保留的 Q19 用户约束后，该运行总成绩为 10/20。链路显示本次已保留事实都被正确使用，主要损失发生在“事实页进入摘要请求”和“摘要请求进入安装摘要”两个阶段。另一次失败运行进入摘要请求 8/19，但没有安装摘要；不能把请求覆盖当作实际保留。

### 14.3 自主委派频率

| arm | 发生委派的运行 | 主代理可委派请求 | 委派工具调用 | 创建子任务 | 完成子任务 | 成功 `inspect_run` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

### 14.4 结论边界

本轮首次把消息 coverage 与 KF 事实链路同时落到真实安装事件上，能够定位事实在哪一阶段丢失。它没有证明 summary 稳定提升闭卷准确率：2 次中仅 1 次安装成功，且成本显著高于 off。mask 的容量收益明确，但闭卷事实保留下降。自主委派样本只有 4 次，且所有委派发生在压缩前、所有主任务均未交付，不能用于判断压缩对自主委派的因果影响或委派收益。默认关闭和优先修复摘要安装、共享预算及可靠交付的结论不变。

## 15. 截断与共享预算修复后的真实模型复跑（2026-10-23）

### 15.1 闭卷准确率与安装结果

| arm | 闭卷准确率 | 摘要安装 | 输入 token | 输出 token | 估算费用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| off | 12/40 = 30% | - | 260,736 | 2,124 | ¥0.07114 |
| mask@65536 | 4/40 = 10% | - | 107,388 | 1,910 | ¥0.03167 |
| summary@65536 | 12/40 = 30% | 0/2 | 387,300 | 26,714 | ¥0.15275 |

summary 与 off 本轮同为 30%，不能解释为摘要保留效果相当：两次摘要都没有安装，答题实际使用的是回退投影。每次均保留 5/19 条 KF 事实并答对这 5 条，加上 Q19 固定用户约束后为 6/20。mask 相对 off 少 58.8% 输入，但闭卷准确率低 20 个百分点；summary 相对 off 多 48.5% 输入、费用高 114.7%，没有得到已安装摘要。

两次 summary 都规划了 4 块、98/98 条消息，低于 8 块上限；第一块响应均为合法 JSON，`finish_reason=stop`，请求 `max_completion_tokens=16384`。因此上一轮的输出截断问题已经修复。新的直接失败原因是安装侧 `SUMMARY_BUDGET`：

| trial | 原始 JSON 字符 | Kodo token 估算 | 内容预算 | 超出 |
| --- | ---: | ---: | ---: | ---: |
| summary-r1 | 7,729 | 5,591 | 5,242 | 349 |
| summary-r2 | 7,295 | 5,301 | 5,242 | 59 |

提示只要求总长度不超过 `summaryTokens * 4 = 20,968` 字符，而安装又要求 `estimateTextTokens(raw) <= 5,242`。中文与 JSON 标点使两个约束不等价；响应远低于字符上限却超过 token 上限。`SUMMARY_BUDGET` 被视为确定性失败，不会触发一次重试，所以两次都在第一块停止。

这也修正了 coverage 的解释：`98/98` 是四块的**计划覆盖**，不是已安装 coverage。实际安装事件为 0，不能报告 100% coverage；第一块实际输入包含 8/19 条 KF 事实，但没有任何一条进入已安装摘要。当前覆盖结论是“规划完整、安装覆盖不可用”，而不是 42.9% 或 100%。

### 15.2 自主委派与真实交付

| arm | 完整验收 | 有报告 | 自动平均分 | 委派运行率 | 委派调用 / 可委派主请求 | 子任务完成 | 已知费用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 0/2 | 0/2 | 10 | 1/2 = 50% | 1/57 = 1.8% | 0/1 | ¥0.33059 |
| summary@65536 | 0/2 | 2/2 | 75 | 1/2 = 50% | 3/65 = 4.6% | 0/3 | ≥¥0.62158 |

两组的自主委派运行率都为 50%，没有复现 §14 的 50% 对 100%。summary 唯一发生委派的 trial 在首次摘要前一次性创建 3 个子任务，因此不能把更高的请求级调用率归因于压缩。4 个子任务均未完成；off 子任务因新的主代理交付预留而以 `CHILD_BUDGET` 停止，summary 的 3 个子任务也未形成可采用结果。

共享 token 修复得到部分验证：4 个主运行没有再出现 `MODEL_BUDGET`。但完整验收仍为 0/2 对 0/2：off-1 与 summary-2 因 provider `MODEL_PROTOCOL` 失败；off-2 正常结束但没有 `REPORT.md`；summary-1 正常结束并保存报告，summary-2 保存报告后最终响应失败。summary 共发起 13 次摘要，安装 2 次、失败 11 次，其中 10 次是 `SUMMARY_BUDGET`，另 1 次是通用 `INTERNAL`。更大的推理余量消除了截断，却没有解决安装可靠性，并增加了成本暴露。

自动 80/70 分不是人工事实正确率。人工复核两份报告后确认它们覆盖主要主题，但都存在可证伪的 MCP 过度表述：summary-1 的速览称 stdio “始终走原生沙箱”，与同报告后文及 `src/extensions/mcp.ts` 的可选 `sandbox` 分支矛盾；summary-2 称 HTTP `headers` 只能使用环境变量引用，但 `McpConfig` 明确允许字面量字符串。两份报告还都遗漏 Windows 同一用户单写沙箱限制。原自动分保留，不上调为事实验收通过。

### 15.3 当前结论

本轮证实了两个窄结论：输出截断已消失；主代理不再因子任务耗尽共享 token 而直接 `MODEL_BUDGET` 失败。它没有证实摘要 coverage、闭卷准确率、完整交付或自主委派收益。当前阻断项是摘要字符/token 双预算不一致，其次是 provider 协议失败、报告落盘和子任务收敛。修复预算契约前不应继续付费扩样；summary 与自主委派继续默认关闭。

### 15.4 预算闭环已实现，真实效果仍待重测

2026-10-23 后续代码修复已统一生成提示与宿主 token 计量，分离 provider 输出、正文和注入预算，并对“结构/来源合法、仅正文超额”增加一次不重发历史的有界缩写。两份保存响应离线通过结构与来源校验，按新逻辑都会进入缩写，而不是直接 `SUMMARY_BUDGET` 终止；缩写仍超额、改变来源集合或完整 marker 超出注入预算时不会安装，同一来源版本也不会再次生成。

这不是新的真实模型实验。表中 30% 准确率、0/2 安装和费用数据仍描述修复前的真实运行，不能改写成修复后效果。默认关闭和暂停付费扩样保持不变；下一次付费验证应先确认四块连续处理、缩写次数、完整 marker 安装及每块费用，再测事实保留和闭卷正确率。
