# Kodo：从工具收缩转向完整执行闭环与有效并行

日期：2026-10-30。本文先记录日志与源码审阅，再给出轻量协作与动态 DAG 方案。用户随后授权实施，落地内容与验证记录见第 9 节；未追加付费实验。前述历史性能结果不随本次代码修改而变化。

## 1. 结论

审阅所依据的被测版本主代理有 24 个工具，最先要解决的是能力分配和调用协议：主代理可以设计、改代码，却不能直接执行命令，因此把测试、查看差异和提交拆成额外的模型任务。工具入口缩小，工作过程反而变长。

建议以 Pi 的完整单代理工作闭环为默认基础，保留一层可选、轻量、异步的协作能力。并行应来自提前交出独立工作的所有权，而不是把主代理已经设计好的命令分发给更多代理执行。不要继续叠加“必须委派”“必须规划”“必须报告”的提示来弥补接口分工问题。

上轮实现并非无效：多活动待办、事件等待、独立执行副本等机制已经具备。但真实实验没有达到性能或质量目标，不能继续以工具数量或子代理数量作为成功依据。

## 3. 为什么仍没有有效并行

### 3.1 旧的单活动待办已不是本轮解释

当前新协议支持多个活动待办、显式依赖与独立执行副本。本轮优化版创建 11 个子运行，但子运行之间生命周期重叠为零，也没有使用独立副本。主代理和子代理之间存在模型请求重叠，不能说整个系统完全没有并发；缺失的是多个实施者同时推进不同交付。

### 3.2 主代理仍占据主要工作

主代理消耗 155 次请求、至少 37.10 credit、至少 343,695 推理 token；全轮已知小计为 45.27 credit、373,381 推理 token。按已知小计计算，主代理占约 82% 费用、92% 推理；缺失用量使这些不是精确真实总量占比。

首次任意派发在 382 秒，只处理环境和分支；首次源码修改在 1,050 秒，首次实际实施派发在 1,097 秒。主代理先写完整的约 100 行参数传播脚本，再交给子代理执行，昂贵的设计已经串行完成。

### 3.3 职责切割不完整

`src/runtime/role-view.ts` 的 E 关闭主代理 shell/process，却保留文件修改与全部协调能力。实际形成“主代理设计和修改，子代理执行命令”的分工。为了一个普通命令创建会话、传递背景、等待、读取结果，成本可能超过直接调用工具。

这不是证明 E 单独导致全部退步：本轮比较整包修改，且每组仅一次。但它提供了明确的机制解释和优先消融对象，应撤回“禁用主代理命令即可促进有效委派”的设计假设。

### 3.4 执行隔离仍有真实边界

独立 clone 不是 OS 沙箱。无沙箱任意 shell 仍有仓库家族写锁，不能仅开多个副本就宣称命令可并行。多个代理可以并发推理、读取或在受控条件下修改独立文件；任意写命令的并发还需满足执行隔离和资源约束。

本轮没有子代理交叠，首先是分工策略没有采用并行，不能把全部原因推给锁。也不能为提高重叠率放宽写权限、未知写入和进程清理语义。

| 收尾 | 最后源码修改后仍有 789 秒、72 次请求、11.15 credit；提交后仍有 365 秒、29 次请求 | 自动汇总已存在证据，只补缺失验证，不反复手工读记录、改待办、重跑测试 |

前期时间包含必要理解，收尾包含必要复验，不能全部视为浪费。收尾窗口彼此包含，不能相加。工具耗时、模型时间和等待也可能重叠，本报告不承诺机械相减可节约多少分钟。

质量问题必须同时解决：优化版外部功能验证 131/137，基线 137/137。五项失败来自中间件统计跨实例共享，一项来自多层路由显式配置的覆盖顺序；自写测试没有覆盖这些合同边界。更少请求或更快收尾不能以跳过这些验证换取。

## 5. 逐项目借鉴

### Pi：学习默认工作方式，而不是只抄四个名字

固定源码 `73f8de80bc87021375f8b525292ac07492253002`，版本 1.3.0。

- `settings-manager.ts` 明确默认 `read/bash/edit/write`；grep/find/ls 等能力可以由命令完成，也有可选专用工具。
- `system-prompt.ts` 按启用工具组合指导，普通编码没有必须先建立团队、工件合同和验收代次的整套流程。
- Bash 输出有行数与字节限制，截断时保存完整输出路径；减少的是进入模型的重复内容，不是丢弃可复核证据。
- 子代理是示例扩展，可选单任务、并行任务或串行链；并行模式最多 8 个任务、4 个并发。每个子代理独立进程与上下文。
- Agent core 支持同轮工具并发，遇到配置为 sequential 的调用会走串行路径。这是工具执行机制，不等于默认启动多代理，更不证明任意共享写入均安全。

本次历史 Pi 对照使用 `--no-extensions`，没有启用该子代理扩展。它的成绩不能作为“Pi 多代理更快”的证据。也不建议把示例中的 scout→planner→worker 串行链搬成 Kodo 必经流程，那会重新引入重复理解与交接。

### OpenCode：轻量委派与会话复用

固定 v1.19.3 / `e3c4eb242585dcd77be1a867391b7c25fd47ce52`。

- 主代理保留文件和命令工具，普通操作无需转交新代理。
- Task 基本必填字段是 `description/prompt/subagent_type`；`task_id` 可继续既有子会话。
- Todo 是清单持久化，不是派发的先决条件，也不自动触发创建。
- 此版本默认前台 Task，实验性后台开关启用后才暴露后台参数；不能把它当成天然全面异步。

适合借鉴的是低交接成本、明确角色和上下文续用。其配置与能力仍明显多于 Pi，不能作为“全部只保留四工具”的统一先例。

### DeepSeek Harness：少前置条件的异步任务

固定 `22ddee3792402c3e70ec5f86a63c3e3e895a2f60`。

- 普通 subagent 的基本必填是 `description/prompt`，启动后返回 ID，完成通知主代理。
- fresh 用自足任务包；fork 复用已有对话，避免再次口述全部上下文。fork 也有输入成本，不应一律复制全部历史。
- 说明明确鼓励同一响应发起独立任务，主代理继续有用工作，仅剩等待时结束当前轮次，不用 sleep 轮询。
- 实验 Team 是另一配置，不能把它和普通 subagent 工具叠加计算；持久成员、共享任务也不意味着任务就绪就自动启动负责人。

它的实际请求有 25 个工具，值得学的是异步生命周期与简洁任务入口，而不是工具总数。

### Codex：任务、计划和并发准入各司其职

本次重新获取官方仓库固定提交 `398500106707f0a3217c7cf83edc2bf226cc342f` 的相关源码。官方文档页面访问返回 403，因此这里只陈述固定源码行为，不宣称当前所有 Codex 发行版默认一致。

- MultiAgentV2 创建接口主要必填 `task_name/message`，支持 fresh/full-history 选择；创建返回代理身份，不等待完整任务交付。
- `followup_task` 向既有代理发送任务并触发后续轮次，适合延续已有工作。
- `plan.rs` 解析并发布计划更新事件，本入口不派发代理、不绑定待办验收代次。计划与执行生命周期分离。
- `parallel.rs` 依据工具是否支持并行选择共享或排他准入，并非把所有调用无条件并发执行。

可借鉴的是少量清晰参数、任务连续性和按能力判断并发。不能由这些源码断言 Codex 总是提前分工、完全不重复探索或比其他 harness 更快。

## 6. 推荐改动顺序

### 第一优先：恢复完整执行能力，减少必经步骤

默认编码代理保留读、写/编辑、命令执行、受管理的长进程读取，必要时保留专用搜索及询问用户，目标约 6–8 个核心入口；协作主代理加上必要协调能力，目标约 12–14 个入口。数字是设计范围，不是硬性达标指标。优先复用已有实现，不新增一套执行器。

主代理可以自行完成短命令、验证与整合。需要明确分工时，提前交出独立实现的所有权。如果产品仍需要纯负责人模式，应把实现与验证完整交给执行者，而不是保留主代理改代码、只禁用命令的半截分工；纯负责人不宜成为小任务默认模式。

文件管理中的 mkdir/rename/delete 可先评估用已有命令或统一补丁完成；`file.patch/file.apply_patch` 根据能力覆盖保留一个常用编辑入口。若精简会失去受控并发或清晰权限边界，则保留专用入口，不为了凑四个工具转为更粗粒度的 shell 锁。

历史、工件和恢复的普通结果尽量由运行时提供有界摘要与可展开引用。异常需要显式决策时仍提供恢复路径，不静默解除 UNKNOWN_WRITE；使用中的旧会话继续兼容。不要把二十多个动作藏入一个拥有巨大 action 枚举的万能工具。

### 第二优先：轻量协作，交出完整工作而不是命令

复用现有创建、续接、消息、等待和终止实现，缩减普通任务的必填内容：目标、相关入口、边界和完成标准。写范围、身份、依赖及隔离校验继续由运行时保证，不能把权限约束删成自由文本。

完成通知直接附上有界结果：修改范围、当前版本、执行过的命令与退出码、未解决问题、原始输出引用。常规消费结果不再要求反复 inspect 多层工件。需要诊断时仍允许展开。

普通 todo 表示工作计划；改显示说明或完成备注不应创建新任务身份。真正改变任务目标、负责人、依赖或写范围仍需显式重新派发与重新验收。不要用删除版本校验解决调用体验问题。

#### 待办采用轻量 DAG，界面与模型仍使用简单任务操作

沿用现有 `id + dependsOn` 表示有向无环图（DAG），不引入图数据库、通用工作流引擎或新的调度服务。`src/tools/todo.ts` 已有依赖与环检测，`src/runtime/todo-dependencies.ts` 已有就绪检查、依赖版本固定和变化通知；以下是对现有实现的完善，不是从串行清单重新建设图系统。

边只表达真实的产物依赖：后继必须使用前置任务的已验收结果。列表显示顺序不产生依赖；文件写入冲突、模型并发额度和进程锁属于调度准入条件，不伪装成任务依赖。DAG 可以暴露并行机会，但不能代替模型划分独立工作。

在现有任务与运行记录上区分三类数据，不为此新建平行的数据系统：

| 数据 | 语义与版本规则 |
|---|---|
| 任务定义 | 稳定任务 ID、目标、完成标准、负责人、写范围、依赖；实质变化需要新的执行依据 |
| 执行尝试 | 复用 run 与事件，保存任务版本、实际使用的依赖版本、输出和验证证据；重试不覆盖既有尝试 |
| 展示信息 | 标题、进度说明、完成备注；更新不改变任务定义版本，不使既有证据失效 |

任务状态仍区分工作完成和验收，不把模型写下 completed 当作语义正确的证明。旧会话和旧卡片沿用原协议；新行为由明确协议版本承载，避免旧记录被重新解释。

#### 动态调整规则

| 实际操作或结果 | 图与执行行为 |
|---|---|
| 发现新的独立工作 | 添加节点；无依赖的任务不阻塞无关分支 |
| 未开始任务需要前置结果 | 原子增加依赖，检查自依赖、环、缺失引用及版本冲突；已排队的旧派发须撤销或显式重绑，不能因代次不匹配永久等待 |
| 未开始任务需要拆分、合并或删除 | 同一事务更新节点和受影响的边，处理旧派发；不留下悬空依赖，不把旧任务证据自动转移给新目标 |
| 运行中任务需要调整 | 只补充未改变目标和范围的事实时可续接；改变目标、范围或依赖时，先显式处理原尝试，再发起新版本，不静默改写输入 |
| 前置任务结果发生实质变化 | 标记相关下游证据需要核对，已运行任务保留原输入快照；必要时沿依赖传递影响，不自动取消所有后继或重跑全图 |
| 验证失败、需要修复 | 建立新的修复任务或执行尝试，再进行新一次验证；依赖图保持无环，历史事件可以表达多轮反馈 |
| 只修改标题、完成备注 | 只更新展示信息，不换任务代次，也不重新验证 |

新增依赖和验收操作必须检查当前上游版本，历史 completed 不得绕过依赖变化检查。涉及多个节点的修改、依赖合法性检查与提交必须原子完成；失败时整批不生效。保留现有事务与 revision 冲突检测，重试使用既有恢复机制，不另建一套并发控制。

#### 模型操作与运行时分工

- 在现有 todo 工具中支持按任务 ID 的局部更新和必要的原子批量更新，不要求修改一个备注就重传整个清单，也不新增大量图专用工具。
- 运行时计算可开始、运行中及阻塞原因。已明确派发的任务在依赖满足后按资源、写范围和隔离条件准入；单纯变为可开始不会自行创建代理或扩大授权范围。
- 通知由状态变化触发并去重；不为刷新图定时请求模型。普通响应只包含相关任务、阻塞原因、近期结果和变化影响，完整图按需读取。
- 不要求模型输出拓扑排序、手工维护派生状态或逐个轮询子运行。模型负责目标拆分、实质变更判断和语义验收。

### 第三优先：先证明两条有效工作线

以 FastAPI 类任务为例，在确认可分离文件和接口后：

1. 主代理负责核心路由参数传播与优先级；一个执行者负责独立中间件实现及实例隔离验证。两方明确文件归属，避免同时修改同一实现。
2. 合同边界分析、测试设计可与实施并行，但依赖新接口才能运行的测试等接口就绪再执行，不能抢先用后台 shell 等待并占锁。
3. 核心与独立模块完成后汇合，统一集成并跑全套。同一验证者续接处理失败；不为每轮结果新建一个代理。

这是示例分解，实际文件依赖不允许时调整边界或串行，不强求代理数量。主代理有自身实施任务时，不再重复设计子代理拥有的模块；纯负责人模式则将两条实现线都交出。

并行应区分代理生命周期、模型输出重叠、独立文件修改和命令执行四层。验收关注有用工作是否脱离关键路径，不能仅统计“创建了几个代理”。

### 第四优先：输出复用与明确结束条件

一次验证保留完整日志、摘要、命令、退出码、相关代码版本及环境；同版本同条件复用证据。代码或依赖发生实质变化、结果不完整或存在未决风险时才补跑。Git 提交本身不是必然需要重跑全部测试的理由，也不能无条件把提交前的旧工作树结果绑定到新内容。

系统提示保留短规则：先确认边界再动手、独立工作尽早分出、修改前读取相关代码、结果对应版本、满足要求后结束。删去重复规划和重复报告要求，但不设置僵硬的探索分钟数或禁止必要复验。

### 实施批次

| 批次 | 范围 | 完成条件 |
|---|---|---|
| P0 | 恢复主代理完整命令能力与角色指导 | 可独立读取、修改、验证；进程登记、超时与恢复不退化 |
| P1 | 精简默认工具与重复说明 | 默认请求集合稳定；常用文件操作和长命令路径完整 |
| P2 | 轻量 DAG 动态更新、任务与展示分离、简化交接与续接 | 图变更原子、旧尝试可追溯、派发版本一致；正常完成不再需要整表改写 |
| P3 | 提前分工、结果复用、明确结束条件 | 两条独立工作线实际交叠；依赖等待不占执行资源；只补缺失验证 |

这些是下一轮批次，与旧方案已经完成的 P0–P4 分开记录。每批运行相关验证，全部完成后运行全量测试、类型与 ESLint 检查，再冻结实验构建。

## 7. 如何验证下一轮确实变好

先检查实际首请求，确认默认工具集与提示确实改变，并用离线测试验证待办展示更新、任务连续性、长命令输出和冲突处理。再分别比较完整能力的精简单代理与轻量协作；不要再次一次性混入十几项变化后只测一组。

轻量 DAG 的验收必须包含以下正常、失败及恢复路径：

| 检查 | 必须观察到的结果 |
|---|---|
| 两条无依赖工作线及一个汇合任务 | 在资源与写范围允许时两条线均能开始；汇合任务只在前置验收后开始 |
| 自依赖、循环、缺失节点、并发修改冲突 | 整批更新被拒，已有图和派发状态不变 |
| 修改标题或完成备注 | 任务定义版本不变，已有有效证据仍可使用 |
| 修改真实目标或写范围 | 旧尝试可追溯，旧证据不能直接验收新定义 |
| 拆分已排队但未开始的任务 | 不重复执行、不留下永远无法就绪的旧派发，后继引用有效 |
| 上游变化时后继尚未开始、正在执行或已经完成 | 分别正确处理派发、输入快照和证据有效性；无关分支不重跑 |
| 验证失败后修复再验证 | 图无环，失败证据保留，新尝试绑定正确版本 |
| 图更新后重启及通知重试 | 恢复同一任务与派发关系，已有执行不重复启动，通知不重复触发模型工作 |

图验收既检查依赖正确性，也记录模型为维护 todo 所用的调用数和输入量，避免机制更完整但交互更繁琐。该功能不改变无沙箱命令的写锁或 UNKNOWN_WRITE 恢复约束。

真实实验至少同时报告：外部功能/回归质量、墙钟、所有代理总费用与缺失用量、总推理与输入、首次实施时间、重复探索与命令型委派、实际实施重叠、最后修改/验证/提交至完成的时间、协议纠错次数。

单次结果只用于定位；稳定速度或费用优势需要后续重复观察。付费实验规模沿用用户确认范围，不在本次研究中新增运行。保存请求、可获得的模型输出、工具结果、进程时间、快照和最终验证；保持原始记录不变，派生分析另存。
